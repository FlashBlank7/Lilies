# LLM 输出与对话上下文：9 月 27 日修正

## 本次实现

LLM 积木声明结构化输出时，仍先校验 Schema，再调用模型，最后严格校验实际输出。必填字段在输入末尾再次明确；未知业务事实不应为了凑齐字段而编造。

项目使用 OpenAI 兼容协议且输出明确为对象时，请求增加 `response_format={"type":"json_object"}`。这适用于支持该参数的服务，包括 DeepSeek 的 Chat Completions 接口。JSON 模式约束 JSON 语法，不能替代必填字段及业务正确性校验；依据为 [DeepSeek JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)，2026-09-27 核对。

普通文本、顶层数组/数字/联合类型、Anthropic Messages 连接和旧自定义 Provider 保留原有调用方式；不会为启用 JSON 模式更换服务、地址或模型。工具会话不附加该参数。接入服务返回 HTTP 400 时，错误提示会提醒核对 JSON 模式支持，不回显服务商响应中的潜在敏感内容，不自动降级或追加请求。

输出缺少必填字段时仍失败，不补造字段、不交给后续节点。错误显示节点及原校验原因，提醒从原运行继续以重试失败节点。恢复沿用现有机制，没有新增自动重试循环。

项目对话将所有工作流共用的调用说明从各条目录项提到目录外一次提供；工作流编号、用途、输入输出、修订号及按需读取入口保留，每轮仍读取当前草稿。没有清空会话、裁剪员工回答或更改历史结果。

## 后续真实复测与原生历史整理

原漏字段案例实际使用 DeepSeek 的 Anthropic 兼容连接，因而不受 Chat Completions 的 JSON 模式影响。本次保留该连接、模型、关闭思考选项及2,200输出上限，提取原失败解释节点的相同输入，在隔离平台建立只包含该解释节点的诊断流程，正常提交两个独立任务。没有重跑统计、初次分析或训练，也没有重新打开已完成原任务。

两次均一次返回四个必填字段，`needs_input=false`、`questions=[]`，耗时8.41/5.82秒。合计未缓存输入391、缓存输入4,731、输出2,780，即7,902服务报告token；费用未报告。原任务及文件哈希保持。仅两个局部案例，不代表稳定成功率或全部业务解释正确：第二份解释仍把未明确的标识/批次字段在预测时点的可用性写成已知，需在后续质量打磨中处理，不能用格式通过掩盖语义问题。

官方智能体新增可清空的原生整理阈值设置；原会话保留，整理进度出现在现有对话活动中。未新增摘要智能体、自动任务重跑或平台阶段限制。配置与接口依据见[官方智能体说明](OFFICIAL_AGENT.md)。

使用已有Luna/max线程，以32,768上下文阈值发起一次只读问题：核对原数据规模、重复数、员工当时是否明确业务含义及是否已经训练。原生`contextCompaction`实际开始并完成，持久记录包含`compacted`；随后读取两份既有产物，正确回答24行、7列、1条完全重复、标签含义和预测时点当时未知、未训练。没有混入后续验收变体的新定义，线程、原任务和原文件保持。

这次耗时56.87秒，整理事件跨度约28.81秒。整理后服务报告上下文13,035 token；随后的两次推理实际输入23,599/27,343 token（包括当前项目上下文和工具结果），输出616/333。任务用量为51,891报告token，其中23,296为缓存输入。服务没有单独报告整理这一步的用量，不能认为它免费，也不能把任务计数当作完整订阅扣额。整理前最后一次推理的输入为34,938；前后问题、工具读取和缓存不同，不能推导普遍节省比例。

主平台通过页面验证阈值保存、刷新、键盘清空恢复默认，并最终设置为65,536；`max_tokens=null`、Luna/max、600秒、单并发及50%额度保留保持。该值用于避免低阈值导致频繁整理，并未证明是最优成本点。主前后端已更新，54个项目保留，原始模型出口关闭；真实调用只在隔离实例进行，已停止该实例。
