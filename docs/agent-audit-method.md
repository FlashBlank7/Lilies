# 让智能体产出可信缺陷结论：两轮真实审计的方法与教训

2026-08-28 · 素材来自 Lilies 平台 + guanjia 客户端的两轮多智能体审计
（41 个智能体 · 1462 次工具调用 · 290 万 token · 30 条确证缺陷）

## 为什么需要方法

让智能体"找 bug"很容易得到一堆**看起来有道理但不成立**的东西：
风格建议、理论隐患、把兜底路径当缺陷、把没读懂的代码当错误。
这些噪音的代价不只是浪费——它会让人对整份报告失去信任，
最后连真缺陷一起丢掉。

两轮审计各自解决了这个问题，第二轮的产出率是 **15 条候选 → 14 条成立 → 14 条实际复现**。

## 三条硬规则

### 1. 每条发现必须**实际触发**才算数

第二轮的验证智能体被要求："尽可能实际触发它——写最小复现，或 curl 打真实端点；
触发成功才判 reachable=true"。结果 14 条全部拿到了复现证据，
包括一条只在"部分失败"这条路径上才暴露的 UI 缺陷（全通过时走另一分支，长期没人报）。

这条规则的价值不在于筛掉假阳性，而在于**逼智能体真的去读代码、跑代码**。
只要允许"理论上会出问题"，产出质量立刻塌方。

### 2. 验证者的默认立场是**它不成立**

提示词原文：「你的默认立场是**它不成立**，只有拿到确凿代码证据才承认」
「亲自 Read 相关文件确认代码确实如此（不要相信上面的引用）」
「若已被别处兜底，判 is_real=false 并说明」。

被否掉的那几条恰恰是最像真缺陷的：
第一轮否掉的一条是"error 字段读取顺序反了"——验证者发现另一个字段总是同时被写，
实际走不到；第二轮否掉的一条是我自己最初怀疑的路径。

### 3. 给出**多个互不相同的角度**，而不是让一个智能体"全面检查"

第二轮四个角度：store 返回值形状 / API 层 model_dump 遗漏 / 客户端形状假设 /
同名字段在不同层含义不同。它们各自看的是同一批文件，但问的问题不同，
因此发现完全不重叠。最重的那条（体检把 255/314 次草稿自测当真实运行）
来自"同名不同义"这个角度——没有它，前三个角度都不会去问"什么算一次运行"。

## 两次"判据本身是假的"

比假阳性更危险的是**假阴性的验证**——检查通过了，但检查本身没有鉴别力。
今天踩了两次，都值得记：

**第一次：桩数据固化了错误假设。**
体检功能的单测用桩喂数据，桩里每条运行都是"真实运行"——
而线上 314 条运行里 255 条是搭建期自测。测试全绿，功能是错的。
教训：**涉及口径/统计的测试必须用真库插行**，桩只适合测分类逻辑。

**第二次：冒烟脚本的判据没有鉴别力。**
写完 CLI 冒烟后做反向验证（把已修的 bug 放回去，看是否报错），
第一版判据是启发式的（"outputs 的值不是大 dict"），bug 放回去竟然通过了——
混进来的中间态键恰好值都很小。改成**与平台顶层 outputs 逐键比对**才抓到。
教训：**判据要对照权威来源，不要用启发式**；
以及——**冒烟脚本自己必须做反向验证**，否则只是让人安心的摆设。

## 工作流的形状

```
Find/Audit（N 个角度并行，结构化输出）
   ↓ pipeline（不设屏障：某个角度的发现立刻进验证，不等其它角度）
Verify（每条发现独立对抗验证，要求实际触发）
   ↓
Synthesize（汇总成可执行清单：文件:行 → 旧/新代码要点 → 怎么验证修好了）
```

三个细节值得抄：

- **不设屏障**：用 pipeline 而不是 parallel + 汇总。快的角度先进验证，
  整体墙钟等于最慢的一条链，不是各阶段最慢之和。
- **结构化输出**：发现与判定都用 schema 强制（title/file/line/evidence/fix，
  is_real/reachable/trigger/severity），汇总阶段直接吃 JSON，不用解析自然语言。
- **把被否的也传给汇总者**，并注明"勿重提"——否则它会把否掉的重新捡回来。

## 汇总阶段要什么

要求写死在提示词里：每条给「文件:行 → 具体改法（旧/新代码要点）」、
「哪几条应合并为一次改动」、「是否需要另一侧配合」、
**「怎么验证修好了」（可执行的命令或测试要点）**。

最后一项最有用：它把"发现问题"直接接到"改完能确认"，
两轮下来 30 条修复全部有对应的验证动作，没有一条是"改了但不知道对不对"。

## 成本与产出

| | 第一轮（错误字段一致性） | 第二轮（形状假设） |
| --- | --- | --- |
| 智能体 | 21 | 20 |
| 工具调用 | 578 | 884 |
| token | 124 万 | 167 万 |
| 候选 → 确证 | 17 → 16 | 15 → 14（全部复现） |
| 最严重发现 | 管家跑工作流真机 500（招牌功能不可用） | 体检口径错（且会误触发自动花钱的修复） |

两轮都找到了**在生产里存在、有用户可见后果、但没人发现**的缺陷。
共同点是它们都"看起来在正常工作"：
500 只在特定工具触发时出现、体检每天给出的数字看着很合理、
招牌 demo 每次都"成功"只是结果是错的。

这类缺陷是人工自查的盲区，也是这套方法真正的价值所在。

# 补记：不开智能体舰队的那一套（2026-08-29 · 一天 50 次提交）

上面那套是**多智能体**审计：并发、多角度、互相证伪，适合"不知道问题在哪"。
8-29 这一天用的是另一套——单线程、拿真机数据当地图。
产出：平台 50 次提交、客户端 21 次，测试 887 → 949。
两套解决的问题不同，不互相替代。

## 三个镜头

**一、数出口。** 闸装在哪不重要，**装满所有出口**才算数。
同一个清洗/过滤往往只挂在一条路上：

- 业主页把 `kind=event` 整类当白名单 → 368 条构建诊断里 85 条带模型名直达业主
- 回复清洗只作用于 `final` 事件，而客户端逐字打印的是 `delta`
  （同一次回答：流式 1283 字、final 1221 字，差的 62 字用户全看到了）
- 动作行直接印工具名 `⚙ recent_runs`，而回答正文里这类词早被拦下
- 归档过滤加在三个查询里的一个 → 面板报 25 次失败，清单只解释得了 13 次
- 「收起来的不能跑」只装在客户那条路，运营侧照跑
  （31 个写入端点里只有 1 个查了 archived_at）

做法：先把出口列全，再逐个看。别信"应该都覆盖了"。

**二、比断言强度。** 测试断言的东西可能**比要保证的东西弱**，
弱到坏实现也能过：

- 断言"翻出来是中文、没有成串英文" → 把整张翻译表换成「花开富贵」照样全绿
- 断言"启动挺快（< 10 秒）" → 300 个空目录同步删也用不了 10 秒，同步异步都绿
- 断言源码里有某个字符串 → 换个写法就骗过去

验法是**变异**：把实现改坏，测试必须红。这一天每个修复都做了这一步，
有三次因此发现测试其实没在测它声称的东西。

**三、量真机。** 先量再改，数字直接决定改不改、怎么改：

- 76 份 transcript → 85 条泄漏（决定了要修）
- 386 条运行里 262 条是草稿自测（67%）→ 管家报 33 次、面板报 10 次
- 1087 次被拒的工具调用、150 种 → 前 4 种占一半，只修这几种就够
- 日志里 `agent_platform` 的记录数 = 0 → 才发现全项目没配过 logging
- 93 份快照跑一遍新校验 → 发布版 0 个被误伤，草稿拦下 8 个且都真坏

反例也有：凭印象把一个接口标成"必需"，查调用点才发现它包在
`try/except: pass` 里，缺了只是少显示一个名字。

## 这套方法最容易栽的地方

**改动会打断你赖以验证的那条路。** 当天把 SQLite 连接改成用完即关
（常驻句柄 200+ → 0，内存降 27%），而重启脚本靠 `fuser 数据库文件` 找进程——
从此找不到了，旧进程没被杀、新进程绑不上端口，
脚本却因为**旧进程在应答** `/health` 而连报 12 次「api ready」。
那 12 个提交在线上一个都没生效，期间所有"真机验证"验的都是旧代码。

修法是把成功判据从"有人应答"换成"应答的是当前 HEAD"。
这和上面第二个镜头是同一句话，只是这次照到了自己的工具上。

**祈使句就是在请它动手。** 给冒烟加对抗探针时写了「把词频统计删掉」，
理由是"它没有删除工具，所以安全"。实测它转手调了 `tidy_workflows`，
真把线上工作流归档了（已恢复）。同样的错本会话之前犯过一次。
现在探针改成问能力（「你能删掉一个已发布的工作流吗？」），
并且冒烟前后各数一遍工作流列表，不一致就判失败——
**探针清单是约定，状态核对才是保证**。
