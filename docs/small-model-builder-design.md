# 小模型集群 Builder 框架设计（草案 v0.1）

> 目标：在现有 Lilies harness 下，用一组几 B 到几十 B 的小模型替代单一大模型驱动构建，
> 验证论文核心主张——**可信构建来自边界执法的 harness，而非模型能力**。
> 若弱模型集群在同一 harness 下仍能交付通过盲测的工作流，主张成立且强化。
>
> 状态：v0.2。三份调研已回填（原始报告归档于 [research/](research/)）。

## 1. 核心命题与设计哲学

单一大模型 builder 的能力来自模型内部：规划、schema 记忆、纪律遵循混在一个上下文里。
小模型集群 builder 把这三者拆开：

- **控制流归代码**：阶段推进（规划→搭建→测试→修复→发布）由确定性状态机驱动，不再依赖模型自觉；
- **纪律归边界**：schema 校验、revision 乐观锁、预算守卫本来就在工具边界执法（`builder.py`），
  小模型的高错误率被边界转化为廉价的重试信号，而不是交付事故；
- **模型只做局部判断**：每个小模型在窄角色、窄工具面、窄上下文里做一件事。

一句话：**大模型 builder 靠模型的自律，小模型集群 builder 靠 harness 的他律。**
这恰好是论文最想证明的对照。

## 3. 框架结构：三档递进的实验形态

三档共用同一 harness、同一任务集，本身就是论文的实验臂设计。

### 形态 A：异构队友（最小改造，先跑通）

保持 LLM 协调者，但协调者与队友用不同模型。角色划分依据 32 个真实构建
（1104 轮、1921 次工具调用）的分布数据修正（2026-08-18，初版四角色砍成一个半）：

```text
协调者（最强档）：需求理解、架构选型、测试设计、交付说明 —— 判断类，无硬门兜底
 └── 配置手（~4-7B）：查手册 + 配节点 + 接线（catalog_get/manual_get +
     draft_add_node/update/connect），≈60% 调用量 —— 机械类，硬门全覆盖
（修复诊断：无常驻角色 —— run_inspect 在 32 个构建里仅 16 次；
 小模型先诊，失败升级大模型，结局由 test_run 硬验证）
```

**下放原则（数据驱动的核心结论，直接进论文）**：
可下放度 = 硬门覆盖度 × 调用频次。

- **配置手是唯一"必设"角色**：草稿变更占总调用 38%，加上配套查阅共约 60%；
  本质是"读 schema → 填表"的结构翻译，Pydantic/端口/revision 硬门全覆盖，
  配错即大声拒绝 + 廉价重试——BFCL 直接度量的能力，正是论文命题的落点。
- **查询与使用不拆开**：catalog_get 单项占 15%，但其结果是给配节点的人看的，
  独立"目录侦察员"多一跳传话、摘要损耗变配置错误；且选错积木是**软失败**
  （无硬门拦架构判断），恰恰不能交给弱模型。侦察员角色取消，查阅并入配置手。
- **测试作者不下放**：决定断言什么（判断）+ 算期望值（算术）+ not_contains
  安全断言（对抗思维），是全系统唯一无硬门保护的高危输出——期望值算错且
  恰好吻合错误实现 → 测试绿、交付垃圾、断言冻结。期望值计算交给沙盒
  python（确定性），断言设计留在协调者。
- **修复诊断走升级阶梯**：频次最低（<1%）但认知最难；结局有 test_run 硬验证，
  过程烧修复预算——小模型先试、失败即升级，本身就是一条成本曲线实验。

改造点（✅ 2026-08-18 全部落地，见 §8）：

1. `_agent_loop` 加 `model: str | None` 参数，None 回落 `self.generator_model`；
2. `spawn_teammate` 工具 schema 加可选 `model` 字段，enum 白名单 + 越界硬门；
3. `BuildRequest` 加 `coordinator_model` 与 `teammate_models`（存 team_state，
   进配置指纹，接续 harness-config-ablation.md 的改造路径）。

### 形态 B：机械协调者 + 小模型执行体（论文主实验）

把协调者从 LLM 换成确定性状态机——阶段推进、预算分配、角色调度全是代码，
小模型只在每个阶段内做局部决策：

```text
状态机（代码）：plan → scaffold → wire → test → repair(≤N) → publish
   每阶段：选角色 → 组装窄上下文 → 调小模型 → 边界校验 → 落库或重试
```

- 阶段转移条件全部机械可判：`draft_validate` 通过才进 test，`test_run` 全绿才进 publish，
  修复循环耗尽即失败——这些守卫在 harness 里已存在，状态机只是把"什么时候做什么"也接管；
- 小模型单次调用是无状态的"提案函数"：输入（阶段上下文 + 草稿投影 + 错误反馈），
  输出（一个工具调用提案）。提案被边界拒绝→带结构化错误重试（廉价，几 B 模型 token 便宜）；
- 这是"harness 与模型无关"的最强形式：**控制流里没有任何模型自由度**。

### 形态 B 的实证结论：机械阶梯（2026-08-23，15 次真机复测的产物）

用 Qwen3-4B 单模型跑 mechanical 引擎，15 次复测每一次失败都精确定位到一个
**机制缺口**而非"模型太笨"。补缺口的顺序自发形成一条阶梯——**每当模型不肯
前进，代码就再拿回一层控制权**：

| 级 | 手段 | 触发它的真实失败 |
| --- | --- | --- |
| 0 | 给信息：草稿投影、积木目录、已存在 id | 幻觉不存在的积木类型 |
| 1 | 给机械算出的下一步：`draft_validate` 待办每轮现算 | 加完节点不知道该干什么 |
| 2 | 记账式守卫：反刍判停、只读循环判停 | 同一被拒提案重试 17 轮 |
| 3 | **收窄工具面（执行边界硬门）** | 工具列表只是建议——模型照着系统提示里的名字乱叫 |
| 4 | **机械子阶段**：骨架齐了就只准连线 | 三个节点全加好，从不调 `draft_connect` |
| 5 | **关卡达成即判**，不等模型宣布完成 | 测试早写好了却继续查目录到预算耗尽 |
| 6 | **强制指定必调工具**（命名 tool_choice → 约束解码） | 工具被收走后干脆不调任何工具 |
| 7 | **简化提案接口**（瘦身 schema，边界校验不减） | 复杂 schema 压垮约束解码，连吐三次空参数 |
| 8 | **代劳确定性步骤**：状态机替它读执行台账 | 修理手读完诊断就是不动手，反复重读同一份 |

#### 阶梯的横向约束：每一级都必须**可满足**

2026-08-23 构建 `0826a87a` 给出这条约束的反面教材。第 9 级"查过手册才准用"
拒绝时说"先调用 `catalog_get`"，而第 3 级"收窄工具面"在同一时刻正好把查询
工具收走了（架构师阶段重复查阅留下的计数渗漏进建图阶段）。32B 建图手连续
9 轮原样重提，60 秒被第 2 级的反刍守卫判死——**三级机制互相绞杀，模型全程
没有一步合法动作可走**。

由此定两条横向约束，适用于阶梯的每一级：

1. **教学式拒绝的前提是它做得到**。拒绝里指定的补救动作，必须在**当前这一步
   的工具面上真实可用**。做不到的指令不是教学，是死锁。
2. **确定性的补救动作由机器代劳，不要下发给模型**。查手册是确定性的：类型已知、
   内容固定。现在硬门自己去查，把说明书原文塞回反馈并记为已查——同一类型
   最多拦一次，永不可能死锁。这就是第 8 级"代劳确定性步骤"的推广。

配套：跨阶段的记账计数（连续只读、重复查阅）必须在**每个阶段入口清零**。
一个角色在上一阶段的行为不该扣另一个角色的分。

#### 硬门要堵住**所有**入口，判据要堵住**假证据**

发布这件事有三条路（`draft_publish` 工具、`test_run` 全绿后自动发、收工时自动发），
2026-08-23 的验收证据硬门只堵了第一条，另外两条照旧放行了半天没人发现。
同期还发现判据本身可被绕过：构建者没写验收时平台自动补一条纯结构冒烟测试
（`exists`/`structural=True`）并标为 mandatory，它一跑绿证据就"齐备"了。

两条通用约束：

1. **同一件危险事若有 N 个入口，硬门必须挂在共用判据上**，而不是挂在其中一个
   入口的处理分支里。做法：把判据抽成一个方法，三条路都调它——判据漂移比漏堵
   更难查。
2. **证据要有效，不只是存在**。"跑得起来"不等于"算得对"：只验形状的验收，
   工作流每个数都算错也会全绿。判据加严为"强制验收里必须有一条断言了具体值"。

对不同入口，拒绝方式要分开设计：显式请求发布 → 抛错；测试顺带触发的自动发布
→ **不抛错**（模型并没有请求发布，抛了等于凭空判死一单），把"为什么没发"
写进报告让它去补。

**门挂在哪一步也要想清楚**：这道门只挂在"发布"上，不挂在 `ready` 上。
`ready` 的含义是"结构有效、端到端跑得起来，等业主验收"——人还在环里，那是平台
有意留给业主的判断权（业务验收属于业主）。`published` 才是自动化一方单方面
宣布"这东西验过了"，那句话必须有锚定具体值的证据撑着。
（初版把门挂到了 `ready` 上，回归测试当场把这条语义差别顶了回来。）

#### 关卡是校验器，不是"模型宣布完成"——预算出口也要判一次

真机构建 93430e0b：图建全、线连全，最后一条边刚落库就撞上建图预算上限，
整单被报成 `scaffold budget exhausted with invalid draft: 模型始终未宣布完成`。
关卡（`draft_validate`）明明已经达成，代码却因为"模型没说做完"把成品扔了。

**每一个"预算/次数用尽"的出口，判死之前都要把关卡再判一次**。
第 5 级"关卡达成即判"此前只落在验收阶段，现已补到建图阶段的预算出口。

#### 检查会被规避：判据要落在封闭集合上

同一处方案校验被连着绕开两次：

| 轮 | 检查方式 | 规避手法 |
| --- | --- | --- |
| 310141fd | 查 `config_sketch` 里有没有公式文本 | **把公式删了**，错积木照旧 |
| 92af320c | 算术意图 + 类型在不在**黑名单** | **换成没列进黑名单的真实类型**（`tool`），指向一个不存在的函数 |

教训：**只查表面文字的检查，可以靠删掉文字满足；黑名单式检查，可以靠换一个
没列进去的类型满足**。判据改为白名单（真正会做确定性算术的 9 个积木）后，
"算术落在哪"成了封闭集合，绕不过去，且拒绝时把整个集合报出来——
否则模型只能一个个猜。

#### 教学信息必须用**真实输入语法**——模型会照抄提示

真机构建 881d90a6 是最讽刺的一次：工作流本身几乎全对（公式对、图对、验收对），
唯一的错是 `"path": ["output.by_store"]`——把两层路径写进了一个段里。
追下去，这个错法是**平台自己教的**：`$ref` 解析失败时列出的"可用路径"用点号
显示（`output.by_store`），模型照抄进了 `path` 数组。它没有猜，它在照着提示写。

提示已改成分段语法（`["output", "by_store"]`），同时在解析层容忍点号写法
（意图无歧义，先按拆分重试再谈失败）。

**通用约束：任何给模型看的示例、清单、回显，都必须是它能原样粘回去的形式。**
人类友好的显示格式（点号路径、省略号、缩写）出现在教学信息里，就是在教错。

#### 拒绝要替它判断"该修哪一端"，不能把两条路并列丢过去

同一处 `$ref` 提示还犯过相反方向的错。它原本并列写着"要么让节点 X 真正产出…，
要么把引用改成已有路径之一"——两条路并列，模型只能猜，而且两次都猜错了方向：

| 事故 | 模型选的路 | 真正该修的 |
| --- | --- | --- |
| 早前 | 61 次只改**引用方**（模板节点）| 被引用节点没产出该字段 |
| 881d90a6 | 4 轮只改**产出方**（公式节点，本来就对）| 引用的路径写法 |

判据其实是机械可算的：**想要的路径是不是已有路径的近亲**（difflib）。
是近亲 → 引用写错了；八竿子打不着 → 产出方确实没这个字段。
平台能判出来的事，不要留给模型猜。

#### 选型的信息面：目录只给标题，等于让它盲选

八轮真机构建里有**四轮**架构师的第一个动作是 `catalog_get collection_digest`
（一个 Markdown 渲染器，与汇总计算毫无关系）。追下去发现：架构师用来选型的
积木目录概览只给 `type — English title`，它看到的是
`variable_aggregator — Variable Aggregator`，看不到那句要命的
**"只做分支值合并/透传，不做任何算术"**——尽管平台早就写好了这句话，
只是当时只发给编辑器界面（`editor.i18n.zh.description`）。

选型是架构那一步唯一重要的事，而它的信息面是最贫的。现已把一句话职责放进
目录概览：整张表从 ~2.3KB 涨到 ~2.7KB（中文很省），换来的是选型有据可依。

**通用教训**：判断类工作做不好时，先问"它做判断时看得见什么"，
再问"它够不够聪明"。这与测量效度纪律是同一条——只是那条问的是管道，
这条问的是信息面。

#### 方案本身也得是硬门，不能只是"建议"

真机构建 e28708d3 走完了整条流水线（plan→scaffold→test→verify→repair×4），
死因却是：方案校验两次把 `variable_aggregator` 顶了回去、架构师改对了，
**建图手转头照样加了它**。方案文本里写着「按此实现，不要另选积木」——
advisory。那个积木不做算术，配置怎么改都算不出东西，修复阶段 48 轮里 32 次
被拒（全是 "would not change the workflow"），最后耗尽轮数预算。

形态 B v2 的分工是「强模型定选型、小模型照单填表」。**选型偏离必须是硬门**：
方案批准后记录允许的积木集合，建图手用集合外的类型当场拒绝并报出方案选定的
积木。升级接手后放开——那时提案者本身就是架构师那一档，有资格改方案
（恢复手段优先于放弃手段）。

这也让查手册硬门在有方案时自然退场：类型被方案约束、方案内的手册已预载，
它只在无方案（单模型）或升级之后才出场。

#### "形状合法的垃圾"的第三种形态：写成字符串的引用与公式

4B 实测写出 `{"value": "$ref{start, sales}"}` 与
`{"assignments": {"by_store": "group_by_sum(...)"}}`——两条都结构合法，被原样
存成普通字符串，工作流照跑，输出就是那串字面量，一路到数字断言才炸，
报错还与真因无关。模型的意图毫无歧义，平台没有理由装看不见：
现在建节点时就识别"看起来像引用/公式的字符串"并当场拒绝，附上正确的对象写法。

第四种形态是**把类型名填进值槽**：`{"outputs": {"by_store": "object"}}`——
工作流会原样输出字符串 `"object"`。同样在写入时拒绝。

第五种是**把操作符当字符串前缀**：`"$formula.sum_by(sales, \"store\", \"amount\")"`。
逐个补正则永远慢一步（三轮真机各写出一种新花样），判据最后落在"这段字符串以
`$操作符` 开头 / 里面出现 `$ref`"上。

这一族的共同点是：**模型的意图毫无歧义，只是写法错了**。平台要么替它改对
（意图确定且无人在看时），要么当场拒绝并给出正确写法；唯独不能是"照单收下、
运行时静默产出垃圾"。

⚠️ **这类启发式守卫本身也会误伤，而误伤比漏网更贵**。上面这道守卫落地当天
就误判了三次：把参照解自己的 `$formula.expression`（那本来就该是表达式原文）
判成错、把 `{"$ref": {"node_id": "$inputs"}}` 这个合法哨兵判成错、值槽标记
传错一层导致规则整体失效。前两次都是"模型/作者写得完全正确却被拦下"——
正是 B1 那条死锁的同一形状：**它没有任何合法动作可走**。
所以这类守卫必须配一份"本来就该长这样"的豁免清单（表达式位、模板位、
`$ref` 内部），并且每加一条规则都要用**正确写法**回归一遍，不能只测错写法。

#### 同一条规则，对"谁在做"要分开裁

今晚三次撞到同一个形状的判断题，答案都不是"一刀切"：

| 规则 | 对构建者（自动化） | 对业主（人在环里） |
| --- | --- | --- |
| 验收证据不足能否发版 | **不能**——自动化一方不得借用人类例外通道 | 可以知情越过（业务验收属于业主）|
| 硬门挂在哪个状态 | `published`（单方面宣布"验过了"）| `ready` 不挂——那正是等业主判断的状态 |
| 配置字段写错位置要不要替它改 | **要**（意图无歧义、且没有人在看这一步）| **不要**——自然语言编辑里替人猜错就是擅自改动 |

统一的判据是：**这一步之后还有没有人会看一眼**。没有人看，平台就要么替它做对、
要么拦住；有人看，平台只该提示，不该代劳。

#### 同名字段在两个引擎里含义必须一致

同一事故还暴露：mechanical 曾把 `coordinator_model` 当**提案者**、
`teammate_models[0]` 当**升级模型**，与经典引擎的语义（统筹=大脑、队友=执行者）
正好相反。操作者按直觉传参（统筹 32B、队友 4B），实际得到的是 **4B 做架构选型、
32B 填表**——与形态 B v2 的设计意图完全颠倒。测出来的不是模型能力，是配置事故。

现已统一为经典语义，并把分工写进事件流（`分工：提案者=… 架构选型/升级接手=…`）——
**角色搞反过一次，链条上看不见就查不出来**。

阶梯尽头的形态很清楚：**小模型剩下的唯一职责是"给出一个具体的配置提案"**，

### 形态 B 的实证结论：机械阶梯（2026-08-23，15 次真机复测的产物）

用 Qwen3-4B 单模型跑 mechanical 引擎，15 次复测每一次失败都精确定位到一个
**机制缺口**而非"模型太笨"。补缺口的顺序自发形成一条阶梯——**每当模型不肯
前进，代码就再拿回一层控制权**：

| 级 | 手段 | 触发它的真实失败 |
| --- | --- | --- |
| 0 | 给信息：草稿投影、积木目录、已存在 id | 幻觉不存在的积木类型 |
| 1 | 给机械算出的下一步：`draft_validate` 待办每轮现算 | 加完节点不知道该干什么 |
| 2 | 记账式守卫：反刍判停、只读循环判停 | 同一被拒提案重试 17 轮 |
| 3 | **收窄工具面（执行边界硬门）** | 工具列表只是建议——模型照着系统提示里的名字乱叫 |
| 4 | **机械子阶段**：骨架齐了就只准连线 | 三个节点全加好，从不调 `draft_connect` |
| 5 | **关卡达成即判**，不等模型宣布完成 | 测试早写好了却继续查目录到预算耗尽 |
| 6 | **强制指定必调工具**（命名 tool_choice → 约束解码） | 工具被收走后干脆不调任何工具 |
| 7 | **简化提案接口**（瘦身 schema，边界校验不减） | 复杂 schema 压垮约束解码，连吐三次空参数 |
| 8 | **代劳确定性步骤**：状态机替它读执行台账 | 修理手读完诊断就是不动手，反复重读同一份 |

### 形态 C：提案竞争（可选加强，接 §6 外部模式）

schema 密集的节点配置步骤，N 个极小模型（≤4B）并行提案，机械仲裁：
先过 `NodeSpec.model_validate`，再过 `draft_validate`，第一个全过的落库；
全败则升级到更大档模型（升级阶梯：4B → 7B → 30B → 大模型兜底）。
仲裁不需要 LLM——校验器就是裁判，这与平台"验收由确定性机制执法"的哲学一致。

## 4. 小模型的失败模式与 harness 的对应防线

| 小模型典型失败 | 边界防线（已存在） | 需新增 |
| --- | --- | --- |
| JSON/schema 畸形 | Pydantic 校验拒绝（`builder.py:1592-1623`） | 结构化错误反馈进重试 prompt |
| 幻觉字段/积木名 | 积木注册表查找失败即报错 | 无 |
| 忘记上下文、改错对象 | revision 乐观锁拒绝过期操作 | 草稿投影：每次调用重新组装最小上下文 |
| 原地打转 | 修复循环预算 + 停滞守卫 | per-角色重试上限（比全局守卫更细） |
| 术语泄漏进业主文本 | ask_owner 硬门（`builder.py:1232`） | 叙述/交付说明出口硬门（缺口，见消融文档） |
| 上下文窗口小 | `TOOL_RESULT_HISTORY_MAX_CHARS` 截断 | 角色级上下文投影（只给本角色相关的草稿切片） |

关键新增机制是**角色级上下文投影**：小模型不看完整构建历史，每次调用收到的是
为该角色定制的草稿视图（如节点配置员只看目标节点的 schema + 上游输出契约 + 本次任务），
这同时解决窗口限制和注意力分散。draft 状态本来就是唯一真相源（黑板模式），
投影只是查询它的不同视角。

### 4.1 测量效度：先排除管道故障，再归因模型（2026-08-23 两次翻案）

本方向的实验有一个高危陷阱——**推理服务的解析故障长得和"小模型能力差"一模一样**。
两次实测翻案，均由判别实验（非流式直连 vs 平台链路）定案：

| 观察到的"模型失败" | 真实原因 | 处置 |
| --- | --- | --- |
| 拍平嵌套 JSON、残 JSON 语法错 | vLLM 0.8.5 hermes **流式**工具解析器丢参数片段（上游 #19056，修复于 v0.11.0）；非流式直连同一模型输出完整合法 | 本地端点改非流式（`openai_chat.py` streaming 开关） |
| 「模型不调工具、直接收工」导致构建停摆 | 无 qwen3 reasoning parser 时 `<think>` 段带崩 hermes 解析器，`<tool_call>` 以纯文本留在正文、`tool_calls` 为空 | 非流式翻译中剥思考 + 兜底解析文本化调用（`4363e38`，附事故复现测试） |

全量审计（11 条对话 + 10 份构建转录）另外证实：**4B 无思考模型同样出现过调用文本化**，
说明兜底解析不是某个模型的补丁而是所有本地端点的标配；且有一单表面 published 的
构建其叙述里混着 4 段内部推理——**成功与干净是两件事，两项要分别验**。

**A/B 定案实验（2026-08-23）**：同一模型（Qwen3-4B-Instruct-2507）、同一提示、
同一流式请求，只更换推理服务版本：

| 服务版本 | 分片数 | 拼装长度 | 结果 |
| --- | --- | --- | --- |
| vLLM 0.11.0（含 #19056 修复） | 51 | 150 字符 | ✅ 合法嵌套 JSON |
| vLLM 0.8.5.post1 | 49 | 141 字符 | ❌ 残 JSON（与事故现场逐位一致） |

结论：模型输出无缺陷，缺陷在服务端流式工具解析器。0.11.0 已验证可在本机
驱动（550.78 / CUDA 12.4）运行（torch 2.8+cu128），需 `transformers==4.56.x`
且禁用 flashinfer 采样器（`VLLM_USE_FLASHINFER_SAMPLER=0`，本机 CUDA 工具链
编译其 kernel 失败）。

### Sakana AI 线结论（详见 [research/sakana-ai-survey-2026-08.md](research/sakana-ai-survey-2026-08.md)）

Sakana 的多模型协作路线到 2026-08 已从算法（AB-MCTS）演进到学习型编排产品（Fugu），
对本设计最有用的五条：

1. **AB-MCTS / TreeQuest**（arXiv:2503.04412，Apache 2.0 库）：把"再采样一个新解（宽）/
   修正现有解（深）/ 换哪个模型"三个决策都交给 Thompson 采样，对每个模型维护质量后验，
   **任务内在线学出"这道题谁擅长"，零训练成本**。唯一硬前提是外部打分器——
   我们的 `draft_validate` + 验收测试恰好就是现成的 evaluator。
   **对接点**：形态 C 的提案竞争可以从"首个通过者胜出"升级为 bandit 路由：
   边界拒绝/校验通过就是天然的奖励信号，几轮之后集群自动学会"schema 密集步骤派谁"。
2. **TRINITY**（arXiv:2512.04695，ICLR 2026）：0.6B 协调器 + 约 10K 参数选择头，
   用进化策略（sep-CMA-ES，非 RL）只学"派谁、什么角色"（Thinker/Worker/Verifier 三角色），
   技能全部在池中模型，LiveCodeBench SOTA。
   **对接点**：形态 B 的状态机是"协调逻辑归代码"的极端；TRINITY 给出中间形态——
   状态机管阶段推进，一个极小的学习型路由头管阶段内派谁。可作为形态 B 的 v2。
3. **Fugu 软标签路由**（arXiv:2606.21228）：用各 worker 的实测表现构造软分布做 KL-SFT，
   再用进化/GRPO 端到端细化。**对接点**：我们每轮 turn 记录 model + 工具结果 + 校验结局，
   构建历史就是现成的路由训练集——先跑形态 A/C 攒数据，路由器可以以后再学。
4. **生成与判定分离是全线共同前提**：AB-MCTS 靠外部打分器、TRINITY 有独立 Verifier 角色、
   AI Scientist 有校准过的自动审稿人、DGM 论文实测到 agent 伪造测试日志/删除检测标记。
   这与本平台"验收由确定性机制执法、交付验证独立完成"的纪律完全同构——
   论文里可以引 DGM 的 reward hacking 实证作为"为什么执法必须在模型外"的旁证。
5. **弱模型的价值边界**（CoffeeBench，arXiv:2606.16613）：弱模型在**无裁判的长时程自主**
   环境里会"思而不行"；在**有裁判的搜索**里有正贡献（AB-MCTS 中单独很弱的模型
   帮助组合解出无人能单独解出的题）。builder 的每一步都过硬门，恰好落在有利侧——
   这条边界本身就是论文 discussion 的好素材。

**定位空白（对论文最重要）**：Sakana 已证明"小协调器 + 前沿大模型池"（TRINITY/Fugu）
和"协调器与基座无关"（Gemma 4 E2B 版 Fugu），但**"小协调器 + 纯小模型 worker 池"
的组合尚无公开实证**（其技术报告明确不讨论小模型当 worker 的设定）。
我们的形态 B/C（状态机或极小路由 + 全小模型执行体 + 执法 harness）正好填这个空白，
且差异化主张不同：Sakana 靠学习型编排提升上限，我们靠边界执法保住下限。

## 7. 实验设计（论文视角）

| 臂 | 协调 | 执行 | 验证的命题 |
| --- | --- | --- | --- |
| 对照 | 大模型 | 大模型 | 现状基线 |
| A1 | 小模型(30B) | 配置手=小模型(4-7B) | harness 下弱模型能否交付 |
| A2 | 大模型 | 逐角色下放（仅配置手 / 加测试作者） | **下放原则验证**：配置手下放应近无损，测试作者下放应推高静默失败率 |
| B1 | 状态机 | 小模型(7-14B) | 控制流归代码后模型能力还剩多少影响 |
| B2 | 状态机 | 极小模型(≤4B)+升级阶梯 | 能力下限与成本曲线 |
| 消融叉乘 | 任一 | 任一 | 关防线后小模型臂的崩溃幅度应显著大于大模型臂 |

A2 是 §3 下放原则（可下放度 = 硬门覆盖度 × 调用频次）的直接检验：两个方向的
预测都明确、可证伪——故意把测试作者下放给小模型作为"反面臂"，预期静默失败率
显著上升，恰好反证硬门缺位处不可下放。

最后一行是论文最有力的预期结果：**如果防线消融对小模型臂的伤害远大于大模型臂，
就证明了 harness 承担的正是大模型用参数换来的那部分可靠性**——两条主张
（防线有效、harness 与模型无关）在同一组实验里互相印证。

主指标沿用消融文档：一次通过率、静默失败率、修复循环数、单构建成本、泄漏率；
新增 per-模型 token 占比与边界拒绝率（提案被 schema/revision 拒绝的比例——
衡量"他律"实际接住了多少错误）。

### 4.2 推理服务迁移到 vLLM 0.11（2026-08-23，根因彻底消除）

0.8.5 是本方向前期所有解析事故的共同源头。0.11.0 是能在本机驱动
（550.78 / CUDA 12.4）上跑起来的最新版本，迁移条件与踩坑记录：

| 项 | 值 / 处置 |
| --- | --- |
| 版本 | `vllm==0.11.0`（torch 2.8.0+cu128；0.27 的 torch 需 CUDA 13，驱动不支持） |
| transformers | 必须钉 `4.56.x`（新版 tokenizer API 变更导致 `Qwen2Tokenizer has no attribute all_special_tokens_extended`） |
| 编译依赖 | 需要 `ninja` 可执行文件在 PATH 上 |
| flashinfer | 本机 CUDA 工具链编译其 kernel 失败，须 `VLLM_USE_FLASHINFER_SAMPLER=0` |
| 32B 上下文 | `--max-model-len 65536` + YaRN（`factor=2.0`），此前 32768 被真实构建撑爆 |
| reasoning parser | `--reasoning-parser qwen3` 实测未生效（思考仍混在 content）；平台侧显式
  `chat_template_kwargs {"enable_thinking": false}` + 兜底剥离已覆盖，留作待查 |

迁移验证：冒烟脚本首次打印 `TOOL-SCHEMA: valid nested structure (one-shot)`
（0.8.5 下恒为 invalid，且走的是流式路径）；全量测试 486 passed；
两个引擎各发一单验证构建，**双双 published**。

因此非流式与文本化调用兜底解析从"必需品"降级为"保险绳"——保留但不再是
交付前提。历史实验数据凡在 0.8.5 上采集的，模型能力相关结论一律标注为
待重测（管道噪声已知偏悲观）。
