# v0.2.42 Builder Build-level Watchdog

## 1. Stage Goal

Add an optional whole-build elapsed-time boundary for Builder builds.

v0.2.40 made provider stream timeout observable. v0.2.41 showed that an entire Builder run can still be long and expensive. v0.2.42 adds a persisted build-level watchdog that is visible in API, stream events, and Platform Harness metadata.

## 3. Completed Items

- Added optional `max_elapsed_seconds` to `BuildRequest`.
- Added compatible SQLite migration for `builds.max_elapsed_seconds`.
- Persisted `max_elapsed_seconds` in build records.
- Passed `max_elapsed_seconds` through the create-build API.
- Added `BuildDeadlineExceeded`.
- Builder now emits `build.deadline.configured` and `build.deadline.exceeded`.
- Builder now records build-level deadline in Platform Harness task metadata.
- Build-level timeout now finishes as `needs_attention` with `failure.type=build_timeout`.
- Added deterministic regression coverage that distinguishes `build_timeout` from `model_provider` timeout.

## 6. Compatibility Boundary

- Old build requests without `max_elapsed_seconds` continue to work.
- Existing SQLite databases migrate by adding nullable `builds.max_elapsed_seconds`.
- New build requests can set `max_elapsed_seconds` without changing `max_turns` or provider stream timeout.
- The watchdog currently wraps the top-level coordinator `_agent_loop()`. Long post-agent-loop validation paths are not separately wrapped in this stage.
