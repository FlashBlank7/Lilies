# design_v0348_step_progress_data_flow

Status: completed

## Source

- Source stage report: `docs/stage-report-archives/v0.3.x/v0.3.47_natural_language_workflow_edit.md`
- Source task: Add step progress/data-flow visibility.
- User product correction: after pressing start, users should see the workflow has data moving and which step it is on.

## Problem

Trace is useful for engineers, but it is not a customer-facing progress model. Users need a step list that shows waiting, running, completed, blocked, or not-started state in plain language.

## Boundary

- Use available workflow nodes, run status, and visible trace events.
- Do not invent exact per-node runtime completion if trace evidence is absent.
- Mark unknown states honestly.

## Proposed Solution

- Derive customer step progress from workflow nodes plus visible node events.
- Show completed/running/waiting/blocked/not-started states.
- Show a compact data-flow summary: input ready, progress evidence count, current state, output readiness.
- Preserve raw trace below for technical inspection.

## Acceptance Criteria

- Run tab shows a customer step-progress panel.
- Progress reflects current run/trace state without claiming unsupported precision.
- Data-flow summary is visible without opening raw trace JSON.

## Final Evidence

- Implemented in `platform/frontend/app/applications/[id]/page.tsx` with `customerStepProgressItems`, `customerDataFlowItems`, and `data-customer-run-interface="step-progress"`.
- Progress is derived from existing `visibleTraceEventsForRun`, `pendingPermission`, and `run.state.waiting_node_id`.
- Verified by `tests/test_v03_48_customer_facing_workflow_run_interface.py`.
