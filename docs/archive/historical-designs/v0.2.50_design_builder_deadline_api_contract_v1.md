- Final status: completed

## Problem

Builder deadline enforcement existed in storage and harness metadata, but the API surface did not expose it as an explicit caller-facing contract. That made deadline behavior feel like hidden experiment plumbing instead of a real Builder control.

## Boundary

- In scope: create/get/list build API normalization for deadline fields and focused backend regression coverage.
- In scope: preserving the raw `max_elapsed_seconds` field while adding a stable `deadline` summary block.
- Out of scope: frontend controls, countdown timers, or scheduler-wide deadline policy.

## Final Design

- Add a shared helper that converts `max_elapsed_seconds` into:
  - `deadline.enabled`
  - `deadline.max_elapsed_seconds`
- Echo deadline configuration in create-build responses.
- Annotate get-build and list-build payloads with the same normalized deadline block.
- Extend the focused build watchdog regression to assert the new contract on create/get/list paths.

## Acceptance

- Create-build echoes the configured deadline.
- Get/list build responses expose a normalized deadline block.
- Existing build deadline/watchdog behavior remains covered by regression tests.

## Evidence

- `platform/backend/src/agent_platform/api.py`
- `tests/test_workflow.py`
- `docs/workingon-archives/v0.2.50/implementation_v0.2.50_builder_deadline_visibility.md`

## Remaining Risk

- The API now exposes the configuration clearly, but it does not by itself guarantee that every future UI surface will display it.
