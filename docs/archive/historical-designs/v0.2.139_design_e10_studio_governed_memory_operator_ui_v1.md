# v0.2.139 E10 Studio Governed Memory Operator UI

Status: completed

## Source Stage Report

- `docs/stage-report-archives/v0.2.x/v0.2.138_e10_runtime_memory_retrieval_integration.md`
- Next-stage task: Implement E10 Studio governed memory operator UI.

## Problem

E10 has a permission-scoped backend API and opt-in runtime retrieval, but Studio has no operator surface for creating scoped memory, inspecting memory status, revoking records, or viewing audit evidence. Without this UI, governed memory is technically integrated but not product-operable.

## Tasks

1. Add typed frontend contracts for governed memory permission, source, item, and audit event shape.
2. Add a Studio monitor panel that can create scoped memory for the current application.
3. Add active/revoked/expired status visibility through an operator-safe status filter.
4. Add revoke controls that require reasoned permission and refresh audit evidence.
5. Add audit stream inspection for `governed-memory:{owner_id}:{scope_id}`.

## Acceptance

- Studio monitor tab exposes a governed memory operator panel.
- Operators can set scope, actor, purpose, reason, content, source metadata, retention, and expiry.
- Operators can refresh active/all/revoked/expired views.
- Operators can revoke memory from the UI and see status/audit evidence refresh.
- Runtime retrieval remains opt-in and active-only.

## Final State

- Backend `GET /api/v1/platform/governed-memory` accepts `status_filter=active|revoked|expired|all` through read permission.
- Studio monitor tab includes a governed memory operator panel for create, status-filtered view, revoke, and audit stream inspection.
- Frontend contracts, i18n strings, and CSS are implemented.
- Evidence: `docs/workingon/evidence_v0.2.139_e10_studio_governed_memory_operator_ui_summary.md`.

## Boundaries

- Do not introduce unrestricted filesystem/background memory.
- Do not claim E10 globally complete until the version evidence proves the UI and API path.
- Do not resolve E02 true human panel in this version.
