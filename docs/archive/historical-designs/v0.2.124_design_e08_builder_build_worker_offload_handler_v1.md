## Problem

`builder_build` is the final required worker task kind still unavailable after v0.2.122. Existing Builder execution already owns build status, events, model/tool usage, deadlines, and task finish semantics for API-started builds. Worker offload must consume a queued `builder_build` task without creating a duplicate harness task.

## Boundary

- Do not remove API `/applications/{application_id}/builds`.
- Do not duplicate `harness.start_task()` for already queued worker tasks.
- Do not claim production worker supervision or distributed queue semantics.
- Do not claim full Platform Harness sidecar completion.

## Final Scheme

Add `WorkflowBuilder.run_claimed_build(build_id)` and `builder_build_handler()`:

- queued worker task id must match `build_id`;
- worker path reuses the existing Builder run logic;
- API path keeps existing `Builder.start()` behavior and still creates its own harness task;
- worker path skips Builder-managed harness start/finish and lets `PlatformHarnessWorkerRunner` finish the claimed task;
- failed worker builds preserve build status/error in worker result metadata.

## Acceptance

- A queued `builder_build` task can be claimed and completed by `PlatformHarnessWorkerRunner`.
- Existing API build path still publishes through `Builder.start()`.
- Failed worker builds update build status and fail the worker task deterministically.
