# v0.2.71_design_complexity_router_supporting_guardrails_preservation_v1

## Source

- Stage: `docs/stage-report-archives/v0.2.x/v0.2.71_complexity_router_default_safety_gate.md`
- Original design: `docs/current-design/design_complexity_router_supporting_guardrails_preservation.md`
- Final status: implemented as preservation / deferred guardrails

## Problem

v0.2.70 selected the default-safety gate first, but the supporting guardrails still needed to remain visible and protected from accidental loss.

## Boundary

This design preserved supporting guardrails only. It did not implement classification, editable override controls, or rollout metrics.

## Final Design

- The default-safety gate includes supporting guardrail IDs:
  - `requirement_classification_contract`
  - `operator_override_plan`
  - `rollout_metrics_prerequisites`
- Missing prerequisites are returned explicitly in API and generated evidence.
- Future implementation remains stage-report-selected only.

## Acceptance

- Supporting guardrail IDs appear in backend status and generated evidence.
- Stage report carries them forward as deferred candidates.

## Evidence

- Backend: `platform/backend/src/agent_platform/complexity_router.py`
- Evidence: `docs/workingon-archives/v0.2.71/default_safety_v0.2.71_complexity_router_summary.md`

## Remaining Risk

The next version must choose one concrete supporting guardrail rather than treating this preservation list as an active roadmap.
