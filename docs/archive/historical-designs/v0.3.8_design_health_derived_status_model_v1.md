## Problem

The frontend currently displays a static connected status. That can mislead non-technical users when the backend is unavailable, stale, or the API token is invalid.

## Boundary

This stage should not add a full observability console. It should add a small, reusable frontend status model based on the existing `/api/platform/health` proxy and existing auth error detection.

## Solution

Add a runtime status classifier with these states:

- `checking`
- `connected`
- `auth_required`
- `stale`
- `unavailable`

The classifier should consider expected runtime version, `current_code_ready`, route availability, and whether protected API calls reported auth failure.

## Acceptance Criteria

- Classifier is source-testable without a browser.
- Static "connected" text is no longer the only status source.
- Stale and unavailable states are distinguishable.
