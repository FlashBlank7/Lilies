# design_e05_data_analyzer_breadth_case

## Problem

After `v0.2.46`, the unresolved E05 question is no longer "can deep customer-support stop timing out?" but "is `shallow` the most stable default reuse-depth candidate across more than one family?" Current evidence still leans heavily on code-review and customer-support.

## Boundary

- In scope: add a third E05 case based on `data_analyzer`, run bounded paid/live comparison, produce JSON/summary/DOCX, and update E05 ledger/index/stage artifacts.
- In scope: compare `none` / `shallow` / `deep` within the new family and interpret whether `shallow` still looks like the best default candidate.
- Out of scope: closing all of E05 globally, changing Builder runtime policy yet, or turning this stage into a broad multi-family benchmark suite.

## Solution

Use the built-in `data_analyzer` template as the next E05 family because it is structurally different from code-review and customer-support while still carrying a clear benchmark contract and moderate workflow complexity.

## Implementation Plan

1. Add a `data_analyzer` experiment case to the E05 runner with:
   - explicit requirement text,
   - benchmark reference,
   - required node types,
   - clear mandatory tests for report/statistics outputs.
2. Run deterministic script tests first.
3. Run bounded paid/live comparison for the new family.
4. Produce raw JSON, summary, and DOCX report.
5. Update `docs/experiment-status/ledgers/E05_template_reuse.md` and `docs/experiment-status/v0.2_experiment_status.md`.

## Acceptance

- A new E05 family result exists with interpretable `none` / `shallow` / `deep` evidence.
- The report explicitly answers whether `shallow` still looks like the stable default candidate or whether the evidence changes.
- Stage artifacts are complete enough for archive without reopening `v0.2.46`.

## Final Conclusion

The new family produces an interpretable answer and changes the policy picture: `deep` publishes inside the build budget while `shallow` hits `BuildDeadlineExceeded`, so `shallow` is no longer a credible fixed default reuse-depth candidate across families. The next stage should translate this into an adaptive reuse-depth policy instead of collecting more ambiguous fixed-depth evidence.
