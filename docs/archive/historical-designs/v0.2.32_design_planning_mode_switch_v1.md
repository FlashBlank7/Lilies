## 1. Problem

E01 asks whether plan-first improves complex BlockFlow quality compared with node-by-node construction. Current Builder behavior only has implicit `auto` planning. Without an explicit switch, a paid A/B would be confounded by prompt wording rather than controlled Builder behavior.

## 2. Design Goal

Goal:

- Add `planning_mode` to `BuildRequest` and `BuildTeamState`.
- Support `auto`, `required`, and `disabled`.
- In `required`, require `build_plan` before draft/test mutations.
- In `disabled`, hide the `build_plan` tool and instruct the Builder to build node-by-node.
- Preserve existing behavior with default `auto`.

Non-goals:

- Do not expose this in Studio UI yet.
- Do not migrate old build records.
- Do not change WorkflowRuntime.

## 4. Control Flow

API build request -> `BuildTeamState.planning_mode` -> Builder system prompt + tool definitions -> optional mutation guard -> build events and team state expose mode.

## 5. Implementation Plan

1. Add the literal field to `BuildRequest` and `BuildTeamState`.
2. Pass the field through `create_build()`.
3. Add a Builder prompt suffix based on mode.
4. Omit `build_plan` from tool definitions when disabled.
5. Enforce `required` mode before draft/test/template mutations.
6. Add tests for disabled hiding and required preflight guard.

## 7. Risks

- This is an experiment control, not a product contract. Stage report must avoid treating it as user-facing API commitment.
- Required mode may cause extra turns if the model ignores the guard.

## 8. Acceptance Criteria

- Default `auto` behavior remains backward compatible.
- Tests prove disabled mode prevents `build_plan` usage.
- Tests prove required mode blocks mutation before `build_plan`.
