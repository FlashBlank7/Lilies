# design_v0.2.33_complex_benchmark_case_v1

## Goal

Make `scripts/live_builder_benchmark_suite.py` support named benchmark cases so v0.2.33 can run a complex E01 A/B without source-code prompt edits.

## Module Boundary

- In scope:
  - `scripts/live_builder_benchmark_suite.py`
  - focused deterministic tests in `tests/test_workflow.py` or a script-level test if existing patterns allow it
- Out of scope:
  - changing Builder prompt semantics
  - changing benchmark scoring formula unless the complex case exposes a concrete false-negative
  - changing Studio UI

## Design

Introduce a small in-script benchmark case registry.

Required case names:

- `summary_smoke`: current article-summary case, preserving v0.2.32 behavior.
- `complex_research_brief`: a multi-module research brief BlockFlow case.

The script should read:

- `LIVE_BUILDER_BENCHMARK_CASE`, default `summary_smoke`.
- `LIVE_BUILDER_BENCHMARK_PLANNING_MODE`, already available.

Each case should provide:

- application name prefix
- requirement text
- benchmark suite name and case name
- reference workflow
- required node types
- optional required harness nodes
- minimum score/pass-rate if needed

## Complex Case Shape

`complex_research_brief` should ask Builder Team to create a BlockFlow that:

1. accepts `question`, `source_notes`, and optional `audience`;
2. extracts typed research constraints;
3. classifies the task difficulty or report style;
4. assembles context;
5. generates a structured answer or brief;
6. renders a final Markdown response;
7. records an audit event or includes a soft harness node such as `event_recorder` or `budget_gate`;
8. returns a final answer through `end`.

Reference node types should include:

- `start`
- `parameter_extractor`
- `question_classifier`
- `context_assembler`
- `model_turn`
- `template_transform`
- `event_recorder`
- `end`

## Acceptance Criteria

- Running the script with no case env var behaves like the prior summary benchmark.
- Running with `LIVE_BUILDER_BENCHMARK_CASE=complex_research_brief` records the case name in result JSON and evaluates the candidate against the complex reference.
- Tests cover case selection and required complex reference node types.
- No paid call is made by deterministic tests.
