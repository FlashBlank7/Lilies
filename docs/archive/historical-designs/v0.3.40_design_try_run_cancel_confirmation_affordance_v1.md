## Problem

v0.3.39 tells users to cancel explicitly if an active Try run appears stuck, but the current cancel button posts immediately. A non-technical user can stop a queued/running run by accident while exploring the result card.

## Boundary

- Frontend confirmation only.
- No backend API change.
- No automatic cancellation, retry, or new run.

## Solution

- Change the first cancel click into an inline confirmation state.
- Require a second explicit stop action before calling `/runs/{id}/cancel`.
- Provide a keep-waiting action that dismisses the confirmation without mutation.

## Acceptance Criteria

- First cancel click does not call the cancel API.
- Confirmation panel is tied to the current active run id.
- Confirm action calls the existing cancel API once.
- Keep-waiting action clears the confirmation state.
