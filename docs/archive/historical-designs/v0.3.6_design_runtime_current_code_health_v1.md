## Problem

v0.3.5 had to start a temporary backend on port `8002` because the existing backend on `8001` did not expose the newly added cleanup route. This means local usability validation can accidentally test stale runtime state.

The current `/health` endpoint only reports generic provider/tool information and the FastAPI app still advertises version `0.2.0`, so a script cannot easily prove that a running service represents current v0.3.x code.

## Boundary

This design should not introduce deployment infrastructure or a broad environment manager. It should add a small runtime identity surface and a local audit script that can verify current-code signals.

## Solution

- Add backend runtime metadata to `/health`, including API version, current git commit if discoverable, branch if discoverable, and route availability for selected v0.3.x product routes.
- Keep `/health` unauthenticated because it already is, but do not expose secrets, tokens, or environment variable values.
- Add a v0.3.6 runtime health evidence script that:
  - queries `/health`,
  - queries the frontend home route if available,
  - verifies the smoke cleanup route is present by inspecting backend routes in-process and, when live, by checking a safe negative request path,
  - records whether the observed backend version is stale or current.

## Acceptance Criteria

- Runtime metadata exists in `/health`.
- A focused API test verifies health metadata and selected route availability.
- A local evidence script records backend/frontend reachability and current-code signals.
- Evidence makes stale runtime obvious instead of silently passing.

## Evidence Requirements

- API code change.
- Focused pytest.
- v0.3.6 runtime health JSON in `workingon/`.
