## Problem

v0.3.44 prevents invalid inputs from starting a Try run, but after the user fixes the inputs the UI only restores the buttons. For non-technical users, that is too implicit: they may not know whether the correction worked or whether the run controls are safe to use again.

## Boundary

- Frontend state and copy only.
- No run API call, no model call, no auto-fix, and no mutation of entered values.
- Preserve existing parser-error guard and active-run duplicate-start guard.

## Proposed Solution

- Track whether a parser error has appeared during the current Try input editing session.
- When that error clears and inputs are valid, expose a recovered-ready state near the run controls.
- Mark the run controls with a testable recovery data marker so readiness after correction is explicit.
- Clear the recovered-ready state after a successful explicit run start.

## Acceptance Criteria

- Parser errors still block draft and published run actions.
- After a parser error clears, the UI shows a recovered-ready section before the run buttons.
- The run controls expose a recovered state marker while the recovered-ready section is visible.
- Starting a run remains an explicit user action.
