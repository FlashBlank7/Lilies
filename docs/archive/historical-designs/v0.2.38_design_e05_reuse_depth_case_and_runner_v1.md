# design_v0.2.38_e05_reuse_depth_case_and_runner_v1

Status: completed in `v0.2.38`.

## 1. Goal

Create a controlled E05 experiment runner that compares `reuse_depth=none`, `shallow`, and `deep` on the same Template-friendly Builder Team requirement.

The runner must collect real build evidence and Template-specific instrumentation, not only final benchmark score.

## 2. Module Boundary

Primary files:

- `scripts/e05_template_reuse_depth_experiment.py`
- `tests/test_workflow.py`

Read-only dependencies:

- `platform/backend/src/agent_platform/builder.py`
- `platform/backend/src/agent_platform/workflow_models.py`
- `platform/backend/src/agent_platform/template_store.py`
- `templates/*.json`

## 3. Data Flow / Control Flow

For each arm:

1. Build a requirement that explicitly sets the intended `reuse_depth`.
2. Create an application through the real FastAPI app in-process.
3. Start Builder Team with `planning_mode=required`, bounded `max_turns`, and bounded `max_repair_cycles`.
4. Wait for terminal build state.
5. Fetch draft snapshot, build event stream, and Platform Harness task metadata.
6. Evaluate the generated workflow against a fixed benchmark reference.
7. Extract arm metrics:
   - build status and error
   - benchmark pass/score/pass_rate
   - draft node/edge/test counts and node types
   - model/tool call counts from Platform Harness usage
   - whether a BuildPlan exists and its `reuse_depth`
   - number of `template_suggestions` and `template_expand` operations
   - recommended actions and template candidates observed in stream events

## 4. Implementation Plan

1. Implement `ReuseDepthArm` definitions for `none`, `shallow`, and `deep`.
2. Build a Template-friendly requirement around a code-review / test-repair BlockFlow, because the built-in `code_reviewer` template should be relevant.
3. Add deterministic preflight that checks the template suggestion API returns no suggestions for `none`, and suggested actions for `shallow`/`deep`.
4. Add a paid/live execution path using configured DeepSeek provider and in-process TestClient.
5. Add a `--skip-paid` or environment flag only for focused tests, not for the real stage run.
6. Write summary JSON under `docs/experiment-status/evidence/`.
7. Add focused tests that validate arm construction and preflight metric extraction without paid model calls.

## 5. Acceptance Criteria

- The runner produces one JSON artifact containing all three arms.
- The JSON artifact contains template operation metrics for each arm.
- The runner records provider/model, budget boundary, command mode, and environment-derived skip reason if live execution cannot proceed.
- Focused tests verify the three-arm setup and suggestion preflight behavior.
- The runner is safe to import in tests without starting paid runs.

Acceptance result:

- Completed. The runner produces a three-arm JSON artifact with template suggestion/expand metrics and paid/live model evidence.
- The initial live attempt revealed a design gap: runtime model and provider timeout needed to be explicit in the evidence. The script was revised and rerun.
- Focused tests pass: `3 passed, 1 warning`.
