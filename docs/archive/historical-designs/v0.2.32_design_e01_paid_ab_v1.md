## 1. Problem

E01 remains open despite multiple prerequisite fixes. The project needs a real paid/live A/B comparing plan-first and node-by-node on the same requirement family.

## 2. Design Goal

Goal:

- Run two bounded paid/live Builder builds:
  - plan-first: `planning_mode=required`
  - node-by-node: `planning_mode=disabled`
- Evaluate both with the same benchmark suite shape.
- Produce a concise DOCX report with background, experiment design, result, conclusion, and evidence.
- Update experiment ledger with an honest E01 status.

Non-goals:

- Do not overgeneralize from one A/B pair.
- Do not run unbounded paid calls.
- Do not close all Builder quality questions.

## 3. Module Boundary

- `scripts/live_builder_benchmark_suite.py`
- `docs/experiment-status/evidence/`
- `docs/experiment-status/reports/`
- `docs/experiment-status/v0.2_experiment_status.md`

## 4. Data Flow

Same requirement -> plan-first paid run + node-by-node paid run -> benchmark reports -> A/B summary JSON -> E01 DOCX report -> experiment ledger -> stage report.

## 5. Implementation Plan

1. Extend the live benchmark script to accept `LIVE_BUILDER_BENCHMARK_PLANNING_MODE` and include it in build request/result metadata.
2. Run the plan-first mode with bounded budget.
3. Run the node-by-node mode with bounded budget.
4. Compare build status, benchmark pass/fail, score, model/tool calls, draft node types, tests, and failure modes.
5. Generate E01 A/B DOCX report.
6. Update `docs/experiment-status/v0.2_experiment_status.md`.

## 6. Referenced Intellectual Assets

## 7. Risks

- One A/B pair is not statistically strong. It can close the first formal E01 tranche only if the report states the boundary.
- Required planning may spend extra turns and lose on cost even if quality improves.

## 8. Acceptance Criteria

- Both paid/live result JSON files exist or a bounded failure is recorded.
- A/B summary JSON exists.
- DOCX report exists and passes structural QA.
- Ledger marks E01 as completed for first formal A/B tranche or clearly explains why not.

## 9. No Next-stage Authority

This design expands one accepted v0.2.32 task only. It does not select or prioritize future stages.
