# 项目三：Home Assistant 持久事件监控与受控自动化

## 客户问题

一个小型设施使用 Home Assistant 接收门禁和环境状态。标准的“门持续打开五分钟”
自动化在 Home Assistant 重启或自动化重载时会重置等待状态，值班人员可能漏掉
通知。客户希望 Lilies 生成一个可发布的工作流替代这条通知自动化，同时保留
Home Assistant 的事件、实体、身份和服务体系。

## 业务目标

工作流必须订阅 Home Assistant WebSocket 状态事件。门打开后建立一个持久等待；
门在期限前关闭则取消；到期时仍然打开才向受限通知系统发送一次通知。重复事件、
WebSocket 断线和 Lilies 平台重启不能产生重复通知或丢失合法等待。

标准生产规则为持续打开 300 秒。公开调试和密封 Seed 可以使用 1 至 5 秒的缩短
等待验证同一状态机，但必须同时核对计算出的逻辑期限、通知计数和恢复轨迹，不能
把“脚本睡眠后手工调用工作流”替代平台的持久定时唤醒。

## 输入

- Home Assistant 2026.7.2 `/api/websocket` 的 `state_changed` 事件；
- 被授权的门实体清单；
- 每个实体的新旧状态、事件时间和 Home Assistant context identity；
- 等待时长；
- 可选的高风险设施动作请求；
- 高风险动作的人工批准或拒绝。

## 处理规则

1. 只有授权实体、状态为 `on/open` 或 `off/closed`、具备事件时间和事件身份的
   消息可以进入状态机。
2. `on/open` 建立或保持该实体的一个持久定时器；相同事件重放不得新增定时器。
3. `off/closed` 只取消比自己更早的等待；过旧关闭事件不能取消较新的打开事件。
4. 到期唤醒必须重新核对该实体当前 Home Assistant 状态。仍然打开才通知，已经
   关闭则安全结束。
5. 相同实体和打开事件只能形成一个物理通知。通知写入必须使用稳定幂等身份。
6. WebSocket 断线后自动重连并重新订阅。已接受事件和定时器保存在 Lilies，
   不能依赖 WebSocket 会话内存。
7. Lilies 平台在等待期间重启后，必须恢复订阅和未到期定时器；到期后仍执行。
8. 门通知替代流程绝对不能调用 Home Assistant 设备服务。
9. 单独的高风险动作请求必须暂停等待人工。批准后才可调用受限动作接口；
   拒绝或缺少批准时零动作。
10. 临时连接错误可以有界重试；认证/权限拒绝不得当作普通重试或成功通知。

## 最终交付

- 通知决定：实体、打开事件、逻辑期限、当前状态、是否通知、通知回执；
- 持久定时与恢复轨迹：建立、重放、取消、重连、重启恢复、到期和完成；
- 受控动作回执：请求、人工决定、是否尝试、客户系统结果；
- 已发布的不可变工作流版本。

## 公开业务验收

至少覆盖：

1. 门持续打开，到期只通知一次；
2. 门提前关闭，零通知；
3. 打开事件重复，仍只有一个定时器和一个通知；
4. 打开后重启 Lilies 平台，到期仍通知一次；
5. WebSocket 断开后恢复订阅，后续事件仍被处理；
6. 较旧关闭事件不能取消较新打开；
7. 两扇门并发等待不串线；
8. 通知权限被拒绝时不伪装成功、不调用设备服务；
9. 高风险动作人工批准后一次执行；
10. 高风险动作人工拒绝后零执行。

## 基线、回滚和声明边界

基线是 Home Assistant 官方 state trigger 的 `for: 00:05:00`。官方文档明确说明
等待中的 `for` 在 Home Assistant 重启或自动化重载时会重置。本项目比较同一
事件序列下的通知语义和重启持久性，不比较大规模吞吐。

回滚方式是停用 Lilies 发布工作流和事件订阅，再重新启用冻结的 Home Assistant
自动化；不修改实体、通知或身份配置。

本题不验证真实门锁硬件、互联网推送到达率或家庭/设施安全认证。受控环境用
Home Assistant 真实 API 与真实 WebSocket，门实体由 REST 测试入口设置状态。
