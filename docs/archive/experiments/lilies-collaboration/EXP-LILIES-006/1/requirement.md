# 预测驱动的受约束补货计划与 ERPNext 草稿

我们使用 ERPNext 管理库存和采购计划。请搭建一条生产增强工作流：读取客户授权
的历史需求、计划期参数以及 ERPNext 当前库存，调用已经批准部署的需求预测模型，
在预算、总采购能力、安全库存、MOQ 和订货批量约束下形成可解释的补货方案。

模型准备与生产工作流分离。Builder 可以从客户模型库导入兼容候选、微调候选，
或在没有合适候选时使用客户授权历史训练新模型；必须使用按时间切分的独立
回测，保存来源、数据摘要、算法和基础版本血缘，经人工明确批准后才能成为
带修订的部署。生产工作流只能调用已部署模型，监控异常只提出重训建议，
不能在处理补货批次时在线训练或自行更换模型。

业务规则如下：

- 历史不足、日期乱序、单位冲突、负需求或无效约束必须在计划前安全停止；
- 每个物料要输出点预测和预测区间，且能追溯到模型、版本、摘要和部署修订；
- 规划必须满足库存平衡、安全库存、MOQ、订货批量、共享采购能力和预算；
- 如果全部需求不可满足，必须返回可行的降级方案、缺口和真正生效的约束；
  如果连最低履约目标都不可行，则只解释不可行性，不写 ERPNext；
- 高金额或存在预测/约束风险的计划必须暂停给库存计划员复核；
- 人工批准后只能在 ERPNext 创建 `docstatus=0` 的 Material Request 草稿；
  禁止提交 Material Request、创建 Purchase Order、Stock Entry 或过账交易；
- 同一计划批次重放不得新增第二份 Material Request；权限拒绝必须停止，
  临时错误只有在能证明未写入时才允许有界重试；
- 最终必须从 ERPNext 公开 REST API 读回草稿并与计划逐项核对。

最终交付三类机器可读工件：预测与模型血缘、约束计划与解释、ERPNext 草稿与
读回回执。每份结果必须能追溯到计划批次、工作流发布版本、模型版本、人工决定
和客户系统记录。

Builder 只能使用本包公开材料、公开积木手册、公开 schema 和 Lilies 平台公开
API。不得读取受保护 Seed、标准答案、平台数据库或平台实现源码来寻找答案。
ERPNext 接口必须由公开 OpenAPI schema 生成通用连接器；禁止增加 ERPNext 或
本项目专用平台适配器。

本题证明受控本地环境中的预测治理、约束规划和 ERPNext 草稿交付，不证明公开
合成需求代表客户真实需求，也不证明长期生产预测精度。
