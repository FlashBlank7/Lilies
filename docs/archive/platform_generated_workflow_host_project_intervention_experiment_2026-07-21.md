# 平台生成工作流介入真实项目的增补与替换实验预注册

> 日期：2026-07-21
> 版本：v2
> 状态：宿主项目与接口已完成官方资料资格审查；本地宿主基线和平台干预实验尚未开始
> 最高约束：接口适配必须由平台完成，实验人员不得预先编写适配器
> 宿主资格证据：`docs/evidence/host_project_intervention_qualification_2026-07-21.json`
> 当前平台接口审计：`docs/evidence/platform_interface_capability_audit_2026-07-21.json`
> 组件探针证据：`docs/evidence/platform_workflow_candidate_probe_2026-07-21.json`

## 1. 执行结论

实验对象不是 PyOD、OR-Tools 等算法库能否运行，而是平台生成的工作流能否真正介入已有软件项目。

本实验只接受两类真实干预：

1. **增补型**：宿主项目原本没有完整覆盖某项业务流程，平台根据需求和官方接口材料生成新工作流，通过宿主的正式接口完成任务。
2. **替换型**：宿主项目已经有一段核心流程，平台生成工作流在保持输入、输出和副作用合同不变的条件下替换它，并与原实现进行正确性、性能、可靠性和维护成本对比。

两类实验共同检验：

```text
自然语言需求
  -> 平台识别宿主接入点
  -> 平台理解接口和认证
  -> 平台建立事件、schema、调用和写回
  -> 平台生成并测试工作流
  -> 工作流完成真实任务
  -> 独立测试器判断正确性、性能和可靠性
```

实验人员只允许提供：

- 冻结的宿主项目版本和源码。
- 官方接口文档、OpenAPI/schema、SDK 类型或 CLI 帮助。
- 测试环境地址和秘密引用。
- 原始业务需求、权限边界和批准选择。
- 独立 oracle、负载发生器和故障代理。

实验人员禁止提供：

- 为平台预写的 REST/MQTT/WebSocket/SDK 适配器。
- 字段映射、认证代码、Webhook 接收器或项目插件。
- 已经能够完成目标任务的隐藏脚本。
- 对平台生成结果的人工代码修补。

任何人工适配代码都使本次运行的 `automatic_interface_alignment=false`。人工修复后可以单独报告“人工救援成功”，但不得计入平台自动交付成功率。

## 2. 两种干预模型

### 2.1 增补型 `AUG`

增补型回答：

> 宿主项目缺少一条跨数据、判断、人工和外部动作的流程时，平台能否自己找到接口并补上？

比较组：

| 组 | 定义 | 用途 |
| --- | --- | --- |
| `AUG-BASE` | 原项目加现有人工操作 | 业务现状基线 |
| `AUG-HUMAN` | 工程师手工实现扩展 | 可行上界和工程成本基线 |
| `AUG-PLATFORM` | 仅给平台需求和官方接口材料，由平台自动生成 | 主要处理组 |

`AUG-BASE` 可能根本无法自动完成新任务，因此不能用“原项目延迟为零”与新增流程比较。业务结果比较 `AUG-BASE`，实现时间和运行开销主要比较 `AUG-HUMAN`。

### 2.2 替换型 `REP`

替换型回答：

> 平台能否保持宿主项目现有接口和语义，用生成工作流替换一段真实流程？

替换必须进一步分开：

| 子类 | 替换内容 | 主要归因 |
| --- | --- | --- |
| `REP-FLOW` | 保留相同规则、模型或算法，只替换编排和运行机制 | 平台接口、编排和运行时能力 |
| `REP-STACK` | 编排、算法或技术栈一起替换 | 整体方案能力，不能单独归因于平台运行时 |

比较组：

| 组 | 定义 |
| --- | --- |
| `REP-ORIGINAL` | 宿主项目原始流程 |
| `REP-HUMAN-PORT` | 工程师在相同兼容边界上人工移植，可选但推荐 |
| `REP-PLATFORM` | 平台自动生成的兼容替代流程 |

`REP-FLOW` 必须先通过语义等价门，才能比较延迟和吞吐。`REP-STACK` 必须同时报告任务质量变化和系统性能变化，不能把更换算法后的准确率变化写成工作流引擎性能。

## 3. 平台必须自行完成的接口对齐

### 3.1 输入给平台的材料

平台可以读取：

- 项目 README、官方文档和冻结源码。
- OpenAPI、JSON Schema、GraphQL schema、Webhook 示例。
- MQTT topic/QoS 说明、WebSocket 消息协议。
- SDK 类型声明、CLI `--help` 和插件规范。
- 测试环境暴露的能力清单。
- 用户通过选项式澄清提供的业务决定。

平台不能读取隐藏 oracle、故障脚本和人工参考实现。

### 3.2 平台完成条件

一次接口对齐只有同时完成以下步骤才算通过：

1. 识别正确的触发接口和写回接口。
2. 识别认证方式，并只引用 Secret Store 中的秘密。
3. 生成输入、输出、错误和分页 schema。
4. 完成字段、枚举、单位、时间和主键映射。
5. 建立 Webhook/MQTT/WebSocket/SDK/CLI 所需运行连接。
6. 处理超时、限流、重试、幂等和重复事件。
7. 对高风险写入配置权限和人工批准。
8. 自动生成并运行契约测试。
9. 保存连接器版本、接口版本和验证证据。
10. 宿主接口小版本变化后能够检测失效并重新生成或阻断。

### 3.3 自动对齐指标

```text
字段自动映射率 =
  无人工编辑且通过隐藏契约测试的必要字段数
  / 必要字段总数

接口自动对齐率 =
  无人工代码且完整通过认证、触发、读取、写回和错误合同的干预数
  / 全部干预数
```

同时记录：

- 平台主动提出的必要澄清数和无关问题数。
- 人工填写秘密以外的配置字段数。
- 人工修改 schema/映射/代码的行数。
- 第一次契约通过时间。
- 接口调用前即发现错误的比例。
- 上游接口变化后的自动修复率和错误阻断率。

## 5. 六个项目的增补与替换任务

### 5.1 `HOST-01` Paperless-ngx

现有能力：文档消费、OCR 后归档、标签/往来方/文档类型匹配、文档工作流和 REST API。

**增补任务 `AUG-PAPERLESS-INVOICE`**

```text
新文档完成消费
  -> 判断是否为发票
  -> 抽取发票字段和行项目
  -> 校验币种、税额、总额和重复发票
  -> 异常进入人工复核
  -> 回写 Paperless 自定义字段和标签
  -> 批准后生成会计导入工件
```

平台必须自行理解 Paperless 触发器和 REST schema。可以自行选择 invoice2data 或 Docling，但实验人员不提供包装器。

**替换任务 `REP-PAPERLESS-MATCH`**

- `REP-FLOW`：用平台工作流复现 Any/All/Exact/Regex 等确定性匹配并回写相同元数据。
- `REP-STACK`：替换 Auto 匹配，比较原神经网络匹配与平台选择的分类方案。

核心指标：字段 F1、元数据 macro-F1、重复入账率、文档吞吐、端到端 p95、人工复核分钟、错误写回数。

### 5.2 `HOST-02` InvenTree

现有能力：库存、物料、采购/销售/生产订单、低库存通知、REST/OpenAPI 和事件插件。

**增补任务 `AUG-INVENTREE-REPLENISH`**

```text
每日读取库存、消耗、在途和交期
  -> 预测需求
  -> 计算补货量和缺货风险
  -> 形成采购建议
  -> 人工批准
  -> 通过 InvenTree API 创建或更新采购单
```

**替换任务 `REP-INVENTREE-LOW-STOCK`**

- `REP-FLOW`：替换低库存通知和自动发单事件流程，保持原阈值语义。
- `REP-STACK`：用预测需求替换静态阈值，质量与性能分开比较。

核心指标：确定性通知一致率、采购单正确率、缺货率、库存成本、重复订单数、事件到动作 p95、API 请求量。

### 5.3 `HOST-03` ThingsBoard

现有能力：设备遥测接入、Rule Engine、告警、外部调用和设备 RPC。

**增补任务 `AUG-THINGSBOARD-MAINTENANCE`**

```text
MQTT 遥测
  -> schema、单位和时间窗校验
  -> 异常检测与风险分级
  -> 建立/更新告警
  -> 高风险人工确认
  -> 写入 mock 维修系统
  -> 保存设备、告警和工单关联
```

**替换任务 `REP-THINGSBOARD-RULE-CHAIN`**

- `REP-FLOW`：把冻结的温度验证、转换、告警和 REST 写回 Rule Chain 替换为平台工作流。
- `REP-STACK`：将规则检测替换为平台选择的 PyOD/模型模块。

核心指标：消息语义一致率、丢失/重复动作、msg/s、p50/p95、CPU、内存、积压、重启恢复时间和超时补偿。

### 5.4 `HOST-04` Actual Budget

现有能力：交易导入、去重和 reconciliation、按序执行的分类规则、NPM API 和 CLI。

**增补任务 `AUG-ACTUAL-RECEIPT`**

```text
收据或发票
  -> 提取商户、日期、金额和类别候选
  -> 与未匹配交易对账
  -> 冲突人工确认
  -> 通过 Actual API 更新交易并附证据
```

**替换任务 `REP-ACTUAL-RULES`**

- `REP-FLOW`：复现冻结规则集的条件、顺序和最后规则覆盖语义。
- `REP-STACK`：用学习分类器替换规则分类，但保留导入和去重合同。

该项目没有普通 REST API，平台必须自行建立受控 Node SDK 或 CLI 桥接。若平台只支持 HTTP，这里应真实失败并形成缺口。

核心指标：交易分类 macro-F1、规则语义一致率、余额不变量、去重错误、导入吞吐、p95、人工确认量。

### 5.5 `HOST-05` Chatwoot

现有能力：客户会话、消息、团队和坐席分配、标签、Webhook 与事件/条件/动作自动化规则。

**增补任务 `AUG-CHATWOOT-SUPPORT`**

```text
新会话或新消息
  -> 判断意图、紧急度和客户上下文
  -> 检索知识并生成回复候选
  -> 低置信度或高风险转人工
  -> 回写标签、团队和批准后的回复
```

**替换任务 `REP-CHATWOOT-AUTOMATION`**

- `REP-FLOW`：替换冻结的一组路由、标签和分配规则，保持事件/条件/动作结果一致。
- `REP-STACK`：以分类模型或 RAG 辅助替换关键词路由。

核心指标：路由/标签一致率、意图 macro-F1、错误自动回复数、事件到分配 p95、Webhook 重复处理、坐席人工分钟。

### 5.6 `HOST-06` Home Assistant Core

现有能力：设备状态、事件、服务动作、REST/WebSocket 和触发器/条件/动作自动化。

**增补任务 `AUG-HA-ENERGY`**

```text
能耗和环境传感器事件
  -> 质量检查和窗口
  -> 异常/预测
  -> 通知与节能建议
  -> 高风险设备动作前人工批准
```

**替换任务 `REP-HA-DURABLE-TIMER`**

用平台工作流替换“门持续打开五分钟后通知”的标准自动化。Home Assistant 官方说明，`for` 等待在重启或自动化重载后会重置；该任务可以直接检验平台持久计时和恢复是否提供真实改进。

核心指标：事件到动作一致率、通知 p95、漏报、重复动作、重启中等待状态保留率、恢复时间和资源开销。

该项目属于个人/小型设施泛化实验，不计入传统企业成功率。

## 6. 公平比较与性能实验

### 6.1 先正确，再谈快

每次比较按以下顺序：

1. 接口契约通过。
2. 任务必要结果和副作用通过。
3. 幂等、权限和数据不变量通过。
4. 前三项通过后才比较速度、吞吐和资源。

错误结果的低延迟不计性能优势。

### 6.2 固定条件

- 相同宿主版本、数据快照和接口配置。
- 相同硬件、进程资源上限和网络故障代理。
- 相同输入顺序；需要随机化时保存种子。
- 相同算法用于 `REP-FLOW`。
- 相同隐藏 case 和负载曲线。
- 原流程和替换流程随机交叉运行，避免机器热状态偏差。
- 每组预热后至少 30 次延迟样本；吞吐采用至少 10 分钟稳态窗口并重复 5 次。

### 6.3 指标层

| 层 | 指标 |
| --- | --- |
| 接口 | 自动识别率、字段自动映射率、零人工代码契约通过率、首次通过时间 |
| 任务 | 项目专属准确率、约束、不变量、业务代价 |
| 系统 | p50/p95/p99、吞吐、CPU、内存、冷启动、队列积压 |
| 可靠性 | 故障成功率、恢复率、重复副作用、状态丢失、MTTR |
| 工程 | 人工配置数、人工代码行、生成/修复轮次、上游升级适配时间 |
| 费用 | 模型调用、token、外部 API、计算和人工分钟 |
| 可用性 | 非技术用户能否配置、启动、理解结果和处理失败 |

### 6.4 替换通过门槛

每个项目预注册自己的非劣界限，至少满足：

- 所有安全、余额、唯一写入和权限不变量零违反。
- `REP-FLOW` 确定性语义一致率为 100%。
- 任务质量不低于预注册界限；不得事后放宽。
- p95 和吞吐分别报告，不以平均值掩盖长尾。
- 运行开销即使更差也如实报告，不因功能更丰富而隐藏。

`REP-STACK` 若任务质量提升但速度下降，结论必须写成明确权衡，不能只给一个综合分。

## 7. 可靠性与接口故障注入

| 类别 | 故障 | 正确行为 |
| --- | --- | --- |
| 接口描述 | 缺字段、过期示例、文档与 schema 冲突 | 询问、探测或阻断，不猜写入 |
| 认证 | token 过期、权限不足、错误 scope | 识别并提示最小权限，不泄露秘密 |
| REST | 429、500、分页、超时后成功 | 退避、续页、幂等重试 |
| Webhook | 重放、乱序、签名错误、响应丢失 | 验签、去重、顺序策略和回执 |
| MQTT | 断线、重复 QoS 消息、迟到消息 | 重连、去重、窗口和状态恢复 |
| WebSocket | 断线、重订阅、消息关联错误 | 恢复订阅且不漏发/重复动作 |
| SDK/CLI | 版本不兼容、进程退出、非零状态 | 版本阻断、错误解析和受控重试 |
| schema | 枚举新增、单位变化、字段重命名 | 检测漂移、重新映射或阻断 |
| 宿主升级 | 小版本接口变化 | 使旧证据失效并重新验证 |
| 副作用 | 重复订单、重复消息、重复设备动作 | exactly-once 或明确补偿 |
| 平台运行时 | worker 被杀、服务重启、租约过期 | 从检查点恢复且状态不丢失 |

每种故障对同一冻结工作流运行“机制开启/关闭”配对实验，测量机制实际救回多少 case，而不是只检查代码中是否存在该机制。

## 8. 接口失败如何转化为平台模块

### 8.1 当前平台代码审计

当前结论不是“平台完全没有 Connector”，而是：

- 已有有价值的受治理 HTTP Connector 底座：手工注册的版本化 manifest、请求/响应对象校验、Secret 引用、租户/角色策略、dry-run、精确载荷批准、幂等回执、补偿、回调记录和不可变版本。
- 现有测试由测试代码先构造字段 schema 和 Connector manifest，再调用注册接口。它证明“合同已经有人写好后，平台可以受治理地执行”，没有证明平台会从宿主项目自动生成合同。
- Connector 当前只接受 HTTP(S) base URL，认证类型只有 `none` 和 `bearer`。没有外部 OpenAPI 导入，也没有 MQTT、WebSocket、SDK/CLI 或项目插件运行时。

对 `IF-01` 至 `IF-14` 的静态代码审计结果为：

| 状态 | 数量 | 能力 |
| --- | --- | --- |
| 完整 | 0 | 尚无一项达到真实宿主零人工适配的完整闭环 |
| 部分 | 5 | `IF-04`、`IF-05`、`IF-11`、`IF-12`、`IF-13` |
| 缺失 | 9 | `IF-01`、`IF-02`、`IF-03`、`IF-06`、`IF-07`、`IF-08`、`IF-09`、`IF-10`、`IF-14` |

因此，按当前代码直接开始六个宿主实验，Paperless、InvenTree 和 Chatwoot 也需要人工先写 manifest 和 schema；ThingsBoard 的 MQTT、Actual 的 Node SDK/CLI、Home Assistant 的 WebSocket 会直接缺运行时。按照本预注册，这些都应判平台自动对齐失败，而不是由实验人员补适配器。

完整逐项证据见 `docs/evidence/platform_interface_capability_audit_2026-07-21.json`。

### 8.2 缺口分类

失败不能只记为“项目不兼容”。必须落入下列能力编号：

| ID | 缺口能力 | 典型失败表现 |
| --- | --- | --- |
| `IF-01` | 接口资料摄取与接入点发现 | 读了项目但找错 API、事件或写回边界 |
| `IF-02` | OpenAPI/JSON Schema 导入 | 不能形成类型化端口和请求/响应合同 |
| `IF-03` | 语义 schema 映射 | 字段名相近但主键、单位、枚举或时间语义映错 |
| `IF-04` | 认证与 Secret 映射 | 要求用户把 token 写进节点或权限 scope 过大 |
| `IF-05` | Webhook 生命周期 | 不会注册、验签、回执、重放保护或注销 |
| `IF-06` | MQTT 运行时 | 不会 topic、QoS、重连、会话和重复消息 |
| `IF-07` | WebSocket 运行时 | 不会认证、关联请求、订阅和断线恢复 |
| `IF-08` | SDK/CLI 桥接 | 只能调用 HTTP，无法受控运行 Node/Python/Java SDK 或 CLI |
| `IF-09` | 插件/事件桥接 | 无法根据正式插件规范订阅宿主内部事件 |
| `IF-10` | 分页、限流和异步任务 | 只处理第一页或把异步接受当作任务成功 |
| `IF-11` | 幂等、回执和补偿 | 超时后造成重复业务副作用 |
| `IF-12` | 自动契约测试 | 生成调用但无法证明与真实接口一致 |
| `IF-13` | 连接器版本与证据注册 | 宿主升级后继续沿用过期成功证据 |
| `IF-14` | 接口诊断与自动修复 | 只显示 500/unsupported，不能定位和修正映射 |

### 8.3 领域能力

领域能力继续单列：

- 文件与 Artifact Store。
- DataFrame/schema/数据质量。
- OCR 和文档结构化。
- 模型导入、推理、评估和监控。
- 时间序列预测与回测。
- 优化求解与无解解释。
- RAG 摄取、权限、引用和更新。
- Excel/CSV 生成和独立校验。
- 记录级人工复核界面。

优先级不凭感觉决定，而按失败证据计算：

```text
优先级 =
  跨项目出现次数
  x 导致自动交付失败的概率
  x 业务风险
  x 可复用性
  / 实现与维护成本
```

## 9. 实验规模与因果设计

六个宿主项目各有一个增补和一个替换候选，共 12 个干预合同。

### 9.1 接口资格轮

```text
12 个干预
x 3 次独立生成
= 36 次接口自动对齐实验
```

本轮不允许人工代码，先测平台真实接口能力并产生 `IF-01` 至 `IF-14` 缺口分布。

### 9.2 生成机制消融

从资格轮选择 3 个增补和 3 个替换任务，保持协议和任务原型多样：

```text
6 个代表干预
x 6 个机制条件
x 3 次独立生成
= 108 次 pilot
```

条件包括完整平台、一次性 LLM、去澄清、去类型合同、去验证模块复用、去验收/修复。正式轮提高到每条件 5 次，即 180 次。

### 9.3 运行可靠性

```text
6 个已通过 clean case 的干预
x 8 类相关故障
x 3 次重复
x 机制开启/关闭
= 288 次配对运行
```

主要效应：

```text
ATE(Mi) =
  P(可靠交付通过 | Mi 开启)
  - P(可靠交付通过 | Mi 关闭)
```

同时报告触发率、救援率、正确阻断率、误阻断率和成本。

## 10. 执行阶段

### 阶段 0：冻结

- 冻结宿主 tag/commit、许可证、接口材料和任务合同。
- 冻结原流程、数据、负载、指标和非劣界限。
- 建立隐藏 oracle 和故障代理。

注意：这里只建立测试器，不建立给平台使用的适配器。

### 阶段 1：宿主原始基线

- 启动原项目并跑官方健康检查。
- 复现待增补接缝和待替换原流程。
- 记录原流程任务质量、延迟、吞吐、资源和故障行为。

### 阶段 2：人工对照

- 工程师实现 `AUG-HUMAN` 和可选 `REP-HUMAN-PORT`。
- 记录代码量、时间和维护边界。
- 人工实现只用作对照，平台不可读取。

### 阶段 3：平台零适配资格轮

- 给平台需求、官方资料和测试环境。
- 平台自行生成连接器和工作流。
- 运行隐藏接口契约。
- 把失败映射到 `IF-01` 至 `IF-14`。

### 阶段 4：补平台能力

- 依据跨项目缺口优先级实现平台模块。
- 不为单一项目写隐藏专用适配器。
- 新模块必须能在至少两个不同宿主项目复用。

### 阶段 5：生成、替换和可靠性实验

- 完成 108 次生成 pilot。
- 完成 288 次配对故障运行。
- 分开报告增补、`REP-FLOW` 和 `REP-STACK`。

### 阶段 6：股东会报告

报告必须展示：

- 六个项目各自的原流程、干预边界和证据等级。
- 接口自动对齐率及人工救援率。
- 增补任务相对人工流程的业务改善。
- 替换任务相对原实现的正确性、性能和可靠性。
- 平台缺失模块、失败次数和优先级。
- 成功、失败、未运行和环境阻塞的完整分母。

## 11. 当前诚实状态

已经完成：

1. 两种干预模型和公平对照方法已经明确。
2. 六个真实宿主项目的版本、commit 和官方接口已完成资格审查。
3. 六个算法/处理组件的轻量运行探针仍可作为后续组件候选证据。
4. 接口能力缺口已经形成 `IF-01` 至 `IF-14` 的可判定分类。

尚未完成：

1. 六个宿主项目尚未在统一实验环境完成原始基线。
2. 平台尚未对其中任何项目完成零人工适配。
3. 尚无增补或替换任务达到正式通过。
4. 尚不能对外声明接口自动对齐率、性能改善或可靠性提升。

首轮执行优先选择：

1. `REP-HA-DURABLE-TIMER`：接口和业务语义小而清晰，可以快速暴露 WebSocket、事件、持久状态和重启恢复缺口。
2. `AUG-PAPERLESS-INVOICE`：覆盖文档触发、REST schema、文件、人工复核和结构化工件。
3. `REP-THINGSBOARD-RULE-CHAIN`：覆盖 MQTT、流式负载、告警副作用和严格性能对比。

三个任务分别代表个人事件自动化、企业文档流程和工业设备流，不能互相替代分母。
