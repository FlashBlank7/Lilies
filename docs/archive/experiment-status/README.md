# experiment-status

本目录维护 Lilies 实验闭环、工程应用和当前版本完成情况。

它不是普通阶段记录。它回答三个严肃问题：

1. 哪些实验真的完成了？
2. 哪些实验结果已经用于工程改进？
3. 每个阶段结束后，原始实验 backlog 是否被切实推进或明确延期？

## 1. 维护原则

- 实验未完成时，不得把实验假设写成工程结论。
- 实验可以失败；失败实验也可以用于工程改进，但必须有完整实验设计、结果、结论和证据链。
- 已经用于工程改进的实验必须标记为 `已应用`。
- 工程改进后，必须在实验报告或本目录的状态台账中补充应用说明和证据链。
- 原始实验 backlog 必须逐项关闭。关闭只能是：`已完成`、`已应用`、`显式废弃`、`被新实验替代`、`阻塞并有下一步`。
- `部分实现`、`已有代码能力`、`确定性测试通过` 都不等于实验完成。

## 2. 状态词

| 状态 | 含义 |
| --- | --- |
| `未开始` | 没有实验设计执行记录。 |
| `部分实现` | 相关工程能力已做，但实验问题没有闭环。 |
| `实验完成` | 已有实验报告、结果和结论。 |
| `已应用` | 实验结果已经指导工程改进，并有应用证据链。 |
| `验证应用` | 实验用于验证某次改进有效，而不是触发新的改动。 |
| `延期` | 当前阶段不做，但下一步明确。 |
| `阻塞` | 缺模型、数据、工具、权限或成本边界，不能继续。 |
| `替代` | 被更新、更准确的实验设计取代。 |

## 3. 读取与维护结构

当前采用“索引 + 单实验 ledger + raw summary”结构：

- `v0.2_experiment_status.md`：只保留总览、状态表、关键证据链接和下一步。
- `ledgers/<experiment>.md`：保存单个实验的状态、证据链、应用标记和关闭边界。
- `evidence/*_summary.md`：raw JSON 的小摘要，保留 arm、status、calls、failure、benchmark、结论等日常字段。
- `evidence/*.json`：完整原始证据，只在争议、字段缺失或需要复盘完整事件轨迹时读取。
- `scripts/summarize_experiment_evidence.py`：为 evidence 目录中的 raw JSON 批量生成或刷新 `*_summary.md`。

常规自动演进默认读取索引、ledger 和 summary，不直接读取 raw JSON。

## 4. 每阶段维护规则

每个 stage 结束前必须更新当前版本实验状态文件，例如：

`docs/experiment-status/v0.2_experiment_status.md`

至少维护：

- 原始 backlog 逐项状态。
- 本阶段新增实验。
- 已完成实验报告路径。
- 已应用实验的工程改进路径。
- 仍未关闭实验的下一步。
- 是否允许归档当前 stage。

如果 stage 目标包含实验，但实验报告没有产生，stage report 不能把该实验写成完成，只能写成 `部分实现`、`延期` 或 `阻塞`。

## 5. 已应用标记

当实验结果被用于工程改进时，必须记录：

- 应用标记：`已应用` 或 `验证应用`
- 实验报告路径
- 原始证据路径
- 触发的工程变更
- 代码锚点
- 测试或 live acceptance 证据
- 对应 stage report

如果 `.docx` 实验报告可编辑，直接在报告末尾追加“工程应用补充”。如果暂时无法编辑 `.docx`，必须在本目录台账中补充同等证据链，并把 `.docx` 补充列入下一步。
