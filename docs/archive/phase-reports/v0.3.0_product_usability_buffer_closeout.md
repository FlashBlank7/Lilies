## Original Objective

`v0.3.x` was deliberately inserted as a usability buffer. Its purpose was to make Lilies understandable and operable for non-specialist users before adding more platform depth: improve application creation, draft/canvas comprehension, first run, customer-facing execution, workflow editing, acceptance feedback, and recurrent bug repair.

## Honest Result

The phase materially improved Lilies, but it did not produce a release-ready product. The application and run flows are more usable, yet the phase accumulated 57 small stages, many with one narrow design, and coupled historical static checks to the active regression-lane name. Later v0.4 work also changed Builder and runtime behavior without reconciling the complete suite.

The clean parent of the v0.4.2 control work still has 30 known failures. The current dirty v0.4.x worktree has 150 failures, including 120 additional failures concentrated in the changed regression-lane manifest, historical v0.3 static audits, Builder planning behavior, and workflow runtime expectations. Those failures are not reclassified as success by this archive.

The Japanese-learning scenario reports remain in the archive as historical experiment records only. They are not a current customer segment or product direction.

## Phase Conclusions

1. Customer usability must remain a first-order product constraint, not a final polish step.
2. Customer Runtime, Engineer Studio, and Governance Console need separate information architectures.
3. Acceptance should provide evidence and repair assistance; it should not universally block publishing.
4. Natural-language workflow editing, visible run progress, and readable results are valid product foundations worth retaining.
5. A large number of tiny version reports does not prove a coherent capability. Future versions need a locked, serious vertical contract and independent closure audit.
6. Historical regression scripts must not silently become the current release gate, but current behavior changes must be reconciled with explicit tests rather than deleting old expectations wholesale.
