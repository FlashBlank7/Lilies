日期：2026-08-02

用途：改进 Lilies 对持续事件、长时状态和人工治理工作流的理解、平台操作与可靠交付能力

结果：4 分 19 秒内完成全新环境、全新应用、随机化业务验收、发布和真实 Home Assistant WebSocket 验证

## 一、项目题目与业务目标

项目三模拟设施运维：Home Assistant 持续上报门、设备或传感器的状态变化。工作流
不能看到一次“打开”就立刻报警，而要为每个设备分别记住截止时间；若设备在截止前
恢复就取消，若到期仍未恢复才通知。重复、迟到和乱序事件不能造成重复通知。临时
故障可以重试，权限拒绝必须安全停止。高风险设备动作必须由人批准，拒绝时不得写入
客户系统。

这不是简单的定时器，而是一条跨越实时事件、持久状态、截止时复查、外部通知和人工
决定的完整业务链。

## 三、工作流是怎么解决问题的

工作流先验证事件类型和设备身份。对于正常状态变化，它根据设备身份建立一份互不
干扰的持久计时记录：打开时安排截止任务，关闭时取消。重复事件只返回原处理结果，
较旧事件不能覆盖较新的设备状态。

截止时间到达后，工作流不会相信旧事件，而是重新读取 Home Assistant 的当前状态。
若设备已经恢复，则记录“已恢复、不通知”；若仍然异常，则向受控通知系统只写一次，
并保存决定与通知回执。通知服务临时返回 503 时可以重试，403 则停止且不伪装成功。

对于高风险动作，流程先暂停等待人工。批准后才调用允许的设备动作；拒绝后生成审计
回执并结束，客户设备零写入。每条完成路径都留下可追溯的 JSON 工件。

## 四、测试任务与 Seed 设计

随机化 Seed 不提供答案，只改变业务身份、事件身份和发生顺序；验收检查的是跨不同
数据仍成立的业务不变量。本轮公开 Seed 为 30301，覆盖：

| 测试任务 | Seed 如何施压 | 通过意味着什么 |
|---|---|---|
| 异常持续到截止 | 随机设备与事件身份 | 到期重新查状态，恰好通知一次 |
| 截止前恢复 | 打开后快速关闭 | 计时被取消，绝不通知 |
| 重复事件 | 同一事件再次发送 | 不重复安排、不重复通知 |
| 迟到事件 | 新事件后再发送旧时间事件 | 旧状态不能覆盖新状态 |
| 两个设备并发 | 两个随机设备交错发生 | 每个设备的计时和通知互不污染 |
| 权限拒绝 | 通知端返回 403 | 安全停写且留下错误工件 |
| 临时故障 | 通知端首次返回 503 | 有界重试后成功且仍只写一次 |
| 人工动作治理 | 同时覆盖拒绝与批准 | 拒绝零写入，批准才执行一次 |

此外，本轮没有只靠直接调用工作流来代替真实入口：创建了实际 Home Assistant
WebSocket 订阅，把 `binary_sensor.exp003_fast_websocket` 从关闭改为打开。平台收到
真实事件后生成两次 version 1 运行：一次安排计时，一次由到期任务触发复查和通知；
计时历史依次为 scheduled、dispatched、completed，通知系统中恰好出现一条记录。

## 五、项目三快速 Prompt

```text
这是一个实时事件驱动、跨重启持久、恰好一次交付的企业自动化工作流。

先写出业务不变量：
1. 每个 subject 独立保存最新事件时间、当前状态和截止任务；不能用一个全局定时器。
2. duplicate 返回原结果；out-of-order 事件不得覆盖更新状态。
3. 截止触发时必须重新读取客户系统当前状态，不能用安排计时时的旧快照做决定。
4. 恢复则取消或安全完成；仍异常才通知；同一业务截止最多产生一次外部通知。
5. 503 是可重试技术故障；403 是权限拒绝，必须安全停止并留下真实分类。
6. 高风险动作先人工批准；拒绝时客户系统写入数必须为零。
7. 所有结束路径生成带来源、事件、计时、决定和外部回执的工件。

平台操作顺序：
- 确认事件订阅、持久计时、HTTP、人工暂停和工件能力存在；
- 创建应用并一次提交完整状态机和强制业务测试；
- 保存客户 Secret，只在运行时引用；
- 先跑 duplicate、乱序、并发、恢复、403、503 和人工批准/拒绝；
- 全绿后发布不可变版本；
- 把真实 WebSocket 事件源绑定到这个发布版本，确认连接、事件计数、发布版运行、
  计时历史、客户系统副作用和工件五层证据一致。

不得以图验证通过、直接调用工作流成功或订阅显示 connected 单独宣称完成。
```

## 六、快速使用平台的经验

1. 先把事件状态机画成“接收—安排/取消—到期复查—交付”，再选择平台能力。否则
   Builder 很容易把“延迟 5 分钟”错当成普通 sleep，跨重启后丢失。
2. 随机化业务验收一次覆盖八类不变量，比每次看到一个失败就改图更快。失败时先定位
   是入口、状态机、外部副作用还是工件，不进行盲目迭代。
3. 真实事件验收必须同时看订阅、运行、持久计时、客户通知和工件。任意一层缺失都只
   能说明部分能力可用。
4. 发布动作目前不会自动部署事件订阅。Builder 必须另调一个公开 API，并重复填写
   网络地址、握手、Secret、字段映射、静态输入和 workspace。这是平台重构债务，
   不应固化成 Lilies 的长期提示词负担。
