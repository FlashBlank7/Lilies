## 二、项目和工作流逻辑

项目把 OCR 后的收据事实与 Actual 中已有银行交易对账。工作流先按名称发现预算和
账户，再读取余额、交易、分类和规则；不能把环境生成的 UUID 写进图里。

每张收据先验证 schema 并按原始输入位置去重。随后先检查稳定导入身份和收据标记，
确认以前是否已处理；只有未处理记录才按日期、负整数分金额和商户证据匹配。唯一候选
为匹配，多候选为歧义，同日同商户但金额不同为冲突，没有候选为新交易。

所有可能改变账本的记录合并为一次人工暂停。匹配、人工选择后的歧义和新交易只有明确
批准后才调用 Actual；拒绝、缺少选择、无效输入和金额冲突都是零写入。新交易使用官方
import，让 Actual 自己执行规则与去重；已有交易使用官方更新语义。金额全程是整数分。

写入后工作流重新读取交易和余额。分类或备注更新不能改变余额，只有批准的新交易可以
改变余额，并验证 `closing = opening + approved_new_amount`。最后生成逐收据 JSON、
两张表的 Excel 以及 Program 执行与宿主回读结果。

## 三、测试和 Seed 设计

两项公开强制测试分别证明：坏金额在任何 Program 调用前停止；已处理批次重放仍输出
完整结果和 JSON/Excel，但报告写入数为零、余额 invariant 成立。

完整 Seed 应建立一个新 Actual 账户并生成 8 类收据：唯一匹配、歧义选择、已有导入
身份、已有收据标记、金额冲突、新交易批准、重复输入和人工拒绝。主运行只允许两个
已有交易更新和一个新交易导入；原样重放后必须零新增、余额不变。

一个 Seed 通过应同时看到：8 类状态正确、一次主运行人工暂停、3 个真实物理变化、
正确余额、JSON 和 Excel 类型正确，以及重放再次暂停但 0 报告写入、0 宿主变化。
本轮随机 Seed 在创建测试账户阶段终止，没有进入上述判断，故没有通过数字。

## 四、快速 Prompt

```text
这是一个有真实财务副作用的收据对账工作流。

先写不变量：
1. 金额只用整数分；Actual 支出为负数；禁止浮点比较。
2. schema 校验后按物理输入索引去重，每个重复件仍保留独立回执。
3. stable imported_id 和收据标记检查必须早于相似匹配。
4. 唯一匹配、歧义、金额冲突、新交易必须由日期、整数金额和商户证据区分。
5. 所有可能写账记录先统一人工审批；拒绝、缺选择、冲突和无效输入严格零写入。
6. 新交易只使用官方 transactions import；不得用 addTransactions 绕过去重。
7. 写后从新客户端回读交易和余额；只有批准的新交易允许改变余额。
8. JSON、Excel、Program receipts 和宿主回读必须来自同一最终状态。

平台操作顺序：
- 在构建前取得 deployment receipt，确认 Actual、Program profile、Node runtime、
  workspace 工具、Secret、网络和可写缓存全部 ready；
- 从空应用按最终期望状态原子提交完整图和两项强制业务测试；
- 先通过无效输入与重放零写测试；
- 发布 version 1；
- 新建随机业务账户，跑 8 类主运行，再原样重放；
- 用独立 Actual 客户端回读余额、交易和稳定身份，并检查 JSON/Excel 单元格类型。

验收环境准备失败时不得改工作流。必须返回可操作的 prepare receipt 和原始安全错误类。
```

## 五、快速使用平台的经验

1. CLI 型客户系统的 profile 不是一段命令清单，还必须声明并检查语言运行时、工具目录、
   网络、Secret 和缓存可写性。看到 profile 已注册不能认为可运行。
2. 图要按“发现—读取—判断—审批—执行—回读—交付”搭建，且从 start 到每个业务节点
   做一次整体可达性检查，不要逐节点补线。
3. Desired-state 构建不能复用已消费的 mutation idempotency key。删除再添加节点会删除
   相连边，但旧 add-edge key 仍然占用；恢复工具必须比较最终图并生成新的 reconcile key。
4. 无效输入测试和真实重放测试用途不同：前者证明前置安全，后者证明 Program、账本、
   幂等、余额和工件完整性。两者都要通过才发布。
5. Seed runner 的客户环境准备必须先独立完成并签发 receipt。否则 Builder 无法判断
   “工作流失败”和“验收器没准备好”。

## 六、9 分 22 秒调试路径

| 阶段 | 约占比 | 结果 |
|---|---:|---|
| Actual 启动、Program profile 与平台进程重载 | 20% | profile 可见 |
| 复用 Builder 经验从空应用构建 | 10% | 31 节点，旧辅助程序丢主边 |
| 期望状态修复与结构校验 | 10% | 补齐入口链后 valid |
| 首次业务测试与正则进程归因 | 15% | 临时平台从 stdin 启动导致 spawn 失败 |
| 使用真实文件入口重启并恢复正则 | 10% | 无效输入测试通过 |
| Program 执行与沙箱 runtime 归因 | 15% | 发现旧镜像缺 Node |
| 重建仓库既有沙箱、公开测试和发布 | 15% | 2/2，version 1 |
| 新 Seed 环境准备 | 5% | Actual 账户创建失败，冻结结论 |

业务图本身没有经历逐案例调试。主要时间消耗在平台部署碎片：profile 只在启动加载、
stdin 启动破坏 multiprocessing、镜像标签存在但内容过旧、验收器准备失败又隐藏错误。

## 七、可靠交付 Prompt

```text
按六层验收财务对账：
A. 输入：schema、整数金额、来源摘要和物理重复位置正确。
B. 分类：已处理优先；匹配、歧义、冲突和新交易证据可解释。
C. 人工：任何潜在写账都暂停；拒绝与缺选择严格零写。
D. 宿主：只用官方 CLI，实际交易、imported_id、备注、分类和数量可回读。
E. 不变量：更新不改余额；只有批准新增改变余额；重放零新增。
F. 工件：JSON 与 Excel 内容一致，数值/日期/布尔类型正确且无公式。

还要单独验收环境：Program profile 的运行时、工具、Secret、网络、缓存和宿主准备必须
在工作流前 ready。环境失败不得计为业务失败，也不得通过修改图规避。
```
