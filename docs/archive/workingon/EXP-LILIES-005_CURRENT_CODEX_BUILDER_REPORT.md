## 二、题目和真实业务场景

客户是一家使用 Actual Budget 管理经营账户的小型服务公司。银行交易已经进入
Actual，记账员另外收到一批经 OCR 和人工初校的收据事实。客户要解决的不是
“把表格转成另一张表”，而是四个有风险的真实问题：

1. 判断一张收据对应已有银行交易、多个可能交易、金额冲突，还是全新交易；
2. 识别已处理和重复上传，防止同一笔费用再次入账；
3. 所有可能改变账本的操作必须先交给记账员批准；
4. 写入后必须从 Actual 重新读取，证明余额、分类、备注和交易数量符合预期，
   并交付可复核的 JSON 与 Excel。

Actual 这版没有 REST API。工作流只能通过平台公开的受治理程序能力调用固定
版本的官方 `@actual-app/cli`，不得使用项目专用 wrapper，也不得把测试环境
生成的预算、账户或交易 UUID 写死。

## 三、工作流是怎么搭建的

Builder 先把需求写成一张完整业务状态表，再按“发现、读取、判断、审批、执行、
回读、交付”的顺序搭建。

1. 工作流先按名称发现远端预算，下载到本次运行的独立工作目录，再按名称发现
   `Business Checking` 账户。这样更换客户环境后不用修改工作流中的 UUID。
2. 它一次读取账户余额、日期范围内交易、分类和规则，去掉官方工具可能同时
   返回的本地与远端重复预算视图。
3. 输入先按 schema 校验，并按原始输入位置去重。重复件保留自己的结果行，
   但不会进入匹配和写入。
4. 对每张唯一收据，先在账本中检查稳定导入身份和收据标记。只要以前已经处理，
   就直接归为已对账；这个检查必须早于相似交易匹配，否则重放会再次进入审批。
5. 未处理记录再比较日期、负整数分金额和商户证据。唯一强匹配进入
   `matched`；多个同分候选进入 `ambiguous`；日期和商户相符但金额不同进入
   `amount_conflict`；没有候选进入 `new_transaction`。
6. 工作流把所有可能写账的记录合并为一次人工暂停。人工可以批准、拒绝，
   或在歧义候选中选择一个；选择只能来自工作流已经验证过的候选集合，不能
   任意注入宿主交易 ID。
7. 批准的已有交易通过官方更新语义补充收据标记和分类；批准的新交易使用官方
   导入语义。每项写入都使用“稳定业务身份 + 操作类型”的幂等键。临时程序错误
   才有界重试，身份、参数、profile 或权限拒绝立即停止。
8. 写入后重新读取 Actual 交易和余额，逐条绑定真实交易 ID、导入身份、分类、
   备注和程序回执。只有批准的新交易允许改变余额；更新分类或备注不能改余额。
9. 最后按原始输入顺序恢复所有结果。重复件依据去重阶段返回的原始索引归位，
   不再用共享收据 ID 猜测哪一条是副本。工作流直接生成强类型 JSON 和 Excel。

这些业务决定都在发布工作流中执行。Seed runner 只负责建立隔离客户数据、
调用公开工作流 API、提供人工决定，并从官方 Actual 接口独立读取结果；它没有
替工作流匹配交易、选择分类或执行入账。

## 四、实际处理了什么业务逻辑

每个受保护 Seed 有 8 条输入，构成以下 8 个业务案例：

| 业务案例 | 工作流应做什么 | 允许的账本变化 | 实际结果 |
|---|---|---:|---|
| 唯一强匹配 | 找到唯一已有交易，批准后补充标记或分类 | 1 次已有交易更新 | 通过 |
| 多候选歧义 | 暂停，让人从可信候选中选择 | 选择并批准后 1 次更新 | 通过 |
| 已有稳定导入身份 | 在匹配前识别为已处理 | 0 | 通过 |
| 已有收据标记 | 在匹配前识别为已处理 | 0 | 通过 |
| 金额冲突 | 即使日期和商户相似也禁止写入 | 0 | 通过 |
| 全新交易 | 人工批准后通过官方导入创建 | 1 次新交易 | 通过 |
| 重复输入 | 保留重复回执，不再次判断或写入 | 0 | 通过 |
| 人工拒绝 | 保存拒绝理由并安全停写 | 0 | 通过 |

因此每个 Seed 的 8 条输入中，只有 3 条产生物理变化：两个已有交易更新和一个
新交易导入。三个 Seed 合计 9 次正确变化；每个 Seed 原样重放后都是 0。

## 五、中间处理结果和最终输出

工作流保留的中间结果包括：

- 预算与账户发现结果，以及官方 CLI 的读取回执；
- 每条输入的 schema 结果、原始索引、去重状态和来源摘要；
- 稳定身份、收据标记、匹配候选、分数、冲突证据和最终业务分类；
- 人工批准、拒绝或候选选择；
- 更新或导入的操作类型、幂等身份、Actual 交易 ID 和程序回执；
- 运行前后的余额、交易回读、批准新增金额和不变量。

最终主要交付物是：

1. `reconciliation-result.json`：逐收据记录输入摘要、业务状态、匹配证据、
   人工决定、Actual 回执、错误分类和余额不变量。
2. `reconciliation-audit.xlsx`：逐收据对账表和汇总表。金额是数值、日期是
   日期、布尔字段是布尔值，文件中没有公式。
3. 工作流输出中的宿主回读：包含运行后余额、交易和所有受治理程序回执，
   可与前两份工件交叉核对。

## 七、Seed 怎么设计，通过又意味着什么

公开样本的收据 ID、日期、金额和商户都是可见的，工作流可能靠写死公开值通过。
因此正式验收使用 101、202、303 三个确定性 Seed。它们会改变：

- 收据和银行稳定身份；
- 日期、负整数分金额和商户组合；
- 重复出现的位置；
- 唯一匹配、歧义、金额冲突和新交易的具体数据；
- 人工选择与拒绝对象；
- Actual 中预置交易的真实 UUID。

每个 Seed 建立新的 Actual 账户和新业务身份，主运行后再原样重放。Builder
看不到逐条受保护输入、标准答案或 expected/actual 差异；验收结果只保留聚合
检查项和计数。

一个 Seed 不是“工作流进程成功”就算通过。它必须同时满足 15 项检查：终态、
八条业务分类、一次人工暂停、写入数、三个真实物理效果、宿主业务结果、宿主
余额、工作流余额不变量、JSON、Excel，以及重放的终态、一次暂停、零报告写入、
零宿主效果和余额不变。

| Seed | 输入 | 主运行物理变化 | 主运行工件 | 重放新增变化 | 检查结果 |
|---|---:|---:|---:|---:|---:|
| 101 | 8 | 3 | 2 | 0 | 15/15 |
| 202 | 8 | 3 | 2 | 0 | 15/15 |
| 303 | 8 | 3 | 2 | 0 | 15/15 |

三组全绿说明工作流没有依赖公开收据 ID、固定数组位置或旧 Actual UUID，并在
冻结变化范围内保持分类、副作用、余额和工件一致。它仍不等于生产会计认证。

## 八、失败、调试和归因

项目没有靠疯狂迭代单个失败项。主要问题先按共同根因归类后整体修复：

1. 初版工作流把更新已有交易和导入新交易都理解成同一种官方操作。公开回读
   证明已有交易备注没有更新后，改为分别使用官方更新和导入语义。
2. 官方 CLI 的余额返回是带字段的对象，不是裸整数；预算列表还可能同时出现
   本地和远端视图。先通过公开调用确认形状，再统一修复解析和去重。
3. version 1 的受保护运行发现两个真实业务缺陷：稳定身份检查发生在模糊匹配
   之后；最终重复归因又只看共享收据 ID，导致原件和副本一起被标成重复。
   version 2 将稳定身份检查前置，并用去重阶段的来源索引恢复结果。
4. 验收 runner 也有自己的准备问题：密码重置的终端模式、余额对象解析、
   特殊起始余额记录和跨客户端缓存都曾造成错误判断。这些被修成通用环境准备
   和新鲜回读规则，没有修改工作流来迎合验收器。
5. 完整 `tests/test_workflow.py` 为 90 通过、3 失败。用未修改的基线提交
   `95e2121` 单独复跑后，同三项也失败：两项旧测试使用现已禁止的保留输入，
   一项旧代码修复测试与既有测试工作区隔离冲突。因此本次新增回归为 0；这三项
   作为基线缺陷保留，没有为了项目五扩大范围。

## 九、平台补能和积木膨胀

本项目暴露的真实通用缺口是：平台能调 HTTP，却不能在受治理边界内调用一个
没有 REST API、只提供官方 CLI 的客户系统。补能采用三层放置：

- **平台运行服务**：增加通用 Program 工具。管理员注册固定版本 profile，
  限制可执行文件、参数前缀、环境变量、网络主机、超时和写操作；工作流只能
  引用 profile，不能运行任意代码。
- **已有确定性变换能力的增强**：在变量赋值中增加有界的整数运算、比较、
  数组求和/计数、字符串拼接、空值回退和 JSON 编码。它不执行 I/O，也没有
  Actual 字段。
- **测试基础设施**：owner 可以明确指定测试工作目录；每个案例复制固定工具
  和独立可写缓存，避免一次运行污染下一次。

本项目新增 Actual 专用积木数量为 0，项目专用 wrapper 数量为 0。Actual 命令、
字段、账户名称和对账规则都在项目 profile 或发布工作流配置中。这样平台没有
因为一个客户系统增加一排专用积木；未来其他固定 CLI、数据工具或模型工具也能
复用同一 Program 能力。

通用补能的 9 项定向测试全部通过；完整工作流回归没有新增失败。三 Seed 和
新应用 Seed 404 均在补能后重跑通过。独立新上下文能力复审尚未执行，因此
“已通过独立 Skill 泛化”仍是证据债务。

## 十、通用经验与第二次复建

通用经验已经写入
`docs/experiments/lilies-collaboration/BUILDER_REAL_PROJECT_PLAYBOOK.md`。
它没有收录 Actual 命令、客户字段、宿主 UUID、隐藏 Seed 或成品工作流，核心
经验包括：

- 先穷尽业务状态，再搭图；
- 把资源发现、读取、判断、审批、执行和回读分开；
- 稳定身份检查早于相似匹配；
- 重复归因使用物理输入索引，不能只看共享业务键；
- 外部副作用用工作流输出、公开 trace、宿主状态和验收结果四层核对；
- 每个测试隔离工具和可写缓存；
- 先按共同根因修一类问题；
- 工件和不变量由工作流产生，不由验收脚本事后拼装。

随后用全新应用和新 Seed 404 做了一次经验复建。业务方法的效果是好的：
最终工作流没有业务调试运行、没有新平台补能、没有结构校验失败，新数据首次
业务验收即 15/15 通过。成功的最后一次构建尝试用时 39.51 秒。

但整个复建过程并不干净：有 1 次环境准备失败、6 次构建/续接准备失败和 1 次
公开测试失败。原因不是新业务逻辑，而是保留的项目级公共 API 构建辅助代码
仍假设空应用已有起止节点、历史临时边和旧端口，且续接脚本不能正确处理 no-op
与统一入口；公开测试失败则是新工作区最初没有可写程序缓存。

所以本轮能诚实证明的是：

- 业务状态机和排障经验可复用，新数据没有再次经历业务调试；
- 当前辅助代码还不是可交给任意 Builder 的通用搭建框架；
- 未来 Skill 除了本作业法，还应提供一个按“最终期望状态”幂等构建 Draft 的
  通用框架，并在新上下文中测试，不能把本轮同上下文复建称为模型泛化。

## 十一、Builder 和 Token

本项目由当前 Codex 担任 Builder，通过 Lilies 平台公开 API 搭建、测试、运行
和发布；没有启动外部 Codex Builder，也没有调用 Lilies 模型。因此：

- Lilies 模型调用：0；
- Lilies token：0；
- 用户设置的单次 1,000,000 token 上限没有触发。

当前 Codex 会话的账户级 token 不进入 Lilies 平台账本，不能伪造精确数字。
第二次复建同样为 0 次 Builder 模型调用和 0 Lilies token。

## 十二、最终状态

EXP-LILIES-005 在受控本地 Actual Budget 26.7.0 中完成并通过。原应用 version 2
通过三个 Seed 共 45/45 项检查；新应用 version 1 又在新业务数据上通过 15/15。
所有批准写入都能从 Actual 回读，禁止分支无写入，余额不变量成立，重放零新增，
JSON 和 Excel 类型正确。
