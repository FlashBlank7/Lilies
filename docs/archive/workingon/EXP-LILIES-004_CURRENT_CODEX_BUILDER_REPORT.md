## 二、题目和真实业务场景

客户是一家已经用 ThingsBoard 接收旋转泵遥测、但尚未把机器学习预测可靠地
接入设备运维流程的制造企业。设备每次上报温度、振动、电流、压力和转速。
设备运营人员需要减少漏报，可靠性工程师需要控制误报，模型负责人需要知道
生产决策究竟来自哪个模型版本。

客户授权 Builder 使用公开的合成训练集、独立验证集、五项特征和单位合同、
ThingsBoard 测试租户、MQTT 遥测入口、REST/OpenAPI 告警接口以及人工复核
输入。Builder 可以训练新模型、微调候选模型、评估、批准部署和回滚；生产
工作流只能调用已经批准的部署，不能在处理一条设备消息时自行训练或更换模型。

自动化边界如下：

- 数据完整、风险明确且置信度足够时，可以自动决定是否创建告警。
- 风险或置信度不明确时，必须暂停并等待可靠性工程师批准或拒绝。
- 输入无效、过旧、乱序、低风险、人工拒绝或权限不足时，不能写入错误告警。
- 临时且能证明“请求尚未到达客户系统”的故障可以有限重试；写入结果不明确时
  不能盲目重试。
- 工作流只能操作授权的 ThingsBoard 告警，任何分支都禁止向设备发送 RPC
  或控制命令。

最终交付不是一个简单的高/低标签，而是三类机器可读结果：逐事件的决策与告警
回执、实际生效模型及评估证据、观测窗口的漂移报告。

## 三、工作流是怎么搭建的

Builder 先确定了四条业务原则：先验证再预测；只有已批准模型才能进入生产；
不确定风险由人决定；客户系统写入必须可证明且不可重复。这个顺序很重要。
如果先预测再检查单位，摄氏度和华氏度可能被当成同一数值；如果先写告警再请人
复核，人工拒绝已经来不及；如果模型版本不先冻结，事后无法解释同一数据为何
产生不同结果。

一条设备记录经历以下过程：

1. 工作流先按设备 ID 从 ThingsBoard 读取这一时刻的五项遥测，而不是相信
   调用者把测量值直接塞进工作流。读取回执成为后续证据来源。
2. 它把测量值、单位、事件时间和事件身份整理成统一记录，检查五项数据是否
   齐全、是否为数值、是否在允许范围、单位是否与模型特征合同一致。
3. 结构正确后再检查时间。过旧消息和早于设备最近已接受时间的乱序消息在此
   安全停止，不会覆盖更新的设备状态。
4. 合格记录调用部署名所指向的当前批准模型。返回结果包含风险概率、置信度、
   模型 ID、模型版本、模型摘要和部署修订，而不是只有一个标签。
5. 风险概率至少为 0.8 且置信度至少为 0.8 时，工作流自动创建高严重度告警；
   风险低于 0.35 时不写告警；中间区域或置信度不足时暂停。
6. 人工复核看到的是原始遥测和模型证据。批准后才创建人工确认的告警；拒绝后
   保存意见并结束，不写告警。每次暂停绑定当前运行，恢复不会串到另一条记录。
7. 相同设备和事件使用稳定的业务身份。重复重放得到同一告警，不新增第二个
   物理告警。
8. 客户系统返回临时 503 时，只有受信任的测试代理明确证明请求未发往
   ThingsBoard 才重试，最多三次；403 权限拒绝立即终止。这样既能恢复真正的
   短暂故障，也不会在“可能已经写成功”的情况下重复写入。
9. 无论记录走自动、人工、低风险还是安全停写分支，成功结束的运行都会汇总
   业务决定、模型血缘和漂移结论，并生成三份相互可追溯的工件。漂移为
   stable、warning 或 critical 只产生报告，从不触发在线训练。

这套业务逻辑运行在平台发布的工作流中。项目脚本只负责启动公开测试环境、
通过 MQTT 喂入测试遥测、通过公开 API 搭建和运行工作流，以及从 ThingsBoard
公开接口核对结果；脚本没有替工作流做风险判断、人工分流或告警决策。

## 五、中间处理结果和最终输出

工作流的中间结果可以沿着一条业务记录逐步审查：

- 读取阶段保存 ThingsBoard 遥测和读取回执。
- 校验阶段形成“有效/无效”结论及精确错误位置，例如缺少电流或振动单位不兼容。
- 时间阶段形成“可继续/过旧或乱序”结论。
- 推理阶段形成概率、置信度、预测标签、模型 ID、版本、摘要和部署修订。
- 人工阶段保存批准或拒绝以及复核说明。
- 写入阶段保存 ThingsBoard 告警 ID、状态、严重度和宿主回执。
- 监控阶段保存逐特征偏移分数、整体 stable/warning/critical 状态，并明确
  `automatic_training_triggered=false`。

最终三份工件分别是：

1. **设备事件决策**：把输入验证、时间判断、推理、人工决定、告警回执和最终
   动作放在同一份逐事件结果中。
2. **模型证据**：记录训练或微调来源、特征与单位、基础版本、验证指标、模型
   摘要和当前部署修订。
3. **漂移报告**：比较当前观测窗口与训练基线，说明哪些特征发生偏移以及整体
   状态，但不会自动训练。

每份工件都带运行 ID、生成节点、数据来源和内容摘要。发布后的运行还绑定
workflow version 1；它实际使用模型 v1，而不是报告中写一个并未生效的版本号。

模型治理本身也完成了实际闭环：

- 用 240 条公开合成训练记录形成模型 v1，并在 80 条独立验证记录上评估。
- 以 v1 为基础微调出 v2，保留基础版本血缘。
- v2 的本题合成验证集 precision、recall、F1、AUPRC 均为 1.0，
  Brier 分数约为 0.00217。这个结果只说明冻结合成数据可分，不代表工厂精度。
- 明确批准 v2 后，实际工作流运行显示生效模型版本为 2，并产生一个告警和
  三份工件。
- 回滚到 v1 后，下一次实际运行显示生效版本为 1，同样产生正确告警和工件。

## 七、Seed 设计和验收含义

公开案例会暴露设备名、事件位置和具体数值。一个工作流即使把这些值写死，也
可能在公开测试中得到 9/9，所以正式验收另外使用三个可重复的伪随机 Seed。
Builder 工作时看不到逐条隐藏值、标准答案或实际与预期差异；验收只向 Builder
返回聚合类别和计数。

每个 Seed 有 12 条输入，覆盖低风险、高风险、人工批准、人工拒绝、错误单位、
缺少特征、数值越界、过旧、乱序、重复、写入前临时 503 和权限 403。不同
Seed 会改变设备身份、事件时钟、特征组合、异常和重复出现位置、人工结果以及
漂移窗口。三个漂移窗口分别应得到 stable、warning 和 critical。

每个 Seed 都新建设备并使用独立事件身份，所以本工作流可见的遥测、告警和
幂等身份不会跨 Seed 复用。它们运行在同一受控 ThingsBoard 测试租户中，并非
每次销毁和重建整个物理租户；因此这里证明的是设备/事件级隔离，不把它夸大为
基础设施级租户重置。

“进程成功”只表示工作流没有崩溃。“11 条成功、1 条终止”也不自动表示通过，
因为权限案例本来就应该终止。一个 Seed 真正通过，需要同时满足每条决定正确、
人工暂停次数正确、模型血缘正确、漂移等级正确、告警数量和身份正确、工件
齐全、临时故障按规则恢复、权限故障安全停止以及 Device RPC 为零。

| Seed | 输入规模 | 关键变化 | 人工暂停 | 交付物 | 工作流结果 | 宿主验收 | 最终结论 |
|---|---:|---|---:|---:|---|---|---|
| 4101 | 12 | 新设备/时钟/特征组合，stable 漂移窗 | 2 | 33 | 11 成功 + 1 个预期权限终止 | 3 个正确告警、0 RPC | 85/85，通过 |
| 4102 | 12 | 重新变化设备、顺序和数值，warning 漂移窗 | 2 | 33 | 11 成功 + 1 个预期权限终止 | 3 个正确告警、0 RPC | 85/85，通过 |
| 4103 | 12 | 再次变化身份、故障位置和数据，critical 漂移窗 | 2 | 33 | 11 成功 + 1 个预期权限终止 | 3 个正确告警、0 RPC | 85/85，通过 |

三个 Seed 全绿能证明工作流没有依赖公开设备名、固定记录位置或固定异常顺序，
且在冻结的本题变化范围内没有可见的跨运行状态污染。它仍不能证明真实工厂
故障标签质量、模型长期准确率、生产网络稳定性或所有外接模型库兼容性。

## 八、失败、偏差和剩余差异

本项目没有把调试过程中的失败藏掉：

1. 第一次 Seed 4101 显示 69/85。所有漂移项都来自验收用词把平台的
   `stable` 错写成 `normal`，不是 16 个不同业务故障；修正验收用词后该组
   分歧消失。
2. 第一次临时 503 测试没有被重试。平台无法知道一个写请求是在发送前失败，
   还是客户系统已经写入但响应丢失；盲目重试会制造重复告警。修正不是放宽
   安全规则，而是增加可验证的“写入前失败”证明，仅该条件成立时允许重试。
3. 模型回滚后，平台强制测试曾因复用同一工件目录而把合法的新模型证据误判
   为覆盖旧文件。根因是测试运行工作区没有隔离。平台现在为每次测试及每个
   案例创建独立目录；针对“草稿版本变化后连续测试”的回归已经通过。
4. 发布后第一次手工调用因检查脚本没有先建立工作目录，被入口正确拒绝；
   建立独立目录后，同一发布版本一次运行成功。另一次 shell 状态变量命名错误
   发生在运行已经创建之后，没有改变工作流；公开运行记录证明该运行最终成功。
5. 一次诊断搜索错误地扫到了本地公开运行事件文件。它不包含隐藏 Seed、oracle
   或平台数据库，且没有被用作通过依据，但它不符合“检查只走公开 API”的
   过程纪律。本报告将其记为操作偏差，后续诊断搜索必须显式排除状态目录。

最后仍有三项证据债务：未使用真实工厂标注数据评估模型；未实际连接外部模型
注册库搜索和导入候选；三个 Seed 使用同一测试租户内的新设备实现逻辑隔离，
没有每次重建完整租户。

## 九、平台补能

项目公开需求暴露了两个原平台无法完整表达的通用缺口。

第一，平台过去能调用普通 API，却不能完整管理表格型预测模型从训练或导入、
微调、独立评估、模型卡、人工批准、版本化部署、工作流推理、漂移到回滚的
生命周期。现在这些能力通过统一的公开平台 API 和两类工作流能力提供，不含
ThingsBoard 设备字段、告警端点或本题阈值。通用测试使用独立的表格数据合同，
验证训练、评估、部署、推理和漂移。

第二，外部写入的 503 不能简单视为“可以重试”。平台新增的是通用的写入前失败
证明机制：只有受信任代理的响应满足管理员配置的证明合同，运行时才把它归类为
安全可重试；否则仍然停止。这对任何有副作用的 HTTP/OpenAPI 连接器都适用，
不是 ThingsBoard 专用豁免。

另外还修正了每次强制测试复用工件目录的问题。测试目录现在按测试批次和案例
隔离，因此模型版本、输入或输出合法变化不会与上一次运行冲突。

项目目录中的 MQTT 发布器、环境启动脚本和故障代理都是验收夹具：它们负责
提供输入和制造可控错误，不参与客户生产决策。工作流里的 ThingsBoard 接口
来自公开 OpenAPI schema；项目专用映射保留在工作流配置，不进入通用平台代码。

聚焦回归覆盖模型生命周期、已部署推理、漂移、连接器安全重试和测试目录隔离。
这些补能尚未获得真实生产网络、外部注册库和跨客户环境的认证，因此不能越过
本报告的受控本地声明上限。

## 十、Builder 表现和经验

本次 Builder 是当前 Codex，而不是独立 Lilies 模型进程。Codex 先冻结公开题包，
再用公开平台 API 从空应用搭建，公开 debug 全绿后才进入三个 Seed，最后发布并
运行发布版本。Lilies 模型调用次数为 0，Lilies token 消耗为 0，所以用户设定的
“单次运行最多 1,000,000 token”没有触发；当前 Codex 会话的账户级 token
不在 Lilies 平台账本中，不能伪造一个数字。

从应用创建到发布约 56 分钟；若从题包冻结时间算起约 76 分钟。最有用的收敛
决策是先一次性确定完整业务链，再跑公开案例和聚合 Seed，不对单个失败随意
修改工作流。两次真正需要平台改动的地方都先由客户系统状态、运行结果和错误
分类共同证明。

需要沉淀到后续 Prompt/Skill 的经验是：

- 先核对业务决定和客户系统副作用，最后才看图结构。
- 有副作用的 5xx 先判断“是否可能已经写入”，不能只按状态码重试。
- 每次测试运行使用新工作目录；重置客户环境时同时轮换所有相关状态世代。
- Seed 失败先按共同根因聚类，不能把同一命名差异报成许多业务故障。
- 模型提升和回滚必须各运行一次工作流，不能只看管理记录。
- 诊断命令必须显式排除状态目录，Builder 证据只保留公开 API 结果。
