## 二、题目设计：模拟什么真实业务

一家制造企业使用 Paperless-ngx 接收供应商发票和质量证明，使用 InvenTree
管理供应商、采购单、物料、采购数量和相关附件。客户已有 OCR 结果会提供
供应商、采购单号、物料号、数量、批次、日期、证书类型和置信度。

企业需要自动完成以下工作：

1. 同一业务单据不能因为重复上传而重复写入。
2. 关键字段缺失或 OCR 置信度不足时必须让人判断，系统不能猜。
3. 自动处理前必须查询客户系统里的真实采购单、供应商和采购行。
4. 供应商、采购单、物料或数量存在冲突时不得写入。
5. 写回前还要检查相同来源的附件是否已经存在。
6. 临时服务错误可以有限重试，权限拒绝不能重试成“成功”。
7. 每条记录都要留下可解释结果，最后同时交付机器可读 JSON 和业务 Excel。

这道题验证的是“利用已有 OCR 数据完成受控对账和写回”，不验证 OCR 模型
训练，也不验证长期监听 Paperless 新文档的事件触发。

## 三、工作流是怎么解决问题的

工作流遵循一条业务原则：只有首次出现、字段可信、客户系统中的采购关系完全
一致、附件尚不存在且写入权限正常的记录，才允许改变客户系统。

### 1. 先按业务来源去重

整批记录进入后，先按单据来源标识区分原记录和副本。副本直接得到“重复，
不操作”的结果，不会进入采购查询、人工暂停或写回路径。这使防重发生在业务
流程前端，而不是等客户系统报错。

### 2. 判断当前 OCR 结果是否足以自动处理

对首次出现的记录检查关键字段和置信度。字段缺失或置信度不足时，只暂停当前
记录并请求人工决定。本次测试统一选择拒绝，因此这些记录明确停写，同时不
影响同批其他记录继续处理。

### 3. 查询真实客户数据，而不是相信输入里的“答案”

可信记录使用采购单号查询真实 InvenTree 采购单，再核对供应商；随后查询该
采购单的采购行，比较真实物料号和数量。version 2 不再读取输入中预先附带的
`host_*` 便利字段，隐藏数据是否换编号、换顺序或换数值都不会改变判断方法。

### 4. 在写回前检查已有附件

采购关系完全一致后，工作流继续查询该采购单已有附件。若相同来源已经存在，
当前记录按重复处理，不再建立第二条关联。

### 5. 只保留一个受控写回出口

只有所有检查通过的记录才建立 InvenTree 附件关联。明确的临时 503 最多按
限定次数重试，并保持同一业务幂等身份；恢复后仍只形成一次最终副作用。403
权限拒绝立即停写，不继续尝试，也不会伪装成普通业务冲突。

### 6. 把所有分支汇总成同一种业务结果

无论记录是正常写入、人工停写、重复、冲突、重试成功还是权限拒绝，最终都
形成统一结构：记录身份、来源身份、业务决定、原因、人工决定、写回状态和
Connector 回执。工作流再用同一批结果生成 JSON 和 Excel，避免两个交付物
各说各话。

## 五、Seed 怎么设计，通过意味着什么

公开数据会展示场景和预期，适合搭建和调试；Seed 则用同一套业务规则生成
Builder 未见过的业务标识、采购组合、物料、数量、日期、顺序、PDF 形态和
故障位置，用来排除按公开编号或固定值硬编码的工作流。

Seed `101`、`202`、`303` 只是三组可重复的数据生成编号，不代表难度等级。
每组有 36 条记录，继续覆盖正常写入、人工复核、重复、业务冲突、临时错误和
权限拒绝六类风险。每组均重新准备客户环境，避免上一组写入污染下一组。

三组业务运行结果一致：

| 结果 | 每组数量 |
|---|---:|
| 直接写入 | 12 |
| 临时故障后写入 | 3 |
| 人工停写 | 6 |
| 重复不操作 | 6 |
| 冲突停写 | 6 |
| 权限拒绝 | 3 |
| 合计 | 36 |

Seed 101 使用最终 revision 41 草稿运行，随后未改图直接发布为 version 2；
Seed 202 和 303 使用已发布 version 2 运行。三次均成功结束、各发生 6 次人工
暂停并生成 2 个交付物。

现有宿主检查器仍显示 `31/39`。剩余 8 项来自一个统计归因问题：它按共享
来源身份把原记录的一次真实写入同时算给后来的 6 条 duplicate，再派生出两个
汇总失败。工作流 trace 显示 duplicate 分支没有调用写回操作。因此本报告把
业务工作流记为完成，但不把该检查器结果伪写成 `39/39`，也不为“刷绿”改变
正确的业务去重逻辑。

还需注明证据上限：本次协调上下文后来误显示过受保护记录内容，因此不能把
当前上下文声称为严格独立盲测。它不改变实际运行和客户系统结果，但限制了
“独立黑箱验证”的声明强度。

## 六、实际调试路径，以及为什么超过十分钟

本轮没有因为平台缺少业务能力而补能。超时主要来自 Builder 把连接器配置、
客户环境和自制验收流程拆成过多轮操作。

主要问题按共同原因归并如下：

1. 第一组是工作流配置错误：嵌套分支端口、复合表达式求值和 Excel 列 schema
   没有一次整体校对，导致多次小修。
2. 第二组是 Connector 配置错误：InvenTree 官方返回允许空值，但最初生成的
   schema 过严；Secret owner 和 binding tenant 又没有一次对齐。
3. 第三组是重试配置错误：写回的授权、幂等身份和同节点重试约束没有在首次
   设计时一起处理。
4. 第一次公开通过后，Seed 101 暴露出真正的泛化问题：旧图相信输入里的
   `host_*` 便利字段。最终图改为查询 InvenTree 真实采购单和采购行，这是必要
   的业务修正。
5. 最后一次 debug 前刷新了旧 Connector 的 secret 名称，导致一次 401 零写入
   失败；读取 version 2 的公开 binding 后用正确名称刷新，随即成功。

按平台时间戳粗略还原的耗时占比：

| 阶段 | 时间占比 | 发生了什么 |
|---|---:|---|
| 平台、空应用和客户环境准备 | 约 8% | 启动平台，创建应用，准备 Paperless/InvenTree |
| 首版工作流与公开调试 | 约 47% | 配图、Connector 配置、处理端口/schema/表达式问题 |
| 真实客户数据查询修正并发布 version 2 | 约 19% | 去除 `host_*` 便利输入，改为查询真实 PO 和采购行 |
| Seed 101/202/303 环境与运行 | 约 16% | 三次客户环境准备和 36 条业务运行 |
| 最终 version 2 公开 debug | 约 10% | 重建公开环境、修正过期 secret 名称并完成最终运行 |

这些比例是依据应用、发布和运行时间戳重建，不是独立计时器的逐工具精确统计。
真正工作流执行只需约 21–38 秒；约 63 分钟的大头是 Builder 调试和四次真实
客户环境准备。十分钟失败的主要责任在 Builder 执行策略，不在运行性能。

## 七、平台能力、配置和项目脚本的边界

项目一业务能力全部由 Lilies 平台工作流提供：批量迭代、去重、条件分支、
人工暂停、Connector 查询与写回、有限重试、错误分类、JSON 工件和 Excel
工件。没有把业务判断藏进外部脚本。

外部代码只负责搭建测试所需的 Paperless/InvenTree 客户环境、注入可重复故障
和准备测试数据。这些代码不参与工作流运行时决策，也不替工作流完成匹配或
写回。

本轮通过公开 API 生成和配置了 InvenTree Connector version 6，使其公开四个
实际使用的操作：查采购单、查采购行、查附件、建附件。它没有新增平台积木，
也没有为某个固定采购单、物料或 Seed 硬编码答案。

## 八、可沉淀为 Prompt / Skill 的通用经验

以后同类 Builder 任务应使用下面的最小闭环：

1. 先写出唯一允许产生副作用的业务条件，以及所有必须停写的条件。
2. 一次检查 Connector 的 binding tenant、secret 引用、响应 nullable 字段、
   权限范围和重试语义，再开始搭图。
3. 工作流不得相信测试输入附带的客户真值；必须通过客户公开 API 查询真实
   业务状态。
4. 先构建整条最小业务链，再做一次结构验证和一个小样本运行；相同根因的错误
   一次整体修正，不进行高频碎片化改图。
5. 公开 debug 只做一轮完整分支覆盖；通过后冻结发布版本。
6. 客户环境重建后，只轮换公开 binding 实际引用的 secret，不重复创建连接器。
7. 区分四类证据：工作流结果、Connector 回执、客户系统状态、自制检查器。
   发生分歧时先找归因，不为自制检查器绿灯破坏正确业务逻辑。
8. 十分钟预算按阶段设硬上限：2 分钟理解题目、4 分钟整图、2 分钟公开调试、
   2 分钟发布和报告；真实客户系统初始化与 Seed 验收单独计时并明确报告。

最重要的改进不是再造一个更复杂的正式实验框架，而是给 Builder 一份简短任务
说明、一个工作目录、平台公开 API 和上述闭环，让它直接完成真实业务结果。
