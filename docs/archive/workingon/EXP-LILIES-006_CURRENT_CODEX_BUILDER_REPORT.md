预测算法，也不是只检查工作流结构。

- 原应用为 `9ddd33f5-ecb9-4f07-96e9-cf39435c40b8`，最终 Draft revision 79，

  零新增补能。

本报告的结论上限是：在受控本地 ERPNext v16.20.0 中，发布工作流能够正确完成
模型部署调用、实时库存读取、约束补货、人工审批、草稿写回、回读和幂等重放。
它不是生产采购授权、通用预测精度认证或长期高并发证明。

## 二、题目和真实业务场景

客户是一家使用 ERPNext 的制造或分销企业。库存计划员每周面对三类信息：

1. 商品过去的需求历史；
2. ERPNext 中的当前库存，以及业务提供的在途、安全库存、最小起订量和批量；
3. 全局采购能力与预算。

客户要解决的问题是：先用经过批准的模型预测未来需求，再在容量、预算和采购
规则下求一份可行补货计划。如果最低服务要求根本无法满足，要解释缺多少资源，
而不是硬凑一张表；如果计划可行，要让库存计划员审查，只有明确批准后才能在
ERPNext 创建未提交的 Material Request 草稿。

工作流不得提交 Material Request、创建 Purchase Order、创建 Stock Entry 或
过账。训练新模型、提升版本和回滚属于模型负责人流程，普通补货运行只能调用
已经部署的模型。

## 三、工作流是怎么搭建的

工作流按“校验—读库存—预测—规划—审批—写前查重—写入—回读—交付”搭建：

1. 首先校验批次、单位、时间序列、物料规则、预算和容量。输入结构或单位不合格
   时安全停止，不读取或修改客户系统。
2. 工作流通过公开 Frappe REST 接口一次读取 ERPNext 库存。它按物料编码和
   仓库名称匹配每条计划项，把实时库存加入计划输入；没有唯一库存记录时停止。
3. 它调用命名的生产预测部署，而不是在工作流中训练。返回每个物料未来七天的
   点预测、区间、模型摘要、不可变模型摘要、部署修订、最近回测误差和重训建议。
4. 它把预测、实时库存、在途、安全库存、MOQ、批量、单位成本、最低满足比例、
   优先级、共享容量和预算交给约束规划服务。
5. 如果最低满足要求超过共享资源，工作流直接输出不可行原因、容量缺口、预算
   缺口和逐物料最低需求；不进入人工审批，更不会写 ERPNext。
6. 如果存在可行方案，工作流输出逐物料补货量、计划后库存、成本、服务满足率、
   总容量和总预算。库存计划员一次性审查预测、约束、模型监控和计划。
7. 人工拒绝时保留拒绝理由并停止。人工批准不能改写补货量；要改数量必须作为
   新输入重新规划。
8. 批准后，工作流先按稳定批次标题查询 ERPNext。已有同批次草稿时直接复用；
   没有时才创建 `docstatus=0` 的 Material Request。
9. 创建或复用后，工作流按 ERPNext 记录 ID 重新读取草稿，核对状态和明细。
10. 最后直接生成三份 JSON：预测与模型证据、约束补货方案、人工决定与 ERPNext
    交付回执。工件带来源和内容摘要，验收脚本没有事后代替工作流拼报告。

这些业务决定都在发布工作流中执行。环境脚本只负责启动官方 ERPNext、创建测试
公司/物料/库存和调用公开平台 API；Seed runner 只提供随机化输入、人工决定并
独立读取 ERPNext 结果，不替工作流预测、求解、审批或创建草稿。

## 四、模型训练、部署和工作流调用是什么关系

本题明确区分两层。

模型管理层完成：

1. 用前 21 天训练周期预测候选；
2. 用后 7 天做时间顺序回测，而不是随机打乱未来数据；
3. 保存 WAPE、MAE、RMSE、MASE 和区间覆盖率；
4. 保存训练数据摘要、单位、算法、来源和不可变模型版本；
5. 指标满足门槛且模型负责人批准后，提升到
   `exp006-demand-production`；
6. 新版本变差时支持回滚到上一部署修订。

业务工作流只完成：

1. 按部署名调用当前批准版本；
2. 保存这次实际用到的模型 ID、版本、摘要和部署修订；
3. 根据运行数据计算监控信号；
4. 超过误差门槛时输出“建议重训”，但
   `automatic_training_triggered=false`，不会在补货运行中换模型。

所以平台既支持 Builder 自己训练，也为未来“从外部模型库导入候选，再微调、
评估和部署”保留了统一生命周期；本题选择从客户历史训练，是因为冻结数据的
周期结构足以验证完整生命周期，不需要付费外部模型。

## 六、中间处理结果和最终输出

工作流保留的中间结果包括：

- 输入 schema、单位和批次身份；
- ERPNext 库存读取回执，以及物料/仓库匹配结果；
- 每条序列的点预测、上下界、预测总量；

- 每个物料的可用量、理想补货量、最低补货量、批量化结果、成本和满足率；
- 总容量、预算、目标值、生效约束或不可行缺口；
- 人工批准/拒绝和理由；
- 写前查询、创建回执、回读草稿和是否发生真实宿主写入。

1. `forecast-evidence.json`：预测、区间、模型谱系、评估和监控；
2. `replenishment-plan.json`：计划明细、资源使用、生效约束或不可行解释；
3. `erpnext-delivery.json`：人工决定、创建/复用状态、Connector 回执和草稿回读。

## 八、Seed 怎么设计，通过意味着什么

三个 Seed 为 6101、6202、6303。每个 Seed 都改变：

- 三个物料的每周需求形状和日期；
- 在途量、安全库存、MOQ、批量、单位成本和优先级；
- 由这些值独立计算的补货量、总能力和总成本；
- 候选模型、评估记录、不可变模型摘要和部署修订；
- Material Request 的稳定业务身份。

每个 Seed 执行四条路径：

1. 可行且批准：应创建恰好 1 张未提交草稿；
2. 同一输入重放：应复用同一张草稿且无新写入；
3. 可行但拒绝：应无写入；
4. 容量和预算不足：应同时解释两项缺口且无写入。

每个 Seed 的 16 项聚合检查还覆盖时间评估、部署谱系、预测值、独立库存平衡、
模型监控、三份工件和人工暂停数量。第三 Seed 额外制造最近周期漂移，验证
“建议重训但不在线训练”。

| Seed | 运行 | 人工暂停 | 工件 | ERPNext 主草稿 | 重放新增 | 检查 |
|---|---:|---:|---:|---:|---:|---:|
| 6101 | 4 | 3 | 12 | 1 | 0 | 16/16 |
| 6202 | 4 | 3 | 12 | 1 | 0 | 16/16 |
| 6303 | 4 | 3 | 12 | 1 | 0 | 16/16 |

Builder 没有读取逐条受保护输入、oracle 或 expected/actual 差异，只收到聚合检查
数量和失败类别。因此 3/3 通过意味着在冻结变化范围内，模型生命周期、预测、
离散约束、人工门、宿主副作用和工件都一致；不意味着未来任何需求分布都能得到
同样精度。

## 九、失败、调试和归因

项目按问题类别整体处理，没有为每个错误反复小改。

1. **环境准备类**：ERPNext 新站点需要仓库类型、单位、物料组、财年和期初库存
   的正式主数据。统一补齐公开 API 初始化流程后，不再逐错误启动。
2. **公开合同类**：Frappe 忽略了最初假设可用于查重的可选备注字段。公开回读
   证明字段未保存后，改用正式可查询的 Material Request 标题作为稳定业务身份；
   没有在平台里硬编码 ERPNext 规则。
3. **图类型类**：首次搭图发现 Draft 响应层次、迭代端口、分支到迭代输入以及
   变量赋值结果位于 `output`。统一核对公开 schema 和积木手册后，一次修正整类
   引用和连接。
4. **公开测试类**：原应用第一次完整公开测试为 2/3，因为计划身份引用少了一层
   `output`。修复后 3/3；此后发布工作流没有再因业务逻辑修改。
5. **经验复建环境类**：第一次新应用复建结构一次通过，但公开测试复用了原应用
   的业务编号，ERPNext 正确返回已有草稿，测试却期待新建，结果 2/3。这不是
   工作流缺陷。冻结图并核对输出、宿主和测试后，测试框架增加每次新建业务身份；
   第二个全新应用 3/3，新数据 16/16，工作流零修改。
6. **全量工作流回归**：`tests/test_workflow.py` 为 90 通过、3 失败。失败项与
   项目五记录的基线完全相同：两项旧测试仍把保留人工输入键当公开输入，一项
   旧代码修复测试仍引用隔离测试目录之外的工作区。本次没有新增失败，也没有
   为项目六扩大范围去修改这些历史测试。

过程偏差也如实保留：Builder 阶段曾为确认测试对象结构误读一次平台
`workflow_models.py`，随后改由公开 `/openapi.json` 获取合同。该读取没有看到
隐藏 Seed、oracle 或题目答案，也没有据此修改业务逻辑，但不满足严格黑箱
Builder 的源码隔离，所以本次只能声明“当前 Codex 公开 API 交付”，不能冒充
全新独立黑箱会话的泛化证据。

## 十、平台补能和积木膨胀

项目暴露了两个真实通用能力缺口：

- 平台没有显式的预测模型训练/导入/微调、评估、不可变版本、提升、回滚、推理
  和监控生命周期；
- 平台没有可在 MOQ、批量、库存、最低满足率、共享容量和预算下输出可行方案或
  不可行解释的确定性规划服务。

补能采用“重服务、轻积木”：

- 模型生命周期放在平台服务和公开 API，不把训练、评估、提升、回滚拆成一排
  画布积木；这些是模型负责人在工作流外执行的管理动作。
- 约束规划放在通用运行服务，支持任意物料名和通用字段，不包含 ERPNext。
- 画布只增加两个不可再拆的动作：调用已部署预测、调用受约束规划。
- ERPNext 端点和字段全部来自项目 OpenAPI 生成的 Connector，物料、仓库、标题
  和写回映射只存在于项目配置。

因此本项目新增通用原子积木 2 个，ERPNext 专用积木 0 个，项目专用 adapter、
mapper 或 wrapper 为 0。四个聚焦测试覆盖客户模型目录候选导入、微调、回测、
两次提升、回滚、生产推理、可行/不可行规划、公开 API 和“积木定义不出现
ERPNext”门禁；公开项目、三个 Seed 和经验复建均在补能后通过。
