# 平台生成工作流真实项目实验设计与 GitHub 项目选择报告

> 日期：2026-07-21  
> 状态：实验预注册方案 v1；候选项目轻量探针已完成，平台工作流正式实验尚未开始  
> 实验对象：智能体/工作流生成平台产生的可编辑工作流  
> 结果对象：真实任务结果、工件、系统副作用、恢复记录与可追溯证据  
> 非实验对象：把莉莉丝修改开源代码的能力冒充平台工作流交付能力  
> 候选探针证据：`docs/evidence/platform_workflow_candidate_probe_2026-07-21.json`

## 1. 执行摘要

本实验不再从“电梯”“光纤”“GitHub issue”之类名词直接建立路线图，而是先抽象真实工作流的任务结构，再选择能够覆盖不同结构的企业与个人需求，最后用冻结的 GitHub 项目、数据、接口和独立 oracle 检验平台生成工作流的交付能力。

一个真实 AI 工作流的本质是：

```text
触发 + 输入数据/材料 + 历史状态
  -> 确定性处理、模型、检索、优化和/或人工判断
  -> 决策、工件和外部系统动作
  -> 验证、回执、失败恢复和持续运行
```

因此，工作流是否可靠，不能用“生成成功”“画布上有积木”或“某次运行返回文本”判断。可靠交付必须同时满足：

```text
需求忠实
AND 输入与 schema 正确
AND 核心任务结果通过独立 oracle
AND 文件/API 等交付正确
AND 权限和人工边界正确
AND 故障可阻断、恢复或补偿
AND 结果可追溯
AND 在隐藏输入上可重复
```

本报告选择六个第一批可重复实验底座：

1. PyOD：异常检测与设备风险分流。
2. StatsForecast：多序列预测。
3. OR-Tools：排程、路径和约束优化。
4. invoice2data：票据和业务文档结构化。
5. Haystack：检索、引用和 RAG 管线。
6. Evidently：数据、模型和 RAG 质量监控。

六个项目均已在隔离环境中完成轻量运行探针。探针只证明项目可作为实验组件，不证明平台已经交付对应工作流。

第二批扩展项目包括 Docling、Anomalib、MLflow/BentoML、Paperless-ngx 和 Actual Budget。它们更接近 OCR、工业视觉、模型部署和真实应用集成，但运行成本和环境依赖更高，不适合作为高重复机制消融的第一批底座。

实验分成两项主研究：

- **生成与交付研究**：比较完整平台、去除某个机制的平台、一次性 LLM 生成和人工参考工作流。
- **运行可靠性研究**：冻结同一个工作流版本，通过故障注入逐个开关重试、检查点、幂等、人工门禁和 Trace，测量每个机制的真实救援效果。

只有这种“同任务、同模型、同数据、只改变机制”的设计，才能回答哪些机制最有助于可靠工作流交付。

## 2. 研究问题与边界

### 2.1 核心研究问题

| 编号 | 研究问题 |
| --- | --- |
| `RQ-01` | 平台能否从非技术用户需求生成可编辑、可运行、可验证的真实工作流？ |
| `RQ-02` | 生成的工作流能否在隐藏输入和真实故障条件下保持业务正确性？ |
| `RQ-03` | 需求澄清、能力合同、模块复用、验收修复、持久运行、权限和 Trace 中，哪些机制贡献最大？ |
| `RQ-04` | 机制之间是否存在交互，例如“验收用例只有与自动修复结合才产生明显收益”？ |
| `RQ-05` | 当前平台缺少哪些通用功能模块，导致工作流依赖手写代码、外部人工或无法运行？ |
| `RQ-06` | 外部 GitHub 项目的算法能力与平台的编排、可靠性和交付能力分别贡献了什么？ |
| `RQ-07` | 企业场景中得到的机制结论，能否泛化到个人和小微团队场景？ |

### 2.2 必须分开的对象

| 对象 | 本实验如何使用 | 不能被误写成什么 |
| --- | --- | --- |
| GitHub 项目 | 提供真实算法、解析器、检索器、监控器或目标系统 | 不是平台能力本身 |
| 平台 | 澄清需求、生成工作流、承载积木、运行、修复和交付 | 不能靠外部库运行成功自动获得成功 |
| 莉莉丝 | 生成和编辑工作流 | 不能用其代码修复能力替代工作流结果 |
| 人工参考工作流 | 提供可行上界和任务合同校验 | 不能混入平台自动生成成功率 |
| 公开数据 | 提供可重复代理实验 | 不能写成某家客户生产验证 |
| mock API | 检验 schema、超时、幂等和补偿 | 不能写成真实客户系统上线 |

### 2.3 第一轮排除项

- 医疗诊断、司法决定、信贷拒绝等高风险自动决策。
- 需要真实工厂控制器或物理设备写入的动作。
- 没有合法公开数据、许可证或独立 oracle 的项目。
- 只能靠主观 LLM 打分判断成功的任务。
- 必须依赖未授权生产账户或无限付费 API 的任务。
- 修改 GitHub 项目源代码本身的 Codex 类任务；它们属于莉莉丝次级实验线。

## 3. 真实需求的任务本质

### 3.1 八种可组合任务原型

| 原型 | 本质问题 | 常见输入 | 常见结果 | 主要 oracle |
| --- | --- | --- | --- | --- |
| `A1 接入与结构化` | 能否把真实材料变成受约束数据 | CSV、Excel、PDF、图片、API、传感器 | 类型化记录、质量报告 | schema、单位、行列、hash |
| `A2 抽取与归一化` | 能否提取字段并消除格式差异 | 发票、合同、表单、邮件 | 字段、表格、实体、匹配关系 | 字段级真值、总额关系 |
| `A3 检测与诊断` | 当前是否异常、是什么问题 | 表格、时序、图片、日志 | 类别、分数、原因、升级 | AUPRC、召回、误报、拒判 |
| `A4 预测与决策` | 将来会怎样、现在应如何处理 | 历史数据、当前参数、上下文 | 预测、评分、推荐、阈值决定 | MAE/WAPE、校准、业务代价 |
| `A5 检索与解释` | 证据在哪里、能否据此回答 | 文档、知识库、权限 | 引用答案、拒答、来源 | Recall@k、引用有效性、泄漏率 |
| `A6 优化与规划` | 约束下怎样安排最优或可行 | 需求、资源、成本、时间窗 | 排程、路径、组合、参数 | 约束可行性、目标值、稳定性 |
| `A7 交付与执行` | 如何把结果真正交给人或系统 | 结构化结果、权限、目标接口 | Excel、报表、API 写入、回执 | 文件读取校验、exactly-once |
| `A8 监控与适应` | 长期运行时何时告警或更新 | 新批次、指标、版本、反馈 | 告警、复核、更新、回滚 | 检出延迟、误报、版本链 |

复杂任务至少应组合三个原型，并包含一个真实交付或受控副作用。只做一次 LLM 问答不属于本实验的复杂工作流。

### 3.2 电梯与光纤例子的正确抽象

- 电梯故障检测代表 `A1 + A3 + A7 + A8`：设备数据接入、检测与诊断、人工/工单处置、持续监控。
- 光纤参数继承或预测代表 `A1 + A4 + A7`：历史与当前数据校验、预测或决策、Excel 与 API 交付。

它们说明了任务结构，但不是强制项目、固定优先级或唯一工业场景。

### 3.3 企业还存在的需求

| 需求族 | 示例 | 原型组合 |
| --- | --- | --- |
| 设备与过程风险 | 设备异常、能耗异常、质量偏移、预测维护 | `A1+A3+A7+A8` |
| 质量与视觉检查 | 表面缺陷、包装错误、文档与实物一致性 | `A1+A3+A7` |
| 需求与产能计划 | 销量预测、备件需求、人员和产线容量 | `A1+A4+A6+A7` |
| 服务与物流调度 | 技师派工、车辆路径、仓储拣选、生产排程 | `A1+A6+A7+A8` |
| 财务与业务文档 | 发票、报销、采购单、合同、对账 | `A1+A2+A4+A7` |
| 企业知识与合规 | 设备手册、制度、合同条款、客服知识 | `A1+A5+A7+A8` |

| 跨系统自动化 | 表单到 CRM/ERP、报告到工单、审批后写回 | `A1+A4+A7+A8` |

### 3.4 个人和小微团队还存在的需求

| 需求族 | 示例 | 原型组合 |
| --- | --- | --- |
| 个人文档管理 | 收据、保单、合同、证件归档与检索 | `A1+A2+A5` |
| 个人财务整理 | 银行流水分类、发票匹配、预算例外复核 | `A1+A2+A4+A7` |
| 个人知识工作 | 多资料检索、研究笔记、带引用总结 | `A1+A5+A7` |
| 持续信息监控 | 价格、政策、职位、项目更新的定时跟踪 | `A1+A3+A7+A8` |
| 计划与资源安排 | 日程、旅行、学习或小团队排班 | `A4+A6+A7` |
| 小微业务运营 | 客户线索、票据、库存、售后和内容流转 | `A1+A2+A4+A7+A8` |

## 4. GitHub 项目选择

### 4.1 硬门

项目进入第一批正式实验前必须满足：

1. 存在明确许可证和可冻结版本/提交。
2. 核心探针不需要生产密钥。
3. 可在 CPU 或有界资源内重复运行。
4. 输入、输出和失败可以机器校验。
5. 可以设计隐藏输入和故障注入。
6. 外部项目不会替平台完成待测的可靠性机制。
7. 项目代表一种可泛化任务原型，而不是只代表一个行业名词。
8. 项目基线先独立复现，之后才允许生成平台工作流。

### 4.2 第一批核心项目

| 项目 | 冻结版本/提交 | 承载能力 | 进入原因 |
| --- | --- | --- | --- |
| [PyOD](https://github.com/yzhao062/pyod) | `v2.0.7` / `aebd3bf...` | 异常检测、分数、置信度 | CPU 可运行、独立指标明确；固定在 2.x 避免其 3.x agentic 功能污染归因 |
| [StatsForecast](https://github.com/Nixtla/statsforecast) | `v2.1.1` / `264166e...` | 多序列预测、区间、回测 | 覆盖需求/产能/能耗等广泛预测需求 |
| [OR-Tools](https://github.com/google/or-tools) | `v9.15` / `551ad10...` | 排程、路径、约束优化 | 结果可用约束与目标函数确定性验收 |
| [invoice2data](https://github.com/invoice-x/invoice2data) | `v1.0.0` / `5d913b5...` | 票据抽取、模板、结构化 | 企业和个人都存在，字段和总额有明确真值 |

## 5. 第一批复杂任务包

### 5.1 `RWD-01` 异常检测到维护处置

**用户**：设备运维或质量团队。  
**GitHub 项目**：PyOD；后续可叠加 Evidently。  
**公开代理数据**：UCI AI4I 2020。

工作流必须完成：

```text
CSV/批次输入
  -> 文件 hash 与重复批次检查
  -> schema、类型、单位、范围、缺失检查
  -> 固定特征变换与版本记录
  -> 冻结 PyOD 模型加载或训练
  -> 异常分数、阈值、置信度/拒判
  -> 高风险、待复核、正常三级分流
  -> 人工复核待复核项
  -> 维护候选 Excel
  -> mock 工单 API exactly-once 写入
  -> 回执、Trace、失败恢复
```

隐藏验收：

- 未见批次上的 ROC-AUC、Average Precision、关键 failure 召回和误报。
- 缺列、单位互换、重复行和极端值必须在模型前被处理或阻断。
- 同一数据、模型和配置重复运行结果一致。
- API 超时后重试不能创建两个工单。
- 模型文件缺失时不得伪造故障结论。

该任务不是为了证明“AI4I 等于电梯”，而是检验检测与诊断类工作流。

### 5.2 `RWD-02` 多序列预测到补货/产能计划

**用户**：零售、制造、仓储或能源计划人员。  
**GitHub 项目**：StatsForecast + OR-Tools。

工作流必须完成：

```text
历史销量/需求 + 库存 + 提前期 + 容量/预算
  -> 时间序列 schema、频率和断点检查
  -> 时间切分与多窗口回测
  -> Naive 基线与候选模型比较
  -> 点预测和区间预测
  -> 不确定性、缺货代价和安全库存
  -> 预算、容量、最小订货量约束优化
  -> 不可行解释或人工调整
  -> 补货/产能 Excel
  -> 审批后写入 mock ERP
  -> 回执与计划版本
```

隐藏验收：

- 时间切分不能泄漏未来。
- 报告 WAPE/MASE、区间覆盖率和相对 Naive 改善。
- 每项计划必须满足库存、预算和容量约束。
- 不可行输入必须返回冲突说明，不能编造可行计划。
- 延迟数据到达后，重复调度只生成一个有效计划版本。

这个任务同时检验预测结果能否进入确定性业务决策，而不是停在图表或文字总结。

### 5.3 `RWD-03` 技师派工与动态重排

**用户**：现场服务、物业、售后或维修调度员。  
**GitHub 项目**：OR-Tools。

工作流必须完成：

```text
工单 + 技师技能 + 班次 + 地理/时间矩阵
  -> schema 与主键检查
  -> 硬约束/软约束合同
  -> 优先级和逾期代价
  -> 求解排程
  -> 可行性与目标函数检查
  -> 人工批准
  -> 派工 API
  -> 技师缺席/紧急工单事件
  -> 局部重排并控制计划扰动
  -> 新版本与变更解释
```

隐藏验收：

- 技能、班次、时间窗和唯一分配等硬约束零违反。
- 与先到先服务基线比较完成率、路程和逾期代价。
- 无解时返回冲突约束和可选择的放宽项。
- 重排不得无故改变不受影响工单。
- 批准前不能写入派工系统。

### 5.4 `RWD-04` 发票/票据接入、核验和记账候选

**用户**：财务、采购、小微企业或个人。  
**GitHub 项目**：invoice2data；第二阶段加入 Docling、Paperless-ngx 或 Actual Budget。

工作流必须完成：

```text
PDF/文本票据
  -> 文件保存、hash、恶意/损坏检查
  -> OCR/文本抽取
  -> 供应商/模板选择
  -> 发票号、日期、币种、税额、总额、行项目抽取
  -> 类型、必填、行项目求和和币种校验
  -> 重复发票检查
  -> 低置信度/总额不一致人工复核
  -> Excel/CSV 记账候选
  -> 审批后 mock 会计系统写入
  -> 原文件、结构化记录和回执关联
```

隐藏验收：

- 字段级 precision/recall、金额绝对误差、日期和币种准确率。
- 行项目之和、税额和总额的确定性关系。
- 模板未匹配、字段拼写错误、缺字段和多页表格的明确状态。
- 同一文件不同文件名不能重复入账。
- OCR 失败不得输出伪造字段。

### 5.5 `RWD-05` 版本化知识库、引用问答和拒答

**用户**：客服、运维、HR、合规、专业人员或个人知识工作者。  
**GitHub 项目**：Haystack；第二阶段加入 Docling。

工作流必须完成：

```text
PDF/Markdown/网页文档
  -> 文档 hash、版本和访问组
  -> 解析、切分和元数据
  -> 索引构建
  -> 查询、权限过滤和检索
  -> 重排
  -> 带引用回答
  -> 证据不足拒答
  -> 引用、答案和检索 Trace
  -> 文档更新/删除后的索引一致性
```

隐藏验收：

- 固定问题集上的 Recall@k、MRR 和引用命中。
- 每条引用可以定位到真实文档版本和片段。
- 无权限文档泄漏率必须为零。
- 不可回答问题必须拒答。
- 删除或更新文档后，旧内容不得继续无标记出现。
- LLM judge 只能作为补充；核心检索、引用和权限由确定性脚本检查。

### 5.6 `RWD-06` 模型/数据质量持续监控与受控更新

**用户**：数据、算法、运维和业务负责人。  
**GitHub 项目**：Evidently；后续加入 MLflow 或 BentoML。

工作流必须完成：

```text
定时或事件触发
  -> 获取当前批次和冻结参考
  -> schema/质量检查
  -> 数据漂移、性能或 RAG 指标
  -> 规则化严重程度
  -> 去重告警
  -> 人工判断是否调整阈值、重训或重建索引
  -> 候选版本验证
  -> 批准后切换
  -> 失败回滚、版本和证据记录
```

隐藏验收：

- 注入已知漂移时的检出率、检出延迟和误报。
- 同一漂移事件不得被每日重复告警。
- 参考数据缺失、标签延迟和指标计算失败必须区分。
- 未批准时不能切换模型或索引。
- 切换失败后恢复旧版本，且回滚记录完整。

### 5.7 第二批 `RWD-07` 工业视觉缺陷分流

使用 Anomalib 和公开视觉异常数据，检验图片输入、模型资源、热图/区域、阈值、人工复核和结果 API。它提供重要的模态泛化证据，但不进入第一批高重复消融。

### 5.8 第二批 `RWD-08` 个人/小微文档财务助手

使用 invoice2data + Paperless-ngx 或 Actual Budget，把真实本地收据、银行导出和合同整理为可审核记录。该任务单独报告隐私、去重、人工确认和导入正确性，不进入传统企业成功率分母。

## 6. 正式实验流程

### 6.1 每个任务先建立外部参考包

在调用平台前冻结：

- 需求简报和角色。
- 可公开给 Builder 的材料。
- 隐藏测试材料。
- 数据、模型、项目版本与 hash。
- 输入和输出 schema。
- mock 服务合约与错误脚本。
- 独立 oracle。
- 人工参考工作流。
- 允许的资源、模型、网络与费用上限。

Builder 不得读取隐藏 oracle 和隐藏故障脚本。

### 6.2 四个比较对象

| 组 | 定义 | 作用 |
| --- | --- | --- |
| `HUMAN-GOLD` | 人工构建并通过全部测试的参考工作流 | 可行上界与任务合同验证 |
| `LLM-ONESHOT` | 同一模型一次性生成 WorkflowSpec，不使用平台澄清、合同、模块和修复 | 最低智能生成基线 |
| `PLATFORM-FULL` | 使用完整平台机制生成、验收和修复 | 主要处理组 |
| `PLATFORM-ABLATION-*` | 只关闭指定机制，其余条件不变 | 机制因果归因 |

人工参考组不计入平台自动交付成功率。任何人工补丁必须记录修改行、原因和耗时；补丁后的成功另列为“人工救援成功”。

### 6.3 单次生成到交付的标准流程

1. 提交原始需求和允许材料。
2. 记录平台提出的全部选项式问题。
3. 使用预注册答案或领域人员选择。
4. 冻结生成工作流 `v0`。
5. 运行静态和组件验收。
6. 允许平台在固定预算内自动修复。
7. 冻结待发布版本。
8. 运行 clean、hidden 和 fault-injection case。
9. 独立 oracle 计算结果。
10. 验证 Excel/JSON/API 回执和 Trace。
11. 重启运行环境并复验重复运行/恢复。
12. 记录人工介入、模型调用、token、时间和失败分类。

## 7. 机制与可靠交付的因果实验

### 7.1 待测机制

| ID | 机制 | 当前平台基础 | 预期直接作用 |
| --- | --- | --- | --- |
| `M01` | 选项式需求澄清 | 已有 | 减少目标、输入、权限和验收遗漏 |
| `M02` | F/G/X 能力合同与执行包络 | 已有 | 明确工作流、平台、外部系统的责任 |
| `M03` | 类型化端口、schema 与静态图验证 | 部分已有 | 在运行前发现结构和数据合同错误 |
| `M04` | 版本化模块与证据注册 | 已有底座 | 减少重复生成和未经验证的自定义实现 |
| `M05` | 独立验收 Harness 与隐藏用例 | 已有底座 | 将“看起来正确”变为可判定结果 |
| `M06` | 基于失败上下文的自动修复 | 已有基础 | 把验收失败转成工作流改进 |
| `M07` | 持久任务、检查点、恢复与取消 | 已有 | 处理重启、长任务和中断 |
| `M08` | 重试、退避、幂等与补偿 | 部分已有 | 避免暂时故障和重复副作用 |
| `M09` | 权限门禁与人工复核 | 已有基础 | 阻止越权或低置信度动作 |
| `M10` | Trace、版本、工件和回执证据 | 已有底座 | 支持解释、复验和责任定位 |
| `M11` | 定时/事件触发与去重 | 已有定时基础 | 支持持续工作流而不重复执行 |
| `M12` | 领域数据、模型、RAG、工件模块 | 当前主要缺口 | 让通用可靠性机制承载真实任务 |

`M12` 不是一个开关，而是平台需要从实验中识别和补齐的产品能力集合。

### 7.2 研究 A：生成可靠性消融

固定：

- 同一任务简报和公开材料。
- 同一模型、推理档位、temperature、预算和工具集合。
- 同一项目版本、数据、适配器和环境。
- 同一隐藏测试。

改变：

| 条件 | 关闭内容 |
| --- | --- |
| `G0` | 一次性 LLM 生成，不使用平台机制 |
| `G1` | 完整平台 |
| `G2` | 去除 `M01` 选项式澄清 |
| `G3` | 去除 `M02+M03` 能力/类型合同 |
| `G4` | 去除 `M04` 验证模块复用 |
| `G5` | 去除 `M05+M06` 验收反馈与修复 |

第一轮 pilot：

```text
6 个核心任务
x 6 个条件
x 3 次独立生成
= 108 次生成
```

pilot 用于估计方差、失败分布和费用。正式轮默认提高到每条件 5 次，即 180 次生成；如果 pilot 显示某些条件几乎必然失败，可按预注册早停规则停止该条件，但仍保留失败证据。

### 7.3 研究 B：运行可靠性配对消融

使用同一个已冻结并通过 clean case 的工作流，不重新生成图，只切换运行机制。每次故障采用 `机制开启/关闭` 配对运行：

- `M07`：中途杀死 worker、重启服务、恢复检查点。
- `M08`：HTTP 429/500、超时后成功、响应丢失、重复请求。
- `M09`：权限拒绝、人工拒绝、低置信度。
- `M10`：工件被替换、版本不一致、缺少回执。
- `M11`：重复定时触发、时区边界、迟到事件。

第一轮规模：

```text
6 个核心任务
x 8 类任务相关故障
x 3 次重复
x 机制开启/关闭
= 288 次运行
```

这种设计把模型智能固定住，直接测运行机制是否救回任务或阻止错误。

### 7.4 研究 C：模型与架构贡献

在 `RWD-01`、`RWD-04`、`RWD-05` 三个代表任务上，抽取 20% 的正式 case：

- 固定完整平台，比较两个模型档位。
- 固定模型，比较 `LLM-ONESHOT` 与 `PLATFORM-FULL`。
- 对确定性数据、优化、文件和 API 任务加入“无 LLM 运行基线”。

由此分别估计：

- 模型对需求理解和修复的贡献。
- 平台结构对相同模型的贡献。
- 不需要模型的确定性机制贡献。

### 7.5 机制效应计算

主要效应：

```text
ATE(Mi) = P(可靠交付通过 | Mi 开启) - P(可靠交付通过 | Mi 关闭)
```

同时报告：

- 机制触发率：相关 case 中机制实际被调用的比例。
- 救援率：原本失败的 case 被机制恢复为通过的比例。
- 阻断正确率：危险或无效动作被正确阻止的比例。
- 误阻断率：本应成功的 case 被机制无故阻止的比例。
- 人工时间变化。
- 首次获得有效工作流的时间变化。
- 模型调用、token 和运行成本变化。

二元结果使用配对差异、McNemar 检验和 bootstrap 置信区间；连续结果使用配对分布和 bootstrap。样本足够后使用带任务随机截距的 logistic/线性混合模型，估计跨任务主效应和交互：

- `M01 × M02`：澄清是否只有进入类型合同后才有效。
- `M05 × M06`：验收是否只有能反馈修复时才显著提高交付率。
- `M07 × M08`：恢复与幂等是否必须共同存在。
- `M09 × M08`：审批与写回可靠性是否共同减少危险副作用。

不根据结果临时改指标、删失败 case 或改变通过门槛。

## 8. 故障注入目录

| 类别 | 注入 | 正确行为 | 主要机制 |
| --- | --- | --- | --- |
| 输入 | 缺列、错类型、错单位、重复主键、空文件 | 模型前阻断或明确隔离 | `M02 M03 M10` |
| 文件 | 损坏 PDF、重复文件、表格跨页、编码异常 | 保留原件、失败可定位、不伪造结果 | `M03 M10 M12` |
| 模型 | 文件缺失、版本不符、NaN、超时、低置信度 | 停止、降级或人工复核 | `M07 M09 M10` |
| 预测 | 频率断点、未来泄漏、冷启动、极端变化 | 回测失败或明确降级 | `M03 M05 M12` |
| 优化 | 不可行约束、求解超时、输入规模突增 | 返回无解证据或受控近似 | `M05 M07 M12` |
| RAG | 无答案、冲突版本、无权限文档、删除后残留 | 引用、拒答、零泄漏、索引一致 | `M05 M09 M10 M12` |
| API | 429、500、超时、响应丢失、重复回调 | 退避、exactly-once、回执或补偿 | `M07 M08 M10` |
| 运行时 | worker 被杀、服务重启、租约过期、重复触发 | 恢复且不重复副作用 | `M07 M08 M11` |
| 人工 | 超时、拒绝、修改结果、重复提交 | 保留状态，只执行批准版本 | `M07 M09 M10` |
| 工件 | Excel sheet/列/格式错误、工件被篡改 | 验收失败并阻止上传 | `M05 M10 M12` |

## 9. 通过门槛与指标

### 9.1 可靠交付硬门

每个任务分别判定：

1. 需求忠实度。
2. 输入/schema/版本正确性。
3. 核心算法或业务 oracle。
4. 工作流从触发到终点完整运行。
5. 文件或 API 交付正确。
6. 权限、人工和危险动作边界正确。
7. 重试、恢复、幂等和重复运行正确。
8. Trace、工件和回执可追溯。
9. 非技术用户能够理解结果、失败原因和下一步。

所有任务必要硬门均通过，才记为 `reliable_delivery_pass=true`。不以加权平均掩盖严重失败。

### 9.2 分层指标

| 层 | 指标 |
| --- | --- |
| 需求 | 关键决策覆盖、错误假设数、澄清轮次、需求变化保真 |
| 生成 | Build 成功、静态错误、验证模块使用率、自定义代码量 |
| 任务 | AUPRC/WAPE/Recall@k/约束目标/字段准确率等任务专属指标 |
| 交付 | 工件通过率、API 合约通过率、exactly-once、人工审批正确率 |
| 可靠性 | 故障包含率、恢复率、重复执行率、误告警、数据泄漏 |
| 可追溯 | 输入/模型/模块/工作流/结果/回执版本链完整率 |
| 效率 | 墙钟时间、模型调用、token、CPU/内存、人工分钟 |
| 可用性 | 用户能否找到输入、启动、进度、结果、失败原因和复验动作 |

### 9.3 证据等级

| 等级 | 含义 |
| --- | --- |
| `H0` | 设计审查，不执行工作流 |
| `H1` | 静态合同、图结构和配置验证 |
| `H2` | 隔离本地 Workflow Runtime 组件/工作流验证 |
| `H3` | 本地认证服务、持久存储和合约 fixture 集成 |
| `H4` | 明确启用的真实模型、工具或外部目标 |
| `H5` | 只读客户生产观测，不在该模式启动或修改工作流 |

候选 GitHub 项目的独立探针是平台实验前的项目选择证据，不会自动提高平台的 H0-H5 等级。本报告没有产生这些新任务的 H2-H5 平台工作流结果。

## 10. 如何发现平台缺少哪些模块

### 10.1 当前事实

- 当前注册 46 种积木：19 个业务工作流积木、26 个智能体架构积木、1 个旧兼容积木。
- 需求澄清、能力合同、模块证据、验收、修复、调度、持久任务、Connector 和 Trace 有代码与测试基础。
- 本次针对上述机制的 8 个测试文件共 `63 passed`。
- 当前没有一等的数据集、DataFrame、模型生命周期、OCR、RAG、Excel、优化求解和业务 oracle 闭环。

因此，第一批真实任务很可能暴露“底座可靠，但没有业务载体”的问题。

### 10.2 步骤承载标记

每个任务步骤必须标记为：

| 标记 | 含义 |
| --- | --- |
| `N` | 平台原生一等积木 |
| `V` | 有版本和证据的复用模块 |
| `A` | 冻结外部适配器 |
| `C` | Builder 临时生成的自定义代码 |
| `H` | 运行外人工手工处理 |
| `X` | 当前无法承载 |

一个任务的原生交付覆盖率为：

```text
(N + V 承载的必要步骤数) / 必要步骤总数
```

`A` 可以作为外部能力，但必须有正式合同。`C/H/X` 都是平台产品缺口，不能因为最终结果勉强完成就隐藏。

### 10.3 预期模块缺口

| 优先级 | 模块/平台服务 | 被哪些任务重复需要 | 不能退化成什么 |
| --- | --- | --- | --- |
| `P0` | 文件与 Artifact Store | 01、04、05、08 | 一个字符串路径 |
| `P0` | 表格/DataFrame schema 与质量 | 01、02、03、04、06、08 | LLM 对数据描述的总结 |
| `P0` | 受控 Python/容器执行模块 | 01-07 | 无边界 shell 命令 |
| `P0` | 模型导入、版本、推理、指标和阈值 | 01、02、06、07 | 通用 LLM 节点 |
| `P0` | Excel/CSV 生成与独立验证 | 01、02、04、08 | Markdown 表格 |
| `P0` | 任务专属 oracle/评测适配器 | 全部 | 只看节点类型 |
| `P1` | 时间序列回测与预测模块 | 02、06 | 无时间切分的数据分析 |
| `P1` | 优化求解与无解解释模块 | 02、03 | LLM 猜测排程 |
| `P1` | 文档解析/OCR 与模板注册 | 04、05、08 | 只接收纯文本 |
| `P1` | RAG 索引、权限、引用和更新 | 05、06 | 一次性 prompt 拼接 |
| `P1` | 监控基线、告警去重和版本切换 | 01、02、05、06 | 定时重新运行同一摘要 |
| `P1` | 记录级人工复核表单 | 01、02、04、07、08 | 一个通用 textarea |
| `P1` | 业务 Connector 的 schema/幂等/补偿 | 01-04、08 | 裸 HTTP POST |
| `P2` | 图片数据集、资源/GPU 和可视化工件 | 07 | 把图片描述成文本再判断 |

### 10.4 模块优先级计算

实验后按以下因素排序，不凭感觉增加积木：

```text
GapPriority =
  跨任务出现频率
  x 对可靠交付通过率的影响
  x 当前人工/自定义代码成本
  x 错误风险
  x 可复用性
  / 实现与维护成本
```

模块是否应成为原子积木、复用子工作流、Runtime 服务、不可绕过平台控制或外部 Connector，必须根据状态、复用、权限和用户是否需要在画布上理解它来决定。

## 11. 实验执行阶段

### 阶段 0：冻结与预注册

- 冻结本报告、项目版本、数据 hash、指标和早停规则。
- 为六个核心任务建立公开材料与隐藏材料。
- 建立统一结果 schema。

出口：任何结果产生前，任务、处理组和通过规则已经固定。

### 阶段 1：外部项目与适配器

- 复现比轻量探针更完整的官方基线。
- 建立固定输入/输出 adapter。
- 建立 mock ERP、工单、会计和派工服务。
- 对外部库自身做契约测试。

出口：外部项目失败与平台失败可以区分。

### 阶段 2：人工参考工作流

- 为六个核心任务建立 `HUMAN-GOLD`。
- 验证隐藏 oracle 和故障脚本确实能区分好坏实现。
- 记录平台尚无法表达的步骤。

出口：至少存在一条可通过的路径，否则任务设计无效。

### 阶段 3：平台生成 pilot

- 执行 108 次生成实验。
- 运行 clean/hidden case。
- 分类 Builder、图结构、业务模块、运行时和环境失败。
- 冻结正式轮样本量和成本。

出口：得到可执行的正式消融方案，不对外宣称产品成功率。

### 阶段 4：正式生成与运行可靠性实验

- 执行正式生成重复。
- 执行 288 次配对故障运行。
- 计算机制主效应、交互、救援和误阻断。
- 形成模块缺口优先级。

出口：能够回答“哪些机制帮助最大、帮助什么、代价是什么”。

### 阶段 5：高成本和真实应用扩展

- Docling + 复杂 PDF/OCR。
- Anomalib + 工业视觉。
- MLflow/BentoML 模型版本和服务。
- Paperless-ngx/Actual 真实应用写入。

出口：至少一个受控真实外部目标达到 `H4`；否则只报告已实际达到的 H2/H3。

### 阶段 6：股东会报告

股东报告必须由证据包自动生成，包含成功、失败和未完成项，不允许手工选择性摘录。

## 12. 证据包与股东会口径

每次运行保存：

- 原始需求、所有澄清问题和选择。
- 模型、参数、预算和随机种子。
- WorkflowSpec、每次 diff 和发布版本。
- 项目 tag、commit、依赖锁和环境。
- 数据、模型、文档和工件 hash。
- 每节点输入输出、Trace、错误和恢复事件。
- 人工操作和耗时。
- Excel/JSON/图片/报告工件。
- API 请求、响应、幂等键和补偿回执。
- 隐藏 oracle 原始输出。
- 处理组和机制开关。

股东会至少报告：

| 指标 | 必须如何呈现 |
| --- | --- |
| 任务覆盖 | 按任务原型、企业/个人分母分开 |
| 自动交付率 | 无人工补丁且全部硬门通过 |
| 人工救援率 | 单独列出修改内容和时间 |
| 可靠性 | clean、hidden、fault 分开 |
| 机制贡献 | 百分点变化、置信区间、代价 |
| 外部库贡献 | 与平台机制明确分开 |
| 模块缺口 | 频率、风险、影响、优先级 |
| 证据等级 | 使用平台既有 `H0-H5`，不得跨级宣传 |
| 失败 | 原因、是否可复现、下一步 |

允许声明：

- 某个冻结任务在某个证据等级真实通过。
- 某个机制在配对实验中提高了多少恢复率或降低了多少危险副作用。
- 某类任务目前必须依赖多少自定义代码。

不允许声明：

- 外部库能运行，所以平台已经支持该业务。
- 公共代理数据通过，所以某个具体行业已经生产可用。
- 一次成功运行等于可靠交付。
- 加权平均较高，所以权限泄漏、重复写入或错误文件可以忽略。
- 个人简单任务成功可以抬高企业复杂任务成功率。

## 13. 当前结论与下一步

### 已经确认

1. 真实需求应按任务原型和交付合同建模，而不是按用户举例的行业名词建模。
2. 六个第一批 GitHub 项目可以在当前 Python 3.12 隔离环境中运行轻量探针。
3. 当前平台已有相当多可靠性机制底座，针对性机制测试为 `63 passed`。
4. 当前最大风险不是完全没有治理，而是缺少能承载真实数据、模型、文档、优化和工件的产品模块。
5. 只有机制开关的配对消融和故障注入，才能严肃回答哪个机制帮助最大。

### 尚未确认

1. 平台尚未生成并交付任何一个本报告中的正式工作流。
2. 尚无 `H2-H5` 的新真实任务工作流结果。
3. 尚未知道完整平台相对一次性 LLM 生成提高多少成功率。
4. 尚未知道哪一个机制的平均贡献最大。
5. 尚未完成 Docling、Anomalib、Paperless-ngx、MLflow/BentoML 或 Actual 的本地正式基线。

### 实验启动顺序

1. 先建立 `RWD-01` 和 `RWD-04` 的人工参考包：一个结构化 ML 任务，一个文档/工件任务。
2. 同时实现两者共同需要的最小文件、表格 schema、受控执行、Artifact 和业务 oracle 能力。
3. 平台生成这两个工作流并完成第一轮生成消融。
4. 再加入 `RWD-02` 与 `RWD-03`，检验预测和优化。
5. 最后加入 `RWD-05` 与 `RWD-06`，检验 RAG 和持续运行。

这个顺序不是把两个具体行业设为锚点，而是用最少的垂直任务覆盖最多的任务原型和平台缺口。
