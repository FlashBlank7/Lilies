# 自愈实验：已发布但跑不通的工作流，闭源智能体能自己修好吗

2026-08-28 · 对象=`daily-report-benchmark-2`（2026-08-22 发布后一直跑不通）· 构建者=闭源智能体（DeepSeek 经典莉莉丝）

## 起因

体检（`GET /api/v1/health-report`）报出：近 7 天 6 次运行全部失败，
原因摘要 `公式包含不支持的字符 '.'（位置 8）`。这是一个**已发布**的工作流——
平台此前没有"修复"路径，用户只能重新生成一个新的。

## 做法

给管家加 `repair_workflow` 工具：在**原应用**上开一次修复构建（读现有草稿，
不推倒重来），把体检给出的失败原因原样写进需求。用户只说一句：

> daily-report-benchmark-2 坏了，帮我修一下

管家自主完成：`health_report`（取原因）→ `repair_workflow`（开修复构建）→ `build_status`（跟进）。

## 结果：修好了

| | 修复前 | 修复后 |
| --- | --- | --- |
| 发布版本 | v1 | **v3** |
| 近期运行 | 6 次全败 | 带正确输入连跑 **2 次全成** |
| 验收用例 | 有但不覆盖故障 | `main_test` 通过（A店 2000、B店 3000、总计 5000） |

莉莉丝在修复过程中找到了**比报错更深的根因**——不止公式里的 `.`：

1. `assigner` 的 `$formula` 用了 `by_store.A店 + by_store.B店`，`.` 不被引擎支持；
2. **真正让输出为空的**是 `end` 节点的 `outputs` 填了类型名（object/number/string）
   而不是数据来源引用；
3. `reporter` 模板里 `{{ by_store.A店 }}` 同样会渲染失败；
4. 顺带清理了悬空的 `aggregator` 节点并按 schema 重配。

即：报错只指向表层症状，智能体从现有草稿出发做了完整的因果排查。

## 过程中的两个事故（均已修）

**1. 测试打断线上构建**（已修，conftest 护栏）
修复构建跑到一半变成 `needs_attention: platform restarted while building`。
真因不是平台重启，而是我新写的测试忘了 `data_dir=tmp_path`，
`TestClient` 启动时执行了"把 queued/building 构建标成 needs_attention"——
**测试连上了线上库**，顺带塞进 2 个测试应用。
修法：`tests/conftest.py` 加 autouse 护栏，任何用默认 `data_dir` 构造的 `Settings`
自动改指 tmp；反向验证（故意不给 data_dir，线上应用数 73→73 未变）。
`resume` 后修复构建从断点继续，最终发布成功——**中断可恢复这条链路也顺带验证了**。

**2. 失败运行在客户端"无错误原因"**（排查中）
验证修复时用空输入试跑，得到 `failed | error: None`——看似无从诊断。
实际平台侧信息完整：顶层 `error` 列写着 `node start failed: missing required input: sales`，
只是 `state.error` 为 None，而 guanjia 的 `workflow.run()` 只读后者。
这是客户端字段读取缺陷，已展开专项排查。

## 结论

1. **自愈可行**：给定失败原因 + 现有草稿，闭源智能体能定位并修正结构性错误，
   且会自行发现报错未指出的关联缺陷；
2. **"修复"必须是一等路径**：从原应用开构建（保留草稿与历史）比重新生成有本质优势——
   莉莉丝改的是已有结构，用户的输入契约不变；
3. **体检 → 原因 → 修复**这条链闭合后，"工作流统筹管理"支柱才算完整：
   发现问题、说清原因、动手修好，三步都在对话里完成。
