# 传统企业 AI 工作流真实项目实验计划

> 日期：2026-07-21
> 状态：纠偏后的实验立项基线；正式业务实验尚未开始
> 最高依据：`docs/PRODUCT_NORTH_STAR.md`
> 审计依据：`docs/lilies_product_intent_drift_audit_2026-07-21.md`
> 首要实验对象：平台生成的可编辑工作流
> 次要实验对象：莉莉丝作为 Claude 式智能体

## 1. 实验目标

实验必须分别回答三个问题，不能混成一个总分：

1. 智能体/工作流生成平台能否从传统企业需求出发，生成真正可运行的 ML/DL、RAG、数据和系统交付工作流？
2. 莉莉丝作为一个基于 Claude 式架构的智能体，能否完成需要长上下文、工具反馈和真实验证的复杂任务？
3. 成败中哪些来自大模型智能，哪些来自工作流/智能体架构、工具、状态、权限、重试、数据和确定性工程？

第一项是产品主实验。第二项保留，但不进入平台客户能力成功率分母。

## 2. 实验对象边界

| 对象 | 要验证什么 | 不允许替代什么 |
| --- | --- | --- |
| 平台 | 从需求补全到生成、运行、结果、工件和系统交付的完整链 | 不能用莉莉丝改代码成功替代 |
| 莉莉丝 | 需求理解、规划、工具循环、修复、停止和证据能力 | 不能用来宣称平台工作流解决了工业问题 |
| 生成工作流 | 对未见过的真实输入重复产生业务结果 | 不能用 Build 成功或节点齐全替代 |
| ML/DL 模型 | 可冻结、可评估、可版本化的算法组件 | 不能用 LLM 自述“已分析”替代 |
| 企业系统与工件 | Excel、API、工单、告警、知识答案等实际交付 | 不能用 Markdown 总结替代 |

## 3. 首批平台场景组合

### 3.1 核心场景总表

| 编号 | 真实企业需求 | 核心智能 | 真实交付 | 当前状态 |
| --- | --- | --- | --- | --- |
| `ENT-ML-01` | 电梯故障自动检测 | 时序/表格 ML 或 DL 模型 + 规则 | 故障类别、置信度、告警/工单候选、Trace | 用户锚点；数据与模型候选待冻结 |
| `ENT-ML-02` | 光纤工艺参数继承/预测 | 表格 ML/DL + 工艺规则 | Excel 结果、人工复核状态、指定 API 回执 | 用户锚点；需要真实或脱敏 schema |
| `ENT-RAG-01` | 企业设备/工艺知识问答与处置建议 | RAG + 权限过滤 + 引用 | 带证据答案、无法回答状态、检索 Trace | 候选；文档集待冻结 |
| `ENT-VISION-01` | 工业缺陷检测与复核 | 图像 DL 模型 + 阈值 + 人工复核 | 缺陷类别/位置/置信度、复核记录、MES 接口候选 | 候选；公共数据与项目待调研 |
| `ENT-HYBRID-01` | 规则、模型、LLM 和人工共同完成质量决策 | 混合智能工作流 | 结构化决策、解释、文件与系统回写 | 跨场景综合验收；依赖前四项 |

`ENT-ML-01` 和 `ENT-ML-02` 是不可删除的第一优先级。其他场景只有在找到真实需求、数据、模型和独立 oracle 后才进入正式分母。

### 3.2 为什么不再使用 GitHub 场景作为主组合

pytest issue 接诊、CI 诊断、开源项目发布决策和 GitHub 写回主要服务软件研发团队，与传统企业 ML/RAG 工作流的关键缺口不同：

- 它们几乎不验证工业数据接入与质量。
- 不验证 ML/DL 模型生命周期。
- 不验证 RAG 数据权限和引用。
- 不验证 Excel/文件工件。
- 不验证模型结果如何嵌入企业工艺与人工复核。

这些任务仍可用于莉莉丝代码智能体实验或通用 Connector 压力测试，但必须单列。

## 4. 场景一：电梯故障自动检测

### 4.1 业务目标

设备运维团队接收电梯运行或传感器数据，平台生成的工作流自动完成数据检查、模型推理、规则融合和结果交付。高置信度异常形成告警或工单候选，低置信度和异常数据进入人工复核。

### 4.2 正式输入契约

正式实验开始前必须冻结：

- 设备与采样标识。
- 时间戳、传感器或运行参数字段、单位和允许范围。
- 缺失值、乱序、重复和异常值处理规则。
- 故障标签体系与标签来源。
- 训练、校准、隐藏测试的时间或设备切分。
- 模型文件、依赖、版本和推理资源需求。

如不能取得真实电梯数据，可以先选择公开预测性维护或设备故障数据做组件实验，但必须标成“代理设备数据”，不能直接声称完成电梯业务验证。

### 4.3 平台应生成的工作流

```text
数据/文件输入
  -> schema 与质量检查
  -> 时间窗/特征处理
  -> 版本化模型推理
  -> 置信度与业务规则
  -> 故障类别/解释/证据
  -> 低置信度人工复核
  -> 告警或工单接口
  -> 回执、失败和 Trace
```

### 4.4 独立验收

- 隐藏集模型指标由固定脚本计算，不由 LLM 打分。
- 数据质量错误必须在模型前阻断或进入明确降级。
- 同一模型、数据和配置重复运行结果一致。
- 每个判断可追溯到数据版本、特征版本、模型版本和阈值。
- 低置信度样本按规则进入人工复核。
- 未授权时不允许真实工单写入。
- 模型不可用时不能输出伪造的故障结论。

## 5. 场景二：光纤工艺参数继承/预测

### 5.1 业务目标

客户提交历史测试参数和本次拉丝过程参数。工作流判断哪些参数可以继承、哪些需要重新预测或人工确认，生成规定格式的 Excel，并上传指定接口。

### 5.2 正式输入契约

必须由客户或脱敏样本明确：

- 历史测试参数表结构、主键、单位和版本。
- 拉丝过程参数、采样规则和工艺批次关系。
- “继承”“不继承”“需复核”的业务定义。
- 目标变量、训练标签、代价不对称和容忍范围。
- Excel 模板、sheet、列、格式、公式和必填规则。
- 上传 API schema、认证、幂等键、错误码和回执。

缺少上述材料时只能做契约设计或模拟数据组件实验，不能声称业务工作流已经完成。

### 5.3 平台应生成的工作流

```text
历史测试参数 + 拉丝过程参数
  -> schema/单位/批次校验
  -> 清洗与特征构造
  -> 版本化 ML/DL 模型
  -> 工艺规则与阈值融合
  -> 继承/预测/复核决策
  -> 人工确认低置信度结果
  -> Excel 生成与内容校验
  -> 指定 API 幂等上传
  -> 回执、重试、失败说明与 Trace
```

### 5.4 独立验收

- 模型指标在冻结隐藏集上计算。
- 关键业务类别单独报告，不能只报总体准确率。
- Excel 用程序读取并检查 sheet、列、类型、值、格式和行数。
- 上传端使用冻结合约服务验证认证、schema、幂等和错误分支。
- 重试不能产生重复业务记录。
- 人工拒绝后不能继续上传。
- 每一行结果能追溯到输入批次、模型版本、规则版本和复核人。

## 6. 场景三：企业设备/工艺知识 RAG

### 6.1 业务目标

从设备手册、工艺规程、故障案例和内部制度中回答运维或工艺问题。结果必须引用真实片段，遵守文档权限，并在证据不足时拒绝编造。

### 6.2 平台应生成的工作流

```text
文件接入
  -> 解析/OCR
  -> 文档与权限元数据
  -> 切分与 Embedding
  -> 版本化索引
  -> 查询改写与检索
  -> 重排与权限过滤
  -> 带引用生成
  -> 事实/引用/拒答评测
  -> 客户结果与检索 Trace
```

### 6.3 独立验收

- 文档集、问题集和参考答案冻结并版本化。
- 引用必须能定位到实际文档和片段。
- 未授权文档不能出现在检索或答案中。
- 无支持证据的问题必须拒答。
- 分别报告检索召回、引用有效性和答案正确性。
- 文档更新后索引版本和答案变化可追踪。

## 7. 平台能力缺口与实验依赖

正式运行上述场景前，需要逐项判断能力承载位置，不能默认全部新增为积木：

| 能力 | 推荐承载位置 | 当前事实 |
| --- | --- | --- |
| 文件/表格/图像输入 | 输入积木 + artifact service | 缺少一等闭环 |
| schema/数据质量 | 数据积木或可复用模块 | 缺少工业数据语义 |
| 特征/参数处理 | 可复用模块 + 受控计算执行 | 未形成产品能力 |
| 模型训练/导入/推理 | 模型运行服务 + 可配置工作流积木 | 未形成一等生命周期 |
| 模型注册/部署/监控 | 平台服务 + 治理界面 | 未形成闭环 |
| RAG 链 | 文档/索引服务 + 可组合积木 | 只有报告级概念 |
| Excel 生成 | artifact service + 输出积木 | 未形成 |
| API 上传 | Connector/HTTP + 幂等/回执 | 有通用底座，需业务契约 |
| 人工复核 | `human_input` + 客户运行 UI | 有基础，需领域表单 |
| 证据 | Evaluation Harness + 业务 oracle | 有底座，缺工业用例 |

## 8. 实际项目与数据选择协议

后续网络调研不能再先选“知名 GitHub 仓库”，而要按以下顺序：

1. 先冻结业务任务和所需输入/输出。
2. 搜索公开工业数据集、论文官方代码、模型仓库和许可证。
3. 优先选择有明确数据卡、训练/测试切分、指标脚本和可复现基线的项目。
4. 检查许可证、数据使用边界、硬件需求和下载稳定性。
5. 在固定沙盒中复现基线，记录提交、数据 hash、环境和命令。
6. 只有基线复现成功，才把项目列为正式候选。
7. 公共代理数据与客户真实业务必须分层报告，禁止直接外推。

当前还没有按此协议完成工业项目候选冻结，因此本报告不编造“已选定项目”或“可立即正式运行”的结论。

## 9. 完整实验流程

### 9.1 平台主实验

```text
真实需求与材料
  -> 莉莉丝选项式澄清
  -> 能力/数据/模型/系统合同
  -> 自动生成可编辑工作流
  -> 人工只做预先定义的领域校准
  -> 组件与契约测试
  -> 发布冻结版本
  -> 运行未见输入
  -> 独立业务 oracle
  -> 文件/API/人工交付验证
  -> 重复运行与失败恢复
```

必须保存：

- 原始需求和所有澄清选择。
- 生成工作流每个版本和 diff。
- 数据、模型、代码、依赖和环境 hash。
- 运行输入、节点 Trace、工件和接口回执。
- 隐藏验收脚本与结果。
- 人工介入次数和原因。
- 所有失败、超时、取消和未运行项。

### 9.2 莉莉丝次级实验

已完成的 Click、pytest、Sphinx、Django、NetworkX 和 Locust 故障基线探针继续保留，用于验证莉莉丝作为 Claude 式代码智能体的能力。

该实验线单独报告：

- 仓库理解与上下文使用。
- 搜索、编辑、命令和测试反馈循环。
- 权限、沙盒、预算、停止和恢复。
- 补丁正确性与隐藏测试。
- 同模型不同架构、同架构不同模型的差异。

它不计入 `ENT-*` 场景成功率。

## 10. 模型与架构归因

每个可负担的正式场景至少设计以下对照：

| 对照 | 固定项 | 变化项 | 解释目标 |
| --- | --- | --- | --- |
| 模型对照 | 工作流、工具、数据、预算 | 模型档位 | 大模型智能贡献 |
| 架构对照 | 模型、数据、任务 | 无状态单次调用 vs 有状态工作流/Agent | 状态与反馈贡献 |
| 工程对照 | 模型与业务步骤 | 无/有 schema、重试、幂等、权限、Trace | 确定性平台贡献 |
| 生成对照 | 任务与运行环境 | 人工基准工作流 vs 莉莉丝生成工作流 | 自动生成质量 |

权限拒绝、重试、幂等、Excel 格式和接口回执等确定性能力不需要用更强模型证明。需求理解、特征建议、流程组合和失败修复更受模型能力影响。

## 11. 通过规则

每个 `ENT-*` 场景分别报告以下硬门：

1. 需求忠实度。
2. 数据与 schema 正确性。
3. 模型或 RAG 业务指标。
4. 工作流运行完整性。
5. 人工复核与权限边界。
6. Excel/文件/API 等实际交付。
7. 失败恢复、幂等与重复运行。
8. 客户可理解性。
9. 证据可追溯性。

任一必要硬门失败，该场景不得通过。节点数量、图结构覆盖和 Builder 完成状态只作诊断指标。

## 12. 股东会声明规则

可以声明：

- 已经真实运行并有证据的能力。
- 组件、契约、受控真实和生产观测分别达到什么等级。
- 失败在哪里、缺什么数据或客户环境、下一步是什么。

不可以声明：

- 用公共预测性维护数据完成组件实验，就已经完成电梯生产验证。
- 莉莉丝修好开源代码，就证明平台解决传统企业问题。
- `data_analyzer` 处理文本描述，就证明能处理 CSV 或工业数据。
- 本地 mock API 通过，就证明已完成客户系统生产接入。
- Build 和结构验收通过，就证明业务结果通过。

## 13. 立即下一步

1. 分别为电梯和光纤场景收集真实需求材料、字段 schema、模型现状、业务规则、交付接口和保密边界。
2. 并行调研可合法使用的公共工业数据和官方基线，只作为组件预实验候选。
3. 建立企业数据、模型生命周期、RAG 和 artifact/Excel 的平台能力差距合同。
4. 先实现一条最小但真实的端到端垂直链，而不是继续新增治理机制。
5. 完成后再让莉莉丝从自然语言重新生成该工作流，并与人工基准工作流做隐藏输入对照。
