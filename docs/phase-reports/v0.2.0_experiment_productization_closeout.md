## Current Honest Status

Lilies now has a serious platform kernel rather than only a demo idea. The strongest verified outcomes are:

- E05/E07/E08/E10 have productized surfaces or guarded default behavior.
- E01-E10 each have a current disposition and evidence trail.
- All non-external v0.2.x experiment/productization work is currently closed.
- `current-design/` and `workingon/` are clean after archive.

The important non-negotiable caveat is:

- Full global experiment completion is not claimed because E02 true human timing still has `0` participant rows.
- The E02 panel is ready to run, but not run.
- E10 unrestricted/background/filesystem memory remains forbidden.
- E08 full sidecar completion does not mean cloud-specific deployment hardening is finished.

## Phase Conclusion

`v0.2.x` should be considered complete as an internal experiment/productization and process-governance phase.

It should not be considered complete as a market validation phase, production release hardening phase, front-door usability phase, or external human-panel completion phase. Those belong in later work.

## Handoff Correction: v0.3.x Product Usability Buffer

After the closeout, direct product review found a higher-priority problem than the original operational-readiness handoff: the project is not yet practically usable. A user can enter the frontend or a concrete draft/canvas and still feel lost. There are also enough visible bugs that advancing straight into diligence, cloud readiness, or external validation would create misleading maturity.

Therefore `v0.3.x` is a buffer phase for actual usability, functionality, and bug repair. Operational readiness remains useful, but it is no longer the first `v0.3.0` theme.

## v0.3.x Direction

| Priority | Direction | Closure signal |
| --- | --- | --- |
| P0 | `v0.3.0_product_usability_stabilization` | A new or non-maintainer user can open the frontend, understand the primary object, find the main action, enter a concrete draft/canvas, and know what to do next without reading developer docs. |
| P0 | Draft/canvas comprehension | A concrete draft view explains status, purpose, selected block/workflow shape, available actions, disabled reasons, success state, and error state in the UI itself. |
| P0 | Functionality and bugfix tranche | High-impact bugs on the create/open/edit/build/run/test path are reproduced, prioritized, fixed or explicitly deferred, and covered by smoke or focused regression checks. |
| P0 | User-flow acceptance evidence | At least one front-door-to-draft-to-action user journey has fresh screenshot/Playwright or equivalent black-box evidence. |
| P1 | Test-suite stabilization | Full pytest passes under explicit current runtime defaults, or historical evidence tests are separated from current-runtime acceptance tests; this supports the usability tranche but does not replace it. |
| P1 | Maintainer startup / inspection baseline | Maintainer start/inspect/verify/stop evidence is refreshed after the product usability path is no longer confusing. |
| P2 | E02 / diligence / cloud boundary decisions | External human panel, diligence package, and production/cloud hardening are deferred until the product can be understood and exercised in normal frontend flows. |

## Handoff Rule

The first `v0.3.x` stage must start from `docs/stage-report-archives/v0.2.x/v0.2.144_v02x_closeout_and_v03_handoff.md` and this phase report, with the handoff correction above taking precedence over the original operational-readiness baseline wording.

The next version target is `v0.3.0_product_usability_stabilization`. Do not start `v0.3.x` from E02, diligence, cloud hardening, or generic operations before the frontend and concrete draft/canvas experience are made understandable and usable.

`docs/workingon/` may hold intermediate evidence only after a concrete `v0.3.x` task is accepted. It must not be used to invent or reorder the next major-version task set.
