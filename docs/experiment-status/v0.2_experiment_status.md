## 6. 工程闭环提醒

v0.2.3-v0.2.17 对 Platform Harness 做了多轮真实工程推进，包括 task monitor、observability UI、durable storage、owner budget、stale reconciliation、secret policy、HTTP egress 和 tool egress。但这些 stage 多数是 `backend slice` 或 `platform policy slice`，不能被表述为“Platform Harness 已完整闭环”。

当前仍未闭环的 Platform Harness 方向包括：

- stdio MCP / sandbox/container egress enforcement：v0.2.22 已完成 restricted-policy guard，v0.2.23 已完成 sandboxed no-network stdio runner，v0.2.24 已完成 read-only policy controls，但还没有 allowlist-grade sandbox firewalling。
- secret store 与 secret reference injection：v0.2.21 已完成本地 store/API/runtime 注入，v0.2.25 已完成 local envelope storage，但还没有 KMS、key rotation 或 legacy plaintext migration。
- worker lease / durable execution 语义：v0.2.20 已完成 lease primitive，v0.2.26 已完成 worker runner primitive，v0.2.27 已完成 CLI/helper 和 scheduler manual trigger handler，v0.2.28 已完成 lease renewal loop，但还没有完整 handler catalog、分布式 heartbeat registry 或分布式 queue 语义。
- policy controls 的完整 UI/API 可操作面。
- 生产级 operational runbook 和长时间运行验证。

后续 stage report 必须声明工程 closure level：`backend slice`、`vertical slice`、`platform boundary`、`product capability` 或 `research experiment`。如果只完成切片，必须写成切片完成，不能写成完整能力完成。

以后每个 stage 归档前必须更新本文件或对应版本实验状态文件，并回答：

1. 本 stage 是否新增实验？
2. 本 stage 是否使用实验结果改进工程？
3. 已应用实验是否标记 `已应用` 或 `验证应用`？
4. 工程改进是否补充进实验报告或本台账？
5. 原始 backlog 是否有条目被真正关闭？
6. 如果没有关闭，是 `未开始`、`部分实现`、`延期`、`阻塞` 还是 `替代`？
7. 本 stage 的工程 closure level 是什么，是否真的达到？

没有完成这些问题，不能把 stage 说成实验闭环完成。
