### 1.1 更正：形态 A 的"日报 published"是假成功

事后核查发现该单是**绕过验收证据发布**的：最后一次 `test_run` 明确
`passed=false`（`node assigner failed: 变量 by_store 未绑定`），协调者随即
`draft_publish{explicit:true}`，平台发布决策记录 `missing_evidence /
blocked=false`，仍然产出正式版 v1。产物把样例门店名硬编码进公式
（`$formula: "by_store.A店 + by_store.B店"`），换成 C店/D店 直接崩——
正是本项目要消灭的"形状合法的垃圾"。

根因是平台层有意"只提示不阻断"（业务验收属于业主，人类可知情越过），
而构建者用 `acknowledge_warnings=True` 借走了这条人类例外通道。已修
（`b7167bd`）：构建者发布前必须持有对当前草稿有效的验收证据，人类路径不动；
附回归测试（撤掉修复即红）。

**补漏（同日晚）：这个洞当时只堵了三分之一。** 复查发现发版有三条路：

| 路径 | 触发 | b7167bd 之后 |
| --- | --- | --- |
| `draft_publish` 工具 | 构建者显式请求 | ✅ 已堵 |
| `test_run` 全绿 + auto_publish | 测试一绿立即发版 | ❌ 完全没有门 |
| 收工时 auto_publish | 构建循环结束 | ❌ 完全没有门 |

而且**证据本身可以是假的**：构建者没写验收时，平台会自动补一条纯结构冒烟测试
（`operator=exists, structural=True`）并标为 mandatory。它只证明"跑得起来"，
一跑绿证据状态就是 `current`——零真实验收的工作流照样出正式版。

现已统一：三条路走同一道判据，且判据加严为**强制验收里必须有一条断言了具体值**
（`equals`/`contains`，非 `structural`，`expected` 非空）。`test_run` 那条不抛异常
（模型并没有请求发布，抛了等于凭空判死一单），而是把"为什么没发"写进报告让它去补。
形态 B 的验收编写关卡同步加严（此前只数"有没有测试"）。各附回归测试。

该单（`55434ea9`）的记录作废。**在 §1.2 之前，复杂任务无人通过**。

### 1.3 五轮攻关：每一处修的都是平台自己的洞

| 轮 | 死因（现场记录） | 平台侧修复 | 轮数 / 拒绝率 |
| --- | --- | --- | --- |
| 1 | **基准在积木层根本无解** | 公式引擎补 `sum_by` / `pluck` + 参照解回归测试 | — |

这条轨迹坐实了本项目最重要的一条方法论：**在护栏不完备的平台上评价模型能力，
测到的多半是平台自己的缺陷**（与 §5 测量效度同源）。形态 A 的判断力一直够用，
是接口在坑它。

端口清单、接线缺口提示、方案机械校验（白名单）、`catalog_get` 近似匹配、
预算出口判关卡、方案内积木手册预载、平台内部调用改记 `platform_tool_call`。

顺带挖出的两处"形状合法的垃圾"：赋值里漏 `$` 或拿函数名当键（`{"sum_by": [...]}`）
此前**完全不报错**；写成字符串的引用/公式（`"$ref{start, sales}"`）也被静默存成字面量。
两处都已在写入时拒绝并给出正确写法。

## 2. 形态 B 的失败谱系（33 单机械台账）

## 3. 能力边界：读手册不等于有判断力

复杂任务 7 跑的共同死因是**选错积木**——用 `variable_aggregator`（只合并变量、
不做算术）实现分组求和。逐跑的机制加码与结果：

| 跑次 | 加的机制 | 结果 |
| --- | --- | --- |
| 1–3 | 兜底 JSON 修复、config 包裹提示 | 空轮 29→1，格式类错误基本消失 |
| 4 | 升级阶梯真正生效（try 作用域修正） | 32B 接手 32 轮、17 次成功操作，仍未过 |
| 5 | 校验警告纳入待办 | 仍选错积木，撞平台工具预算上限 |
| 6 | **查过手册才准用**（第 10 级） | 先查 5 次、**选到了正确类型的积木**，配置写错被判停 |
| 7 | 升级阶梯推广到全阶段 | **读了手册仍选回错积木** |

结论：**选积木是无硬门保护的判断类工作，机械阶梯能把机械错误压到接近零，
但压不出判断力**。这与设计文档 §3 的下放原则（可下放度 = 硬门覆盖度 ×
调用频次）完全一致。

⚠️ **本节 7 跑的归因需打折**：这些跑发生在基准无解（§1.1）且教学拒绝尚未落地
（§1.3 第 2–4 轮）的平台上，"选错积木"里有多少是判断力不足、多少是错误信息
不指路，当前数据分不开。形态 B 必须在修好的平台上重测才有归因效力。

形态 B 若要攻复杂任务，正确路线是设计文档已写明的 **B v2**：状态机管阶段推进，
一个更强的模型（或学习型路由头）管阶段内的选型决策，小模型只做填表。

## 4. 机械阶梯（形态 B 的主要工程产物）

十级，全部由真实失败逼出，详见 `docs/small-model-builder-design.md` §"机械阶梯"：
给信息 → 机械算下一步 → 记账守卫 → 工具面硬门 → 机械子阶段 → 关卡达成即判 →
强制指定必调工具 → 简化提案接口 → 代劳确定性步骤 → 查过手册才准用。

两条配套原则（均由事故催生）：

- **恢复手段优先于放弃手段**：任何阶段的守卫判停前必须先用完升级阶梯；
- **守卫按信息增量判定**：一刀切的"只读不算进展"会误伤正在正经诊断的修理手。

## 5. 测量效度：三次"错怪模型、实为管道"

| 观察 | 真因 | 处置 |
| --- | --- | --- |
| 拍平嵌套 JSON / 残 JSON | vLLM 0.8.5 流式工具解析器丢片段（#19056） | 迁移 0.11 + 非流式兜底 |
| 模型"不调工具"致构建停摆 | `<think>` 带崩 hermes 解析器，调用文本化 | 剥思考 + 兜底解析 |
| 32B 连续 6 轮零调用 | Qwen3 默认开思考，吃光输出预算 | 显式 `enable_thinking:false` |
| 4B 长上下文下 29/44 轮"零调用" | 文本化调用的 JSON 少一个闭合括号 | 兜底走平台自带 `json_repair` |
| 模型"看不见已建节点" | **我们自己**读错快照键路径，投影长期谎报空草稿 | 修键路径 + 投影真实性回归测试 |

纪律：**任何"小模型能力不足"的记录，先用非流式直连复现、排除管道故障后才可归因模型**。

## 6. 局限

单机、单任务族、样本量小（简单任务 4 单、复杂任务 A 5 轮 / B 7 单），判卷人即出题人——
但复杂任务的判卷已机械化（`scripts/daily_report_benchmark.py`），出题人无法临场放水。
作为形态验证与机制清单成立，不作为统计结论。
