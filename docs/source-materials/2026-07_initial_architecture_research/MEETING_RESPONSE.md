## 二、逐项议题分析

### 议题 A: "我们这个项目的核心差异点在哪里？"

**提出者**: 余文清 (00:45-00:55, 01:01-01:09)

**问题原文**:
> "我们要跟别的东西要去做差异化，我们到底在做什么？"
> "核心根基应该立足于我们要做什么，而不是我们用什么，拥有什么架构。"

**回应: Lilies 设计已给出回答**

Lilies 的差异化不在技术上比 Claude Code 或 Dify 更新，而在于**积累方式的不同**：

| 平台 | 积累什么 | 怎么积累 |
|------|---------|---------|
| Claude Code / GPT | 模型能力 (更大的模型, 更好的推理) | 训练 + 微调 |
| Dify | 可视化搭建工具 | 产品功能迭代 |
| **Lilies** | **工业领域的工作流模板 (知识资产)** | **用户搭建 → 测试 → 发布 → 复用 → 打分** |

具体来说，每次用户（或 Builder）在 Lilies 上完成一个工业项目，就产生了一个被测试验证过的 `WorkflowSpec`。这个工作流可以被发布为模板、可以被搜索和复用、可以被 fork 和改进。这就是 Lilies 积累的"知识资产"——不是模型权重，不是产品功能，而是**某行业某领域解决某类问题的最佳工作流是什么**。

这是 DESIGN_RATIONALE.md 中 "工作流固化" 核心理念的直接回应。

**证据**：
- 6 个内置模板已经覆盖了代码审查、数据分析、客服路由、文档摘要、任务分解、长文生成
- 模板质量评分系统 (`quality_score`) 已设计：confidence × log₂(1+usage_count) × (1+rating/10)
- `TemplateExpand` API 支持从模板 fork 新应用

### 议题 B: "应该聚焦工业场景，而非通用平台"

**提出者**: 余文清 (00:46-00:48, 00:57-00:58)

**问题原文**:
> "我们只面临一个群体，只面对一个场景。比如说工业的所有东西都...只限于场工业场景中去把它给做到一个很好。"
> "需求是什么，比用什么技术要更重要。"

**回应: 架构支持领域聚焦，模板和 Builder 是机制而非内容**

Lilies 的架构本身是**通用表达层** + **领域内容层** 的分层设计：

```
通用表达层 (架构):          领域内容层 (模板/知识):
─────────────────────       ─────────────────────
25 积木 + DAG 执行         工业巡检工作流
Builder Team + Agent       法律审判流程
模板市场 + 评分系统         审计查账模板
TemplateStore + API         电梯故障诊断工作流
```

架构提供了**足够强的表达能力**（图灵完备），但**不预设任何领域知识**。领域知识通过以下方式注入：

1. **模板** — 专家手工创建或 Builder 从真实项目中生成
2. **Agent System Prompt** — 随领域需求定制
3. **测试用例** — 验证领域特定的正确性标准
4. **评分/质量系统** — 积累使用的数据反映哪些模板真正有用

这意味着：**Lilies 的架构不需要改变来支持工业聚焦——它天然就是领域无关的积木系统，聚焦哪个领域取决于模板库里有什么。**

### 议题 C: "JSON 配置接口对人不友好"

**提出者**: 昊洋 (00:11-00:12, 00:13-00:14)

**问题原文**:
> "它这个接口对人不友好。这东西我要去解决的。必须是说我自己确实用不来，那我让 AI 技术帮我搭，就得到一个工作流。"
> "这些节点并没有太严明的。并没有把所有东西展示出来，就你光调这些 JSON 是不太行。"

**回应: 当前已有多层解决方案，但不完整**

| 层 | 解决方案 | 状态 |
|----|---------|------|
| Builder Team (AI 搭建) | 自然语言需求 → AI 自动生成工作流，人不需要理解 JSON | ✅ 已验证可用 |
| 模板市场 | 预置的、专家验证过的工作流可直接使用 | ✅ 6 个内置模板 + API |
| 前端画布 (Visual Canvas) | 可视化编辑工作流，拖拽积木、编辑配置 | ⚠️ 部分实现，待完善 |
| Block Manual (积木手册) | 每个积木的用途、示例、反模式 | ✅ 已实现 |
| 自然语言交互 | 在画布上继续对话调整工作流 | 🔜 待开发 |

**核心设计理念**：Lilies 的目标用户不需要直接编辑 JSON。JSON 是**机器间通信格式**（Builder ↔ Runtime ↔ Template Store），人的交互通过 Builder 的自然语言接口和画布的可视化编辑完成。

焦淼提出的**分层用户策略**与此完全吻合：
- 专业用户：可以直接使用 Template API + 画布编辑
- 小白用户：通过 Builder Team 自然语言交互

### 议题 D: "Schedule Trigger 烧了 200 元 token — 缺乏监管"

**提出者**: 昊洋 (00:13-00:14)

**问题原文**:
> "那个 schedule 不在监管里面，所以他把我 token 烧了 200 多，我本来是不用那么多的，但是他失败了，他一直在搁那烧。"

**回应: 这是 Platform Harness 必要性的最直接证据**

这个事件完美验证了 DESIGN_RATIONALE.md §5.5 的论点：

**Lilies 积木（软约束）可以做但不够**：
- `schedule_trigger` 可以配置每天 8:00 运行
- `budget_gate` 可以设置 `max_cost_usd`
- 但攻击路径是：工作流创建者**忘了加** budget_gate → 无限重试 → 烧钱

**Platform Harness（硬约束）才能保护**：
- 平台级 `max_cost_per_run_usd` — 即使工作流没有 budget_gate，也强制执行
- 平台级 `max_retry_per_hour` — 失败任务不会无限重试
- 平台级告警 — Token 消耗异常时自动通知管理员

**当前状态**：Lilies 已有软约束积木但缺少 Platform Harness 硬约束。这是下一阶段的最高优先级任务。

### 议题 E: "Builder Team 是 CC 的壳子 — 这算作弊吗？"

**提出者**: 之骏/昊洋 (01:29-01:33)

**问题原文**:
> 之骏: "因为是我们套了层 cc 的壳子嘛，所以现在是这个 skill 是隐含性的，让这个壳子来完成了。"
> 昊洋: "不能这样要原生的去做这件事情。"

**回应: 不是作弊，是架构的解耦设计**

Lilies 的 Builder 本质上是**任何能调用 API 的 Agent**。当前用的是 DeepSeek + Claude Code 风格的 prompt，但架构设计保证了 LLM 和平台是解耦的：

```python
# builder.py 的核心循环
stream = self.provider.stream(model=..., system=..., messages=..., tools=...)
#                                  ↑
#                    任何兼容 Anthropic API 的 LLM 都可以
```

用 Claude Code 还是用 DeepSeek 还是用 GPT-5 来驱动 Builder，是 Provider 层的选择，不是架构的依赖。**"壳子"是可以换的**。

这恰恰是之骏强调的 **"LLM 和 Harness 解耦"** 理念的体现——Builder 的"智能"来自 LLM，Builder 的"工具"是 Lilies 积木 API，两者通过标准化的 Tool Call 接口连接。换 LLM 不影响积木，改积木不影响 LLM。

### 议题 F: "能力边界在哪里？什么时候可交付，什么时候不可靠？"

**提出者**: 昊洋 (00:23-00:25)

**问题原文**:
> "能够去证明它基本上能够生成可交付智能体能力边界是什么样的，超过哪个边界的时候，交付的可靠性会不够，在哪个边界之内交付的可靠性能够确认。"

**回应: 测试系统已为这个问题提供了基础设施**

Lilies 的测试体系可以直接用于绘制能力边界：

| 测试维度 | 衡量什么 | 工具 |
|---------|---------|------|
| 结构完整性 | 工作流图是否有效（有 Start、有 End、无环） | `validate_workflow()` |
| 工具证据 | Agent 是否真的调用了声称的工具，还是编造了输出 | `required_tools` + `minimum_tool_calls` + `require_cited_tool_urls` |
| 确定性输出 | 对非 LLM 流程的输出是否一致 | `structural_only` 模式 |
| LLM 输出质量 | LLM 节点的输出是否符合预期 | `min_length` + `exists` 断言 |
| 并发安全 | 多用户多工作流是否隔离 | 并发运行测试 |

**如何建立能力边界**：
1. 定义测试基准（benchmark）：100 个真实的工业需求
2. 对每个需求，让 Builder 搭建工作流并运行测试
3. 统计哪个**需求复杂度区间**的通过率 > 90%
4. 这个区间就是"可交付能力边界"

当前 Lilies 已经具备了运行这个流程的全部基础设施。

### 议题 H: 文清关于 "工作流 vs 人 vs AI" 的哲学性质疑

**提出者**: 余文清 (01:10-01:14)

**问题原文**:
> "每一个人都深耕在了某一个专业的领域...让这个流程变得好了，是因为每一个人都深耕在了某一个专业的领域。"
> "里面的主体是人还是 AI？"
> 之骏回应: "是 AI。人的重复性工作可以被自动化掉，不涉及人和人之间的工作交付。"

**回应: Lilies 解决的是"单项工作的流程自动化"，不是"人事管理流程"**

这是一个重要的概念澄清。文清的质疑指向了一个关键区分：

| 类型 | 举例 | Lilies 能解决？ |
|------|------|----------------|
| **技术流程** (单项工作) | 审计查账、代码审查、数据分析、文档生成 | ✅ 是 — 积木 + Agent 自动化 |
| **人事流程** (多人协作) | 审批链、人事任命、跨部门协调 | ❌ 否 — 属于组织设计问题 |

Lilies 聚焦的是**技术流程**。之骏在讨论中已明确了这个边界："对于单项工作的流程化和自动化。"这不是 Lilies 的局限，而是它的设计选择。

### 议题 I: 部署与交付 ("模型怎么给别人用")

**提出者**: 邓伟俊 (01:35-01:37)

**问题原文**:
> "我们融合好的模型，具体拿去交付给别人去用？假设有个人他想用我们融合出来的一个小模型，我怎么给他？"

**回应: Lilies 当前聚焦工作流层面的交付，模型层面的交付是上层问题**

Lilies 的交付物是**工作流**（`WorkflowSpec` + `Template`），不是模型权重。工作流的交付途径：
1. **API 调用** — 发布的工作流有 REST API 端点 (`POST /api/v1/applications/{id}/runs`)
2. **模板导出** — 模板是 JSON 文件，可直接分发
3. **LLM Provider 可替换** — 工作流不绑定特定模型，换 Provider 即可

这呼应了之骏强调的 "LLM 和 Harness 解耦" — 工作流是**模型无关的资产**。
