## 1. Resolve 函子：$ref 解析的数学抽象

### 1.1 直觉

在 Lilies 运行时，每个 `$ref` 引用都需要被"解析"——找到引用的节点，读取它的输出，取出指定路径的值。论文把这个解析过程抽象为一个**函子**：

$$\mathrm{Resolve}: \mathbf{WFlow} \to \mathbf{Comp}$$

- $\mathbf{WFlow}$：工作流的范畴（静态图结构）
- $\mathbf{Comp}$：计算范畴（运行时值）

"函子"在这里的核心含义是：**$\mathrm{Resolve}$ 保持工作流的结构。** 解析后的计算步骤之间的关系，保持了原来 DAG 中节点之间的关系。

### 1.2 对象映射和态射映射

```
对象映射: Resolve(A) = ⟦A⟧  (运行时值类型)
态射映射: Resolve(f: A → B) = λx. execute(f, bind(x, resolve_refs(f, x)))
```

读作："把工作流 $f$ 映射为一个计算步骤：接收输入 $x$，绑定到 $f$ 的 start 节点，解析所有 $ref 引用，按拓扑序执行所有节点。"

### 1.3 你在论文中看到什么

> 定理 3.1（$ref 的函子性）：$\mathrm{Resolve}$ 是 faithful functor。

**翻译**：Resolve 保持恒等、保持复合、且是忠实的（不同的工作流映射为不同的计算）。**"忠实"意味着 Resolve 不会"丢失信息"——两个不同的工作流不会被映射为相同的计算。**

### 1.4 Lilies 对应

```python
# Lilies 中的 Resolve 函子（简化版）：
def resolve_refs(workflow, state):
    """拓扑排序后，直接访问上游节点输出"""
    for node in topological_order(workflow.nodes):
        resolved_inputs = {}
        for key, ref in node.config.items():
            if isinstance(ref, dict) and "$ref" in ref:
                upstream_node = ref["node_id"]
                path = ref["path"]
                resolved_inputs[key] = access_path(state[upstream_node].output, path)
        state[node.id] = execute(node, resolved_inputs)
    return state
```

这就是 Resolve 函子的实现：拓扑排序保证了数据依赖的偏序关系，与 Hom 集查询的函子性一致。

## 2. 忠实函子 (Faithful Functor) 的含义

### 2.1 定义

一个函子 $F: \mathbf{C} \to \mathbf{D}$ 是**忠实的**，当且仅当：
$$\mathrm{Hom}_{\mathbf{C}}(A, B) \to \mathrm{Hom}_{\mathbf{D}}(F(A), F(B)) \quad \text{是单射}$$

翻译成人话：**如果两个态射 $f \neq g$，那么 $F(f) \neq F(g)$。** 函子不会把不同的东西映射为相同的东西。

### 2.2 为什么 Resolve 是忠实的

如果两个工作流 $f$ 和 $g$ 不同，意味着它们通过不同的节点序列产生输出。`resolve_refs` 是确定的（仅依赖图拓扑），不引入歧义。所以 Resolve 保留了 $f$ 和 $g$ 之间的差异。

### 2.3 这在工程上意味着什么

$ref 的解析不会**模糊**工作流之间的差异。两个"看起来不同"的工作流（不同的节点序列），在运行时也会"行为不同"。这似乎是一个 trivial 的性质（当然应该这样！），但形式化它很重要——它保证了 $ref 解析不是一个"信息丢失"的操作。

## 3. 重排不变性：节点布局不影响语义

### 3.1 推论

> 若 $W_1$ 和 $W_2$ 拓扑同构（仅节点布局不同，连接关系相同），则 $\mathrm{Resolve}(W_1) = \mathrm{Resolve}(W_2)$。

### 3.2 直觉

你可以在 Lilies 画布上拖拽节点、重新排列它们。只要连线关系不变，工作流的语义完全不变。这就是**重排不变性**。

### 3.3 为什么成立

$ref 只关心两样东西：
1. `node_id`——引用哪个节点
2. `path`——访问输出的哪个字段

它**不**关心节点画在哪个像素位置、在 JSON 中的排列顺序、缩进。拓扑同构保留了所有 $ref 关系的结构，所以解析结果相同。

## 4. Yoneda 视角：$ref 的理论基础

### 4.1 直觉

这是 §3 最抽象的部分，但也是最深刻的部分。

**Yoneda 引理（一句话版）**：一个对象 $n$ 的**全部信息**等价于"所有其他对象指向 $n$ 的所有态射"。

$$\mathcal{Y}(n)(m) = \mathrm{Hom}_{\mathbf{WFlow}}(m, n)$$

读作："从 $m$ 到 $n$ 的所有态射 = 对象 $n$ 的所有'外部关系'。"

### 4.2 $ref 和 Yoneda 的关系

**论文的论断**（修正后）：
> $ref 在语义上**对应于** Yoneda 嵌入的特例——$ref 捕获的是沿数据依赖边进入 $n$ 的态射子集。

### 4.3 三个层次的理解

论文诚实地区分了三个层次：

| 层次 | 说的是什么 | 工程意义 |
|------|-----------|---------|
| **语义充分性** | Yoneda 嵌入保证所有外部关系有对应 Hom 集元素 | $ref 是唯一的组合算子（不需要第二个） |
| **$ref 的特化** | $ref 只沿数据依赖边捕获态射 | 不捕获非拓扑前驱的态射（工作流执行不需要） |
| **实现策略** | 运行时通过拓扑排序访问上游节点输出 | $O(|V|+|E|)$ 图遍历，不是 Hom 集查询 |

### 4.4 为什么只有 $ref 不够（完全等价于 Yoneda）

"完全"的 Yoneda 嵌入捕获**所有**态射——包括那些不沿 DAG 边、不是数据依赖的态射。在工程上，这些"额外的"态射没有意义——工作流只需要上游节点的输出，不需要知道"理论上从任意节点到目标节点的所有可能关系"。

所以 $ref **恰好**是 Yoneda 嵌入在数据流子范畴上的限制——恰好捕获了工作流执行所需的信息，不多不少。

### 4.5 你在论文中看到什么

> 定理 3.2（$ref 的 Yoneda 视角）：$ref 在语义上对应于 Yoneda 嵌入 $\mathcal{Y}(n)$ 在路径 $p$ 上的求值。

"对应于"而非"等价于"——这是修正后的准确措辞。
