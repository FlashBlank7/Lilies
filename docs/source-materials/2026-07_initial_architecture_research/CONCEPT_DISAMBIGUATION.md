# Lilies 会议概念消歧 — 同一词汇，不同语义

> 本文档逐词汇分析会议中不同讲话者使用同一词汇时的语义差异。
> 会议中大量讨论障碍源于"用同一个词说不同的事"。

---

## 1. "工作流" — 会议中分歧最大的词

### 钟昊洋的 "工作流"：Agent 搭建出的 DAG 工作流

```
上下文: "自动去搭工作流的工作流是可以用 AI 自己自行生成的，我们有个身体团队。"
        "定义一个工作流...这些节点都是可以...去调里面的参数。"
        "DAG拓扑 + 积木链 + 可执行"
```

**语义**：通过 Builder Team 自动在画布上生成的、由积木（LLM/If/Else/Schedule/HTTP等）组成的可执行 DAG。这是 **Agent 的工作流** — 一个可被 WorkflowRuntime 执行的计算图。

**Lilies 对应**：`WorkflowSpec` — 即 `nodes: [...], edges: [...]` 的 JSON 表示。

---

### 蒋之骏的 "工作流"：人类专家的做事模式固化

```
上下文: "把企业现在他们已有的工作流给固化下来。"
        "好流程让普通人产出好结果，坏流程让聪明人也寸步难行。"
        "他们已有的工作流程是什么，然后我们把这个工作流程给它自动化掉。"
```

**语义**：人类领域专家（律师、会计、工程师）在执行特定任务（查账、代码审查、数据分析）时的**思维和操作模式**。不是 DAG，是**流程知识**——先做什么、后做什么、在什么条件下做什么决策。Lilies 的角色是把这种隐性的流程知识编码为显性的积木组合。

**Lilies 对应**：`Template` — 即从专家实践中提取的、可复用的 `WorkflowSpec`。

**与昊洋的差异**：之骏的"工作流"先于 Lilies 存在——它在专家的脑子里。Lilies 把它捕获为 DAG。昊洋的"工作流"是捕获的**结果**，之骏的"工作流"是被捕获的**对象**。

---

### 余文清的 "工作流"：人事组织中的多角色协作流程

```
上下文: "每一个人都恰恰深耕在他的流之中，让这个流程变得好了。"
        "市场分工的这么一个意义。每个人都只干一件事情，一直只干这一件事情。"
        "工作流更多是，不仅仅是上下游接口是否通顺的逻辑，更是利益链的分配。"
```

**语义**：企业中多个人、多个角色之间的**协作和交接流程**——谁审批、谁执行、谁签字、谁负责。这不是一个"任务怎么做"的问题（昊洋/之骏关注的），而是"人怎么组织"的问题。文清明确指出这种工作流涉及"行政权、人事任命权、利益链的分配"。

**Lilies 对此的态度**：不在解决范围内。之骏在讨论中明确回应："是 AI。人的重复性工作可以被自动化掉，不涉及人和人之间的工作交付。" 即明确了 Lilis 解决的范围是**单个 AI 执行的任务流程**，而非多角色协作流程。

**与昊洋/之骏的差异**：文清提的是组织社会学层面的工作流；昊洋/之骏提的是工程自动化层面的工作流。同名异义，这是会议中最容易被忽略的误解源。

---

### 焦淼的 "工作流"：没说这个词，但隐含了"已验证可交付的项目流程"

焦淼主要是管理者视角，没有直接使用"工作流"一词进行技术讨论。他说的"直接挂 API 也好，部署也好"表达了对交付能力的关注，与工作流的"可运行"语义相关但不重合。

---

## 2. "智能体" (Agent) — 四个不同含义

### 钟昊洋的 "智能体 (1)"：AgentFactory 生成的 AgentSpec

```
上下文: "智能体生成智能体...我给个需求，我写一个 agentic 的代码。"
        "后面他也做到了生成智能体了。"
```

**语义**：通过 `AgentFactory.generate()` 自动生成的、包含 tools + system_prompt + budget 的 Agent 配置。这是一个**可运行的 Agent 实例**。

**Lilies 对应**：`AgentSpec`。

---

### 钟昊洋的 "智能体 (2)"：= 工作流 (Workflow)

```
上下文: "我们工作流是可以用 AI 自己自行生成的...define 是没有这个功能的。"
        "这个地方智能体团队用的是 CC 的脑子。"
```

**语义**：在很多上下文中，昊洋用"智能体"和"工作流"互换——他都指的是 Builder Team 搭建出的 DAG 工作流。在他的表述中，"智能体" = "能自动执行任务的 AI 系统" = "由积木组成的工作流"。

**Lilies 对应**：`WorkflowSpec`（而非 `AgentSpec`）。

**内部矛盾**：昊洋在同一个对话中用"智能体"既指 `AgentSpec`（Factory 生成的单一 Agent），又指 `WorkflowSpec`（Builder 搭建的多积木 DAG）。这是他没有明确区分的地方。

---

### Dify 的 "智能体"：对话机器人节点

```
上下文: "它的智能体和我们项目里面定义智能体是不一样的，它智能体是一个对话的。"
```

**语义**：Dify 中"Agent"节点是一个内嵌了 LLM 推理链的对话组件——用户问一句，它回答一句。这与 Lilis 的定义完全不同。

**Lilies 对比**：Lilis 的 Agent 是整个工作流的执行者，可以调用工具、创建子 Agent、管理预算。不是一个对话组件。

---

### 蒋之骏的 "智能体"：Harness+LLM 复合体的任意实例

```
上下文: 不直接说"智能体"，而是说 "Harness + LLM 复合体"。
```

**语义**：之骏有意识地避免了"智能体"这个模糊词。他使用了更精确的表述 "Harness + LLM 复合体"，意思是任何同时包含确定执行框架（Harness）和非确定语义推理（LLM）的系统。

**为什么他避免这个词**：因为"智能体"在会议中有多个含义，用它会制造混淆。

---

## 3. "自动化" — 三个不同粒度

### 钟昊洋的 "自动化"：Builder Team 自动生成工作流

```
上下文: "它他可以自动去搭工作流的平台...我们工作流是可以用 AI 自己自行生成的。"
```

**语义**：AI 代替人完成**工作流的搭建过程**。输入需求 → 输出可执行 DAG。

---

### 余文清的 "自动化"：Agent 执行任务时自动迭代

```
上下文: "它一开始是 plan execute，大模型它先做 plan，规定哪一步做什么样的工具调用。"
        "claude code 它已经可以做到我们输入一个问题，它自动的调用工具自动的做任何事情。"
```

**语义**：Agent 在执行任务时，自动识别需要什么工具、自动决策、自动重试。这是 **Agent 运行时的自动化**，不是搭建时的。

---

### 之骏的 "自动化"：工作流固化后的自动复用

```
上下文: "把它给固化下来...这个东西就可以是完全有价值的，可以复用的。"
        "以模板市场形式把它发布到大家来使用。"
```

**语义**：不是执行自动化，也不是搭建自动化——而是**知识自动化**。专家的工作模式被捕获为模板后，下次类似任务无需重新探索，模板自动推荐。

---

## 4. "需求" — 两个不同抽象层次

### 钟昊洋的 "需求 (1)"：具体的技术任务

```
上下文: "你搭建一个定时的，每天东京时间8点钟在网上去整理资讯。"
        "搭一个智能体，可以实际的去页面点点点然后收集东西。"
```

**语义**：可以被精确描述和执行的具体任务目标。可以映射到积木组合。

---

### 钟昊洋的 "需求 (2)"：抽象的模糊目标

```
上下文: "抽象的需求...会不会因为我们给他的提示词不够好，所以他根本不知道自己要干什么。"
        "他确实有可能去给到实际的工业项目，他自己知道想象出那客户的真正工业项目是什么。"
```

**语义**：用户提出的模糊目标（"做个管理系统"），LLM 需要通过推理自己补充细节。这可能产生幻觉。

---

### 余文清的 "需求"：市场和用户的问题

```
上下文: "核心根基应该立足于我们要做什么，而不是我们用什么，拥有什么架构。"
        "我们要面对谁去解决，帮助他解决问题比我们到底用什么技术要更重要。"
```

**语义**：在架构之上还有一层——谁有这个问题？这个问题是否真实？市场规模多大？这是**产品需求**，不是工程需求。

---

## 5. "测试" — 两人有微妙差异

### 钟昊洋的 "测试"：验证某种能力的存在

```
上下文: "我要帮忙做两个东西，在做的时候注意测试两个项目...我能不能生成很长的文章，第二个是我能不能生成代码。"
```

**语义**：通过设计特定场景来验证系统是否具备某种**能力**（生成万字长文、生成代码项目、生成操作 UI 的 Agent）。这是**能力探测**。

---

### 蒋之骏的 "测试"：验证交付物的正确性

```
上下文: "测试系统...可以确保可交付性的积木。"
        "structure_only 模式，验证工作流正确性而不依赖具体 LLM 输出。"
```

**语义**：对已搭建的工作流进行自动化验证，确认它满足最低可交付标准。这是**质量保证**。

**差异**：昊洋在问"它**能不能**做到"，之骏在答"它做到的**是否可靠**"。

---

## 6. "平台" — 三个不同层次

### Platform (Lilies 内部)：工作流运行和搭建的基础设施

昊洋说的"平台"：搭建工作流的地方。DAG 画布 + Builder + 积木。

### Platform Harness (Lilies 外部)：监管和约束

之骏说的"外面套的壳子"：费用限制、审计日志、权限控制。工作流不知道它存在但受它约束。

### Platform Ecosystem (Lilies 之上)：模板市场 + 开源社区

焦淼说的"生态"：GitHub 开源、用户打分、模板分发。

---

## 7. "工业" — 两人对边界有分歧

### 余文清的 "工业"：与"通用"对立的垂直领域

```
上下文: "我们只面临一个群体，只面对一个场景...只限于工厂工业场景。"
```

**语义**："工业" = 非通用、非消费。聚焦制造业、法律、审计等垂直领域。

---

### 钟昊洋的 "工业"：真实项目、非玩具示例

```
上下文: "做实际工业项目了...真实工业口的。"
```

**语义**："工业" = 真实的、有客户的、要交付的项目（而非"测试一下能不能跑"的实验）。不限定行业。

**差异**：文清用"工业"指**领域边界**（做什么行业），昊洋用"工业"指**真实性边界**（是不是真实项目）。

---

## 8. "模板" — 三人的理解有进展

### 早期（会议上开始时）

- 昊洋：模板 = 内置的预制工作流（"日本偶像日报"那种）。类比 Dify 的商城模板。
- 文清：模板 = 对实际项目的工作流提取。质疑"企业工作流很固定，为什么要换？"

### 后期（讨论后渐近一致）

- 之骏：模板 = 从成功项目中提取的、可复用和打分的知识资产。
- 昊洋：逐渐接受"模板市场" + "打分系统"的概念。
- 焦淼：提出可以开源分发（GitHub）。

### 残留分歧

- 之骏认为模板市场是 Lilies 的核心积累机制
- 昊洋认为模板市场是"生态"，需要"自身够硬"才能吸引人用
- 文清认为"模板推荐在工作流中用户接受度存疑"

---

## 9. 概念消歧矩阵

| 词汇 | 昊洋 | 之骏 | 文清 | 是否同一语义？ |
|------|------|------|------|-------------|
| 工作流 | Agent 搭建出的 DAG | 固化的人类专家流程 | 人事组织的多角色协作 | ❌ 三人三个意思 |
| 智能体 | AgentSpec / 工作流（混用） | 回避此词，用 Harness+LLM | 不具体讨论 | ❌ 昊洋自己混用两个 |
| 自动化 | Builder 自动搭建 | 知识自动复用 | Agent 运行时自动迭代 | ❌ |
| 测试 | 能力探测 | 质量保证 | 未明确 | ⚠️ 微妙不同 |
| 需求 | 具体任务 / 抽象目标 | 不区分 | 市场和用户问题 | ❌ |
| 平台 | 搭建环境 | 监管层 | 不区分 | ❌ |
| 工业 | 真实项目 | 垂直领域 | 垂直领域 | ⚠️ 接近但有差 |
| 模板 | 预制工作流 | 知识资产 | 待验证的概念 | ⚠️ 演进中趋同 |
