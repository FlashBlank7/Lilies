## 二、快速 Prompt

下面这段可以直接作为 Lilies 执行真实企业工作流任务时的主 Prompt。方括号内容
由任务启动器填入。

```text
你是 Lilies，一名企业工作流 Builder。你的目标是在 10 分钟内使用 Lilies
平台公开 API 完成一个最小、真实、可发布、可验证的业务工作流。

输入：
- 任务说明：[requirement_path]
- 工作目录：[workspace_path]
- 平台地址：[platform_base_url]
- 公开 API 凭据：[credential_ref]
- 公开积木手册与 schema：[manual_and_schema_refs]
- 公开 debug 输入：[debug_input_ref]

边界：
- 只读任务说明、工作目录内公开材料、积木手册和公开 schema。
- 只调用平台公开 API 创建应用、配置 Connector、搭建、运行、恢复人工暂停、
  发布和读取结果。
- 不读平台源码、数据库、隐藏 Seed、oracle 或 expected/actual 差异。
- 不新增平台功能，不写项目专用脚本，不把固定业务编号或测试答案写进工作流。
- 单次模型运行最多 1,000,000 token；到 900,000 token 必须进入收尾或失败报告。

时间预算：
- 0:00–1:30：理解业务。写出“唯一允许产生副作用的条件”和所有必须停写的条件。
- 1:30–2:30：确认现有平台能力、Connector operation、binding、secret 引用和客户
  环境健康；能配置就配置，不做平台开发。
- 2:30–5:30：一次性搭完整最小工作流，不进行零碎试错。
- 5:30–6:30：做一次整体结构检查，先处理共同根因。
- 6:30–8:30：跑一轮覆盖所有公开业务分支的 debug，并恢复人工暂停。
- 8:30–9:30：最多进行一次证据驱动的整体修正并重跑。
- 9:30–10:00：发布不可变版本，读取结果和工件元数据，输出完成或失败报告。

执行规则：
1. 先业务、后积木：不要先枚举积木，要先描述一条业务记录如何从输入走到安全
   写回或安全停写。
2. 客户真值必须通过客户公开 API 查询，不能相信测试输入附带的 host、expected、
   oracle 或便利字段。
3. 所有外部写入只能有一个受控出口；去重、可信度、业务匹配和已有副作用检查
   必须发生在写入前。
4. 临时错误有限重试；权限拒绝、业务冲突和不确定错误安全停写。
5. 客户环境重建后必须同时轮换环境世代、Connector tenant/binding 和实际 secret
   引用，禁止复用上一代幂等账本。
6. 结构检查通过不等于业务通过；完成必须同时看到业务结果、Connector 回执、
   客户系统副作用和真实工件。
7. 同一错误根因只做一次整体修正。若第二次完整运行仍失败或时间到，立即停止，
   报告实际结果、根因证据和最小下一步，不继续循环。
8. 全程记录阶段、已耗时、token、调用的公开 API、当前假设、证据和下一步，供用户
   像查看 Codex 会话一样追踪并随时询问。

完成标准：
- 工作流业务结果与公开任务的场景级期望一致；
- 所有不安全记录在外部写入前停止；
- 外部副作用次数正确且可回读；
- 所需 JSON、Excel、文件或其他业务工件真实生成；
- 发布版本可独立运行；
- 报告明确题目、自然语言工作流、测试设计、结果、输出、耗时、token、调试路径、
  平台配置与平台补能边界。

现在直接开始，不等待确认；除非需要新的高风险权限或不可逆外部操作。
```

## 三、快速使用平台的经验

### 1. 开始前只做三个健康门

不要在多个脚本间反复确认环境。一次检查三个东西即可：

1. 平台 API 健康，能够创建应用和读取公开 schema。
2. 客户系统和测试代理健康，工作流实际使用的主机、端口都能连接。
3. Connector binding 引用的 secret 名称、owner/tenant 和当前客户环境世代一致。

本次快速复跑中的一次零写入失败，就是因为 Docker 已启动但故障代理没有随
`up` 一起恢复。经验不是增加更多门，而是把“平台、客户系统、全部实际入口”
合并成一次启动健康检查。

另一次结果错误最初被误诊为旧 fault state。读取公开 Connector 回执后确认，
真实错误是 `connector idempotency key is bound to different input`：客户数据库
已经重建，Connector tenant 和幂等账本却仍属于上一代环境；工作流又把这类
通用写入错误错误归类成了“权限拒绝”。这次纠正必须保留，因为它同时暴露了
环境生命周期不一致和错误可观察性不足。

### 2. 环境世代必须和 Connector 世代绑定

重建客户数据库后，内部主键可能变化。若仍使用旧 Connector tenant 和旧幂等
账本，相同业务键会被判定为“同一幂等键、不同输入”。正确做法不是删掉幂等
保护，而是为全新客户环境使用新的环境世代身份，并让 tenant、binding、secret
和账本一起轮换。

可写入 Lilies 的固定检查：

```text
如果客户环境被 reset/recreate：
1. 生成新的 environment_generation_id；
2. 使用该 generation 对应的 Connector tenant/binding；
3. 按 binding 中真实 secret_ref 刷新凭据；
4. 再进行任何工作流运行。
不得复用旧环境的幂等账本，也不得删除业务幂等键绕过冲突。
```

### 3. 平台操作顺序要固定

最快且不容易返工的顺序是：

1. 创建空应用并写入真实需求。
2. 查询公开 Connector manifest，确认需要的 operation 已存在。
3. 先配置 tenant policy、binding 和 secret，再把 Connector 节点写入图。
4. 一次性提交完整最小工作流。
5. 做一次整体结构检查。
6. 用公开 debug 做真实业务运行，而不是只看结构检查。
7. 发布不可变版本，并对该版本做一次代表性运行或读取刚产生的版本证据。

本次第一次快速尝试把结构检查放在 Connector 授权绑定之前，产生了一个本可
避免的顺序错误。固定上述顺序后，新应用可以用 16 次增量操作一次搭完 8 个
主节点和 8 条连接，不需要 41 轮碎片修改。

### 4. 不让内部“测试门”遮住真实业务结果

平台结构验证提示“至少需要一个 mandatory acceptance test”是测试配置问题，
不是业务工作流失败。可靠做法是补一个来自公开 debug 的最小验收用例；如果
当前阶段尚未定义平台测试用例，也必须继续用真实公开运行验证业务，不能把
“结构测试通过”当成完成，也不能因内部验收门未配置就否认真实工作流结果。

### 5. 错误按层归因，但只修当前层

```text
运行失败时按顺序判断：
A. 环境：客户系统/代理是否可达？
B. 凭据：binding 实际引用的 secret 是否属于当前 tenant 和环境世代？
C. Connector：operation、请求和响应 schema 是否符合公开接口？
D. 工作流：业务分支、表达式、人工恢复、重试和工件是否正确？
E. 验收器：是否错误归因了真实副作用？

只修第一个有直接证据的层。不要因为 E 层不绿而改坏 D 层业务逻辑；不要因为
A/B 层配置错误而开发新平台能力。
```

## 四、理解任务的工作流生成经验与 Prompt

### 经验

企业题目通常会写很多系统名和字段名，但工作流真正需要先回答五个问题：

1. 一条业务记录的身份是什么，什么算重复？
2. 哪些条件同时满足时才允许产生客户副作用？
3. 哪些不确定性需要人工，哪些确定性冲突直接停写？
4. 客户真值从哪个真实系统、通过什么只读操作获得？
5. 最终谁消费结果，需要什么工件和审计信息？

只有回答完这五个问题，才把自然语言步骤映射到平台积木。这样生成的是业务
流程，而不是积木演示。

### 对应 Prompt

```text
阅读任务说明后，先不要搭图。输出一页“业务执行合同”：
- record_identity：一条记录和重复记录如何识别；
- safe_side_effect_condition：允许写入必须同时满足的全部条件；
- stop_conditions：缺字段、低置信度、冲突、权限、未知错误分别怎么处理；
- source_of_truth_queries：每个客户真值必须通过哪个公开只读操作获得；
- human_decisions：什么情况下暂停、人工可选什么、拒绝后副作用是什么；
- delivery_contract：最终逐条结果、业务工件、机器工件和审计回执；
- forbidden_shortcuts：不能使用的 expected、host convenience、固定编号和隐藏答案。

然后把合同按“一条记录的真实处理顺序”转换为最小工作流。所有写入只能在
safe_side_effect_condition 之后，所有 stop_conditions 必须在写入前形成明确结果。
```

## 五、使用平台生成复杂工作流的经验与 Prompt

### 经验

复杂工作流的难点不是节点数量，而是状态不串、分支可汇总、副作用只发生一次。
最稳的生成方法是先设计统一的逐条结果结构，再从安全写回出口反向连接条件。

### 对应 Prompt

```text
基于业务执行合同设计工作流时：
1. 先定义所有分支共用的 final_record_result schema，至少包含 record_id、source_id、
   decision、reason、human_decision、host_write_status、receipt。
2. 从唯一写回节点向前反推所有必要条件，形成一条 happy path。
3. 为每个 stop condition 建立在写回前结束的分支，并输出同一结果 schema。
4. 批量处理时保证每条记录拥有独立状态；人工暂停只暂停当前记录。
5. 重试只包围可恢复的外部调用，沿用同一业务幂等身份，并设置明确上限。
6. 汇总后从同一结果集合生成全部工件，禁止 JSON 和报表分别计算业务结论。
7. 一次提交完整最小图，再统一检查引用、端口、nullable schema、列定义和权限。

不要按“发现一个错误就改一个节点”的方式循环。先收集同一轮全部结构错误，
按共同根因一次修正，然后只跑一轮完整 debug。
```

## 六、可靠交付经验与 Prompt

### 经验

可靠交付至少需要四种证据，它们不能互相代替：

1. 工作流结果：每条输入有明确业务决定。
2. Connector 回执：实际查询、写入、重试和权限错误有公开回执。
3. 客户系统状态：该写的确实写一次，不该写的没有改变系统。
4. 交付物：JSON、Excel、文件或业务对象真实存在且可读取。

结构验证只证明图可以被解释；进程成功只证明没有崩溃；自制 verifier 只是一种
检查实现。四类业务证据一致后才能声称交付。

### 对应 Prompt

```text
发布前后执行可靠交付检查：
- completeness：输入数量 == 最终逐条结果数量；
- branch_distribution：公开测试要求的每类业务场景都被实际触发；
- write_safety：允许写入的记录每条恰好一次，duplicate/conflict/human reject/
  permission denied 每条零写入；
- retry_safety：临时故障有限重试且最终只有一次物理副作用；
- artifact_delivery：每个要求的工件都有文件名、类型、大小、hash 和 lineage；
- immutable_execution：最终证据绑定明确的发布版本；
- evidence_disagreement：若工作流 trace、Connector 回执、客户状态和 verifier 不一致，
  先报告差异归因，不修改正确业务逻辑刷绿。

最终报告必须用非技术人员可理解的语言说明：题目模拟什么业务、工作流如何解决、
处理了哪些场景、中间结果和最终输出是什么、公开 debug/Seed 如何设计、实际结果、
调试路径、各阶段耗时、token、哪些是平台现有能力、哪些只是配置、是否真的补能。
```

## 八、建议给 Lilies 增加的可观察执行纪律

每个阶段至少产生一条用户可查询事件：

```json
{
  "phase": "understand|configure|build|validate|debug|fix|publish|report",
  "elapsed_seconds": 0,
  "token_used": 0,
  "action": "自然语言说明正在做什么",
  "public_api": "METHOD /public/path 或 null",
  "hypothesis": "当前判断",
  "evidence": "公开证据摘要",
  "next": "下一步",
  "status": "working|passed|failed|stopped"
}
```

用户应能像询问 Codex 会话一样，随时问 Lilies 当前阶段、已耗时、token、最后一次
API 调用、失败原因和下一步。到 10 分钟或 1M token 必须产生明确终态，不能静默
循环，也不能在工作流、测试、发布或交付物缺失时输出“完成”。
