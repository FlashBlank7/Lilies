## 一、项目题目与结果

## 二、工作流如何解决问题

工作流先检查需求历史的时间顺序、单位和商品集合，再到 ERPNext 读取当前库存。
库存不能从测试输入直接相信，而要按商品和仓库与客户系统回读结果匹配。

合格数据进入当前已批准的预测部署。模型为每个商品预测未来七天需求，同时返回模型
身份、版本、评估摘要、部署修订和是否建议重新训练。生产运行只推理和监控，不在线
训练，也不会自动更换模型。

计划器随后计算：

```text
缺口 = 预测需求 + 安全库存 - 当前库存 - 在途数量
建议补货 = 向上取整到整包数量，并满足最小订购量
```

它再统一检查总预算和总仓容。资源足够时返回每个商品的建议量、成本、使用能力和剩余
资源；资源不足时返回不可行状态、容量缺口和预算缺口，不进入人工审批，也不写 ERP。

可行计划只暂停一次，由库存计划员批准或拒绝。拒绝时保留理由并零写入；批准时先用
稳定批次身份查询是否已有草稿。没有才创建 docstatus=0 的 Material Request，有则
复用旧草稿。写后再从 ERPNext 读回单据，确认仍未提交、商品和数量正确。最后从同一
最终状态生成计划 JSON、模型/约束审计 JSON 和补货工作簿。

## 三、测试任务与 Seed 设计

三项公开强制测试不是检查积木数量，而是验证完整业务分支：

| 测试任务 | 实际检查 | 通过的业务含义 |
|---|---|---|
| 可行且批准 | 真实库存、预测、30/20/50 补货量、人工批准、创建并读回草稿 | 正常计划能安全交付 ERP 草稿 |
| 可行但拒绝 | 相同计划由计划员拒绝 | 人工拥有最终写入权，拒绝后 ERP 零变化 |
| 预算与仓容不足 | 同时压低两项共享资源 | 流程能解释两个缺口，并在审批和写入前停止 |

随机 Seed 60601 不提供工作流答案。它重新生成三条稳定但不同的周需求曲线、最小订购量、
整包数量、在途、安全库存、成本和业务批次身份，并重新训练候选模型、按时间切分评估、
批准为新部署修订。随后对同一不可变工作流 version 1 执行：

1. 可行计划批准并创建一张草稿；
2. 原样重放，必须复用草稿而不是再创建一张；
3. 可行计划人工拒绝，必须零写入；
4. 预算和仓容同时不可行，必须点名两个约束且不暂停人工。

Seed 通过意味着：时间切分评估达标、发布版确实使用刚批准的模型、预测值符合独立
季节性计算、漂移提示正确、生产不在线训练、计划量符合独立库存平衡、ERP 草稿保持
未提交、重放零新增、拒绝和不可行零写入、每次三工件、人工暂停次数正确。本轮
16/16 全部满足。

## 四、项目六快速 Prompt

```text
这是一个预测驱动、受共享资源约束、只交付 ERP 草稿的补货工作流。

先写不变量：
1. 历史数据必须按时间验证；库存必须从 ERP 公开只读接口取得，不能相信输入便利字段。
2. 模型训练/导入、时间切分评估、人工批准和部署发生在模型管理阶段；生产工作流只调用
   当前批准版本，不在线训练或自动换模型。
3. 订单量必须同时满足预测需求、安全库存、在途、MOQ、整包、预算和仓容。
4. 不可行时明确列出共享资源缺口，并在人工和 ERP 写入前结束。
5. 可行计划只有人工批准后才能写；拒绝严格零写。
6. 只创建 docstatus=0 的 Material Request；禁止提交、采购、库存过账或绕过 ERPNext。
7. 稳定 batch_id 先查询后创建；原样重放必须复用旧草稿且零新增。
8. 写后重新读取 ERP 单据；计划、模型、约束、人工和宿主回执共同生成三份工件。

平台操作顺序：
- 先取得一个 deployment receipt，确认 ERPNext、Connector operation、Secret、工作区、
  预测部署和模型评估都 ready；
- 训练或导入候选模型，用时间靠后的数据独立评估并批准，不把训练放进生产图；
- 从空应用一次搭建“校验—读库存—预测—约束计划—人工—查重/写草稿—读回—工件”；
- 一轮测试同时覆盖批准、拒绝、不可行和重放；
- 全绿后发布不可变版本，再用新的随机数据重训候选并调用同一发布版验收。

不得用图结构正确代替计划量正确，不得用模型指标代替 ERP 草稿，不得用一次创建成功
代替重放幂等，也不得把提交后的单据冒充安全草稿。
```

## 五、快速使用平台的经验

1. 模型准备和生产推理必须分层。Builder 可选择外接模型、微调候选或从客户数据训练，
   但工作流中的模型步骤只引用一个已批准 deployment；这避免每次业务运行都重训。
2. 先让 Connector 用公开 OpenAPI 合同读取库存并创建草稿，再搭图。这样客户字段、权限
   和草稿语义在业务构建前已经有真实合同证据。
3. 用一个测试批次同时覆盖正常、拒绝、不可行和重放，比逐分支修改快，也能直接比较
   工作流输出、Connector 回执和 ERP 实际状态。
4. 环境恢复不应要求 Builder 知道 compose 密码变量、site 名或重置命令。本轮首次启动
   因旧容器没有保存当前 compose 新增的管理员变量而停止；恢复后又因公开 fixture 路径
   从 `public-inputs/` 移到 `fixtures/public-inputs/` 停止。两次都没有业务图证据，不应算
   工作流失败。
5. 已创建的 application、Connector generation 和客户环境必须有 durable receipt。
   本轮保留同一个空应用继续后，实际模型、搭图、三测试、发布和 Seed 只用了数秒；若
   因路径错误重建一切，反而会制造幂等和资源污染。

## 七、可靠交付 Prompt

```text
按七层验收补货工作流：
A. 数据：历史顺序、单位、商品集合和 ERP 实际库存正确。
B. 模型：时间切分评估达标，推理记录的模型/版本/部署修订与批准记录一致。
C. 计划：MOQ、整包、安全库存、在途、预算和仓容均参与，数量可独立重算。
D. 不可行：明确资源缺口，人工暂停数为零，ERP 写入数为零。
E. 人工：批准才写，拒绝零写；决定和理由可审计。
F. 宿主：只创建未提交草稿，写后读回；相同批次重放零新增。
G. 工件：计划、模型/约束审计和工作簿来自同一最终状态，绑定发布版本。

任一层失败都不声明完整交付。环境 prepare 失败单独报告，不改业务图；trace、Connector
回执、ERP 状态和独立计算不一致时，先定位共同根因，再最多整体修正一次。
```

## 八、结论

项目六证明平台已有能力可以在十分钟内完成“训练/评估/部署模型 + 生产预测 + 约束优化
+ 人工治理 + ERP 草稿交付”的完整闭环。它也证明剩余主要问题不是继续增加原子积木，
而是把客户环境、Connector、模型部署、Secret 和 workspace 收敛成一个可恢复、可查看、
可一次释放的项目 deployment receipt。
