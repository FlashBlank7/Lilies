## 二、项目二快速 Prompt

在项目一的通用快速 Prompt 之后追加：

```text
这是一个权限受控、可更新、可引用的企业 RAG 工作流。先写出以下不变量：

1. ACL 必须在相关性打分和回答上下文构造之前执行；无权内容不能进入候选、引用、
   工件或人工复核内容。
2. 有充分授权证据才回答；无证据、弱证据或只有越权证据时明确拒答并返回空引用。
3. 每个引用必须包含来源身份、客户 URL、来源版本和精确片段。
4. 新版本可以替换旧版本；旧版本不能覆盖新版本；删除必须使旧内容不可检索；
   同一同步事件重放不能增加索引版本。
5. 敏感问题在生成最终可交付回答之前暂停。人工拒绝后最终回答和引用为空，但保留
   不含越权内容的审计轨迹。
6. 每次运行必须从同一最终状态生成回答记录、ACL/检索轨迹和同步回执三份工件。
7. 客户知识只从 BookStack 公开只读 API 获取；工作流凭据不得修改客户页面。

平台操作顺序：
- 确认知识索引服务和同步、权限检索、依据回答三项领域能力存在；
- 创建一个索引，不拆成大量页面级原子积木；
- 先保存只读 Secret，再一次性提交完整工作流和一项真实强制业务测试；
- workspace 只能使用平台公开允许的相对工作区或平台签发的 workspace handle；
- 公开 debug 一次覆盖 7 类问题和重放、更新、旧版本冲突、删除四项生命周期；
- 全绿后发布不可变版本，并用发布版再跑一个带引用问题。

完成必须看到：7 类业务决定正确、forbidden_chunk_count 为零、引用版本正确、
两次人工决定正确、四项生命周期正确、每次三份真实工件、发布版本可运行。
结构验证或测试进程成功不能代替这些业务结果。
```

## 三、理解任务的经验

权限 RAG 不是“检索后让 LLM 回答”。它包含三条相互独立但必须一致的生命周期：

1. 来源生命周期：插入、更新、删除、重放和旧版本冲突。
2. 权限生命周期：调用者身份决定哪些来源能进入检索。
3. 交付生命周期：普通回答直接交付，敏感回答由人工决定，拒绝结果也必须可审计。

理解任务时先产出下面的合同：

```text
source_contract:
  source_id, version, content_digest, customer_url, allowed_roles
sync_contract:
  inserted, updated, deleted, unchanged, replayed, conflict, index_revision
retrieval_contract:
  principal_roles, allowed_sources, filtered_sources, candidates,
  forbidden_chunk_count
answer_contract:
  answered|refused|refused_by_reviewer, answer, citations, evidence_sufficient
delivery_contract:
  answer_record, retrieval_acl_trace, index_sync_receipt
```

不要先讨论 embedding 模型或节点名字。先确认越权内容永远不能进入打分，更新和
删除不会倒退，拒答也有完整交付，再选择平台能力。

## 四、快速使用平台的经验

### 1. 领域模块比原子积木更适合 RAG 生命周期

项目二只需要一个知识索引服务和同步、权限检索、依据回答三项领域操作。把插入、
更新、删除、ACL、重排、引用分别做成大量原子积木，会把一致性和安全责任重新
丢给 Builder，也会膨胀积木目录。

### 2. 强制业务测试应作为图的一部分一次提交

新应用一次提交 16 个步骤、19 条连接和一项真实 BookStack 测试。强制测试不是
单纯断言图结构，而是读取真实页面、回答运营问题、确认 ACL、引用和三份工件。

### 3. workspace 是平台能力，不应让 Builder 猜本机目录

第一次调用把 workspace 传成平台边界外的绝对路径，`tests/run` 返回裸 500。
改成 `.` 后相同测试 1.08 秒通过。第二次脚本虽然传相对路径，却在另一个本机根
目录创建它，平台返回“workspace does not exist”。把目录创建在平台实际 workspace
root 后，业务 debug 立即通过。

给 Lilies 的固定规则：

```text
永远不要根据当前 shell 工作目录猜平台 workspace。
优先使用平台返回的 workspace_handle；没有 handle 时只使用公开合同明确允许、
并已经通过平台 API 创建或确认存在的相对 workspace。
```

### 4. 编排脚本必须失败即停并保留已创建资源身份

第一次整段命令没有启用 fail-fast。构建脚本在强制测试处失败后，后续步骤仍拿
空 application_id 调 secret、publish 和 smoke，产生三个与业务无关的噪音错误。

平台客户端和 Lilies 工具层应做到：

- 创建应用后立即持久记录 application_id；
- 任一步失败立即停止当前流水线；
- 恢复时从已记录资源继续，不重建客户环境或工作流；
- 错误报告区分原始失败和被跳过的后续步骤。

## 五、可靠交付经验与 Prompt

```text
对权限 RAG 的可靠交付按四层验收：

A. 内容正确性
- 授权问题回答来自正确来源；无依据问题拒答。

B. 权限安全
- ACL 在打分前执行；forbidden_chunk_count == 0；越权来源不出现在候选、引用、
  工件和人工内容中。

C. 来源生命周期
- replay 不增加 index_revision；update 引用新 version；stale update 返回冲突；
  delete 后宿主 404 且索引不再返回旧内容。

D. 交付完整性
- 敏感批准/拒绝各准确暂停一次；每次运行生成 answer、retrieval/ACL、sync 三份
  JSON；发布版本再次运行并保留引用和工件。

任何一层失败都不能声明完成。不得用回答文本看起来合理代替 ACL 证据，不得用
索引同步成功代替引用正确，不得用 Draft 运行代替发布版本运行。
```

## 七、对 Lilies 的改进结论

Lilies 需要把“工作区能力发现”和“失败后从已创建资源继续”作为平台操作基本功，
而不是每次重新初始化。RAG 业务 Prompt 则必须强制 ACL-before-scoring、版本单调、
删除生效、拒答和三工件交付；否则即使回答看起来正确，也不能算企业 RAG 完成。
