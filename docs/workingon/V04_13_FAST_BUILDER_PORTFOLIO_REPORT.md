## 二、六道题在解决什么，以及工作流怎么做

### 项目一：供应商单据与库存主数据对账

从 Paperless 读取供应商文档，抽取并校验物料、数量和供应商信息，再到 InvenTree 查询
真实主数据。只有唯一可信匹配且没有重复、冲突或低置信度时才写入；不确定记录交给人，
临时故障有界重试，权限拒绝安全停写。所有逐条决定汇总成 JSON 和 Excel。

### 项目二：权限受控、可更新、带引用的企业知识问答

从 BookStack 同步页面和权限，先按调用者权限过滤，再检索和生成带版本、URL、片段的
引用。无证据或越权时拒答，敏感问题由人批准。页面更新、删除、重放和旧版本倒灌都
不能让索引后退或泄露旧内容，每次交付回答、权限/检索轨迹和同步回执。

### 项目三：跨重启的设施事件自动化

Home Assistant 事件到来后按设备保存最新状态和持久截止时间；恢复则取消，到期时重新
读取当前状态，仍异常才通知。重复、乱序和多设备并发互不污染。高风险动作先人工批准，
403 停止，503 有界重试，外部通知恰好一次。

### 项目四：带模型生命周期的预测性维护

先用授权训练集训练或微调候选模型，用独立数据评估并由模型负责人批准；生产工作流只
调用已批准部署。它从 ThingsBoard 读取遥测并校验单位、范围和时间，高风险高置信自动
告警，不确定时人工复核，重复/旧/无效/拒绝均零写。模型可提升 v2、回滚 v1，生产不
在线训练，漂移只生成再训练建议。

### 项目五：Actual 财务收据对账

读取 Actual 预算、账户和交易，用整数分校验收据，先检查稳定导入身份和已处理标记，再
区分唯一匹配、歧义、金额冲突和新交易。潜在写账统一人工批准，只使用官方 CLI 写入，
写后重新读取余额与交易。更新不能改余额，只有批准新增可以改变余额，重放必须零新增；
输出逐条 JSON、Excel 和宿主回执。

### 项目六：预测驱动的约束补货

按时间验证需求历史，从 ERPNext 读取真实库存，调用已批准的七天需求预测，再综合安全
库存、在途、MOQ、整包、预算和仓容计算补货量。不可行时解释资源缺口；可行计划经人工
批准后只创建未提交 Material Request 草稿，写后读回，重放复用旧草稿；输出计划、模型/
约束审计和工作簿。

## 三、测试和 Seed 到底意味着什么

Seed 不是“固定答案”。它用一个可重复的随机数生成新的业务身份、数据组合、发生顺序
或故障分布，再由独立业务不变量判断结果。通过 Seed 的意义是同一发布工作流不只会处理
公开样例。

| 项目 | Seed/测试怎样变化 | 通过意味着什么 |
|---|---|---|
| 1 | 合格、重试、人工、重复、冲突、403 的记录混排 | 允许写的恰好一次，其余在写前停止，JSON/Excel 一致 |
| 2 | 角色、问题、页面版本和同步事件变化 | ACL 永远在检索前；更新/删除/重放不泄露或倒退；引用可核对 |
| 3 | 设备、事件、顺序、并发、403/503 和人工决定变化 | 持久计时正确，旧/重复事件无副作用，通知恰好一次 |
| 4 | 遥测、风险、置信度、事件顺序、故障和人工决定变化 | 指定批准模型被使用，告警数量正确，拒绝/无效/重复零写 |
| 5 | 8 类收据、账户和人工选择变化，再原样重放 | 三个物理变化准确，余额成立，重放零新增，JSON/Excel 类型正确 |
| 6 | 周需求、MOQ、整包、在途、安全库存、成本和批次变化 | 预测、约束和订单量可独立重算，草稿未提交，重放零新增 |

本轮项目四没有通过 503 恢复类别，因为共享平台没有加载重试所需的 pre-dispatch
attestation；项目五 Seed 在创建 Actual 测试账户时终止，尚未产生工作流业务结果。

## 七、三类可复用经验和对应 Prompt

### 1. 理解任务

先识别“谁在什么条件下允许改变哪个客户系统”，再看积木。固定 Prompt：

```text
先输出业务执行合同：record/event identity、source-of-truth queries、safe side-effect
condition、stop conditions、human decisions、idempotency/replay、delivery contract、forbidden
shortcuts。缺一项就先补合同，不搭图。
```

### 2. 使用平台生成复杂工作流

先设计所有分支共用的最终结果，再从唯一副作用出口反推 happy path 和全部停写分支。
领域生命周期用模块或平台服务承载，不把 RAG、模型、事件、财务或优化内部步骤膨胀成
几十个面向 Builder 的原子积木。固定 Prompt：

```text
一次提交 desired state：节点、边、测试、runtime binding 和 capability refs。按
intake → validate → read truth → decide/model/retrieve/optimize → human → one side effect →
readback → artifacts 排列。先做全图可达性和 schema 检查，再跑一组多分支业务测试。
```

### 3. 可靠交付

固定检查六层证据：输入与业务决定、模型/检索/优化证据、人工决定、Connector/Program
回执、客户系统实际状态、工件与发布版本。固定 Prompt：

```text
若 workflow output、trace、Connector receipt、customer state、artifact 和 verifier 不一致，
先按环境→凭据→Connector/runtime→业务图→验收读取定位第一处直接证据。一次整体修复，
只重跑受影响证据；不得改正确业务图迎合错误验收器。
```

## 八、为什么已经有能力还会慢

六次快跑没有证明缺少大量业务积木，反而证明能力被分散的部署状态遮住：

1. 客户环境、Secret、Connector binding、幂等账本和环境世代不是一个资源。
2. 工作区要求 Builder 猜平台宿主目录，没有统一 workspace handle。
3. 图中的事件触发器发布后不会自动形成版本绑定订阅。
4. Connector 的接口版本、部署 profile、故障代理和环境 generation 混在一起。
5. 模型、Program profile、运行镜像和安全重试证明只在某些启动路径加载。
6. desired-state 恢复仍退化为几十到上百次 mutation，节点替换会丢边，旧 key 会冲突。
7. 测试环境准备失败常被折叠成业务失败或通用错误，Builder 看不到唯一恢复动作。

因此后续重点不是继续增加原子积木，而是一个项目级 `deployment handle`：prepare 一次
返回 host、Connector、model/knowledge/Program、Secret、workspace、runtime binding、
retry attestation 和资源状态；失败可续接，publish 原子部署，stop 一次释放。完整债务与
验收目标见 `V04_13_AGENT_FIRST_REAL_PROJECT_HARNESS_REFACTOR.md`。

## 九、资源、可见性和 Token

- 六个成功快跑应用都保存在同一平台 state root，可在一个应用列表中查看；列表目前
  共 8 项，额外两项是项目一的历史尝试，不应冒充新的项目。
- 项目二至六的客户容器和代理均已停止；当前 `docker ps` 为空，没有后台项目容器继续
  占用 CPU/内存。
- 平台本体保留一个本机进程监听 `127.0.0.1:18100`，用于用户继续检查这些应用；它不是
  Docker 工作负载。
- 本轮由当前 Codex 直接执行，运行环境没有向会话暴露权威 token counter，因此 token
  记录为 `unavailable`，没有估算、没有写 0，也没有调用 Lilies 模型。单次 Lilies 未来
  运行仍应硬限 1,000,000 token，并在 900,000 时强制收尾。

## 十、下一步结论

平台已证明六类复杂工作流都能在十分钟内重建并发布；四类在本轮取得完整新业务验收，
一类因部署证明缺失为 11/12，一类因客户环境准备失败没有 Seed 结果。下一步应先把这份
经验交给真正的 Lilies 冷启动复跑，验证 Prompt/Skill 是否能复现速度；同时把统一项目
deployment handle、desired-state apply、可观察 Builder 会话和稳定环境 prepare 作为
后续大重构，而不是继续增加项目专用积木。
