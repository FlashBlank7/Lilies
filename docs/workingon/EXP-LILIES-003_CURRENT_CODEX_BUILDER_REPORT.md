## 二、题目和真实业务场景

客户是一个使用 Home Assistant 管理门禁和环境传感器的小型设施。值班人员希望：
门刚打开时不要立即打扰；如果持续打开五分钟才通知；提前关闭则不通知。客户还
要求平台升级、重启或 Home Assistant 暂时断线时，这个等待不能消失或重复。

这不是一个单纯“定时五分钟后调用 HTTP”的题。真实业务风险包括：

- 同一个打开事件可能因为重连而重复到达；
- 较旧的关闭事件可能晚于较新的打开事件到达；
- 两扇门同时等待时不能共享状态；
- 平台可能在等待期间重启；
- Home Assistant WebSocket 会断线，需要重新鉴权和订阅；
- 到期时必须重新读取当前门状态，不能相信五分钟前的状态；
- 通知服务可能暂时 503，也可能因凭据错误永久 403；
- 高风险设施动作不能和普通通知混在一起自动执行。

生产规则是持续打开 300 秒。公开调试和 Seed 为缩短测试时间使用 0.3 至数秒，
但检查的是同一个逻辑期限、持久状态机、恢复轨迹和外部副作用，不是由测试脚本
睡眠后手工模拟到期。

客户向 Builder 提供公开需求包、Home Assistant WebSocket 和 REST 合同、允许
监控的实体范围、通知系统合同、工件 schema 和积木手册。Builder 不读取平台
数据库、隐藏 Seed 明细或 oracle，也不通过项目专用平台代码寻找答案。

## 三、工作流是怎么搭建的

工作流先把“事件接收”和“业务决定”分开。平台维持一条经过鉴权的 Home
Assistant WebSocket 订阅，把客户消息转换为统一事件输入；工作流只处理明确
授权的实体、事件身份、时间和状态。断线后平台重新鉴权和订阅，但已经接收的事件
和等待状态不依赖这条网络连接的内存。

一条状态事件按下面的业务过程处理：

1. 先判断事件属于普通状态变化、平台发出的期限到期，还是人工动作请求。未知
   事件安全结束，不进入任何写操作。
2. 对普通状态变化，先核对实体是否在当前授权清单内。未授权实体形成拒绝结果，
   不建立等待，也不访问通知系统。
3. 门打开时，用“业务类型 + 实体身份”建立稳定的等待身份。等待保存打开事件、
   事件时间、逻辑到期时间和到期时要重新运行的输入。
4. 同一个打开事件再次到达时返回“重放”，不新增第二个等待。另一扇门使用另一
   个身份，因此可以并发等待而不覆盖。
5. 门关闭时，只允许比当前打开更新的事件取消等待。过旧关闭会留下
   `stale_ignored` 轨迹，避免乱序消息错误取消较新打开。
6. 到期不是直接发送通知。平台先唤醒同一个已发布工作流，工作流再调用 Home
   Assistant REST 读取实体当前状态。已经关闭就完成等待并交付零通知；仍然打开
   才进入通知写入。
7. 通知使用原始打开事件作为稳定幂等身份。暂时 503 只做有界重试；401/403
   不重试并进入安全失败结果。成功和失败分支互斥，不能同时生成“通知成功”和
   “通知失败”。
8. 每个结果把通知决定、逻辑期限、当前状态、写入回执和恢复信息保存成带运行
   来源的 JSON 工件。不同运行使用独立工件目录，避免同名文件互相覆盖。

高风险动作走另一条明确分支：

1. 收到动作请求后先暂停，向复核人展示动作和实体；
2. 拒绝时直接形成 `attempted=false` 的结果，外部动作接口完全不调用；
3. 批准时才向受限动作接口发送一次请求，并保存客户系统的接受或拒绝结果；
4. 无论批准还是拒绝，项目都不调用 Home Assistant 设备服务。

Home Assistant 负责真实事件、当前实体状态、鉴权和重连对象；受控通知系统负责
记录实际外部副作用。项目脚本只负责环境准备、故障注入和核对客户系统状态。
事件判断、等待、到期重查、重试、人工暂停和结果交付都由发布工作流完成。

## 四、实际处理的业务逻辑

| 业务场景 | 输入如何设计 | 应做出的决定 | 允许的外部影响 | 实际结果 |
|---|---|---|---|---|
| 持续打开 | 真实 WebSocket 收到门从关到开，到期时 REST 仍为开 | 完成持久等待并通知一次 | 通知系统写一次 | 通过，恰好一条通知 |
| 提前关闭 | 建立等待后收到更新的关闭事件 | 取消等待 | 零通知 | 通过 |
| 重复打开 | 相同事件身份连续提交两次 | 第一次建立，第二次标记重放 | 不增加通知 | 通过 |
| 乱序关闭 | 较新的打开后到达更旧的关闭 | 忽略旧关闭，保留等待 | 零即时写入 | 通过 |
| 两门并发 | 两个实体在相近时间打开 | 分别等待、分别通知 | 每个实体各写一次 | 通过，无串线 |
| 平台重启 | 等待未到期时停止并恢复 Lilies | 从持久状态恢复，到期后继续 | 最终通知一次 | 通过，恢复计数为 1 |
| Home Assistant 重启 | 停止并恢复 Home Assistant | WebSocket 重连、重新订阅并处理后续事件 | 后续合法通知一次 | 通过 |
| 到期前实际已关闭 | 到期输入仍来自原打开，但 REST 当前状态为关 | 安全完成，不通知 | 零通知 | 通过 |
| 通知 403 | 临时换成无权限凭据 | 不重试、不伪装成功、走失败结果 | 零通知 | 通过 |
| 通知 503 | 控制服务让第一次请求返回 503 | 重试一次，随后成功 | 最终只写一次 | 通过 |
| 人工拒绝动作 | 动作请求暂停后复核人拒绝 | `attempted=false` | 零动作 | 通过 |
| 人工批准动作 | 动作请求暂停后复核人批准 | 调用一次受限动作接口 | 一个接受的业务动作 | 通过 |

## 五、中间处理结果和最终输出

中间状态可以从平台公开运行和 trace 逐步检查：

- 订阅状态记录当前是否连接、处理事件数、重连次数和最近错误；
- 每个实体的等待记录保存来源事件、逻辑期限、状态、运行身份和恢复次数；
- 等待历史分别记录建立、重放、乱序忽略、取消、调度、恢复、到期和完成；
- 到期运行保存重新读取的 Home Assistant 当前状态；
- HTTP trace 保存重试次数。403 为 0 次重试，单次注入 503 为 1 次重试；
- 人工 trace 保存暂停节点和恢复值；
- 外部系统保存实际通知或动作，因此平台输出不能单方面声称写入成功。

最终交付按业务结果形成：

1. **通知决定**：实体、原始打开事件、逻辑期限、到期当前状态、是否通知、
   幂等写入回执和设备服务动作计数；
2. **持久定时与恢复轨迹**：建立、重放、乱序、取消、调度、恢复和完成；
3. **人工动作回执**：是否请求、是否批准、是否尝试、是否被客户系统接受；
4. **运行工件**：每条终止路径产生独立 JSON 文件，带应用、运行和生成步骤来源。

发布后的公开和 Seed 运行都显式指定 version 2，不是运行草稿。Seed 三轮合计
产生 60 份工件；公开关键结果也有独立工件和客户系统记录。

## 七、Seed 设计和验收含义

公开调试会暴露固定实体和事件顺序，单靠它不能排除 Builder 写死设备名称、依赖
固定事件身份或让不同运行共享状态。因此项目使用 Seed 3301、3302、3303。
每次尝试还加入新的 nonce；即使同一个 Seed 重跑，也会生成全新的实体、事件和
动作身份，不会清空真实持久状态来刷通过。

每个 Seed 覆盖八类业务：

1. 持续打开到期通知；
2. 提前关闭取消；
3. 相同事件重放；
4. 旧关闭乱序忽略；
5. 两个随机实体并发；
6. 通知权限拒绝安全停写；
7. 一次 503 后恢复且只写一次；
8. 人工拒绝零动作和人工批准一次动作。

平台重启和 WebSocket 断线会改变共享基础设施，不适合三个 Seed 同时或连续注入，
因此它们在公开 debug 中各做一次真实重启验证。Seed 重点验证业务值变化、状态
隔离和副作用计数。

验收进程把随机值送入真实 Home Assistant、公开工作流 API 和受控客户系统。
汇总报告只保存类别、计数和布尔结论，不保存精确随机身份或 expected/actual
明细。精确输入仍保留在平台运行记录中供事后审计，因此报告不应被误解为不可
追溯的“只报绿灯”。

| Seed | 业务类别 | 发布版运行 | 人工暂停 | 工件 | 结果 |
|---|---:|---:|---:|---:|---|
| 3301 | 8 | 20 | 2 | 20 | 8/8 通过 |
| 3302 | 8 | 20 | 2 | 20 | 8/8 通过 |
| 3303 | 8 | 20 | 2 | 20 | 8/8 通过 |

三个 Seed 全绿证明 version 2 没有依赖公开实体、固定事件身份、固定动作名或单一
运行状态，并在本题冻结的重复、乱序、并发、权限、暂时失败和人工决定范围内
没有可见串线。Seed 生成器和验收器仍由同一仓库上下文编写，所以这是受控密封
回归，不是第三方独立黑盒认证。

## 八、失败、偏差和保留证据

项目没有用最终全绿覆盖调试失败：

1. 第一批应用图在公开测试中把平台保留的内部事件字段当成普通输入，测试入口
   正确拒绝。修正 Builder 测试输入后，外部调用仍不能伪造该字段。
2. 早期不同运行都写同名工件，生产事件并发时发生覆盖。平台改为每个运行独立
   工件目录；工作流文件名没有改成随机值来绕过。
3. 第一次提前关闭复用了一个已有待处理实体，结果被旧等待污染；该次明确排除，
   使用新实体重验后通过。
4. 第一次重启测试的等待在停止前已经到期，不构成恢复证据；第二次用更长期限，
   停止时确认仍 pending，恢复后 recovery_count 为 1，才计为通过。
5. Home Assistant 重启后的第一条合成状态没有初始化旧状态，严格映射没有把它
   当成合法开门；建立关闭基线后，新事件被正常处理。该初始化竞争保留在公开
   摘要的排除记录中。
6. 第一次 403 运行发现运行器同时放行成功和错误两条路径。工作流 version 2
   一行未改；平台补上通用错误分支互斥规则并加回归测试后，同一发布版重验为
   零重试、零通知、只走失败路径。
7. Seed 3301 首次只有 4/8，因为验收器在计时器中间步骤标记完成后立即读取整条
   运行，终点和工件尚未落盘。四个同步场景通过，四个期限场景一起失败。修正
   共享测试框架等待关联运行最终状态后，以全新随机身份重跑为 8/8。首次失败
   汇总保留为 attempt 1。
8. 一次人工终端脚本使用 zsh 保留变量名 `status`，脚本在运行已暂停后退出。
   该运行从公开 API 正常恢复，没有重建工作流。
9. 一次服务重启把状态根目录误当成数据库目录，空服务返回 version not found。
   正式应用没有被修改；改用 `platform-data` 后恢复。后续环境框架必须从锁定
   描述恢复路径，不能人工拼接。
10. 用户发送新消息后，工具回收了前台 PTY，平台和测试服务同时停止。持久数据
    完整，重启后 collector 12/12。这个是测试进程托管问题，不是工作流恢复失败。

最终没有未解释的业务差异。仍有证据债务：未做高吞吐性能测试、真实移动推送、
物理门设备和第三方独立审计。

## 九、平台补能与膨胀控制

Builder 在公开积木和 OpenAPI 中确认：平台原有日历式定时只能按固定时间触发，
运行内 checkpoint 只能恢复一条已经启动的运行；两者都不能订阅外部 WebSocket、
为每个业务实体建立独立期限，并在进程重启后主动唤醒发布工作流。这是事件驱动
业务的通用缺口，不是 Home Assistant 专用答案。

最小产品补能是一个可选事件自动化能力包：

- 一个宿主无关的 WebSocket 订阅服务：鉴权消息、订阅消息、匹配条件、字段映射、
  事件身份和重连策略全部由公开配置提供；
- 一个宿主无关的持久事件计时服务：按业务主体建立、重放、取消、完成和恢复；
- 两个工作流入口能力：接收外部订阅事件、操作每事件持久计时器；
- 六个公开管理/检查接口，用于创建、查看和启停订阅，以及查看计时器；
- 一个 WebSocket 客户端依赖。

平台代码不包含 Home Assistant 实体名、事件字段路径、通知端点、动作名或本题
答案。这些映射只在项目工作流配置中。相同能力可以接 MQTT-to-WebSocket 网关、
设备管理系统、仓库告警流或其他事件源。

另外三项通用运行修正不增加积木：

- HTTP 只对 408、429 和 5xx 有界重试，401/403 不重试；
- 错误分支输出时，隐式成功边不再同时执行；
- 工件按运行隔离，多个生产事件可使用同一业务文件名。

项目净增加 **1 个可选事件服务、2 个工作流能力、6 个公开管理接口、0 个 Home
Assistant 专用积木**。HTTP、分支和工件修正复用现有能力，积木数为 0。受控
通知系统的 503 故障开关只存在于测试夹具，不进入平台目录。

这比拆出“连接 Home Assistant、订阅 state_changed、创建门计时器、取消门
计时器、发送门通知”等多个项目积木更克制。后续如果 MQTT、Kafka 等协议需要
独立接入，应作为可安装适配器复用同一个事件/计时合同，而不是继续扩充核心画布。

## 十、可复用测试框架

为减少人工开关和终端拼接，本项目增加了一个小型真实项目测试工具层：

- 统一调用公开 HTTP 和平台 API；
- 统一启动发布版运行并等待最终状态；
- 统一处理一次人工暂停与恢复；
- 统一等待持久计时器，再等待其关联运行真正结束；
- 统一读取 trace 和写聚合证据。

项目三脚本只保留 Home Assistant 状态准备、场景序列和客户系统判定。第一轮 Seed
暴露的“计时器完成不等于整条运行完成”已经进入共享等待逻辑，后续项目不应再
重复踩坑。

环境进程托管仍需继续最小完善：由环境锁提供端口、数据目录、工作区、健康检查
和启动命令，一条命令检查并恢复服务。当前已冻结这些信息，但跨用户消息的守护
进程生命周期还没有完全自动化；这不会降低已完成业务证据，但会影响测试体验。

## 十一、Builder 表现和 token

当前 Codex 直接担任 Builder。搭建过程只读取公开需求包、公开 schema、积木手册
和公开 OpenAPI，只通过平台公开 API 创建应用、增加步骤、连接、增加测试、运行
和发布。没有启动仓库中的外部 Codex Builder，没有读取隐藏 Seed 文件、oracle、
平台数据库或通过源码寻找题目答案。

Lilies 模型调用次数为 0，Lilies token 为 0，因此单次 1,000,000 token 上限没有
触发。当前 Codex 会话的 token 不属于 Lilies 平台账本，不能伪装成 Lilies 消耗。

本项目最重要的 Builder 经验是：

- 先把完整事件状态机画清楚，再统一处理重复、乱序、重启和权限，不按单条案例
  疯狂迭代；
- 到期条件必须用客户系统当前状态重新确认；
- 计时器状态、工作流状态和客户系统副作用是三份证据，不能只看其中一个；
- 403 和 503 的业务语义不同，重试策略不能一刀切；
- 测试器必须等待业务终点，不能把中间状态当最终结果；
- 只有能跨宿主复用的缺口才进入能力包，客户字段映射留在工作流。
