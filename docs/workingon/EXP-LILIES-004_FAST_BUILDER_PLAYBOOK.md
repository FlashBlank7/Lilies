## 二、工作流解决问题的逻辑

设备事件到来后，工作流先去 ThingsBoard 读取真实的温度、振动、电流、压力和转速，
再检查字段、单位、范围、时间、新旧顺序和事件身份。只有合格数据才能进入模型。

生产流程只调用当前已批准的模型部署。高风险且置信度足够时自动创建或更新告警；低
风险时不告警；风险不确定或置信度不足时暂停，由可靠性工程师批准或拒绝。拒绝后零
写入。重复事件复用同一业务身份，不能复制告警。

每条路径最后汇总事件、校验、预测概率、置信度、模型 ID/版本/摘要、部署修订、人工
决定和 ThingsBoard 回执，并生成设备决定、模型证据和漂移报告三份工件。漂移只报告，
明确记录不触发在线学习；任何分支都不允许 Device RPC。

模型准备与生产流程分开：Builder 可以训练、导入候选或微调，必须在独立验证集评估，
生成模型卡并获得批准后才能提升；生产事件只使用部署，不训练。提升 v2 和回滚 v1 都
用真实工作流重新运行确认，不能只看模型登记表。

## 三、任务和 Seed 设计

公开 9 类案例覆盖低风险、高风险、人工批准、人工拒绝、单位错误、缺字段、过旧、乱序
和重复。随机 Seed 额外加入数值越界、写入前临时 503、权限 403，并随机化设备、事件、
特征组合、出现顺序和漂移窗口。

通过 Seed 的意义不是“脚本没崩溃”，而是同时满足：逐条业务决定正确、人工暂停次数
正确、实际告警数量正确、模型血缘正确、三类工件齐全、漂移等级正确、503 安全恢复、
403 安全停止且 Device RPC 为零。

## 四、快速 Prompt

```text
这是“模型准备”和“生产推理”严格分离的预测性维护项目。

先写业务不变量：
1. 真实遥测先校验字段、类型、单位、范围、时间、顺序和重复，再调用模型。
2. 生产工作流只能调用明确批准、带版本和部署修订的模型；不得训练或自动换模型。
3. 高风险且高置信自动告警；低风险零告警；不确定或低置信先人工复核。
4. 人工拒绝、无效、过旧、乱序、重复和权限拒绝都不能制造错误副作用。
5. 只有平台能证明写请求尚未到达客户系统时，503 才允许有界重试。
6. 每条结果追溯到事件、发布版本、模型版本、部署修订、人工决定和宿主回执。
7. 漂移只生成报告，不触发在线学习；任何路径禁止 Device RPC。

平台操作顺序：
- 先取得一个项目 deployment receipt，确认 ThingsBoard、OpenAPI Connector、Secret、
  模型服务和安全重试证明均 ready；
- 用授权训练集训练或导入候选，以独立验证集评估，批准 v1；
- 一次提交完整生产工作流和真实强制测试；
- 一次覆盖正常、无效、乱序、重复、人工、503、403 和工件交付；
- 微调候选 v2，评估、批准后实际运行，再回滚 v1 后实际运行；
- 全绿才发布，用发布版本再做一次真实客户系统写入。

不得用模型登记成功代替生产实际使用，不得用工作流成功代替告警数量正确，不得用
测试代理返回 503 代替平台已验证“未写入”的证明。
```

## 五、快速使用平台的经验

1. 模型生命周期先准备到“批准部署 ready”，再搭生产图，避免一边改图一边变模型。
2. OpenAPI 生成后必须比较 requested operations 与 generated operations；注册成功不代表
   所有请求的接口都生成了。
3. 先跑一组覆盖全部业务分支的公开验收，再做 v2 提升和回滚。模型变化各只需要一条
   高风险真实运行，不必重跑九类业务。
4. 发布前把已经通过的真实运行固化成强制测试；发布后必须指定 version 再运行。
5. 共享环境不能使用固定设备名、固定 deployment 名或假定空租户。所有夹具身份应由
   当前 run/generation receipt 命名，重复运行才能快速收敛。

## 七、可靠交付 Prompt

```text
按六层验收预测工作流：
A. 数据：真实客户遥测、单位和时间有效。
B. 模型：独立评估、明确批准、推理轨迹中的版本与当前部署一致。
C. 决策：高/低/不确定、人工批准/拒绝、无效/旧/乱序/重复全部正确。
D. 副作用：告警数量和业务身份正确；403 零写；503 只有可信未送达证明才重试。
E. 交付：三份工件完整且能回溯事件、模型、人工和宿主回执。
F. 发布：强制业务测试通过，发布版指定 version 实际运行；Device RPC 永远为零。

任何一层失败都降低声明上限。把同根失败聚合为一个原因，先整体修复部署合同，再只跑
受影响类别；不要为一个红项连续改业务图。
```
