# 智能体/工作流生成平台产品意图偏移自查报告

> 日期：2026-07-21
> 审计性质：产品、架构、场景、实验、演进控制与记忆的严格自查
> 审计结论：存在严重、系统性的产品意图偏移
> 纠偏依据：用户本轮明确指令及仓库原始材料
> 适用对象：股东、产品负责人、架构负责人、实验负责人和后续执行者

## 1. 执行结论

本项目没有“完全做废”，但已经发生了一个严重的方向倒置：

**原始目标是建设一个对标 Dify、又能由 AI 自动生成工作流的平台，用于传统企业的真实 AI 化；后来的演进却把 Claude/Codex 式智能体架构、Harness、调度、Connector、治理和自身演进机制逐步当成了产品主线。**

这不是某一张场景表措辞不佳，而是五层同时偏移：

1. 目标客户从“尚未 AI 化的传统企业”消失。
2. 客户问题从工业 ML/DL、RAG、数据与系统交付，退化成代码智能体、GitHub、爬虫和治理压力测试。
3. 支撑平台可靠性的技术底座，被误写成产品本身。
4. 实验分母选择了仓库当前容易做的任务，而不是客户真正要解决的任务。
5. 演进控制准确验证了一个不完整的意图登记，产生了“36 个意图全部完成，但产品主能力仍未开始”的假闭环。

2026-07-20 形成的 `P-WF-01` 至 `P-WF-07` 平台实验计划进一步放大了该偏移。pytest issue 接诊、CI 诊断、开源项目发布决策、NetworkX 性能修复、GitHub 情报和写回都可以是软件工程实验，但不能作为传统企业 AI 工作流平台的核心场景总表。该计划及其平台场景 JSON 已从仓库撤回。

## 3. 原始产品意图

### 3.1 产品形态

`PRELOAD_PROMPTS.md` 明确把项目描述为“Claude Code Agent 框架作为大脑 + Dify 风格积木”，并要求：

- 用户用自然语言描述需求。
- AI 团队通过受控积木 API 增量搭建工作流。
- 产物可视化、可编辑、可测试、可发布。
- Draft 可继续人工调整，发布版本不可变。

这里的正确关系是：

```text
Dify 类产品范式
  + 莉莉丝自动理解、询问、搭建、测试和修复
  + 可复用的 Agent 智能底座
  = 智能体/工作流生成平台
```

Claude/Codex 架构是“怎么让莉莉丝和复杂工作流更聪明”，不是“平台最终卖给谁、解决什么”。

### 3.2 目标客户与价值

初始讨论反复出现以下表述：

- 平台是给企业 AI 转型使用的应用。
- 先了解企业已有工作流程，再把它自动化或 AI 化。
- 业务导向，积累客户成熟工作体系形成的模板。
- 聚焦工业和实际技术问题。
- 需要回答训练出的模型在哪里、如何部署、如何形成 API、沙盒生命周期如何管理。
- 具体项目可能就是实现某种机器学习模型。

因此，产品价值不是“我们有完整 Agent 架构”，而是：

```text
传统企业真实需求
  -> 莉莉丝补全需求
  -> 自动生成可编辑工作流
  -> 数据/模型/RAG/规则/人工/系统协同运行
  -> 得到业务结果、文件或系统写入
  -> 经过验证后沉淀为行业工作流资产
```

### 3.3 用户举出的两个例子及后续纠正

1. 电梯故障自动检测：核心是机器学习模型及其数据、推理、告警和人工复核链。
2. 光纤工艺参数继承/预测：根据历史测试参数和拉丝过程参数做 ML/DL 判断，生成 Excel，并上传指定接口。

这两个例子说明平台并不是“所有事情都交给 LLM 文本回答”。它必须承载实际数据、算法模型、确定性工件和企业系统交付。

用户随后明确纠正：它们只是用于解释任务性质的例子，不是不可删除的产品锚点。正确做法是从例子抽象接入与结构化、检测与诊断、预测与决策、检索与解释、优化与规划、交付与执行、监控与适应等任务原型，再选择企业和个人的真实需求以及对应项目。

## 4. 当前项目事实

### 4.1 已有底座

当前仓库有一批真实且有价值的基础能力：

- 自然语言需求补全和莉莉丝 Builder。
- Application、Draft、不可变 Version、Run 和 Trace。
- 可视化工作流、revision、幂等写入和自然语言编辑。
- 工作流运行时、Agent 多轮工具反馈、人工暂停恢复。
- 测试、验收修复、客户运行界面和结构化结果展示。
- 调度、持久任务、Connector、租户隔离、治理与证据登记。

这些能力不是应当删除的错误代码。问题在于它们被当作产品闭环，而没有继续服务原始客户问题。

### 4.2 当前积木投资结构

运行 `build_block_registry()` 得到：

| 类型 | 数量 |
| --- | ---: |
| Agent 架构积木 | 26 |
| 业务工作流积木 | 19 |
| 历史兼容积木 | 1 |
| 合计 | 46 |

当前代码级快捷模板只有 4 个：

1. `codex_like_workspace_agent`
2. `claude_like_coding_agent`
3. `daily_web_collection`
4. `customer_system_embedding`

这 4 个模板完整暴露了近期路线：代码智能体、采集、嵌入，而不是传统企业 ML/RAG 业务。

### 4.3 历史模板的真实状态

根目录有 11 个 JSON 模板：

- 10 个可以被 `TemplateStore` 读取，但全部状态为 `legacy_unverified`。
- `drone_intervention_v1` 因 category、输入输出和版本 schema 不兼容，当前不能加载。
- `app_automation_workflow` 通过模型校验后仍有不可达节点。
- `data_analyzer` 的输入是 `data_description` 文本，核心步骤是让 LLM 生成分析，再抽取文本字段。它没有读取 CSV/JSON 文件，没有真实统计计算，没有机器学习，也没有数据 lineage。

因此，“有 data_analyzer 模板”不能证明平台已经具备数据分析或工业数据能力。

### 4.4 当前缺失的一等产品能力

代码与注册表中没有形成一等闭环的能力包括：

- 文件、表格、传感器、图像等企业数据接入与类型系统。
- schema、缺失值、异常值、单位、时间对齐和数据质量门。
- 特征工程、参数 lineage 和数据版本。
- 机器学习/深度学习训练或已有模型导入。
- 模型评估、注册、部署、推理、阈值、监控和再训练。
- RAG 的解析、切分、Embedding、向量索引、检索、重排、权限过滤、引用和评测。
- 工件存储、Excel 生成与内容校验。
- 文件上传、API 交付回执及业务补偿。

通用 `tool`、`http_request` 和 `llm` 可以暂时承载原型，但不能被宣称为这些领域能力已经产品化。

## 6. 偏移是怎样形成的

### 6.1 v0.2.x：底座探索逐步吞噬产品探索

v0.2.0 的 README 仍明确写着“面向 AI 转型”“固化工作流大于提升单个 Agent”。早期的模板复用、Builder、工作流运行和真实验收都与产品方向一致。

但 v0.2.x 后续出现大量围绕 Harness、worker、lease、secret、egress、复杂度路由、监控和自动演进的微版本。它们解决了真实工程问题，却长期没有回到工业客户垂直任务验证。

结果是：平台越来越会监管自己、验证自己、演进自己，但没有同步扩大能为客户处理的数据、模型和知识任务。

### 6.2 v0.3.x：可用性修复必要，但场景仍未校正

v0.3.x 修复了应用入口、画布、自然语言编辑、客户运行界面和验收可读性。这是必要工作。

但该阶段一度用日语学习者做客户旅程，后来又按用户要求删除。这个事件已经显示场景选择缺少稳定产品约束：只要一个示例适合展示 UI，就可能进入路线，而不必证明它属于目标客户。

### 6.3 v0.4.x：能力模型正确，具体路线被三个技术场景锁定

能力边界报告中的 F/G/X、E0-E5、证据等级、Quick/Guided/Governed、三类界面和 Connector 等分析有架构价值。

问题在于报告只具体展开：

- Codex-like 工作流
- 每日网页采集
- 客户系统嵌入

报告虽在能力目录中提到 RAG 和 artifact store，却没有把传统企业、ML/DL 生命周期、真实工业数据、Excel 交付和工业模板列为产品意图。随后这三个示例被写入 `SCENARIO-001` 至 `003`，并成为 v0.4.4、v0.4.9、v0.4.10 的实际路线。

### 6.4 演进控制把局部报告升成最高产品权威

原 `AGENTS.md` 写明：

- 能力边界报告 Campaign 是最高目标。
- Program Charter、意图登记、阶段报告和合同依次执行。
- 只有登记中的稳定意图可以成为任务来源。

Program Charter 又把产品写成“model-intelligence-first workflow construction and execution product”。

这套机制在程序上很严谨，但它没有外部的客户北极星校验。于是：

```text
范围偏窄的报告
  -> 不完整的意图登记
  -> 严格 Stage Contract
  -> 真实代码与测试
  -> 36/36 终态
  -> 错误地接近“产品完成”
```

问题不是验证器不严格，而是它只验证“登记的东西有没有完成”，不能验证“该登记是否遗漏了产品最重要的东西”。

### 6.5 选择现有优势而不是客户需求

当前仓库最成熟的是 Python、Agent Runtime、测试、GitHub 类代码任务、调度和 Connector。2026-07-20 的实验计划据此选择了 pytest、Click、NetworkX、Locust、Sphinx 和 Django。

这些项目容易复现、有隐藏测试、便于在沙盒里做严格实验，因此适合莉莉丝代码智能体实验。但把它们进一步改写成平台工作流的 issue 接诊、CI 诊断、发布决策和 GitHub 写回，是典型的“从现有工具倒推客户”，而不是“从传统企业需求推导平台能力”。

## 7. Memory 与 Skill 责任审计

### 7.1 Memory

Memory 保存了以下有用事实：

- Claude 架构重构为积木。
- Dify 作为平台参考。
- Builder、WorkflowRuntime、Harness 和真实付费模型验证。

但 Memory 没有稳定保存：

- 目标客户是尚未 AI 化的传统企业。
- 平台首要价值是自动生成真实企业 AI 工作流。
- 工业 ML/DL、RAG、数据、Excel 和客户接口是主产品场景。
- Codex 实验必须与平台客户场景分开。

因此 Memory 不是唯一原因，但它在跨回合恢复时放大了偏移。本次已新增纠偏记忆说明，要求以后先恢复产品北极星。

### 7.2 历史 Skill

历史 `lilies-evolution-development` Skill 主要管理：

- stage report 任务来源
- current-design 展开
- workingon 证据
- 验证、归档和自动继续

它没有定义传统企业客户或工业 AI 场景，因此会忠实推进阶段报告中的局部目标，是偏移的历史放大器。

但是该 Skill 已被用户删除，当前仓库明确禁止恢复、编辑或使用它。它不是当前仍在运行的直接原因。本次不会恢复或修改该 Skill，纠偏放在产品北极星、仓库指令、Charter、意图登记、恢复钩子和 Memory 中。

## 8. 哪些成果应保留

严肃纠偏不等于推翻全部 v0.2.x 至 v0.4.x 工作。下列资产是未来企业工作流必需底座：

- 莉莉丝的需求理解、选项式追问、搭建和修复。
- 可编辑 Draft、版本、运行和 Trace。
- 工作流与 Agent Runtime。
- 人工暂停恢复、权限、沙盒和预算。
- 持久调度、重试、幂等和取消。
- Connector、租户、回执和补偿。
- 验收证据、失败解释、客户运行界面和治理。

需要改变的是它们的地位：从“产品已经完成的主要场景”改为“支撑企业 ML/RAG/业务工作流的基础设施”。

莉莉丝对标 Claude/Codex 的代码任务实验也应保留，但必须作为独立的次级实验线：

- 它回答莉莉丝的智能体架构能做什么。
- 它帮助区分模型智能和架构能力。
- 它不能进入平台生成工作流解决传统企业问题的成功率分母。

## 10. 修正后的实验结构

以后必须分成三个不能互相代替的实验线：

| 实验线 | 首要问题 | 是否进入平台客户能力分母 |
| --- | --- | --- |
| A. 平台生成工作流 | 能否从传统企业需求生成并运行真实 ML/RAG/数据/系统工作流？ | 是，首要分母 |
| B. 莉莉丝智能体 | 莉莉丝作为 Claude 式智能体能否完成代码或复杂工具任务？ | 否，单独报告 |
| C. 模型/架构归因 | 结果来自模型能力还是 Agent/Workflow 架构与确定性工程？ | 不直接计成功率，用于解释 A/B |

首批平台任务组合必须覆盖不同的通用原型，而不是固定行业名称：

1. 检测与诊断。
2. 预测与决策。
3. 文档抽取、检索与解释。
4. 约束优化与规划。
5. 文件/API 交付。
6. 持续监控与受控更新。

权威任务和 GitHub 项目组合见 `docs/platform_generated_workflow_real_project_experiment_design_2026-07-21.md`。

只有在真实需求、数据或可替代公共数据、模型基线、独立 oracle 和系统契约冻结后，才能宣称正式实验开始。

## 11. 当前真实结论

截至本次审计：

- 平台已经具备较强的 AI 自动搭建、可编辑工作流、运行、验收、调度、Connector 和治理底座。
- 莉莉丝的 Claude/Codex 式能力只完成了候选仓库故障基线复现，尚未完成正式求解。
- 平台尚未正式完成任何工业 ML/DL 工作流实验。
- 平台尚未正式完成任何企业 RAG 工作流实验。
- 平台尚未正式完成 Excel 工件生成并上传企业接口的端到端实验。
- 用户举出的电梯故障检测和光纤参数预测例子都还没有形成可运行的正式工作流，但它们不再被视为产品完成的固定必要项目。
- 因此不能向股东声明平台已经证明能解决传统企业核心 AI 化问题。

可以向股东诚实说明的是：

> 平台基础设施已经完成了相当规模的建设和本地验证，但产品场景选择发生了偏移。项目已完成治理纠偏，重新把企业和个人的真实数据、ML/DL、RAG、预测优化、文档工件和系统交付设为分开验证的任务对象；真实结果仍待正式实验。

## 12. 后续纪律

1. 不再从当前最容易运行的仓库反推平台主场景。
2. 不再用一个技术报告单独定义产品北极星。
3. 每个阶段合同都要带目标客户、真实问题、数据/模型/系统、交付物和业务 oracle。
4. 技术底座和客户能力分开记账。
5. Build、结构验收、fixture 和本地集成分别报告，不互相冒充。
6. 平台实验与莉莉丝代码智能体实验分开计算。
7. 没有真实数据时可以做契约和组件实验，但必须标成非业务闭环。
8. 产品意图登记缺项时，验证器通过也不得宣布产品完成。
