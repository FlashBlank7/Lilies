# 原语即耦合：Harness+LLM 作为智能体架构的原子单元

**蒋之骏** · 2026年6月

---

## 摘要

AI 智能体（Agent）领域缺乏一个公认的内涵式定义。"Agent"在不同框架中意味着完全不同的东西——一次 LLM 调用、一个多轮自主循环、一个内嵌推理的可视化节点。这些争论陷入循环，因为各方依赖外延式定义（列举属性），而非内涵式定义（识别不变量结构）。本文提出一个统一范式：**任何智能体系统的原子单元是 Harness+LLM 复合体。** Harness 提供确定性的、可测试的、可组合的执行基础设施。LLM 提供非确定性的、自适应的语义推理。我们证明，所有主流 Agent 框架中每一种"让积木更聪明"的优化，在结构上与被它声称要改进的复合体完全相同——鸡和蛋是同一种东西，只是粒度不同。我们通过将复合体映射到 LangGraph、Dify、AutoGPT、Claude Code、OpenAI Agents SDK 和 Lilies 六个框架，展示了每个框架的设计选择都可归结为唯一一个决策：把复合体放在哪里。该范式产生可验证的预测，规定正确的优化方向，并澄清为何更好的 LLM 能在零架构变更下提升整个平台。在 Lilies 上的参考实现提供了 142 项测试全部通过的定量验证。

## 1. 引言

### 1.1 定义之困

什么是 Agent？

问十个从业者，你会得到十一种答案 [7, 8, 3, 1, 10]。每种定义都是**外延式的**——它列举某个特定系统恰好具有的属性。每种定义在自己的系统内是正确的。每种定义都无法泛化。

根因不是 Agent 系统太过多样而无法统一。根因是**"Agent 是什么"这个问题预设了一个不存在的特权粒度。** Agent 系统不是原子事物。它们是复合结构，同时在多个层次上出现。

### 1.2 鸡和蛋是同一种东西

每一种试图在原子层面让 Agent 框架"更聪明"的尝试，都再现了同一个模式：

```
尝试: 在 if_else 积木内部嵌入基于 LLM 的路由逻辑
结果: 一个微型 question_classifier + if_else 复合体被藏进了更小的壳里
模式: 复合体是同一个。只是容器不同了。

尝试: 创建一个能自动选择策略的"万能Agent节点"
结果: 一个微型工作流编排循环被藏进了节点内部
模式: 复合体是同一个。只是壳更小了。

尝试: 让单次 prompt 完成多步推理（Chain-of-Thought）
结果: 一次 LLM 调用内部的微型推理循环
模式: 复合体是同一个。只是容器变成了 prompt。
```

**鸡（已有复合体）和蛋（被优化的原子单元）在结构上是同一个东西。** 每一种创建"更聪明的原语"的尝试，不过是在更细粒度上重建了同一个复合体。这是本文的核心洞见：Harness+LLM 复合体是不可再分的——它不能被消除，只能被移动到不同的粒度层次。

### 1.3 本文贡献

1. **一个统一范式**（§2）：Harness+LLM 作为所有 Agent 系统的结构不变量。
2. **一个鸡与蛋证明**（§3）：任何"更聪明的积木"优化都在不同粒度上重建了同一个复合体。
3. **一个跨框架映射**（§4）：通过复合体透镜分析六个主流框架。
4. **工程推论**（§5）：范式衍生的预测、规定和否决。
5. **定量验证**（§6）：142 项测试全部通过的参考实现。

## 2. Harness+LLM 复合体

### 2.1 定义

```
能力 = Harness (硬) + LLM (软)

Harness: 确定、可测试、可组合、可验证
LLM:    非确定、自适应、语义化、非确定性
```

**Harness** 是可以用单元测试验证的部分。它是验证积木配置的 JSON Schema。是保证节点 C 不能在 A 和 B 完成前执行的 DAG 拓扑。是在 `spent > max` 时拒绝执行的预算门。Harness 提供可预测性。

**LLM** 是无法用单元测试验证的部分。它是定义角色身份的系统提示词。是将消息分类为"投诉"而非"咨询"的语义推理。是从需求生成系统设计的创造性行为。LLM 提供智能。

**两者构成一个不可再分的单元。** 仅有 Harness 是确定性函数。仅有 LLM 是文本生成器。我们认为是"Agent-like"的任何系统都同时包含两者。任何一方都不能单独构成 Agent。任何一方都不能被归约为另一方。

### 2.2 粒度独立性

复合体没有特权粒度。它在每一个层次上反复出现：

| 层次 | Harness | LLM | 示例 |
|------|---------|-----|------|
| 单个积木 | JSON Schema + 端口 | model_turn 系统提示词 | question_classifier |
| 积木链 | DAG 拓扑结构 | 积木内的 LLM 调用 | 14-block Agent Loop |
| 工作流模板 | 固定积木序列 | Builder 的语义理解 | code_reviewer |
| 整个平台 | 41 积木 + DAG 引擎 | Builder + Agent Factory | Lilies |
| 元认知 | DecisionTracker 结构 | Review Agent 分析 | 提取流水线 |
| 平台边界 | JWT、Docker cgroups、配额 | 无——纯硬约束 | Platform Harness |

**不存在"原子 Agent"。只存在当前层级的 pragma——在此任务中最有用的复合体操作粒度。**

## 3. 鸡与蛋证明

### 3.1 证明结构

考虑任意 Agent 框架 F，拥有一组原子构建块 B。假设我们试图改进 F，创建一个"更聪明"的积木 b'，其内部使用 LLM 推理来做出之前需要通过组合多个简单积木才能完成的决策。

**命题**: b' 在结构上与由 B 中的现有积木构成的子工作流完全相同——只是被包裹在了更小的容器里。

**证明**:

1. 任何使用 LLM 推理的 Agent 决策需要：(a) 一个 Harness 来结构化输入并验证输出，以及 (b) 一个 LLM 来执行语义推理。
2. 这两个组件——Harness+LLM 复合体——对该决策是必要且充分的。
3. 因此 b' 内部必须包含一个 Harness+LLM 复合体。
4. 这个内部复合体是一个更细粒度上的微型工作流。
5. B 中的现有积木已经在框架的原生粒度上表达了该复合体。
6. 因此 b' = 一个 B 的子工作流，被藏进了单个积木中。

**结论**: 任何通过嵌入 LLM 推理来让积木更聪明的尝试，不过是在更细粒度上重建了同一个复合体。复合体是不可消除的——只能被移动到不同的层次。

### 3.2 具体实例

| 框架 | "更聪明的积木"方案 | 它实际上是什么 |
|------|------------------|--------------|
| Lilies | if_else 中的 `auto_strategy` 字段 | question_classifier + if_else 作为微型工作流 |
| Dify | 带内部路由的"智能节点" | 一个 Dify 工作流藏进了单个 Dify 节点 |
| LangGraph | 单节点含 Chain-of-Thought + 工具调用 | 一个 LangGraph 子图藏进了单个节点 |
| AutoGPT | 自动选择子动作的"万能工具" | AutoGPT 循环递归地藏在一个工具内部 |
| OpenAI Agents SDK | 带"自主模式"的 Agent | 一个基于 handoff 的多 Agent 系统坍缩进一个配置 |

**每个案例中：蛋变成了鸡。更聪明的原语就是更细粒度的同一个复合体。**

## 4. 跨框架映射

### 4.1 定义框架的唯一决策

每个 Agent 框架仅仅做出一个架构决策：**把 Harness+LLM 复合体放在哪里。** 所有其他设计选择都由此衍生。

| 框架 | 复合体位置 | 粒度 | 复合体的可见性 |
|------|----------|------|-------------|
| **LangGraph** [8] | StateGraph 结构中 | 图 = Agent | 代码中可见，运行时不可见 |
| **Dify** [3] | 每个节点内部 | 节点 = Agent | 隐藏在节点边界内 |
| **AutoGPT** [7] | 主执行循环中 | 循环 = Agent | 单体式，不可分解 |
| **Claude Code** [1] | 查询引擎会话中 | 会话 = Agent | 工具调用中可见，作为结构不可见 |
| **OpenAI Agents SDK** [10] | Agent 配置中 | 配置 = Agent | 在 handoff 中可见，在拓扑中不可见 |
| **Lilies** | 积木之间的连接关系中 | 拓扑中的位置 = Agent | 在 DAG 中完全可见 |

### 4.2 通过复合体透镜分析框架

**LangGraph**: StateGraph 是 Harness。节点内的 LLM 调用提供语义推理。复合体在图层面——你能看到节点和边，但 Harness+LLM 对在哪些节点调用 LLM 上是隐式的。

**Dify**: 每个节点承载自己的内部 Harness（配置表单）+ LLM（推理链）。复合体在节点层面——你无法看到节点内部的推理过程。可组合性局限于连接预构建的节点。

**AutoGPT**: 整个执行循环是一个单体的 Harness+LLM 复合体。没有分解、没有版本化、没有局部复用。循环就是 Agent。

**Claude Code**: 查询引擎将工具、权限和沙盒包裹在单一模型会话周围。复合体在会话层面。一个会话不能成为另一个会话的子组件。

**Lilies**: 积木要么是纯 Harness（if_else, budget_gate），要么是纯 LLM（model_turn, question_classifier）。复合体从它们在 DAG 中的连接中涌现。这使得复合体在每一种粒度上都是完全可见、可组合、可版本化、可测试的。

### 4.3 这个映射揭示了什么

1. **没有一个框架能消除复合体。** 每个框架都在实例化它。唯一的问题是放在哪里。

2. **框架的限制直接映射为复合体放置的错误。** Dify 的不透明性来自将复合体藏在节点内部。AutoGPT 的刚硬性来自将复合体绑定在单一循环上。Lilies 的可组合性来自将复合体放在连接关系中，使其显式化。

3. **框架之间的比较可以归结为粒度偏好的比较。** 争论"LangGraph vs Dify"就是争论"图层面的复合体 vs 节点层面的复合体"。没有对错。每个框架针对不同的用例做了优化。

## 5. 工程推论

### 5.1 范式的预测

**预测 1（Harness 改进）**: 改进确定性部分将改进所有共享该 Harness 的 Agent，无需行为变更。已证: `max_output_tokens` 8192→4096，Agent Factory 可靠性 ~60%→~85%。

**预测 2（LLM 改进）**: 改进非确定性部分将改进所有使用该 LLM 的 Agent，无需架构变更。已证: DeepSeek V4 Pro `high`→`xhigh`，Builder 速度提升 35%，Agent 提示词长度提升 73%，消除 JSON 截断。

**预测 3（单组件优化）**: 仅改变 LLM 部分而不改变 Harness，效果不可预测且受 LLM 能力边界约束。已证: 提示词工程同类模型 ±15% 波动 vs 模型升级 +73%。

### 5.2 规定

**所有优化应投向组合层**，而非积木层。不存在"更好的 if_else"——只存在"if_else 在更好的工作流中"。

**积木永远不应被变得更聪明。** 它们的智能来自拓扑位置，非内部复杂度。往积木里加 LLM 只是更细粒度上重建了复合体，却不能消除更粗粒度的那个。

**跨层优化制造架构债务。** 将 Layer 3 的能力放进 Layer 1，制造不必要的复合体重复。

### 5.3 三条飞轮

平台的长期竞争力来自三个反馈循环，都不依赖积木改进：

**发现飞轮**: 需求 → 模板搜索 → 匹配 → 展开 → 复用

**提取飞轮**: 搭建成功 → 自动提取 → 门控检查 → 合并 → 置信度↑

**推荐飞轮**: 高置信度 → 排名靠前 → 更多采用 → 更高使用量 → 更高质量分

### 5.4 LLM 杠杆

更好的 LLM 在零 Harness 变更下，同时提升每一个粒度上的每一个复合体。这是唯一能一次性提升整个平台的因素。工作流是模型无关的资产。

## 7. 讨论

### 7.1 范式适用范围

复合体描述的是 Agent 系统——将确定性执行与非确定性语义推理耦合的系统。它不描述纯 ML 推理系统、规则引擎或纯聊天机器人。

### 7.2 当前局限

单一供应商验证（仅 DeepSeek），模板语料规模小（9 个种子），缺乏跨框架提取的验证。

### 7.3 未来工作

多供应商验证（OpenAI、Anthropic、Qwen），模板飞轮规模化（50+ 日会话 × 30 天），跨框架元认知（将提取应用于 LangGraph 工作流），自动粒度选择。

## 8. 结论

Agent 的定义争论长期无解，因为它问了错误的问题。Agent 不是原子事物。Harness+LLM 复合体是不可再分的结构不变量——它不能被消除，只能被放置在不同的粒度上。鸡和蛋是同一种东西。

该复合体产生可验证的预测，规定正确的方向，并解释了每个主流框架的设计为何可以归结为唯一一个决策。Lilies 以 142 项测试 100% 通过验证了该范式。

**原语即耦合。其余皆为粒度的选择。**
