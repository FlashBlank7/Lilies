# 公式引擎字符串函数 A/B：一个积木层缺口如何吃掉 36 倍搭建时间

2026-08-28 · 首次真实账号对话生成 E2E 引出的对照实验 · 构建者=闭源智能体（DeepSeek 经典莉莉丝）

## 设定

同一需求（guanjia 管家对话发起，措辞一致）：

> 输入一段文本 text，输出 line_count（行数）和 char_count（字符数，不含首尾空白）。不要定时。

- **A（修复前）**：公式引擎白名单只有算术（abs/avg/ceil/floor/len/max/min/pluck/round/sum/sum_by/when），`len` 拒绝字符串；build `7068727c`
- **B（修复后，248a9afa）**：新增 `trim`/`split`/`count`，`len` 兼收字符串，`split(文本)` 单参数按行切；手册同步；build `bd187903`

## 结果

| 指标 | A（修复前） | B（修复后） |
| --- | --- | --- |
| 墙钟 | **1464s（24.4 分钟）** | **40s（36×）** |
| 修订数 | rev21 | rev7 |
| 实现方式 | **llm 结构化输出数数** | variable_assigner 确定性公式 |
| 运行期模型开销 | 每次 ~632 output tokens（$0.0002/次） | **零** |
| 确定性 | 不保证 | 同输入两次运行完全一致（实测 3/8 = 3/8） |
| 验收测试 | 有 | 有（莉莉丝自加精确数值断言） |

两版发布后真跑均输出正确（line_count=3，char_count=8）。

## A 的 24 分钟去哪了（转录考古）

莉莉丝把三条确定性路线全部探死后才降级 llm：

1. **公式路线**（~350s）：反复查手册确认无 split/strip/count，`len` 还拒字符串；
2. **regex_extract 路线**（~400s）：撞上无界量词禁令（`.+`/`.*` 不允许，只有 `{m,n}`）与锚点约束；
3. **Bash/Program 路线**（~300s）：工具被接受，但 bagpipe 无 `agent-platform-sandbox:latest` 镜像，沙箱运行即败；
4. 收尾降级 llm structured_output（~400s），带着"不确定又贵"的方案通过验收。

**手册误导加重了损耗**：变量赋值器手册的函数清单连已存在的 pluck/sum_by 都没列（硬编码文本与 `function_names()` 脱钩），莉莉丝按错误清单排除了公式路线又折返。

## 结论

1. **积木层一个小缺口，搭建成本放大 36 倍**，且逼出"llm 做确定性活"的反模式（审计红旗、运行期持续付费）；
2. **手册必须与能力单一真相**：本次把公式函数清单同步进手册（e3a05be0 起管家还会给工作流起可读短名）；
3. 搭建智能体的探索是理性的——它按手册行事；**平台侧的能力与文档质量直接决定搭建时长**，这为"harness 决定小模型上限"的论文主线再添一个可量化案例；
4. 遗留：bagpipe 缺沙箱镜像（Dockerfile.sandbox 现成，构建需拉 ~300-500MB，等流量决策）。
