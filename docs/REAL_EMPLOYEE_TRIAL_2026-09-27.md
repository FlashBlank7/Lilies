## 发现与修正

1. **思考耗尽节点输出额度。** 初次业务 API 沿用默认思考，2,200 token 输出额度用尽且正文为空；官方智能体又以相同配置尝试一次，仍失败。页面手动停止后，在项目模型设置关闭业务 API 思考，再用同一输入运行。官方智能体仍用 Luna/max。运行错误现在说明具体节点、实际输出上限、思考可能计入额度，以及可修改的配置；平台没有自动换模型或扩额。模型设置增加对应说明。
2. **统计解释越过事实范围。** 旧提示词出现把完全重复解释为不同时点、把前几行时间规律推广到整表、混淆产品质量与数据质量的问题，也未在业务含义不清时展示补充表单。模板现在说明统计范围、完全重复定义和业务问题；自编文件不变，仅更新工作流后重跑。最终报告正确保留未知、统计事实和未执行检查。
3. **遗漏待办及无必要追问。** 会议纪要最初遗漏没有负责人却已经决定的内部试用。第一次修正后仍把已给出会议日期说成缺失、给已完成事项增加确认问题；第二次局部修正后，同一资料中试用与培训均在行动项，待确认只保留试用负责人。

失败任务和旧报告均保留。一次新会话复用了旧分析，没有运行新草稿；该请求只记为已有结果读取。随后明确要求重新运行当前草稿，才验证新配置。模板更新不会覆盖员工已经安装的副本；本轮仅通过正常修订接口更新自身试用副本。

修正后数据工作流的两次原始 LLM 分别为 7.14/7.69 秒，报告输入 1,998/3,465、输出 1,438/1,578 token；最终会议节点 1.76 秒、输入 246/输出 262；两次周报节点 3.20/2.52 秒、输入 230/190、输出 714/517。服务未报告费用，不能把存储中的零值称为免费。官方请求时间包括工具操作与等待，不与单个原始 LLM 节点直接比较。

本次解决具体错误并完成路径，**尚未证明稳定低用量**。特别是接续解释的报告用量明显高于业务节点，应按相同任务继续定位上下文读取及工具返回成本，保持回答质量后再比较，不能从这几个不同请求推导提速比例。

### 同日用量定位与第一项修正

只读取上述平台专用会话的已有记录，没有追加模型调用。“不清楚”接续请求的增量为输入135,893、其中缓存输入122,880、输出1,226，合计137,119 token；其中思考输出565，已包含在输出中。该请求有四次用量递增，每次带入约3.1万至3.7万输入token。主要观察到历史上下文多次传入，不能把总量解释成模型生成了13万字的回答，也不能用总token直接推算订阅扣额。

真实工具序列为`respond(wait=true)`、等待式`inspect`、读取Markdown的`inspect`。原`respond`忽略`wait`，刚恢复任务就返回运行中状态和旧问题，造成再次查询。现复用启动任务已经使用的等待、后台与停止机制：默认返回完成、失败或下一道实际问题；`wait=false`明确后台执行；保留原任务、快照及统计进度，`view=full`按需生效。离线测试覆盖成功、失败、后台、停止和连续两道人工作答，相关44项通过。没有前端修改或新增真实请求，实际节省token的比例尚未测量。

另一处仍可改进：分析报告在顶层与`result.markdown`重复，合计大小触发摘要省略，智能体又读取一次正文。下一步应先去掉摘要中的重复内容、保留一次有用结论和文件入口，而非继续缩短所有字段或引入新的流程门槛。对话历史的按需整理应随后用相同任务比较质量与用量。

### 同日第二项修正：报告去重与旧结果按需读取

任务摘要现在只保留一份完全相同的长报告，并标明原始输出路径的对应关系；指标、下载文件与完整输出保持。已有最终分析的输出从13,513降至7,449 UTF-8字节，完整6,050字节Markdown不再因两份副本合计超过8,000字节而被省略。不同内容不会合并，超长单份报告仍可按输出路径读取，存储的结果没有修改。

每次新请求默认附带的最近运行改为任务编号、状态、输出字段和读取入口，不反复附带旧输入与报告。当任务在本请求中完成，或会话明确关联某个任务时，仍直接提供结果摘要，避免后台完成后额外查询。原报告、完整运行详情和历史文件可继续读取。

相关后端85项通过，覆盖原结果保持、相同/不同/超长报告、按索引读取、连续新请求、后台完成接续及原有人工回答路径。最初只精简所有最近结果导致两项后台完成测试失败，修正为本请求结果直接返回后通过，没有削弱原断言。自动测试出口关闭；没有前端改动。
