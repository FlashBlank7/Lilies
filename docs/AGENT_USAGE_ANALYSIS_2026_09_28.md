## 原因、改动和范围

1. **保留原件却只能重建。** `project_workflows`原来只有创建空白成员，没有复制操作。第4、5、8、9轮用来准备和重写已有图，合计63,820 token；其中复制和编辑仍然必要，不能将这个数字全部算作可节省量。现在增加`copy`：复制单个成员完整草稿，保留节点配置、布局、嵌套代码和测试；返回新id及修订/hash，随后只改目标字段。同项目文件、模型资源和下游流程仍共享，未递归复制依赖。复制不执行、不继承发布版本或测试通过状态。
2. **常用编辑工具被藏在发现步骤后。** 第一轮用`task`等泛词匹配名称和描述，还带回四项无关的目标／多智能体工具声明，共10,648B。两次发现及格式查询占全部原生工具输出payload的61.1%（38,449／62,950B）；按可见文本计为65.5%（34,349／52,478B）。现在将`workflow_draft`与读取、执行工具一同直接提供，其他能力仍按需发现。旧名称帮助继续兼容。代价是直接提供的工具定义JSON从5,786增至8,997B；这是为免除常用编辑的发现往返所作取舍，净token影响仍待真实复验。
3. **普通对话被误导去提交任务。** 第13轮没有可提交的业务任务，却调用`project_task_result`；该次响应用了24,283 token，生成区间约10.55秒，随后才正式回复。现在工具介绍、task_id说明、项目说明和错误提示一致：普通对话直接回复；已有业务任务才提交或呈现结果。任务完成与用户停止语义保持。
4. **完成后重复读取。** 第12轮三个返回与已读取值完全一致，共2,900B。两个业务结果已返回后，直到最终回答又花32.255秒及71,863 token；其中最终回答必要，不能全部删算。已有修订/hash摘要足够做针对性的原件核对；本轮还修正重复读取计量，将`project_workflows inspect`计入只读操作，复制重试不被误计为重复读。

上一轮已经修复的强制测试门槛、通用schema重复返回、命名空间帮助兼容，不重复计成本轮收益。没有降低模型或思考模式，没有新增阶段审批、强制手册阅读或任务token上限。
