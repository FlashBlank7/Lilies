# 本机项目备份与恢复

备份覆盖完整 `data/` 和 `workspaces/`：数据库、上传数据、模型、训练笔记、Optuna 记录、需求资料、项目脚本、运行产物和本机 Codex 会话。它不包含平台源码、Python/Node 安装环境或 Docker 镜像；恢复时使用对应平台版本，保留研究记录绑定的镜像。

## 备份

先停止平台 API 及其计算任务，再在仓库根目录执行：

```sh
./scripts/backup.sh
```

默认读取 `data/`、`workspaces/`，保存到 `backups/日期-标识/`，并保存当前 `.env`。自定义位置时：

```sh
./scripts/backup.sh /path/to/data /path/to/backups /path/to/workspaces
```

也可明确指定配置：

```sh
.venv/bin/python -m agent_platform.backup create \
  --data /path/to/data --workspaces /path/to/workspaces \
  --output /path/to/backups --config /path/to/config.env
```

API 与备份共用目录锁；新版 API 运行期间会明确拒绝备份。首次升级前的旧 API 没有此锁，仍须先停止。单独运行的旧脚本或外部工作进程也必须先退出。

备份在临时目录完成复制和数据库检查后才显示为完成；中途失败不会留下可误用的完成目录。APFS 同卷优先使用独立文件克隆，其他文件系统正常复制，不使用硬链接。克隆后的源文件、备份和恢复副本可以独立修改。

外层备份目录权限为 `700`，配置为 `600`；备份包含凭据和企业资料，`backups/` 已加入 Git 忽略。同盘克隆适合本机恢复验证；要应对磁盘故障，仍需将完整备份目录复制到独立存储，并检查其访问权限。符号链接按链接保存，不跟随它们复制本机其他文件。

## 恢复

恢复只写入尚不存在的新目录，不覆盖现有项目：

```sh
.venv/bin/python -m agent_platform.backup restore \
  /path/to/backups/日期-标识 /path/to/restored-lilies
```

恢复后包含 `data/`、`workspaces/`、恢复来源说明及权限为 `600` 的 `.env`；原备份没有配置文件时也会生成。配置中的数据、工作区及宿主挂载路径均指向新目录，并追加以下恢复默认值：

```dotenv
MODEL_EGRESS_ENABLED=false
OFFICIAL_AGENT_EGRESS_ENABLED=false
AUTOMATIC_TASKS_ENABLED=false
```

第三项暂停启动时的排队请求恢复、定时任务、事件订阅、自动改进及事件/产物维护，保留手动查看、运行与下载。正常部署默认值仍为 `true`。它不是只读模式：数据库兼容迁移和中断状态标记仍会写入恢复副本；手动执行的代码或连接器仍可能访问外部系统，演练只选择明确无外部副作用的工作流。

平台保存的运行工作区路径随目录更新，包括历史运行、会话、生成任务、持久定时器及事件订阅的工作区配置；客户代码、固定草稿、业务输入、输出与历史评价不做全文替换。用户脚本自行写死的绝对路径、外部文件、连接器及外部数据库需另行处理。

在对应平台版本中使用恢复的配置启动。进程环境变量优先于 `.env`，不能只修改文件后沿用旧服务的启动环境。可在恢复目录启动独立端口：

```sh
# 替换为与备份匹配、已安装依赖的平台源码目录。
LILIES_CODE=/path/to/Lilies
cd /path/to/restored-lilies
env -u DATA_DIR -u WORKSPACE_ROOT -u WORKSPACE_HOST_ROOT \
  MODEL_EGRESS_ENABLED=false OFFICIAL_AGENT_EGRESS_ENABLED=false \
  AUTOMATIC_TASKS_ENABLED=false PYTHONPATH="$LILIES_CODE/platform/backend/src" \
  "$LILIES_CODE/.venv/bin/uvicorn" agent_platform.api:create_app --factory \
  --host 127.0.0.1 --port 8005
```

携管理员认证请求 `/health`，核对三个开关均为 `false`；匿名健康检查只返回存活状态，不能代替配置核对。若通过前端演练，使用单独前端实例并将 `AGENT_PLATFORM_URL` 指向该端口，不改员工入口。恢复本身不会启动任何任务。

1. 查看项目会话、进展、原任务、最佳模型及训练笔记。
2. 使用已有模型完成一次预测，检查结果文件。
3. 对等待或中断的事项点击继续；不要重新提交已完成训练。
4. 确认后再以恢复目录作为正式数据位置，原目录保留用于回退。

正式接管时先停止旧实例及其独立工作进程，再按实际需要打开自动任务和已获准模型出口；旧排队任务、订阅和定时任务可能随开关恢复执行。不要同时让两份副本处理同一外部业务。`compose.yaml` 的旧 `backup` profile 仅复制部分文件，不含完整工作区，不能替代上述离线备份或用于本次发布回退。

官方智能体使用平台专属服务目录中的登录；直接连接的本机 Codex 使用当前机器登录。平台会重连本项目保存的 thread，并优先读取恢复目录中的会话文件；不会通过新建空白会话掩盖原记录缺失。换电脑时需准备兼容 CLI，核对程序路径并检查连接，登录失效时重新登录；个人主目录中的登录凭据没有随符号链接内容打包。

当前 CLI 的分页会话还在本地索引保存绝对路径。恢复工具仅在离线副本中迁移 `threads.rollout_path` 和 `threads.cwd`，覆盖旧会话目录、当前项目私聊目录以及官方生成/账号目录；不遍历外部符号链接。迁移先检查实际表结构，索引或数据库附属文件为符号链接、结构不兼容时恢复失败并保留原备份。该迁移不是运行中共享 Codex 数据库的接口。

文件数量、大小和 SQLite 完整性会在恢复时检查；这些检查不能替代独立存储上的长期校验，也不表示每个历史工业模型都经过重新验证。

## 使用 Compose 启动恢复副本

在与备份匹配的平台源码目录中运行，端口需与已有实例区分：

```sh
LILIES_STATE_DIR=/path/to/restored-lilies \
LILIES_API_PORT=8008 LILIES_WEB_PORT=3008 ./scripts/docker-up.sh
```

脚本从指定目录读取 `.env`，以相同绝对路径挂载 `data/` 和 `workspaces/`，使 API 保存的路径与宿主计算容器实际使用的路径一致。实例名称和基础计算镜像按数据目录区分，不覆盖其他实例的镜像标签。相对状态目录以源码目录为基准，未设置时使用源码目录。服务仅监听本机回环地址；局域网或公网入口需另行配置代理。

API 和计算进程使用启动者的 UID/GID；启动者必须有数据目录的读写权限及 Docker 使用权限。Linux 根据 socket 所属组设置附加组，Docker Desktop 默认使用容器内的组 0；特殊环境可设置 `LILIES_DOCKER_SOCKET` 与 `LILIES_DOCKER_GID`。脚本不会放宽目录权限或自动修改已有文件所有者。

启动会构建 API、前端、代码和建模镜像，并等待前后端健康检查。历史模型仍绑定其原始镜像摘要，构建新镜像不能替代旧环境。备份不包含这些镜像，迁移时须单独准备。

管理同一实例时始终传入相同状态目录和端口，使用 `--status`、`--logs` 或 `--down`；停止保留数据。恢复目录中的两个模型出口和自动任务开关应保持关闭，直到完成接管验证。API 镜像已包含 Docker CLI 和固定版本 Codex CLI；官方智能体的程序路径、已有登录及会话接续需单独核对，步骤见[官方智能体配置](OFFICIAL_AGENT.md#容器部署)。
