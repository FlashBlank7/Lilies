# 智能体/工作流生成平台产品北极星

> 状态：最高产品意图基线
> 生效日期：2026-07-21
> 适用范围：产品规划、场景选择、架构投资、自动工作流生成、实验分母与对外声明
> 直接依据：用户本轮纠偏、项目早期 README、`PRELOAD_PROMPTS.md`、初始架构讨论与工业场景材料

## 1. 一句话定义

智能体/工作流生成平台是一个对标 Dify 类可视化编排能力、但能够由 AI 根据自然语言需求自动生成和持续编辑工作流的平台。它首先服务尚未完成 AI 化、但有明确业务或技术流程需要自动化和智能化的传统企业。

平台的差异化不在于把 Claude、Codex、Harness、调度器或治理系统本身当成产品，而在于把企业真实问题转化为可运行、可编辑、可验证、可复用、可嵌入现有系统的 AI 工作流。

## 2. 名称与对象

| 名称 | 唯一含义 |
| --- | --- |
| 智能体/工作流生成平台 | 完整产品，包括需求补全、莉莉丝、工作流画布、积木与模块、运行时、数据和模型能力、验收、发布、客户运行界面、连接器与治理。 |
| 莉莉丝 | 平台内部负责理解需求、询问缺口、规划、搭建、测试和修复工作流的具名智能体。莉莉丝也可以单独接受 Claude/Codex 类能力实验，但实验结果不能替代平台产品验证。 |
| 平台生成的工作流 | 交付给客户的可编辑、可运行、可版本化产物。平台成功与否最终由这些工作流能否解决真实业务或技术问题决定。 |
| Claude/Codex 式智能体架构 | 莉莉丝和复杂工作流可复用的智能底座与工程手段，不是目标客户、产品定位或默认场景。 |
| Harness、调度、Connector、治理 | 支撑可靠运行的基础设施，不是独立的产品北极星。 |

历史材料中把整个平台称作 “Lilies” 的用法只作历史语境保留。新产品、实验和阶段文件必须区分平台、莉莉丝与平台生成的工作流。

## 3. 目标客户

首要客户是有 AI 化需求、但缺少成熟 AI 平台、算法工程链路或工作流工程能力的传统企业及其项目团队。典型角色包括：

- 懂设备、工艺、质量、运维或业务规则，但不会搭建 AI 系统的领域专家。
- 需要把已有机器学习、深度学习或知识检索能力接入真实业务的企业工程团队。
- 需要把输入、判断、模型、人工复核、文件交付和既有系统接口串成稳定流程的实施人员。
- 需要从自然语言需求快速得到可审查原型，再由专家校准并沉淀为模板的企业客户。

程序员和开源项目维护者可以是技术实验参与者，但不是平台主实验的默认客户分母。

个人、小微团队和独立专业人士也存在真实的文档、财务、知识、计划、监控和跨应用自动化需求。它们可以作为第二类客户与泛化实验人群，但必须与传统企业场景分开统计，不能混成一个模糊的“通用用户”成功率。

## 4. 首要工作流族

平台必须逐步覆盖以下客户工作流，而不应只覆盖通用 LLM 问答或代码智能体：

1. **工业机器学习/深度学习工作流**：数据接入、质量检查、特征或参数处理、训练或模型接入、评估、版本、部署、推理、阈值决策、人工复核、监控和再训练。
2. **企业 RAG/知识工作流**：文件接入、解析/OCR、切分、向量化、索引、检索、重排、权限过滤、引用、评测和知识更新。
3. **结构化数据与交付工作流**：CSV/数据库/传感器/图片等输入，确定性转换和校验，Excel/文件/报表等工件输出，上传到指定接口并保存回执。
4. **混合智能工作流**：规则、传统程序、ML/DL 模型、LLM、人工判断和企业 API 可以在同一流程内组合。
5. **企业流程自动化工作流**：把稳定、重复、可描述的技术或业务步骤自动化，并把经过验证的流程沉淀为可复用模块和行业模板。
6. **预测、优化与规划工作流**：把历史和当前数据、资源约束、成本与服务目标转化为预测、排程、路径、补货或参数建议，并保留可行性与目标函数证据。

## 5. 从具体例子抽象任务，而不是固化行业名词

平台要处理的本质不是“电梯”“光纤”或其他某个行业名词，而是一个受约束的真实任务合同：

```text
触发 + 输入数据/材料 + 状态
  -> 确定性处理、模型、检索、优化或人工判断
  -> 决策、工件或外部系统副作用
  -> 验证、回执、恢复和持续运行
```

复杂工作流通常组合下列任务原型：

1. **接入与结构化**：读取文件、表格、图片、文本、传感器、数据库或 API，并建立 schema、单位和质量边界。
2. **抽取与归一化**：从非结构化材料中提取字段、表格、实体或事件，并去重、校验和对齐。
3. **检测与诊断**：识别异常、故障、缺陷、风险或类别，给出置信度、原因和升级路径。
4. **预测与决策**：预测未来量、估计结果、评分、推荐或判断是否采取某个业务动作。
5. **检索与解释**：从受权限约束的知识中检索证据，生成带引用答案并在证据不足时拒答。
6. **优化与规划**：在资源、时间、成本、规则和服务目标下求排程、路径、组合或参数方案。
7. **交付与执行**：生成 Excel、报表或结构化记录，调用外部系统，并保存幂等回执和补偿状态。
8. **监控与适应**：按事件或时间持续运行，检测数据、模型或业务变化，触发告警、复核、更新或回滚。

电梯故障检测只是“接入与结构化 + 检测与诊断 + 人工复核 + 外部处置”的例子。光纤参数继承或预测只是“接入与结构化 + 预测与决策 + Excel 工件 + API 交付”的例子。它们不是强制项目、固定优先级或产品完成的必要名称；实验应选择能够覆盖上述原型、具有真实输入输出和独立 oracle 的多样任务。

场景必须从真实需求反推任务原型和能力组合，不能从一个方便获得的开源项目反推客户需求，也不能因为用户举过某个例子就把它写成永久路线图。

## 6. 产品差异化

平台与 Dify 类产品共享可视化编排、积木配置、运行和发布等产品范式；核心增量是莉莉丝能够：

1. 从自然语言和客户材料中识别真实目标、数据、模型、系统、权限和验收缺口。
2. 用选项式询问补齐关键决策，而不是瞎补一段通用需求。
3. 通过受控积木、模块和平台服务增量搭建工作流。
4. 根据运行和业务验收证据修复工作流。
5. 把真实项目中验证过的流程沉淀为行业知识资产。

## 7. 场景选择硬门

任何进入产品路线或平台能力成功率分母的任务，必须同时回答：

1. 是否存在明确的企业或个人使用者，以及一个真实、重复、值得自动化或智能化的问题？
2. 要解决的真实业务或技术问题是什么？
3. 输入数据、已有模型、外部系统、人工角色和最终交付物分别是什么？
4. 平台生成的工作流本身要完成什么，而不是莉莉丝或开发代理完成什么？
5. 是否存在独立业务 oracle、模型指标、文件校验、接口回执或人工专家标准？
6. 该任务补齐的是客户能力、通用平台底座，还是仅用于测试底座的压力场景？

第 1 至第 5 项不完整时，任务不得被称为平台真实场景；只满足第 6 项的 Codex、GitHub、爬虫或 Connector 任务只能作为基础设施压力测试单列报告。

## 8. 非目标与声明边界

- 不把“莉莉丝能像 Codex 一样改代码”写成平台能完成企业或个人的真实 AI 工作流交付。
- 不把 GitHub issue 分类、CI 诊断、开源项目发布决策作为平台主场景组合。
- 不把通用 LLM 对数据描述的分析写成真实 CSV、传感器或工业数据处理。
- 不把一个 HTTP 节点写成客户系统深度集成。
- 不把旧模板能被加载写成模板已经验证可用。
- 不把积木结构通过、Build 完成或本地 fixture 通过写成业务结果通过。
- 不因治理、验收和长任务机制完善，就声明产品能力已经完成。

## 9. 权威关系

权威顺序为：

1. 用户最新明确指令；
2. 本产品北极星；
3. 产品意图登记；
4. 当前阶段报告的任务排序；
5. 阶段合同；
6. 当前设计与中间证据。

能力边界报告、历史阶段报告、技术实验、记忆和恢复钩子都必须服从本产品北极星。它们可以补充实现方法，不能重新定义目标客户、产品对象或平台实验分母。
