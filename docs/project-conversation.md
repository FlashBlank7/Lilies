# 项目进展与统一对话

项目首页以业务能力和对话为中心。每项能力分别记录可用程度与建设状态；可以已经能够试用，同时继续改进。流程画布、共享业务记录、原始结果和开发测试仍在项目中，开发入口保留旧操作方式。

平台根入口 `/` 进入 `/projects` 的“打开项目”页面。新需求可以打开一个空白项目，也可以导入需求包后打开项目；已有工作从同一项目继续。旧单应用首页移到 `/applications`，作为历史工作流与开发工具的兼容入口。

## 推进记录与执行

`GET/PUT /api/v1/projects/{id}/progress` 读取及带 `expected_revision` 更新进展。`value` 是完整替换，包含 `goal`、`summary`、`items`。事项具有稳定 `id`、业务目标、`availability`（not_ready/trial/usable）、`status`（planned/working/waiting/paused/done）、下一步、具体问题、阻塞与实际结果引用。客户问题包含影响及回答后的动作；客户答案保存后不会被较旧的 Agent 摘要覆盖。

`POST .../conversation/messages` 接受 `message` 及可选 `item_id`、`question_id`、`task_id`，不要求客户指定内部阶段。统筹通过 `project_action` 选择查看、搭建、试用、业务执行、续办、需求修订或等待。询问进度不会撤销已确认需求。等待必须关联具体事项和问题或实际阻塞；平台问题与客户数据问题分别显示。

执行中的补充消息保存在原会话，下一轮统筹会收到消息及其事项上下文。阶段切换和加载进展完成后重新读取会话状态，避免异步等待期间收到的补充被旧状态覆盖。浏览器遇到不存在的历史分页位置时重新读取最近消息，保留已显示历史和未发送草稿，再恢复增量读取。待答问题按事项和问题标识共同定位，不会因不同事项使用相同问题标识而残留已回答内容。

统筹调用 `project_action(build)` 后，平台持续推进该次已授权请求中可执行的事项。一轮模型结束时仍有待做动作，就继续同一项目会话；局部等待不阻塞其他事项。连续三次同一失败会保留该事项的实际错误，转向其他事项；没有其他可执行事项时不空转。连续三轮没有实际动作则显示中断原因，不伪装成等待客户资料。用户停止与服务重启保留推进记录，重启后需要用户继续。

工具参数校验失败只返回具体参数错误，不计为业务事项的执行失败，也不撤销建设授权。例如文件读取的 `offset` 和 `limit` 按行计，`limit` 上限为 2000；传入超限值后可以纠正参数并继续。真正执行失败的连续失败处理保留。

`project_action(trial/operate)` 经现有运行器执行，并在启动时固定成员草稿。`resume` 继续原任务及原快照；人机输入节点可指定 `run_id` 与 `inputs` 保存步骤回答，回答只进入该节点，不混入主任务输入而改变运行身份。修改后使用新试用任务，`feedback_task_id` 关联原反馈，不更换旧任务的冻结草稿。“继续推进”保留中断前关联的事项与反馈任务。

`project_task_result` 在统一对话中把中文 Markdown 与文件链接保存为任务的 `presentation`，保留原始运行输出。可指定 `task_id` 为已有本项目结果补业务解释，不需要重新运行。任务运行失败、等待或中断不能被解释成运行成功。原有单应用和旧项目 Agent 结果接口保持原行为。

## 用途与按需读取

成员用途为 business/test，新增时显式标记；`PATCH .../members/{workflow_id}` 或 `project_workflows(classify)` 整理既有成员。旧成员及旧运行迁移后为 unclassified，不根据名称推测用途。新任务来源包括 build_test、customer_trial、business。

`GET .../conversation` 默认返回最近 50 条客户和统筹消息。`before` 加载历史，`after` 增量读取，`kind=tools` 按需加载操作记录。原 `/agent-session` 保留兼容。`GET .../tasks` 支持 purpose、item_id、before、limit；compact=true 省略原始输入输出，详情接口返回完整结果。业务流程视图来自 `/topology` 返回的真实成员调用关系，仍由原主工作流执行。

本机 Codex 的动态工具只能在线程创建时注册。平台工具契约变更时保留项目会话及旧线程标识，创建具有新工具的提供方线程，带入当前项目进展、已确认需求和最近项目消息；普通重连继续同一提供方线程。这是平台升级处理，客户不需要重新提交项目。

对话和结果中的项目相对文件链接会解析到本项目下载接口；路径穿越不生成链接，服务端继续检查文件范围。首页展示业务摘要与最近结果入口，历史附件、需求全文和工具记录按需展开。

## 验证

行为测试位于 `tests/test_project_conversation.py` 和前端 `project-conversation.test.tsx`。替身验证统筹协议、连续推进、隔离、对话路由与恢复；业务试用、反馈后新版本以及等待资源后继续，均通过真实工作流运行器。旧开发工具测试迁到对应组件，原功能继续保留。

需求包只读，平台模型出口保持关闭。项目工具不能修改平台源码，也不能查看其他项目的材料、任务或结果。本期没有新审批体系、后台自动执行或行业专用表单框架。

## 按事项接续与工具流量（2026-09-14）

统一对话每轮默认附带当前事项、相关成员的草稿版本及最新结果摘要，需求正文、节点配置和完整任务记录按需读取。每轮重新读取平台当前修订号，不能依赖模型记忆覆盖用户在画布中的修改。单应用入口继续使用原合同。

项目 `workflow_draft` 默认返回节点/连线及测试索引；`view=nodes,node_ids=[...]` 读取指定节点完整配置，`view=tests` 读取保存测试，`view=full` 读取完整草稿。`batch={expected_revision,expected_content_hash,idempotency_key,operations:[{op,data},...]}` 将同一成员的相关操作原子保存，一次增加一个修订号；失败不保存任何一部分，重复请求不重复修改，旧版本或同键不同内容明确冲突。保留原单操作参数。修改返回当前摘要及 `applied_revision`，幂等重放后的当前版本可能比原操作版本更新。

项目 `project_progress` 默认返回摘要，`item_id` 读取该事项全文，`view=full` 读取完整记录。`action=patch` 携带 `item_id`、`expected_revision` 和 `changes` 修改或创建一项，保留其他事项和已有客户回答；不带事项时仅允许修改整体 `goal/summary`。原 `action=update,value=...` 和 HTTP PUT 仍为完整替换，调用前需读全文，摘要不能作为替换正文。

事项中的 `deliverable` 和 `completion_criteria` 描述本次交付及可观察的完成条件，项目页就地展示；`delivery_request_id` 关联交办。它们复用进展记录，不增加审批或运行门槛。统筹连续完成建设、真实运行、读取错误、修复和受影响回归，客户只需给业务反馈。修改后试用生成关联原反馈的新任务；旧任务、旧结果、待补事实和企业后续目标保留。条件并非测试数量，也不自动代表企业目标全部达成。

`workflow_run` 默认保留小输入输出全文，较大结果带 `inputs_truncated/outputs_truncated` 并给出详细查询方式。`inspect(task_id=...,view=full)` 返回完整记录。成员状态、错误和人工输入节点保留在摘要中，方便继续原任务。保存测试默认返回总览和失败用例；需要所有成功用例时查询关联测试任务的全文。

`GET .../conversation/metrics?request_id=...` 从现有会话事件计算工具调用次数、输入/输出字节、每轮新增上下文字节、相同读取及工具时间并集。字节不是模型 token 或费用；重复返回并不必然是浪费，旧事件缺少计量时明确报告缺失。首个呈现结果与首次可用结果分开：后者必须独立核对业务结果。没有新增指标数据库或完成裁决机制。

独立比较包在 `examples/project-efficiency/`，只包含构造需求和输入，没有实现或答案。只读测量脚本 `scripts/measure_project_efficiency.py` 读取真实试用、原始输出及 CSV，以相同金额、校验分支和反馈条件检查两版结果；不替换任务内容、不向 Agent 提供工程步骤。协议回归见 `tests/test_project_efficiency.py`，其中修复前后的运行都通过实际工作流运行器。
