## 1. 外部集成完备性检查

对每个外部集成点(connector、HTTP endpoint、human_input 模式),提问:

1. **输入合法性可判定?** —— 类型/schema 验证是否覆盖所有输入?(Harness)
2. **已知输入的输出有机制?** —— 模板/规则/确定性处理(减少不必要的 LLM)。
3. **未知输入的输出有机制?** —— LLM 语义处理。
4. **拒绝语义存在?** —— error_branch / 错误路径。

| 检查不通过 | 补什么 |
|-----------|--------|
| 1 不完整 | 增加 Harness schema / input validation |
| 2 对已知子空间不精确 | 增加确定性处理 / 规则 |
| 3 对未知子空间无机制 | 增加 `model_turn` 或 `llm` 节点 |
| 4 缺失 | 增加 `error_branch` 与错误处理路径 |

**适用条件**:任何新增外部集成点。**溯源**:yoneda §6.1(降级为启发式)。

## 2. 新积木判据

判断是否需要**新增积木类型**,而不是复用+组合:

> 如果新的交互模式与已有积木的交互结构**本质不同**,则需要新积木;否则用 `http_request` + `template_transform` 等组合实现。

- 例:`http_request`(URL/method/headers/body → response)与 `web_collection`(sources/policy → content + receipts)结构不同 → 各自独立积木。
- 反例:`graphql_request` 与 `http_request` 结构同构 → 用 http_request + template 即可,不新增积木。

**适用条件**:积木注册表评审。**溯源**:yoneda §6.2(降级为启发式;原"自然同构"表述改为"交互结构本质不同"——后者可操作,前者不可)。

## 3. 测试完备性指导

- **确定性部分**(无穿孔节点):每个输入类型组合至少 1 个用例;每个 error_branch 路径至少 1 个触发用例。
- **非确定性部分**(含穿孔节点):
  - 对每个 LLM 节点的"语义等价类"至少 N 次采样(统计接受)。
  - `structural_only` 模式只检查可判定属性(exists/type/length),不检查内容相等。

**适用条件**:为工作流设计测试集。**溯源**:yoneda §6.3 + core R2(降级为启发式)。

## 4. 架构等价判据(工程近似)

判断两个部署是否"行为等价":

1. 相同输入类型 → 相同输出类型(Harness 层,可判定)。
2. 相同结构化输入 → 相同结构化输出(Det 路径,可判定)。
3. 相同自然语言输入 → 统计不可区分的输出(LLM 路径,统计检验)。

**注意**:这是**近似判据**,不是数学等价定义(图同构/语义等价不可判定,见 §6 G2)。

**适用条件**:版本迁移、多平台对比。**溯源**:yoneda §6.4(降级为启发式)。

## 6. 已知差距(自我批判)

源自 theoretical_review 的四个差距,加上减法发现的新差距:

- **G1 自由选择(FC)未强制**:`validate_workflow` 不检查 FC 性质;存在构造非 FC 工作流的可能(扇入 + 不同条件)。建议:加 FC 检测,命中则告警并降质量评分。**开源项 O2。**
- **G2 图同构 / 语义等价不可判定**:merge_engine 用 Jaccard(类型)+ 图结构距离近似。当前启发式是实际可行解;可增强 Weisfeiler-Lehman 图核。**开源项 O3。**
- **G3 积木分层未落地**:文档称 CORE 6 / 便利 / 域特定,但注册表 51 个积木无分层标记;文档计数漂移(46/41 vs 51)。建议:加 `tier` 字段,Builder 提示词强调核心积木。**开源项 O5。**
- **G4 画布是示意图,非证明环境**:拖拽不保证语义不变性(虽 R7 保证重排语义不变,但编辑操作未做等价性检查)。长期:编辑操作保语义。
- **G5 文档-实况漂移**:README 声称"28 tests/100% pass",实测 987 tests/29 failures。建议:建立文档自检(数字必须有来源)。

## 7. 证据要求

任何规则/推论在声称"已验证"时,必须指明证据等级:

| 等级 | 含义 |
|------|------|
| **E1 代码确定性** | 有可运行的确定性实现 + 单元/集成测试 |
| **E2 集成验证** | 通过真实集成场景(真实模型/真实工具/真实外部系统) |
| **E3 生产运行** | 有生产环境运行证据(事件日志、运行记录) |
| **E-blocked** | 外部证据面不可用,记录 `blocked_by_environment` + 复查触发条件 |

**核心原则**:理论给出"应该做什么",证据等级给出"做到哪一步了"。两者不可互相替代。缺失高级别证据**限制**声称,但不抹除低级别证据。
