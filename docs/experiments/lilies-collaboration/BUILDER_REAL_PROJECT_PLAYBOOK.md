# 真实业务工作流 Builder 通用作业法

> 状态：待包装为平台 Skill 的通用经验候选
> 适用对象：只通过 Lilies 平台公开合同搭建、测试和发布工作流的 Builder
> 不包含：项目答案、隐藏 Seed、宿主 UUID、成品工作流或项目专用代码

## 1. 先定义业务状态机，不先堆积木

把需求改写成一张穷尽业务输入的状态表。每一行至少明确：

- 进入条件；
- 是否需要人工决定；
- 是否允许外部副作用；
- 副作用类型；
- 安全停止结果；
- 重放时应得到的结果；
- 独立验收证据。

先证明所有状态互斥且完备，再画工作流。任何无法归入状态表的输入都应安全
停写，不能依赖数组顺序或默认分支猜测。

## 2. 把发现、读取、判断、审批、执行、回读分开

复杂宿主集成按六段组织：

1. 动态发现客户资源，去掉本地与远端视图造成的重复身份；
2. 一次性读取判断所需的宿主状态，避免高频小查询；
3. 用确定性规则分类，保存候选和冲突证据；
4. 把所有可能产生变更的项目合并成一次人工暂停；
5. 把人工决定重新绑定到可信分类和候选集合，再执行写入；
6. 从宿主重新读取结果，计算不变量并生成强类型工件。

人工输入不能直接携带任意宿主 ID 越过分类结果。审批只决定是否执行，不能
改写金额、稳定身份或候选集合。

## 3. 精确身份检查必须早于模糊业务匹配

处理可能重放的数据时，顺序固定为：

1. 输入级去重；
2. 宿主中的稳定外部身份或业务回执检查；
3. 宿主中的业务标记检查；
4. 强匹配和歧义判断；
5. 冲突判断；
6. 新建判断。

如果先做模糊匹配，再检查稳定身份，重放记录可能重新进入审批或写入分支。
副作用幂等键应由稳定业务身份和操作类型共同组成；更新与新建不能共用同一
操作键。

## 4. 区分“同一个业务键”和“同一个物理输入”

重复输入可能和原件共享业务 ID。最终按原输入顺序回填时，不得只用这个共享
ID 判断哪一行是副本；应使用去重积木返回的原始索引、首次索引和状态回执。

验收副作用也不得把多个别名相加。以宿主返回的不可变交易 ID、请求摘要或
回执序列作为一次物理效果的身份。

## 5. 先确认公开返回形状，再连长链

对于外部程序、连接器和数据积木，先通过公开手册和最小无副作用调用确认：

- 返回值是裸数组、裸整数，还是带 `data`、`balance` 等字段的对象；
- 本地资源和远端资源是否会同时出现；
- 更新、新建和导入的正式命令语义是否不同；
- 工具错误如何区分临时失败、权限拒绝和业务拒绝。

形状确认属于搭建前检查，不是等整条工作流失败后逐节点猜测。

## 6. 外部写入必须有四层证据

遇到“工作流结果、trace、宿主状态、验收器”不一致时，冻结当前版本并依次
核对：

1. 工作流输出中的业务状态、写入状态和回执；
2. 公开 trace 中实际启动的分支和工具节点；
3. 宿主中按不可变身份统计的真实物理变化；
4. 验收器的检查项和结论。

前三层证明禁止记录进入写节点或产生物理变化时，才判为工作流缺陷。共享
业务键导致重复归因时判为验收归因问题。客户环境重建后沿用旧缓存或旧账本
时判为环境世代问题。不得通过关闭幂等或更换业务键刷绿。

## 7. 测试环境要同时隔离工具和可变缓存

需要外部程序的测试至少携带：

- 固定版本可执行工具；
- 只读依赖；
- 每个测试独立的可写缓存；
- 独立工作目录；
- 与客户宿主一致的凭据和网络边界。

每个独立 Seed 使用新客户资源和新业务身份。跨客户端验收时，从宿主重新
下载只读副本，不复用工作流客户端的本地缓存。环境基线尽量用普通业务记录
表达，避免特殊“初始余额”或迁移记录在不同客户端产生视图差异。

## 8. 一次修一类问题，不按失败项疯狂迭代

一次完整运行后，把失败归成以下类别：

- 输入与状态机遗漏；
- 数据返回形状错误；
- 图连接或嵌套边界错误；
- 审批绑定错误；
- 写入语义或幂等错误；
- 宿主缓存、环境世代或权限错误；
- 验收归因错误。

先形成整类原因和影响范围，再做一轮一致修复。修复后依次执行结构校验、公开
业务测试、真实宿主运行、原样重放和受保护 Seed。结构校验只证明图可运行，
不能代替业务验收。

## 9. 工件和不变量是工作流结果，不是事后说明

工作流应直接输出：

- 每条输入的状态、决定、宿主回执和错误分类；
- 运行前后宿主读回；
- 由整数或其他精确类型计算的不变量；
- 带 lineage 的 JSON、Excel 或其他强类型工件。

Excel 中金额保持数值、日期保持日期、布尔值保持布尔值，不用公式把未执行
逻辑藏进文件。最终摘要应由逐条结果聚合，而不是手写常量。

## 10. Builder 完成检查清单

- [ ] 空应用所需的起点、终点、资源发现和工作目录被显式初始化。
- [ ] 按最终期望拓扑搭建，不重放第一轮历史修补或临时连边。
- [ ] 所有边的端点和端口先与公开积木手册核对。
- [ ] Draft 操作可从部分完成状态恢复，明确 no-op 视为已完成。
- [ ] 构建辅助代码有一个统一入口，不依赖文件导入副作用。
- [ ] 业务状态表覆盖正常、歧义、冲突、重复、拒绝、权限和临时失败。
- [ ] 客户资源通过名称或公开身份发现，没有写死环境 UUID。
- [ ] 稳定身份和业务标记检查早于模糊匹配。
- [ ] 所有外部变更都经过一次明确人工审批或需求允许的自动政策。
- [ ] 人工选择重新绑定到可信候选。
- [ ] 更新、新建和导入使用宿主官方语义。
- [ ] 写操作使用“业务身份 + 操作类型”的稳定幂等键。
- [ ] 工作流回读宿主并计算不变量。
- [ ] 去重回填使用来源索引，不用共享业务键猜副本。
- [ ] JSON/Excel 等工件通过 schema 和单元格类型检查。
- [ ] 原样重放报告零新增物理效果。
- [ ] 公开测试与三个新环境 Seed 均通过。
- [ ] 失败、平台补能、调试轮次、耗时和 token 被如实记录。

## 11. 经验复用回归的诚实口径

完成一个项目后，用全新应用和全新客户业务数据重建一次，记录：

- 首次成功前的 Draft 修改批次；
- 结构校验失败次数；
- 公开业务运行失败次数；
- 受保护验收失败次数；
- 新增平台能力次数；
- 首次成功耗时；
- Builder 模型调用和 token。

同一智能体上下文的重建只能证明经验和实施方法的复用效率，不能称为独立
模型泛化。真正评估 Skill 质量时，应把本文件和公开需求包交给一个未见过成品
工作流、平台源码和隐藏 Seed 的新 Builder 会话。

## 12. 预测、模型和优化项目的通用顺序

这类项目不要把“训练”和“每次业务运行”混在一条在线工作流里。通用顺序是：

1. 按时间而不是随机切分历史数据，先训练或导入候选模型；
2. 在未来时间段上回测，保存误差、区间覆盖率、单位和数据来源；
3. 只有指标和人工批准都满足时，才把不可变模型版本提升到命名部署；
4. 业务工作流只调用已部署版本做推理，不在订单、告警或计划运行中偷偷训练；
5. 每次推理返回模型版本、部署修订、数据漂移或误差监控和“建议重训”信号；
6. 重训信号只进入模型管理流程，不能自动替换当前生产模型。

这样可以把“模型是否合格”和“这次业务是否应执行”分开审查，也能在新模型
变差时回滚，而不是让一次业务输入直接改变生产行为。

约束规划必须先从客户系统读回实时状态，再把预测和业务约束放进求解器。输入
至少包括当前存量、在途量、安全库存、最小起订量、批量、成本、共享预算和
共享容量。输出必须区分：

- 可行方案：逐项建议、总成本、资源使用量、目标值和真正起作用的约束；
- 不可行方案：缺少多少容量或预算，以及哪些最低业务要求无法同时满足。

只有可行方案进入人工审批。人工批准不能改写求解器给出的数量；如需修改，
应变成新的计划输入并重新求解。拒绝和不可行路径都不得触达写节点。

## 13. 外部系统计划写回的通用规则

计划类写回先用公开接口读取当前状态，再按稳定业务标题或外部计划 ID 做
read-before-write：

1. 没有同身份草稿时才创建；
2. 已存在时返回“复用已有草稿”，不再写；
3. 创建后立即按宿主记录 ID 回读；
4. 核对未提交状态、明细、数量、日期和宿主回执；
5. 工作流只创建需求允许的最弱副作用，例如草稿；不得顺带提交、下单或过账。

Connector 合同测试的请求体要满足宿主最小真实合同，不能把不确定的可选字段
当成幂等身份。宿主忽略未知字段时，应改用其正式可查询字段，而不是在平台
侧伪造一个只有自己认识的标记。

## 14. 复杂图的一次成型检查

开始长链搭建前，先从公开 schema 和积木手册固定四件事：

- Draft 读取响应中，图、revision 和测试分别位于哪一层；
- start、iteration、branch 和子工作流的真实输入输出端口；
- 每个引用拿到的是节点结果本身，还是结果中的 `output` 字段；
- JSON Schema 的平台上限和宿主 API 的正式字段。

然后按最终拓扑一次生成节点和边，并让构建入口可重入：已存在的节点、边或
测试视为已完成，不把 no-op 当成失败。业务运行前先做图校验和一条最小公开
测试；只有结构和返回形状确定后才跑完整宿主副作用。

## 15. 本轮来源与保留边界

本作业法的新增证据来自 `EXP-LILIES-005`：稳定身份前置、索引级重复归因、
官方程序返回形状、可写缓存隔离、跨客户端新鲜回读和四层副作用核对。上述
内容均被抽象为跨宿主规则；项目命令、字段映射、客户数据和工作流图没有进入
通用经验。

同项目的经验复用回归又补充了五条搭建框架经验：空应用不能假设已有起止或
探针节点；最终拓扑不能通过重放历史临时边获得；端口必须按当前公开手册生成；
部分 Draft 续建必须接受明确 no-op；所有构建阶段必须有统一可调用入口。回归
中的业务工作流在新数据上一次通过，但历史辅助代码的这些隐含假设造成多次
业务运行前失败，因此不能把“新数据通过”夸大成 Skill 已经高效。

`EXP-LILIES-006` 又补充了预测/优化项目的经验：模型准备与在线推理解耦、
时间回测后再提升、不可变部署谱系、漂移只触发建议、实时宿主状态进入约束
求解、不可行解释、审批不改计划、最弱草稿副作用以及正式字段的写前查重。
这些经验不包含 ERPNext 端点、字段映射、客户数据、成品图或 Seed 答案；以后
包装为 Skill 时只保留上述顺序、检查表和失败分类。
