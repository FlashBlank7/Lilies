## 一、真实业务场景

一家制造企业用 ThingsBoard 接收旋转设备的温度、振动、电流、压力和转速。
可靠性工程师希望提前发现未来 24 小时内的故障风险，但不能把一次异常读数
直接变成大量误告警，更不能让预测系统向设备发送控制指令。

本项目保留 ThingsBoard 的 MQTT 遥测入口、设备身份、告警存储和人工告警
生命周期。Lilies 负责搭建一条增强工作流：读取已进入 ThingsBoard 的遥测，
验证数据，调用当前正式部署的风险模型，按风险和置信度决定自动告警、人工
复核或安全停写，并交付推理轨迹、模型证据和漂移报告。

本项目不声称验证真实工厂硬件的故障机理，也不声称一个合成数据训练的模型
具备生产精度。它验证的是：平台能否管理一个可追溯的模型生命周期，并把已
部署模型安全地嵌入真实客户系统工作流。

## 二、模型从哪里来

模型准备是 Builder 的管理任务，不是每次设备遥测触发的生产步骤。Builder
必须能在客户授权范围内选择三条路线之一：

1. 在外接或客户模型库中寻找候选模型，检查特征、单位和任务类型兼容后导入；
2. 以兼容候选模型为基础，用客户授权的遥测和标签微调或 warm-start，并保存
   基础模型、数据和新版本之间的血缘；
3. 没有合适候选时，用客户授权数据训练新模型。

三条路线最终都必须经过同一套控制：冻结特征合同和单位，生成模型卡，在独立
验证集上评估，由模型负责人明确批准后提升为带版本的部署，生产推理引用部署
名而不是某个临时文件。新版本有问题时可以回滚到上一批准版本。

默认没有在线学习。生产推理和漂移监控都不能自行训练、微调或提升模型；漂移
只产生报告和后续治理任务。

## 三、生产工作流如何解决问题

一条设备遥测记录按以下业务顺序处理：

1. 确认设备、时间戳、五个特征和各自单位完整，拒绝未来时间、过旧数据、
   非数值、越界值和不兼容单位。
2. 以设备和事件时间形成稳定事件身份。重复消息只复用已有结论，不再次创建
   告警；晚到的旧消息可以留痕，但不能覆盖设备较新的风险状态。
3. 调用指定部署名下当前已批准的模型。结果必须带风险概率、置信度、模型 ID、
   版本、模型摘要和部署修订号，不能只返回一个不可追溯的高/低标签。
4. 风险高且置信度足够时，在 ThingsBoard 为该设备创建或更新
   `PREDICTIVE_MAINTENANCE_RISK` 告警；相同设备的同一活动告警应更新而不是
   复制。
5. 风险落在不确定区间或置信度不足时暂停，请可靠性工程师查看遥测和模型证据。
   人工批准后才写告警，人工拒绝则记录理由且不写。
6. 低风险、输入无效、单位冲突、过旧或乱序记录都不得写告警。
7. ThingsBoard 临时不可用时只做有界重试；身份或权限错误立即停止并明确归类，
   不允许把失败伪装成低风险成功。
8. 汇总每条记录的输入验证、推理、人工决定、告警回执和失败原因，生成机器可读
   结果、模型卡引用、评估报告和漂移报告。

任何分支都不允许调用 ThingsBoard Device RPC。工作流只改变已授权的告警状态
和交付工件。

## 四、最小平台补能边界

当前公开平台能读取 OpenAPI、调用连接器、暂停人工复核并生成工件，但没有通用
的表格型预测模型生命周期和“调用已部署模型”能力。项目四只补以下通用垂直
切片，不写 ThingsBoard 专用模型代码：

- 以公开 API 导入、训练、微调、评估不可变模型版本；
- 记录特征 schema、单位、数据摘要、基础版本和指标；
- 经人工批准提升部署、按修订回滚；
- 供任何工作流按部署名推理，并返回完整模型血缘；
- 比较生产观测与训练基线，报告漂移但不自动训练。

ThingsBoard 仍通过它的公开 MQTT、REST、Swagger 和告警接口连接；宿主字段
和接口映射由通用连接器从公开 schema 发现，不增加项目专用适配器。

## 五、公开测试任务

公开 debug 数据使用多台旋转泵，覆盖：

- 明确低风险：只保存推理结果，不创建告警；
- 明确高风险：自动创建或更新告警；
- 边界风险或低置信度：分别模拟人工批准和拒绝；
- 缺字段、错误单位、越界值、过旧和乱序：安全停写并给出原因；
- 同一事件重复送达：只产生一个业务副作用；
- ThingsBoard 临时错误：在限制次数内恢复；
- 失效凭据或无权写告警：不重试写入并标为权限错误；
- 一批观测整体分布偏移：生成漂移告警，但不触发自动训练；
- 新模型批准、部署和回滚：推理轨迹始终绑定实际生效版本；
- 全程检查零 Device RPC。

这些测试首先核对客户系统结果和逐条业务结论，最后才检查工作流图、配置和
工件 schema。图结构通过不等于业务通过。

## 六、隐藏 Seed 设计

正式验收使用三个可重复但 Builder 不可见具体记录值的 Seed。每个 Seed 在干净
的 ThingsBoard 租户状态中重建设备和遥测，改变设备编号、时间基准、特征组合、
单位冲突、重复位置、乱序位置、人工分支、临时故障位置和漂移窗口。

每个 Seed 都包含正常低风险、自动高风险、人工批准、人工拒绝、输入无效、
重复、乱序和宿主错误场景；具体数值、标签、预期告警和最终宿主快照与 Builder
隔离。这样可以发现按固定设备名或固定记录位置硬编码、跨运行状态污染、只对
公开样本有效以及“运行成功但告警写错”等问题。

通过一个 Seed 必须同时满足：

- 每条输入都有可追溯业务结果；
- 该告警的设备最终有正确告警身份、严重度、状态和历史；
- 不该告警的设备没有副作用，重复事件没有重复告警；
- 推理绑定已批准模型版本，漂移结论与观测窗口一致；
- 人工暂停和恢复不串记录；
- 交付物与 ThingsBoard 最终状态一致；
- Device RPC 次数严格为零。

工作流进程结束只证明没有崩溃；三个 Seed 全绿才证明在本题冻结变化范围内没有
依赖公开样本值。即使全绿，也不能证明模型在真实工厂数据上的统计精度、长周期
可用性或未授权外部模型库的兼容性。
