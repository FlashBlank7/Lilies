## Problem

The Try flow now explains active waiting and cancellation, but users still cannot tell when the UI last checked the run status. This makes active or cancelling states feel stale even when polling is working.

## Boundary

- Frontend local timestamp only.
- Do not change polling interval.
- Do not add backend timestamps or APIs.

## Solution

- Track a local last-checked time when the UI sets or refreshes run status.
- Show the last-checked signal inside the result card.
- Keep the signal visible for active, cancelling, and terminal result states when a run exists.

## Acceptance Criteria

- Last-checked signal appears only when a run result exists.
- Starting a new run initializes the signal.
- Polling updates the signal after status refresh.
