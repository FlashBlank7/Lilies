# v0.2.91 design: runtime activation observability

## Source

- Source stage report: `docs/stage-reports/v0.2.90_complexity_router_runtime_activation_path.md`
- Source task: `Implement complexity-router runtime activation rollout observability`
- Version target: `v0.2.91_complexity_router_runtime_activation_observability`

## Problem

v0.2.90 activates complexity-router policy in the build runtime path, but operators do not yet have a product-grade metrics surface for active, bypassed, unknown, or request-override decisions.

## Boundary

- Observability must read persisted build state; it must not change routing decisions.
- Metrics must expose activation status, classification class, effective planning mode, runtime reuse depth, and build outcome.
- The surface should be API-first and testable with deterministic builds.

## Design

- Add a `WorkflowStorage` query for recent builds across applications.
- Add a pure metrics summarizer that derives rollout counters from build `team_state.complexity_router` and `team_state.runtime_builder_policy`.
- Expose the metrics through a read-only platform API endpoint.
- Include sampled build records so metrics remain auditable, not just aggregate counters.

## Acceptance

- Metrics distinguish active, bypassed, conservative unknown, and request-override decisions.
- Metrics include classification distribution, effective planning mode distribution, runtime reuse-depth distribution, and build outcome distribution.
- API tests prove metrics are read-only and reflect persisted build state.

## Status

Completed in v0.2.91.
