# v0.2.90 design: rollback and unknown safety

## Source

- Source stage report: `docs/stage-report-archives/v0.2.x/v0.2.89_complexity_router_limited_default_enablement_contract.md`
- Source task: `Preserve rollback-to-disabled and conservative unknown handling`
- Version target: `v0.2.90_complexity_router_runtime_activation_path`

## Problem

Runtime activation can accidentally weaken the v0.2.89 safety contract if unknown or disabled paths receive active builder policy.

## Boundary

- Unknown classifications must remain complex-equivalent and not default-router-enabled.
- Invalid/default-disabled settings must roll back to disabled runtime behavior.
- Operator/user explicit request fields must remain visible and auditable.

## Design

- Reuse v0.2.89 classification contract as the activation gate.
- Only persist runtime builder policy when `default_router_enabled=true`.
- Persist routing decision metadata so tests and API responses can show whether routing was active or bypassed.

## Acceptance

- Empty/unknown build requirements do not activate runtime routing even under explicit limited-default settings.
- Invalid default mode normalizes to disabled.
- API build responses expose enough evidence to audit active or inactive routing.

## Status

Completed in v0.2.90.
