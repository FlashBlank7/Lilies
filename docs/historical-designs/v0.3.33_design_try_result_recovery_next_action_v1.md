## Problem

When a Try run fails or pauses, users are not told whether to edit inputs, inspect trace, resolve permissions, resume human input, cancel, or wait.

## Boundary

- Guidance only.
- Do not call `startRun`, `resumeRun`, or `cancelRun` from the new summary affordance.
- Existing explicit buttons remain the only mutating controls.

## Solution

- Add deterministic `tryResultNextAction` mapping:
  - `failed`: inspect trace, then edit inputs and retry draft.
  - `paused_permission`: resolve the permission card.
  - `paused_human_input`: fill the human input card and resume.
  - `running` / `queued`: wait or cancel explicitly.
  - `succeeded`: inspect output and move toward acceptance/publish.
  - `cancelled`: edit inputs or run draft again.
- Render `data-try-result-next-action`.

## Acceptance Criteria

- Failed state maps to trace and draft retry guidance.
- Paused with permission maps to permission card.
- Paused without permission maps to human input/resume.
- Succeeded state maps to output inspection and acceptance/publish.
- No new auto-run or auto-resume path is introduced.

## Final State

- Implemented in `platform/frontend/app/applications/[id]/page.tsx` as `tryResultNextAction`.
- Added `data-try-result-next-action` states for `not_run`, `running_wait`, `failed_trace_retry`, `paused_permission`, `paused_human_input`, `succeeded_review`, and `cancelled_retry`.
- Preserved the boundary: new guidance does not call `startRun`, `resumeRun`, or `cancelRun`; existing explicit buttons remain the only mutating controls.
