# design_complexity_router_operator_opt_in_rollout

## Source

- Source stage report: `docs/stage-reports/v0.2.83_complexity_router_post_shadow_rollout_decision.md`
- Source task: `Execute complexity-router operator opt-in rollout`
- Version target: `v0.2.84_complexity_router_operator_opt_in_rollout`

## Problem

v0.2.83 selected stage-1 operator opt-in rollout as the next productization path. The project now needs evidence that operator opt-in controls can route simple, medium, and complex requirements with captured reasons while preserving default-disabled behavior.

## Boundary

- Execute only `stage_1_operator_opt_in` from the v0.2.80 rollout plan.
- Use existing local classification and operator override validation logic.
- Capture override reason coverage and unexpected classification rate.
- Do not enable default routing.
- Do not treat operator opt-in as production default behavior.

## Design

- Load the v0.2.83 decision evidence and v0.2.80 rollout plan.
- Reuse v0.2.76 validation cases.
- For each sample, classify requirement text and validate an operator override with a non-empty reason.
- Record operator mode, reason validity, predicted class, effective class, override target, and whether the route matched expected class.
- Compute override rate, override reason coverage, unexpected classification rate, and accidental default enablement count.
- Mark stage-1 exit criteria satisfied when override reason coverage is at least `0.95`, unexpected classification rate is at most `0.05`, and default remains disabled.

## Acceptance

- Generated evidence records `stage_1_operator_opt_in`.
- Metrics include override reason coverage and unexpected classification rate.
- `default_enabled=false` and accidental default enablement count is `0`.
- Tests verify operator opt-in execution without default enablement.

Completed in v0.2.84.
