## 1. Goal

Make Builder provider-timeout failures auditable at the Platform Harness task boundary.

When Builder fails due a `ProviderError`, the build should enter `needs_attention`, the Platform Harness task should finish as failed, and the task metadata should record the error class, retryable flag, status code, and whether it was timeout-like.

## 3. Data Flow / Control Flow

Current chain:

1. Builder model call raises an exception.
2. `WorkflowBuilder._run()` catches generic `Exception`.
3. Build becomes `needs_attention`.
4. Platform Harness task finishes as failed with only a string error.

Target chain:

1. Builder model call raises `ProviderError`.
2. `WorkflowBuilder._run()` classifies the failure as provider/model error.
3. Build becomes `needs_attention`.
4. Platform Harness task finishes as failed with metadata:
   - `failure.type`
   - `failure.error_type`
   - `failure.retryable`
   - `failure.status_code`
   - `failure.timeout_like`
5. Build event includes the same structured error metadata.

## 4. Implementation Plan

1. Import `ProviderError` in `builder.py`.
2. Add a small `_failure_metadata(error)` helper.
3. Use the helper in the `_run()` generic exception handler when calling `harness.finish_task()` and emitting `build.needs_attention`.
4. Add deterministic Builder test with a provider that raises retryable `ProviderError("DeepSeek request timed out")`.
5. Assert:
   - build status is `needs_attention`;
   - build error contains timeout message;
   - harness task is `failed`;
   - harness metadata marks `type=model_provider`, `retryable=true`, and `timeout_like=true`;
   - build stream contains structured error metadata.

## 5. Acceptance Criteria

- Builder provider timeout is observable through build API, stream event, and Platform Harness task.
- Failure metadata does not expose secrets.
- Non-provider exceptions still produce a generic failure metadata shape.
- Full backend regression passes.
