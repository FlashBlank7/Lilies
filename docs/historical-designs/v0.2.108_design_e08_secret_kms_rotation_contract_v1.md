# v0.2.108 E08 Secret KMS Rotation Contract Design

## Source

- Source stage report: `docs/stage-report-archives/v0.2.x/v0.2.107_e08_remaining_sidecar_slice_reselection.md`
- Source task: `Implement KMS/rotation-grade secret envelope contract`
- Current version: `v0.2.108_e08_secret_kms_rotation_contract`

## Problem

Current Platform Harness secret envelopes encrypt new secrets and preserve legacy plaintext reads, but they do not carry key identifiers or support rotation-aware key lookup. A sidecar-grade secret boundary needs a KMS-like contract even when the local implementation remains standard-library based.

## Boundary

- Do not remove v1 envelope compatibility.
- Do not remove legacy plaintext compatibility.
- Do not leak secret material in public API, events, evidence, or storage metadata.
- Do not claim external KMS integration or full sidecar completion.

## Final Scheme

Add a v2 local envelope contract:

- `secret-envelope:v2:` prefix for newly saved encrypted secrets;
- envelope payload includes `key_id`;
- Platform Harness has a current `secret_envelope_key_id`;
- Platform Harness has a keyring containing current and previous keys;
- decrypt selects the key by `key_id`;
- v1 decrypt still uses the current key path;
- plaintext legacy rows remain readable.

## Acceptance

- New secrets are saved as v2 envelopes with a key id.
- Old v2 envelopes can be decrypted after current key rotation when previous keys are configured.
- v1 envelopes and legacy plaintext rows remain readable.
- Public secret metadata reports storage mode/key id without leaking secret values.
