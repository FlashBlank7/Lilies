## Problem

v0.3.0 made the first screen easier to understand, but a non-technical user still has to invent a good requirement from scratch. That keeps the product in an awkward state: it tells users that different customer types exist, but it does not let them behave like those customers immediately.

## Boundary

This design changes the frontend intake and shared copy. It does not change backend application/build APIs, does not start paid model calls by itself, and does not introduce a separate onboarding wizard.

## Solution

Add a product-facing customer requirement intake panel:

- four representative customer examples: business owner, implementation consultant, operator, technical reviewer,
- each example contains need, workflow requirement, expected outcome, and acceptance signal,
- clicking an example fills the existing requirement textarea,
- the selected example remains visible before the user starts build,
- bilingual copy is kept in `platform/frontend/lib/i18n.ts`,
- the original freeform textarea remains the primary creation mechanism.

## Implementation Plan

1. Extend `platform/frontend/lib/i18n.ts` with customer example fixture copy.
2. Update `platform/frontend/app/page.tsx` to render a scenario intake panel and apply selected examples into the existing create form.
3. Add responsive styles in `platform/frontend/app/globals.css`.
4. Ensure markers are stable for the v0.3.1 black-box audit.

## Acceptance Criteria

- At least four customer examples are visible from the home page.
- Each example can fill the requirement textarea without navigating away.
- Examples are concrete enough to drive actual workflow creation.
- User can still edit the generated requirement before submitting.
- TypeScript check passes.
- v0.3.1 customer-flow audit passes.
