## Problem

E08 had an evidence review report and many Platform Harness engineering slices, but it still lacked a runnable comparison between workflow-internal soft harness blocks / passmode behavior and platform-side sidecar/task-monitor hard boundaries.

Without a runnable comparison, future docs could accidentally treat a workflow block such as `permission_gate` or `budget_gate` as equivalent to a Platform Harness boundary.

## Boundary

- In scope: deterministic local API/TestClient experiment.
- In scope: `permission_gate` `always_ask` and `auto_approve` as workflow-internal passmode examples.
- In scope: Platform Harness network egress block as a sidecar hard-boundary example.
- Out of scope: paid model generation, new UI, long-running worker infrastructure, or redesigning Platform Harness.

## Final Design

`scripts/e08_harness_sidecar_passmode_experiment.py` runs three scenarios:

1. `workflow_internal_permission_pause`: a workflow with `permission_gate` in default ask mode pauses and emits workflow/harness signals.
2. `workflow_internal_permission_auto_approve`: the same kind of workflow with `mode=auto_approve` succeeds, proving passmode is workflow-configurable soft behavior.
3. `platform_sidecar_network_block`: a workflow with `http_request` under `platform_harness_network_egress_policy=none` fails at the Platform Harness boundary.

The runner writes raw JSON evidence and compact Markdown summary with enforcement strength, observability, failure isolation, recovery semantics, and cost/progress signal.

## Acceptance

- Runner output shows the soft pause scenario reaches `paused`.
- Runner output shows the auto-approve scenario reaches `succeeded`.
- Runner output shows the sidecar network block reaches `failed` with a Platform Harness policy error.
- The comparison conclusion clearly states that passmode is not a substitute for sidecar/hard-boundary enforcement.
