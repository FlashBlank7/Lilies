## Problem

`v0.3.0` needs a repeatable way to judge product usability from different customer behaviors, not only from developer intuition. The first baseline should cover representative customer intent before broader live testing:

- non-technical buyer evaluating what Lilies does,
- operations user trying to run or inspect an existing workflow,
- builder user trying to create and improve a draft,
- reviewer user checking whether a generated workflow is safe to publish.

## Boundary

This design adds deterministic source-level and build-level checks. It does not recruit external users, make paid model calls, or claim true human usability completion.

## Solution

Add a versioned customer journey audit script that checks the frontend contains the minimum user-facing cues needed for:

- first-use orientation,
- customer scenario selection,
- front-door create/open actions,
- draft/canvas status,
- next-step guidance,
- bug triage visibility,
- run/test/publish safety.

The script must emit machine-readable JSON and fail if required cues disappear.

## Implementation Plan

1. Create `scripts/v03_0_usability_customer_journey_audit.py`.
2. Model customer personas and required UI markers in the script.
3. Check `platform/frontend/app/page.tsx`, `platform/frontend/app/applications/[id]/page.tsx`, `platform/frontend/lib/i18n.ts`, and `platform/frontend/app/globals.css`.
4. Write evidence to `docs/workingon/usability_customer_journey_audit_v0.3.0.json`.
5. Add focused pytest coverage for the script output and minimum pass conditions.

## Acceptance Criteria

- Audit exits non-zero when a required marker is missing.
- Audit records at least four customer personas.
- Audit records at least one front-door and one draft/canvas journey.
- Focused pytest passes.
- Evidence is archived with the stage.

## Evidence Requirements

- Audit command and generated JSON path.
- Pytest command.
- Any known limitation recorded in workingon and stage report.
