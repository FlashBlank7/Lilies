# v0.2.110 E08 Complete Handler Catalog Design

## Source

- Source stage report: `docs/stage-report-archives/v0.2.x/v0.2.109_e08_remaining_sidecar_slice_reselection.md`
- Source task: `Implement complete Platform Harness handler catalog`
- Current version: `v0.2.110_e08_complete_handler_catalog`

## Problem

The Platform Harness worker runner has a real runner primitive and one implemented handler, but the catalog of supported Platform task kinds is incomplete and implicit. Unsupported worker tasks can be skipped when a handler map lacks a kind, which makes product readiness unclear.

## Boundary

- Do not claim every task kind has been migrated to external worker execution.
- Do not implement distributed heartbeat registry in this version.
- Do not reimplement completed stdio, secret rotation, policy-controls, Studio controls, or runbook slices.

## Final Scheme

Add a complete handler catalog for every `TaskKind`:

- every Platform Harness task kind has a catalog entry;
- implemented kinds point to a real handler;
- not-yet-implemented kinds get deterministic `unavailable` handlers that fail with an operator action instead of silently disappearing;
- API exposes handler coverage and missing-catalog gaps.

## Acceptance

- Catalog covers all Platform Harness task kinds.
- `scheduler_manual_trigger` remains implemented.
- Other task kinds fail deterministically through catalog unavailable handlers.
- Coverage API reports full catalog coverage but not full execution coverage.

## Final Status

Completed in v0.2.110.
