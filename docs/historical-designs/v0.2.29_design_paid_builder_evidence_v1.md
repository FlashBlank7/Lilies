## 1. Problem

The original v0.2 experiment backlog remains partially open, and earlier stages repeatedly deferred E01/E02/E04/E05/E08 because they lacked formal reports. v0.2.29 has a real paid/live Builder run, but the result is a failed build plus benchmark evaluation. The stage must preserve that evidence accurately instead of converting it into a false success.

## 2. Design Goal

Goal:

- Extract the paid/live Builder evidence into a stable, readable summary.
- Classify which original experiment questions the evidence can and cannot answer.
- Record the provider/model, budget boundary, command, result, failure mode, and raw evidence path.

Non-goals:

- Do not change Builder code in this design.
- Do not close E01/E02/E04/E05/E08 unless the evidence directly answers the original experiment question.
- Do not hide the `needs_attention` result behind a generic "benchmark completed" phrase.

## 3. Module Boundary

- `scripts/live_builder_benchmark_suite.py`: produced the paid/live result JSON.
- `docs/experiment-status/evidence/experiment_v0.2.29_paid_builder_tranche_2026_07_09.json`: raw evidence.
- `docs/experiment-status/reports/*.docx`: human-readable experiment reports.
- `docs/experiment-status/v0.2_experiment_status.md`: experiment status ledger.

## 4. Data Flow

Paid/live Builder run -> raw JSON evidence -> concise evidence summary -> DOCX experiment reports -> experiment ledger -> v0.2.29 stage report.

## 5. Implementation Plan

1. Parse the raw JSON evidence with `.venv/bin/python`.
2. Extract stable facts: command, time window, requirement, build status, benchmark status, model/tool call counts, draft node types, missing node types, score, pass rate, and failure mode.
3. Map the facts to E01/E02/E04/E05/E08.
4. Label each experiment as `formal first-pass evidence`, `partial`, `not closed`, or `validated application`; do not mark the original backlog closed unless the original method was actually completed.
5. Feed the extracted facts into the DOCX reports and ledger update.

## 7. Risks

- A failed paid/live run can still be valuable, but it must not be reported as a successful experiment closure.
- E02/E04/E05/E08 need additional evidence beyond the single paid Builder run; their reports should state that clearly.
- If visual DOCX rendering is unavailable, the stage must disclose that QA is structural only.

## 8. Acceptance Criteria

- Raw evidence summary is recorded in `workingon`.
- Every original experiment ID in scope has an explicit evidence status.
- The stage does not close any backlog item without sufficient evidence.
- Provider/model, command, budget boundary, and evidence path are documented.

## 9. No Next-stage Authority

This design expands one accepted v0.2.29 task only. It does not select or prioritize future stages.
