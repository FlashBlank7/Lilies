## Problem

Automatic scheduler behavior already works through `WorkflowScheduler.tick()`. Moving toward worker-owned execution must not silently break installations that do not yet run a supervised worker process.

## Boundary

- The default scheduler tick remains direct-run compatible.
- Worker offload is introduced as an explicit scheduler mode, not as an unconditional behavioral replacement.
- This version may enqueue automatic scheduler tasks for worker execution in offload mode, but it does not start or supervise a durable worker process.

## Final Scheme

Extend `WorkflowScheduler` with an optional worker-offload mode:

- default mode keeps the existing direct schedule fire execution behavior;
- offload mode claims the daily schedule fire, creates a `scheduler_trigger` Platform Harness task, then releases it to `queued`;
- the queued task contains enough metadata for the worker handler to execute the already-claimed schedule fire;
- failure while queueing releases the schedule fire and fails the Platform Harness task if one exists.

This keeps existing scheduler behavior available while making the new worker-owned execution path product-testable.

## Acceptance

- Existing daily schedule tests continue to pass without enabling offload mode.
- A dedicated offload test proves `tick()` can enqueue a `scheduler_trigger` task without creating the workflow run directly.
- The worker handler can consume the queued task and complete the same schedule fire.
