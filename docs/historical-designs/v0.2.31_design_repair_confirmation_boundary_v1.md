## 1. Problem

Builder currently checks `state.repair_cycles >= max_repair_cycles` before every `test_run`. With `max_repair_cycles=1`, the first failed test consumes the only repair cycle. If the Builder then changes the draft or test, it cannot run the confirmation test that would prove the repair worked.

The v0.2.29 paid/live evidence shows exactly this pattern.

## 2. Design Goal

Goal:

- Count failed test revisions, not confirmation attempts after a changed revision.
- Permit a test run when the draft revision changed after the last failed test, even if `repair_cycles == max_repair_cycles`.
- Prevent infinite repeated test runs at the same failing revision.

Non-goals:

- Do not increase the default repair budget.
- Do not remove the max repair boundary.
- Do not change `WorkflowRuntime.run_test_suite()` semantics.

## 3. Module Boundary

- `platform/backend/src/agent_platform/workflow_models.py`

## 4. Control Flow

`test_run` requested -> compare current draft revision with `state.last_failed_test_revision` -> allow if this is a changed revision needing confirmation -> run test suite -> if failed, count the failure for that revision -> if passed, clear the last failed revision.

## 5. Implementation Plan

1. Add `last_failed_test_revision: int | None` to `BuildTeamState`.
2. In Builder `test_run`, block when repair cycles are exhausted and the current revision is the same failed revision.
3. Allow confirmation when the revision changed since the last failure and `repair_cycles == max_repair_cycles`.
4. Increment `repair_cycles` only once per failing revision.
5. Add a Builder provider test that fails once, repairs the test, and reaches `ready` with `max_repair_cycles=1`.

## 7. Risks

- If the guard is too loose, Builder could keep mutating and testing forever. The fix must still block after failures exceed the configured repair budget.
- Existing persisted `BuildTeamState` rows need backward-compatible parsing; adding an optional field is safe.
