- Source task: `Implement workflow_run worker offload handler`
- Current version: `v0.2.116_e08_workflow_run_worker_offload_handler`
- Status: completed

## Problem

`workflow_run` is a required Platform Harness task kind, but the worker catalog still treats it as unavailable. This leaves the core workflow execution entrypoint outside the worker-owned offload path.

## Boundary

- Do not replace the existing API `/runs` path.
- Do not duplicate workflow graph execution logic in the worker handler.
- Do not claim full Platform Harness sidecar completion.
- Do not implement builder, test-suite, benchmark, draft-preview, production supervision, or distributed queue slices.

## Final Scheme

Add a `workflow_run_handler()` that:

- reads `inputs`, `version`, `use_draft`, and `workspace_path` from queued task metadata;
- calls `WorkflowRuntime.create_run()` with `parent_task_id` set to the queued worker task id;
- uses `origin="worker"` so runs created through worker offload remain visible;
- returns `application_id`, `run_id`, `version`, and `draft_revision` in worker result metadata.

## Acceptance

- A queued `workflow_run` task can be claimed and completed by `PlatformHarnessWorkerRunner`.
- The handler starts a real workflow run through existing runtime behavior.
- The run's Platform Harness task is parented to the queued worker task.
- Existing API-created workflow runs continue to work.
