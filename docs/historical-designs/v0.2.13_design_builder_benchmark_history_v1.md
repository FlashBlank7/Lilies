# design_builder_benchmark_history_v1

## 1. Goal

Add Builder benchmark history retrieval without creating a separate benchmark storage subsystem. The history API should expose durable Platform Harness `benchmark` task records in a reviewer-friendly shape.

## 2. Module Boundary

In scope:

- `platform/backend/src/agent_platform/api.py`
- `tests/test_workflow.py`
- v0.2.13 docs

Out of scope:

- Frontend benchmark history UI.
- Storing full benchmark reports separately.
- Paid/live benchmark reruns.
- Benchmark scoring changes.

## 3. Data Flow

```text
GET /api/v1/builder-benchmark/history
  -> services.harness.list_tasks(kind="benchmark", filters)
  -> map PlatformTaskRecord to history item
  -> return id/status/owner/resource/timestamps/metadata/usage_counts/error
```

## 4. Implementation Plan

1. Add `GET /api/v1/builder-benchmark/history`.
2. Accept filters:
   - `owner_id`
   - `status`
   - `limit`
3. Return list of dictionaries with stable fields:
   - `id`
   - `status`
   - `owner_id`
   - `resource_id`
   - `created_at`
   - `updated_at`
   - `finished_at`
   - `metadata`
   - `usage_counts`
   - `error`
4. Add regression test:
   - run benchmark suite in one app instance
   - recreate app with same `data_dir`
   - query history and assert task appears

## 5. Referenced Intellectual Assets

- `docs/intellectual-assets/asset_platform_harness_task_monitor_boundary.md`

## 6. Risks

- This endpoint exposes task-level metadata, not full benchmark report details.
- If future benchmark reporting needs detailed case reports, a separate result store may still be needed.
- The endpoint relies on Platform Harness durable task records introduced in v0.2.10.

## 7. Acceptance Criteria

- Benchmark history survives app recreation.
- Filtering by `owner_id` works.
- Existing benchmark suite task metadata appears in history.
- Full backend regression passes.
