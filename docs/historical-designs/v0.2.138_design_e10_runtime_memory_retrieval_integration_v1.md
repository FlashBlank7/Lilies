# v0.2.138 E10 Runtime Memory Retrieval Integration Design

Status: completed

## Problem

v0.2.137 implemented a governed memory surface contract, but workflow runtime does not retrieve governed memory during execution. E10 remains incomplete until memory can participate in runtime context without becoming unrestricted assistant memory.

## Runtime Contract

Workflow runs may opt in with an input key named `__governed_memory__`:

- `enabled`: must be true
- `actor_id`: actor requesting retrieval
- `scope_id`: governed memory scope
- `purpose`: retrieval purpose
- `reason`: audit reason
- `limit`: optional result limit

When present and valid, runtime retrieves active governed memories for `owner_id = application_id` and `scope_id`, then injects:

- `inputs["__governed_memory_context__"]["enabled"]`
- `inputs["__governed_memory_context__"]["items"]`
- `inputs["__governed_memory_context__"]["audit_stream_id"]`
- `inputs["__governed_memory_context__"]["retrieved_count"]`

## Safety Boundaries

- No opt-in input means no memory retrieval.
- Retrieval uses `GovernedMemorySurface.list_active`, which excludes revoked and expired records.
- Retrieval writes governed-memory read audit events.
- Runtime does not index filesystem paths or background activity.

## Completion Criteria

- Runtime opt-in injects active scoped memory into workflow inputs.
- Revoked and expired memory are excluded.
- No opt-in produces no memory context.
- Retrieval produces audit evidence.
- Focused tests and generated evidence pass.

## Final State

Workflow runtime now supports explicit opt-in governed memory retrieval through `__governed_memory__` run inputs. Retrieved active scoped records are injected as `__governed_memory_context__`, revoked and expired records are excluded, and read audit events are written through the governed memory surface.
