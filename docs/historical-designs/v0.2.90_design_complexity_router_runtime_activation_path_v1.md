# v0.2.90 design: complexity-router runtime activation path

## Source

- Source stage report: `docs/stage-report-archives/v0.2.x/v0.2.89_complexity_router_limited_default_enablement_contract.md`
- Source task: `Implement complexity-router runtime activation path`
- Version target: `v0.2.90_complexity_router_runtime_activation_path`

## Problem

v0.2.89 exposes a limited-default contract, but application build creation still uses the request defaults directly. The runtime path does not yet let config-gated complexity routing select Builder behavior.

## Boundary

- Only activate routing when normal settings explicitly configure `complexity_router_default_mode="limited_default"` and `complexity_router_limited_default_enabled=true`.
- Keep default settings behavior unchanged.
- Wire the route into real Builder behavior, not only status metadata.

## Design

- Add a runtime activation helper that classifies the build requirement using the current settings.
- When the classification is default-router-enabled, derive a runtime builder policy from `default_builder_policy`.
- For `planning_mode="auto"`, map `plan_first=true` to `required` and `plan_first=false` to `disabled`.
- Persist the classification and runtime builder policy in `BuildTeamState`.
- Make `template_suggestions` use runtime builder policy `reuse_depth` when the Builder omits an explicit reuse depth and no build plan override exists.

## Acceptance

- Default settings create builds without runtime router policy and keep `planning_mode="auto"`.
- Explicit limited-default settings create eligible builds with persisted classification and runtime builder policy.
- Simple explicit limited-default builds resolve auto planning to `disabled` and default omitted template suggestions to `shallow`.
- Medium/complex explicit limited-default builds resolve auto planning to `required` and default omitted template suggestions to `adaptive`.
