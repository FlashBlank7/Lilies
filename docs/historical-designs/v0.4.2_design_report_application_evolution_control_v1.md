# v0.4.2 Report Application And Evolution Control

Status: completed

## Source

- User-annotated scenario and capability-boundary report.
- Latest revision: `docs/lilies_agent_scenario_capability_boundary_v0_4_x_latest.docx`.
- User requirement: apply the report to the project without mid-task false completion, unfinished sub-stages, or long-iteration intent drift.
- Long-task operating principles: explicit outcome, constraints, definition of done, persistent repository instructions, reusable workflows, and lifecycle checkpoints.

## Problem

The earlier evolution loop allowed prose summaries to become de facto completion evidence. `workingon`, stage reports, design notes, and the next assistant summary could each suggest a different next step. Mandatory work could be split into many tiny versions, silently deferred, or reinterpreted after context compaction. The report itself also contained a large product program whose commitments could disappear once implementation moved to a narrower local task.

## Boundary

- This design controls intent, task authority, evidence, version advancement, interruption recovery, and archive closure.
- It does not declare the report's product capabilities implemented.
- It does not activate the temporarily masked Lilies evolution skill.
- Scope or acceptance changes still require user authority; implementation-route changes may proceed only with a recorded deviation that preserves acceptance.

## Final Design

### 1. Four-Level Authority Model

1. The Program Charter stores durable intent and prohibited reinterpretations.
2. The intent registry assigns stable IDs to every report commitment and records lifecycle state and evidence.
3. The active stage report is the only next-task authority.
4. `workingon` stores intermediate evidence only and is archived at stage closure.

The Charter and registry constrain task meaning but cannot independently schedule work. This prevents a second roadmap from emerging outside the stage report.

### 2. Frozen Stage Contract

Before implementation, each serious version imports the prior Source Task Set and freezes mandatory and optional tasks in JSON. A SHA-256 fingerprint and first Git commit bind the report to immutable contract bytes. Mandatory scope and acceptance cannot be downgraded without explicit user approval.

### 3. Deterministic Closure Audit

Closure validation requires:

- every mandatory contract row to be completed;
- completed-work evidence and at least one passing verification entry per task;
- a fresh auditor finding for every mandatory task;
- a passing version-size gate across at least three work surfaces;
- carried source intents to appear in the next-stage task set unless already terminal;
- no unresolved mandatory task;
- no authoritative next-task keys or headings in `workingon`;
- complete phase report and stage-report archive for every finished major version.

### 4. Interruption And Resume Protocol

Repository `AGENTS.md` and lifecycle hooks reload the Charter, validator-valid active stage report, current task ID, evidence state, and Git status. Checkpoints are explicitly non-authoritative. A Stop hook warns on an open mandatory contract and cannot be silenced by manually writing `Verdict: pass` into an invalid report.

### 5. Controlled Deviation

Implementation-route and evidence substitutions are recorded with acceptance preservation. Scope, acceptance, and safety-boundary changes require user authority. Failed audits remain failures and become remediation tasks; they are not converted into prose exceptions.

### 6. Finite Report-Application Campaign

The latest report is decomposed into stable Product, Architecture, Evaluation, Governance, Scenario, and Evolution intent IDs. Control intents may close in v0.4.2, while product intents remain non-terminal and are scheduled in serious vertical bundles. Campaign closure is valid only when every intent has a terminal disposition and evidence.

## Acceptance Criteria

- The annotated report is revised with all source annotations accounted for and no annotation residue.
- Charter, registry, contract, and their Git locks validate deterministically.
- Negative tests prove that mutable contracts, lost intents, false passes, workingon authority, missing evidence, and incomplete major archives are rejected.
- Hooks resume only from a validator-valid stage and preserve the current mandatory task.
- v0.3.x has a complete stage-report archive and honest phase closeout.
- A fresh-context final audit approves all frozen mandatory tasks before v0.4.2 closes.

## Final State

- Report revision, control architecture, validators, hooks, regression tests, and v0.3.x archive are implemented.
- The first audit failed and its blockers were remediated.
- Fresh-context reviewer `019f66da-5af8-7f31-86cd-2f5829558f73` approved all mandatory tasks after the archive repair.
- Product readiness remains explicitly open; current product regressions are assigned to the next serious version.
