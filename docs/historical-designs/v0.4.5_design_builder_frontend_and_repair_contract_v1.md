# v0.4.5 Builder, Frontend, And Repair Contract

Status: completed and archived in v0.4.5

Tasks: `V04-05-T01D`, `V04-05-T01E`

## Decision

Builder Team inspects the authoritative Capability Build Contract before mutation, maps BuildPlan modules to capability IDs, chooses a carrier before adding blocks, and binds required capabilities to actual draft nodes or registered resources. A plausible prefix is not accepted as implementation evidence, and one capability does not automatically imply one new atomic block.

Unavailable X contracts remain explicit scoped gaps with a claim ceiling. They do not masquerade as workflow graph failures and do not authorize a higher evidence claim.

## Product Integration

- The home intake shows typed option effects, F/G/X content, responsibility ownership, evidence targets, and the final claim scope.
- Application creation stores the exact contract; Builder and draft APIs return it.
- Acceptance cases reference capability IDs and evidence targets.
- Acceptance repair receives failed capabilities, contract claim scope, selected evidence boundary, and unavailable external-contract gaps.
- Customer plan text and machine contract stay consistent because both originate from the same structured result.

## Acceptance

Deterministic provider tests cover option effects and a ready contract, API tests cover persistence and contract-derived routing, Builder tests reject invented references and validate actual Codex nodes, and frontend lint/build cover the customer path. Reference closure tests prove Codex, scheduled collection, and embedded-system requirements do not collapse into one generic plan.
