# v0.2.112 E08 Distributed Heartbeat Registry Design

## Source

- Source stage report: `docs/stage-reports/v0.2.111_e08_remaining_sidecar_slice_reselection.md`
- Source task: `Implement distributed worker heartbeat registry`
- Current version: `v0.2.112_e08_distributed_heartbeat_registry`

## Problem

Worker lease renewal exists, but worker liveness is not exposed as a durable registry. Operators can inspect tasks and leases, but cannot ask which worker ids have recently reported, whether they are idle/running/stale, or which task a worker last touched.

## Boundary

- Do not implement a distributed queue backend.
- Do not claim process supervision or external alerting.
- Do not claim full Platform Harness sidecar completion.
- Do not reimplement completed handler catalog, stdio, secret rotation, policy controls, Studio controls, or runbook slices.

## Final Scheme

Add a durable worker heartbeat registry:

- storage table keyed by `worker_id`;
- Platform Harness methods to record and list worker heartbeats;
- liveness classification (`active`, `stale`) computed from `last_seen_at` and `stale_after_seconds`;
- worker runner records heartbeats at poll start, task execution, renewal, failure, and idle completion;
- API endpoint exposes registry rows to operators.

## Acceptance

- Heartbeats persist across harness instances.
- Stale workers are classified deterministically.
- Worker runner lifecycle updates heartbeat status and active task id.
- API exposes active/stale heartbeat rows.
