# 订单报价与客户反馈

这是独立的平台测试需求，所有订单均为构造数据。

我们需要在项目里提交订单商品清单，获得可检查、可下载的报价。请建立两条可编辑业务工作流：订单校验、报价计算，由主流程依次调用。校验失败要明确指出订单、商品和原因，不进行报价。算法、工作流及测试由搭建者自行完成，本包没有既有实现或结果。

每条商品必须有非空 order_id、item、正整数 quantity 和非负十进制 unit_price；同订单同商品不得重复。每行购买至少3件，整行享受九折，其余原价。计算顺序为未舍入单价乘数量得到原价，按折扣得到实付，再分别按人民币分四舍五入；优惠为舍入后的原价减实付。不能采用银行家舍入，不能预先把单价舍入。各订单合计为其各行实付之和。输入单价以字符串保存，避免精度损失。

主流程接收 request_path，指向本项目的订单 JSON。JSON 内容为 {"lines":[{"order_id":"...","item":"...","quantity":3,"unit_price":"12.50"}]}。
对外返回 status（ok或invalid）、lines（行明细）、totals（按订单合计）、errors（错误清单）及 report_path（本项目 CSV 文件路径，有效请求时提供）。行明细保留 order_id、item、quantity、unit_price，并增加 base、discount、payable 三个两位小数字符串。totals 为对象：订单号映射到两位小数合计。无效请求的 lines 和 totals 为空，errors 不为空；不得同时返回报价或残留旧报告。

有效请求还需 CSV，初次至少包含每行明细并用中文展示，具体列顺序可在客户试用后调整。用户对列名、列序和阅读方式的反馈属于已有报告需求内的修改，计价规则不变。工作流必须根据输入实际计算，不能将样例答案写成固定节点值。对金额边界、无效数量及负单价保留实际运行测试。

本次交付：两条成员和主流程、实际订单试用、中文解释及 CSV、受影响测试。修改后的试用生成新任务和新结果，关联原反馈，原任务结果保留。使用本机 Codex 和已有本地依赖，平台模型出口保持关闭。

企业后续目标还包括供应商实时价格同步，但本次没有接口和凭证；保留这一目标及待补条件，不阻断本次离线报价，不构造远程价格或连接。

先读 input.json 和 invalid.json，再整理需求文档与我们核对；确认后开始搭建。
